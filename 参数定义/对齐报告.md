## A. 键序不一致

### A1 schema.js 与 profile.conf 的键序在 PID 段不同，且 schema 的自述已失效

- 现状：`schema.js` 的 `keys` 块把 `PID_KI_DYN_T / PID_KI_DYN_GATE / PID_KI_DYN_WIN` 排在**最后**，而 `profile.conf` 把它们紧跟在 `PID_KI_RATE` 之后。差异位置为第 22–31 共 10 个键的区间。
- 影响面：`schema.js` 的 `groups[1].subKeys`（= WebUI 实际渲染顺序）用的是同一套顺序，所以**三个动态 KI 键在界面上的位置**会与 `profile.conf` 的阅读位置不同。
- 加重项：`schema.js` 文件头自述「keys / subKeys 的书写顺序与 profile.conf 中键的出现顺序一致」——该自述与事实不符，属**已失效的约束**。
- **裁定：以 `profile.conf` 的键序为准。** 理由：「动态 KI 抑制」三键是对 `PID_KI_RATE` 所定积分速率的调制，`profile.conf` 把它与被调制键相邻属正确的功能分组；`schema.js` 的末尾位置是增量追加的产物。
- 落地：定义文件的 `keys` 数组即权威序；schema 由脚本重建后，其自述同时改写为「键序见 `参数定义/params.def.json`」。

### A2 逻辑说明.md 的参数表是第三种顺序

- 现状：文档表按功能重排成一张扁平表（sysfs → PID → 映射 → 限速 → 拉起 → 调试 → 日志 → WebUI），与 `profile.conf` 完全不同序，表内也**没有任何分组标记**。
- **裁定：文档表保留「按功能重排」的现状，不强行改成 `profile.conf` 键序**——理由：它是人读的速查表，功能聚类的检索效率高于配置书写序。
- **但需 P2 确认**：这意味着定义文件要多承载一份「文档表序」。两个可选做法：
  1. 在 `keys[]` 里加一个 `docOrder` 整数（推荐：一处声明、脚本自动排表）；
  2. 文档表改用 `profile.conf` 键序，用组小标题保留功能聚类（顺序单一来源，但改变读者习惯）。
  **本批次未擅自二选一**，已把现状记为已知差异。

|---|---|
| `tempctrl.c` | `0`（代码默认，注释写明「默认关，刷入时可选开」） |
| `profile.conf` | `1`（出厂值） |
| `customize.sh` | 音量+ → 1、音量− → 0、无操作 → 0 |

### B2 `APP_WATCHDOG`（待办 R8 点名）

|---|---|

| `profile.conf` | `6` |

### B3 `PERF_ENABLED` —— 同一类二义性的第二个实例（R8 未点名，本次新发现）

| 来源 | 值 |
|---|---|
| `tempctrl.c` | `1`（`load_config()` 内 `int perf_enabled = 1;`：配置文件缺失或未写本键时性能参数生效） |
| `profile.conf` | `0`（出厂关闭，需用户自行开启） |

- **裁定：代码默认 = `1`，出厂值 = `0`。** 出厂关性能参数是产品取向（保持合并前行为，不擅自改变用户拿到的默认体验）。
- 落地：定义文件对**全部 52 键**同时给出 `default`（代码默认）与 `factory`（出厂值）；除 B1/B2/B3 外两者恒等。

|---|---|---|
| `tempctrl.c` | 静态初值为空串；运行期派生 `<PRIVATE_DIR>/<二进制名>.log`，**私有目录不可用时**回退 `/cache/<二进制名>.log` 并写 stderr（不静默失败） | 当前实现 |
| `profile.conf` | `/cache/tempctrl.log` | **已作废，待改**（见下方待改项） |
| `逻辑说明.md` | `/cache/<二进制名>.log` | **已作废，待改** |
| 定义文件（本批次） | `default` = `factory` = `/data/data/com.example.waspwingtempctrl/files/tempctrl.log` | 当前值 |

## C. 分组与类型层面的不一致（全部位于 schema.js 自身）

### C1 分组 `id` 命名事故

- 现状：`id` 依次为 `g1, g0, g2, g3, g5`——**没有 `g4`**，且数组顺序（`g1, g0, g2, g3, g5`）与编号顺序不对应（`g1` 是 `[0] 日志 & 调试`，`g0` 是 `[1] 性能参数`）。
- **裁定：以语义 id 为准**，定义文件用 `debug / perf / sysfs / launch / webui`；`[N]` 编号只保留在 `title` 里（它是给人看的显示名，不承担寻址职责）。

### C2 组头开关字段有两个键名且覆盖不全

- 现状：`g1/g0/g2` 同时写 `master` 与 `headerSwitch`（两值相同，纯冗余）；`g3` 只写 `headerSwitch`；`g5` 两个都不写。
- **裁定：统一为单字段 `master`**（值 = 该组的组头开关键名，`null` 表示无组头开关）。定义文件中 `webui` 组的 `master` 为 `null`。

### C3 组内键列表的字段名不统一

- 现状：`g1/g0/g2/g5` 用 `subKeys`，`g3` 用 `keys`。
- **裁定：组内键列表不再独立声明**，而是由每个键的 `group` 字段派生（单一来源，根本消除两份列表漂移的可能）。产物 `params.json` 的 `groups[].keys` 由脚本按定义顺序生成，字段名统一为 `keys`。

### C4 schema 的默认值只覆盖 4/52 键

- 现状：`value` 字段只出现在 `DEBUG_LAUNCH`、`WEBUI_GAP_SEC`、`WEBUI_CURVE_FILTER`、`WEBUI_AUTOSAVE` 四个键上；其余 48 键无默认值 → **界面无法从 schema 拿到初始值**（当前实现靠 `app.js` 里的兜底字面量）。
- 加重项：`DEBUG_LAUNCH` 的 `value: "0"` 与同组 7 个兄弟键不一致（它们都没有 `value`）。
- **裁定：定义文件对 52 键全部给出 `default` 与 `factory`**，`DEBUG_LAUNCH` 的特殊写法自然消失。产物中 `default` 为强类型（`int`/`int[]`/`string`），不再用字符串 `"0"`。

### C5 类型体系可用，但「无范围」与「子开关」需显式声明

- 现状：`type` 有 `switch / int / multi / path` 四种；`path` 无范围字段；`PID_TARGET_DIR`、`PID_SPEED_RECALL`、`APP_LAUNCH_SCREEN_GATE` 的第 1 个取值位是 0/1 开关，却混在 `multi` 的 `fields` 里（`schema.js` 自己的注释也承认 `[4] WebUI 组的键无 tempctrl.c 依据，范围与语义以 app.js 实际使用为准`）。
- **裁定：保持 4 种类型不变（最小改动，避免界面侧返工），但把两处隐含语义显式化**：
  - `path` 键：`min`/`max` 显式写 `null` 并给 `rangeNote` 说明「路径字符串，无取值范围」；
  - `multi` 内的 0/1 取值位：在 `fields[].unitNote` 写明「布尔子开关，取值 0/1」，界面据此渲染开关而非输入框。
- 产物中 `min`/`max` 为 `null` 的只有 `multi`（范围逐字段给）与 `path` 两类，语义唯一，不会与「范围是 0」混淆。

## D. 范围（min/max）与 C 端 clamp 的一致性

口径：C 侧消费的 **47 个键**共 **74 个取值位**（多值键按字段数拆位）。

### D1 自动核对：47 个取值位全部一致

`gen_params.py --audit` 从 `tempctrl.c` 提取 `INT_CFG_KEYS[]` 表内范围与所有 `变量 = clamp(x, lo, hi)` 赋值（就地展开 `#define` 宏，如 `B7X_FAN_RPM_MAX=8000`、`B7X_COLD_MAX=255`），与定义逐位比对：

```
C 侧自动核对（取值位口径）：默认值 通过 66 / 豁免 1 / 无 C 变量 7；
                          范围 通过 47 / 无 clamp 20 / 无 C 变量 7
漂移错误 0 条
```

覆盖的典型位：`fan_rpm_min/max/b7_fan_rpm_max`、`pid_cold_min/max/b7_pid_cold_max`、`HOT_DERATE_*`、`RATE_LIMIT_*`、`COLD_DEADZONE`、`cold_map_*`、`hot_map_*`、`pid_*_coef`、`CPU_ZONE_*`、`cpu_zone_*`、`app_launch_cooldown`、`app_watchdog_cycles`、`BATT_*_DIVISOR`、`CPU_TEMP_DIVISOR`、`LOG_MAX`。

**结论：schema.js 与 profile.conf 声明的范围、以及定义文件的默认值，与 C 端 clamp / 静态初值完全一致，无一处漂移。** 复现方式见报告首节三条命令；反向验证（人为改 C 的一处 clamp 上界、人为删掉 `is_sysfs_key()` 的一个 `strcmp`）均已确认能报错。

### D2 「无 clamp」的 20 位与「无 C 变量」的 7 位（已逐条人工核对，全部一致）

| 组 | 位数 | 为何不可自动核对 | 人工核对结果 |
|---|---|---|---|
| 8 个 `DEBUG_*` | 8 | C 端写 `x = (val != 0)`，无 `clamp` | 定义为 `switch`，范围 0~1 ✓ |
| `PERF_ENABLED`、`SYSFS_ENABLED`、`APP_LAUNCH_ENABLED` | 3 | 同上（首轮扫描里 `atoi(val_str) != 0`） | 0~1 ✓ |
| 4 个路径键（`BATT_TEMP_PATH`、`BATT_CURRENT_PATH`、`CPU_TEMP_PATH_FMT`、`LOG_FILE`） | 4 | 路径字符串，C 端 `config_read_path()` 无范围概念 | `min/max = null` + `rangeNote` ✓ |
| `PID_TARGET_DIR` 第 1 值、`PID_SPEED_RECALL` 第 1 值 | 2 | 布尔子开关（`(on != 0)`） | 0/1 ✓ |
| `APP_LAUNCH_SCREEN_GATE` 三值 | 3 | 布尔子开关（`(on != 0)`） | 0/1 ✓ |
| `PID_KI_DYN_T` / `GATE` / `WIN` 的全部取值位 | 7 | 存于结构体 `ki_dyn_cfg` 的 float 字段（`{4.70f, 1.20f, 0.75f, 5, 0.50f, 36, 0.30f}`），无单变量可提取 | 结构体初值 ×100 后 = `470/120/75`、`5/50`、`36/30`，与定义逐一相等 ✓；范围为**护栏式校验**（越界拒绝、保留旧值），已人工核对 ✓ |

### D3 需界面侧注意的语义差异（非范围不一致）

`PID_KI_DYN_T / GATE / WIN` 在 C 端的越界处理是**整组拒绝、保留旧值**，而界面按 `min`/`max` 钳制会让用户**永远触发不到拒绝分支**。

- **裁定：定义文件保留 C 端的真实范围，并在 `rangeNote` 里写明「越界整组拒绝（不是钳位）」**；界面可以钳制（用户体验更好），但**不得声称「配置值等同 C 端钳制结果」**——两者对越界输入的行为不同（钳制=静默改值，拒绝=保留旧值 + 打日志）。另有三处跨字段护栏 `T1 > T2`、`M < T1`、`N ∈ [6,128]` 也一并写进 `rangeNote`。

## F. 定义文件新增的、四份来源此前都没有的机器可读信息

这些不是「不一致」，而是本次首次结构化的内容，供界面直接消费：

1. **`requires`（前置键）** —— 此前只散落在散文注释里：
   - 7 个 `DEBUG_*` → `DEBUG_ENABLED`
   - sysfs 组 10 键 → `SYSFS_ENABLED`
   - 性能组 23 键 → `PERF_ENABLED`
   - `APP_LAUNCH_COOLDOWN` / `APP_LAUNCH_SCREEN_GATE` / `APP_WATCHDOG` → `APP_LAUNCH_ENABLED`
   界面「未生效」徽标与整块灰显可直接由它推导（正是线 D 需要的输入）。
2. **`default` 与 `factory` 分列** —— 消除 B1/B2/B3 的二义。
3. **`unit` / `unitNote`** —— 无单位的键必须写明原因（如「无量纲倍率，算式内 ÷10」「布尔开关，取值 0/1」），避免界面上出现裸数字。
4. **`daemonConsumes`** —— 5 个 `WEBUI_*` 键为 `false`（守护进程完全忽略），界面可据此把它们从「热重载无需重启」的提示中区分出来。
5. **`crossChecks`（跨处一致性自动核对）** —— 定义文件的 `audit.crossChecks` 段新增两条声明式规则，由 `--audit` 执行：
   - `LOG_FILE` 的 `default` 与 `factory` **必须等于** `tempctrl.c` 的 `PRIVATE_DIR` 宏展开值 + `/tempctrl.log`；
   - `tempctrl.c` 的 `PRIVATE_DIR` **必须等于** `/data/data/<applicationId>/files`，`applicationId` 实时取自 `lsp模块(apk修复+温控接口)/app/build.gradle.kts`。
   这两条把「日志落点」这个**跨三处（C 宏 / Gradle applicationId / 参数定义）必须一致**的事实变成了机器可验的断言——此前它没有任何保护，且**已经真的错过一次**（`PRIVATE_DIR` 少写 `.example`，见 B4）。
   解析安全性：只认单行字符串宏与单行 `applicationId = "..."`；遇到跨行拼接宏或读不到 Gradle 时**降级为「无法自动核对」的 INFO**，不会假通过（已实测）。

### H2 `webroot/schema.js`：选择「加文件头状态说明」而非「更正到与现状一致」

**判断：更正它有引入新漂移的风险，故不更正。** 理由四条：

1. `schema.js` 在本批次启动时被列为**只读对账输入**（文件所有权冻结）。手工更正会把它变成**第四份手抄**，而 P2 的计划是让该文件**由定义生成**——现在手改等于让 P2 先revert再生成。
2. 它的陈旧项里有两个是**路径**（`configPath` 指向 `/data/adb/modules/…`、`dataFile` 指向 `/data/local/tmp/…`）。这些值**没有任何一源在核对**，手改既不能被发现错误、也不会被别人跟随，只会制造「看起来已经校准过」的错觉。
3. 更正 `keys` 键序会**直接消掉** `--audit` 目前唯一的一条 schema 侧提示，使「A1 键序不一致」这条结论在下一轮对账时**无法复现**，报告与脚本失去互相印证。
4. 更正必须逐字复刻 `params.def.json`，任何一处笔误都会被 `check_params.py` 判红——一个「不影响功能」的文件却能把 CI 弄红，收益为负。

**实际动作**：在 `schema.js` 文件头加 11 行状态说明，明确它「**不是运行期文件**、唯一作用是 `check_params.py` 的对账输入之一」，并逐条列出 4 项已知失效的自述，注明**权威来源是 `params.def.json`、请勿按自述反推现状**。`check_params.py` 的对应提示同步改为「schema.js 文件头已将该自述标注为已知失效项」，使工具输出与文件自述一致。改动仅 12 行纯注释（`git diff --stat` 可验），不触碰任何键、任何值。

## I. 已知局限（诚实声明，勿当成已验证）

1. **`check_params.py` 的 C 侧核对是「字符串/数值级」的**：它比对键名集合、静态初值、`clamp` 字面量与宏，**不解析 C 的控制流**。若有人把范围改成运行期计算（如 `clamp(x, f(a), g(b))`），核对会退化为「未自动核对」而不是报错。
2. **`is_sysfs_key()` 的一致性检查会随该函数被删除而失效**（路线 A 若重构成表驱动，脚本的 `__is_sysfs_key__` 集合会变空 → 会报「函数多 []/少 10 键」）。**这是有意的**：重构时应同步改脚本判据，而不是让它静默失效。
3. **范围核对不覆盖「语义正确性」**：`BATT_BASELINE` 的 300~500 与 C 端 clamp 一致，不代表 300 是合理的物理温度。本报告只保证三方一致。
4. **`crossChecks` 只认单行字面量**：`#define PRIVATE_DIR "..."` 必须写在一行、且值里不含 `"` 或反斜杠续行；`applicationId = "..."` 必须单行。不满足时**降级为 INFO「无法自动核对」**（不是静默通过，也不是报错），需人眼确认。若将来 C 端把 `PRIVATE_DIR` 改成由 `#include` 或拼接得到，这两条核对会失效——届时须同步改脚本判据。
5. **`crossChecks` 不覆盖「二进制名」那一半**：规则里 `tempctrl.log` 是写死在定义文件里的后缀，而 C 端实际是按 `get_exe_basename()` 的返回值拼的。若二进制被改名（如 `tempctrl-arm64`），C 端日志会变成 `<PRIVATE_DIR>/tempctrl-arm64.log`，而核对**仍会通过**——这是该规则的已知盲区。
