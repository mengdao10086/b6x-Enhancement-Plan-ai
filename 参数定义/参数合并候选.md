# 参数合并候选清单

> 快照：2026-11-12，**61 键 / 6 组**（键名与默认值以 [`params.def.json`](params.def.json) 与 `python 参数定义/check_params.py` 的输出为准）。
> 口径：只讨论「单参数多值」——把若干总是成组出现、同一机制、同一生命周期的键合并为一个多值键（形如 `UI_CURVE_FILTER=1 15 5`）。
> 本文件**只出候选清单**，不修改任何参数；分级依据 = 收益（减键数 / 降低半改风险）÷ 改动面（C 解析、生成器类型、界面、迁移）。

---

## 0. 结论速览

| 级别 | 候选 | 涉及键 | 合并后 | 净减键 |
|---|---|---|---|---|
| 高 | H1 调试分区 | 7 | `DEBUG_SECTIONS`（7 值） | −6 |
| 高 | H2 温区扫描 | 2 | `CPU_ZONE_CFG`（4 值） | −1 |
| 中 | M1 采样路径+除数 | 6 | 3 个「路径 除数」混合键 | −3 |
| 中 | M2 拉起时间参数 | 3 | `APP_LAUNCH_TIMING`（3 值） | −2 |
| 中 | M3 PID 高级滤波 | 2 | `PID_ADV_FILTER`（5 值） | −1 |
| 低 | L1 双限速 | 2 | `RATE_LIMIT`（6 值） | −1 |
| 低 | L2 PID 核心三键 | 3 | `PID_CORE`（7 值） | −2 |
| 低 | L3 控制组位图 | 4 | `CONTROL_FLAGS`（4 位） | −3 |

> 全部落地最多减 19 键（61 → 42），但 H1+H2 已覆盖一半收益且风险最低。

---

## 1. 高：H1 调试分区 7 开关 → 一个多值键

| 项 | 内容 |
|---|---|
| 涉及键 | `DEBUG_SENSOR`、`DEBUG_EXEC`、`DEBUG_CONN`、`DEBUG_CONFIG`、`DEBUG_MAIN`、`DEBUG_PID`、`DEBUG_LAUNCH` |
| 合并后形式 | `DEBUG_SECTIONS=1 1 0 0 0 0 0`（7 个 0/1，按「传感器 / 执行 / 连接 / 配置 / 主循环 / PID / 自动拉起」固定顺序；也可用位图整数，但多值形式与现有 `UI_CURVE_FILTER` 一致、界面更易渲染） |
| 收益 | 7 键 → 1 键；`profile.conf` 少 6 行；界面用一个多槽行替代 7 个开关，分区总开关语义更集中；默认全 0 的语义不变 |
| 兼容性 | 旧 7 键必须保留读兼容（见旧键即覆盖对应位），首次加载后迁移写回新键并删除旧行；`compat.renames` / `cleanup` 需登记旧键；旧版 APK 读不到新键时会退回默认全 0（调试日志丢失但无功能风险） |
| 改动面 | 定义（1 个 multi + 7 个旧键迁移）、`gen_params.py`（C 默认表/键表）、`tempctrl.c`（`parse_debug_cfg`、7 个布尔变量、层复位）、界面表单、文档与参数表；`params.json` 不新增资源条目，CI 资源基线不变 |

**主要风险**：位序一旦发布即为跨端协议，后续增删分区只能追加；迁移写回失败时须长期保留旧键解析。

## 2. 高：H2 温区扫描两键 → 一个多值键

| 项 | 内容 |
|---|---|
| 涉及键 | `CPU_ZONE`（现为 2 值：min/max）、`CPU_ZONE_RESCAN`（现为 2 值：rescan/keep） |
| 合并后形式 | `CPU_ZONE_CFG=min max rescan keep`（4 值，前两位沿用现区间，后两位沿用现重扫口径） |
| 收益 | 2 键 → 1 键；两者本就属于同一「CPU 温区扫描」机制、同一次重扫时一起读取，合并后不会出现「只改了一半」的配置 |
| 兼容性 | 旧两键保留读兼容并迁移写回；C 端解析路径不同（区间用于候选名单、重扫用于周期），合并只改读取入口、不改判定逻辑 |
| 改动面 | 定义、生成器、`tempctrl.c` 两处解析与默认表、界面表单、文档；无资源变化 |

**主要风险**：`rangeNote` 需同时覆盖区间与周期两组范围；界面需把 4 个槽位的含义写清楚。

## 3. 中：M1 三组「路径 + 除数」→ 3 个混合键

| 项 | 内容 |
|---|---|
| 涉及键 | `BATT_TEMP_PATH` + `BATT_TEMP_DIVISOR`、`BATT_CURRENT_PATH` + `BATT_CURRENT_DIVISOR`、`CPU_TEMP_PATH_FMT` + `CPU_TEMP_DIVISOR`（共 6 键） |
| 合并后形式 | `BATT_TEMP=<路径> <除数>`、`BATT_CURRENT=<路径> <除数>`、`CPU_TEMP=<路径模板> <除数>`（每键首位为路径，末位为整数除数） |
| 收益 | 6 键 → 3 键；路径与除数强绑定，避免只改路径忘改除数导致读数放大/缩小 |
| 兼容性 | 旧 6 键必须保留读兼容 + 迁移写回；路径含空格时需定义分隔规则（现有默认路径均不含空格，但用户可自定义，须定「末尾一段为除数、其余为路径」的切分口径） |
| 改动面 | **需要扩展类型系统**：现有 `multi` 只表达整数取值位，需新增「路径 + 整数」混合类型（定义、生成器、校验器、界面渲染四处）；C 端把两次解析合一；文档 |

**主要风险**：混合类型是生成器层面的新能力，改动面明显大于 H1/H2；若近期没有重构生成器的计划，可暂缓。

## 4. 中：M2 拉起三时间参数 → `APP_LAUNCH_TIMING`

| 项 | 内容 |
|---|---|
| 涉及键 | `APP_LAUNCH_COOLDOWN`（秒）、`APP_WATCHDOG`（连续周期数）、`BT_AUTO_ENABLE_SEC`（秒） |
| 合并后形式 | `APP_LAUNCH_TIMING=<拉起冷却秒> <停滞重启周期数> <蓝牙自开秒>`（3 值） |
| 收益 | 3 键 → 1 键，同属「自动拉起 / 断连恢复」的时间参数，配置文件更紧凑 |
| 兼容性 | 三者单位与语义跨度较大（周期数 ≠ 秒），合并后行内注释必须逐位说明；旧 3 键保留读兼容与迁移 |
| 改动面 | 定义、生成器、`tempctrl.c` 三处解析与默认表、界面表单、文档 |

**主要风险**：可读性下降——一行里混了周期数与秒数；`APP_WATCHDOG` 还带「停滞重启」这一独立机制名，合并后容易被误认为同一节流参数。

## 5. 中：M3 PID 两个「开关 + 系数」→ `PID_ADV_FILTER`

| 项 | 内容 |
|---|---|
| 涉及键 | `PID_TARGET_DIR`（3 值：开关 + away + toward）、`PID_SPEED_RECALL`（2 值：开关 + weight） |
| 合并后形式 | `PID_ADV_FILTER=<方向滤波开关> <away> <toward> <速度回溯开关> <weight>`（5 值，保留两个独立使能位） |
| 收益 | 2 键 → 1 键；两者同属默认关闭的高级滤波，参数页可归为一行 |
| 兼容性 | 两个使能位必须保留（现两者互不依赖）；旧 2 键保留读兼容与迁移 |
| 改动面 | 定义、生成器、`tempctrl.c` 两处解析、界面表单、文档 |

**主要风险**：一行 5 值，界面横向空间紧张；两项机制不同，合并只省 1 键，收益有限。

## 6. 低：L1 双限速 → `RATE_LIMIT`

- 涉及键：`RATE_LIMIT_FAN`（3 值）、`RATE_LIMIT_COLD`（3 值）。
- 合并形式：`RATE_LIMIT=<风扇步长> <风扇防抖> <风扇取整> <制冷步长> <制冷倍率> <制冷死区>`（6 值）。
- 收益：2 键 → 1 键。
- 兼容/改动面：旧 2 键读兼容 + 迁移；C 端两套限速变量与默认表合并；界面一行 6 值。
- 不建议优先：风扇与制冷是两条独立执行器，6 值一行过长且易串位，收益仅 1 键。

## 7. 低：L2 PID 核心三键 → `PID_CORE`

- 涉及键：`PID_SPEED`（3 值）、`PID_TARGET`（3 值）、`PID_CH_THRESHOLD`（1 值）。
- 合并形式：`PID_CORE=<速度系数> <非线性阈值> <非线性指数> <目标系数> <目标滤波> <目标上限> <CH 阈值>`（7 值）。
- 收益：3 键 → 1 键。
- 不建议：三者调参节奏与语义不同（速度映射 / 动态目标 / 受控量阈值），合并会掩盖差异，且 7 值一行极难核对。

## 8. 低：L3 控制组 4 开关 → 位图

- 涉及键：`UI_TEMP_STOP`、`UI_BACK_HIDE`、`UI_AUTO_UPDATE`、`UI_DEPLOY_ENTRY`。
- 合并形式：`CONTROL_FLAGS=1 0 1 1`（4 位）。
- 收益：4 键 → 1 键。
- **不建议**：四者语义完全无关（临时停止 / 返回隐藏 / 自动部署 / 部署入口），位图会让配置与界面都失去可读性，且 `UI_TEMP_STOP` 有开机失效逻辑、`UI_AUTO_UPDATE` 由开机脚本读取，生命周期不一致。

## 9. 通用落地前提（任何候选都适用）

1. **旧键读兼容**：新键上线后，`load_config` 必须继续识别旧键（映射到新键的对应位/槽），否则存量 `profile.conf` 会静默丢配置。
2. **一次性迁移写回**：首次读到旧键时按现有 `commit_config_rewrite` 口径改写为新键并删旧行；写失败保留旧键、不丢行为。
3. **compat 登记**：`params.def.json` 的 `audit.cVars`、`compat.renames`、`compat.cleanup` 同步登记旧键，供界面「清理旧版遗留键」使用。
4. **生成器与校验**：只改 `params.def.json`，产物全部由 `gen_params.py` 重生成；`check_params.py` 的 `EXPECTED_KEY_COUNT` 与三源审计随之更新。
5. **界面与文档**：多值键需要表单逐槽标签与说明；参数表段自动生成，正文口径需人工同步。
6. **CI**：`params.json` 是资产、不产生资源条目，`BEFORE_ENTRIES` 基线通常不变；若同时改动布局/样式则另算。

---

## 10. 不建议合并的类型（排除项）

- **主开关与成员**：`*_ENABLED` 与组内参数职责不同，保持独立。
- **跨机制同名参数**：如 `COLD_RPM_MAP` / `HOT_RPM_MAP` 虽同为映射，但输入量与曲线横轴不同，合并会迫使两套范围共用一行。
- **类型不同的强绑定**（M1 之外的 path/path 组合）：没有统一分隔约定时，合并后的解析歧义大于收益。
- **纯界面展示键**：`UI_RPM_AXIS_MIN`、`UI_PID_MARK`、`UI_CHART_SWAP`、`UI_START_PAGE` 等互不相关，合并只会降低可读性。
