### 一句话结论

静态看，**daemon 的自有节拍并不贵**（1s 拍 3 次 `open`、2 次 `stat`，无 `fork`）；真正的大头是三处：①调节期的 `am broadcast` fork 链（每次下发一次 `am` 进程，平滑下发一拍最多 5 次）；②`/proc` 全目录扫描（15s 仲裁 + 60s 看门狗，占 daemon `open` 总量的约 9 成）；③模块侧每秒一次 status 原子写（tmp+rename+8 次反射）与曲线页每秒一次全量重解析（约 2 万对象/s）。

#### 哪里能靠缓存省掉（按收益排序）

1. **`poll_bt_request()` 每秒 `open`**（5154）：请求极稀疏（限频侧在钩子）。可改为先 `stat`（或只在 5s 拍）再读——省 60 open/min，占 1s 路径的 1/3。
2. **曲线路径每拍 `fstat`+`stat`**（5065）：换 inode 只在人为删除时发生。可降到压缩拍（60s）校验一次——省 120 次元数据调用/分钟。
3. **`maintain_temp_stop()` 每 5s 重写标记文件**：模块判新鲜窗口是 15s（`TEMP_STOP_FRESH_MS`）。改 10–15s 重写可省 2/3 的写+chmod+unlink。
4. **`read_battery_temp()` 的 `stat`**：值比较已经是主判据（2255），mtime 只是补充信号；可只在值未变时才 `stat`。
5. **`/proc` 全扫**：`app_process_scan` 已做「合并扫描 + 命中即停 + 已确认未安装的包剔除」（3474–3494），已是当前结构下的上限；进一步只能改事件驱动（`inotify`/`binder`）或拉长 15s→30s，属产品口径变更。

### A2 休眠/待机时还在做什么

**daemon**：无 wakelock（全文件无 `WakeLock`/`PARTIAL_WAKE`），CPU 可进 suspend，但**没有任何「屏幕熄灭/待机」分支**——1s 主循环、曲线写行、`poll_bt_request` 在息屏时照跑。断连时只是从 5s 控制块走 `continue`（5676/5688），1s 采集层不停。真正「降频」的只有：
- 等待设备循环 `sleep(5)`（5569），期间每轮 `dumpsys`/`/proc`/`pm` 探测；
- `is_screen_awake()` 只在断连的拉起链里，且息屏退避到 10–12s（3327/447）。

**模块（MainHook，跑在散热器 app 进程里）**：
- 状态写线程 1 Hz（567）：`writeStatusFile()` 每秒 `tmp` 写 + `rename` + 8 次反射 getter（488–521）；
- `checkCommandStall()` 每秒（550）：`isTempStopFresh()` 读标记文件 = `isFile`+`lastModified`+`open/read/close`（2878–2896）；
- 后台重连 tick 同线程，断连且息屏时 10s 一次（938）；
- 守护消费线程 250ms 轮询（3024–3062），**启动后永不退出**；
- SDK `runFetchLoop` 的队列被包装成「空则 `sleep(50)`」（1552–1566）——**这是进程内最高的空闲唤醒源：约 20 次/s**。

**UI**：三条轮询链都在页面不可见时停（Chart `onPause`/`setPageHidden`、Log `onPause`/页面可见性、Status `onPause`/`onPageVisible`），已核实（见 D）。**WebUI(lite)** 的 `chartClose/logClose/statusClose` 也都能 `clearInterval`，切页即停。

**本可停掉/降频的循环**（列事实，不代表已定方案）：
1. daemon 无 BLE 连接时，1s 采集可降到 5s（曲线本来就是断联留空洞）；
2. `poll_bt_request` 1s → 5s/事件驱动；
3. 模块 `writeStatusFile` 在 `!bleConnected && bleLastOwner==0` 时仍每 1s 空转一次判据（476 行），可拉长；
4. 消费线程 250ms 可退避到 1s（队列空时）；
5. SDK 队列包装的 50ms sleep 是「防 CPU 满载」手段（1551 行注释），不宜直接去掉；可评估 80–100ms，需真机验证命令延迟。

| 项 | 数值 | 依据 |

**长期运行代价**：
- 追加侧：86 400 × 57 B ≈ **4.9 MB/天**；
- 重写侧：1 440 × ≈40 KB ≈ **57.6 MB/天**（且是截断重写）；
- 合计 ≈ **62 MB/天 ≈ 22 GB/年** 的逻辑写。相对每行追加量，**重写放大约 12×**（40 KB / 60 s ÷ 57 B/s）。
- 另有每拍 `fstat`+`stat` 2 次 = **172 800 次元数据调用/天**，只为检测文件被替换。
- 判定：对 eMMC/UFS 寿命影响小（同目录小文件、F2FS 会合并），但**它是本系统最大的稳态写盘源**；真正的物理写放大（4 KB 块、F2FS 原地更新策略）**需采样**（见 C-1）。

### A4 UI 绘制

**`ChartView.onDraw`（1187–1306）**：不分配对象、不做 IO、不调 `String.format`；几何全部由 `rebuild()` 预算（29–31 行注释与实际一致）。逐段核对：画笔全部是字段复用；增强 `for` 遍历 `float[]` 不产生迭代器；`endLabels`/`dots` 是 `rebuild` 产出的不可变持有对象。**结论：onDraw 干净。**

**每帧以外、每秒一次的代价（曲线页可见时，`REFRESH_INTERVAL_MS=1000`，ChartFragment:74）**：
1. 新起一个 `Thread`（298–305），读文件尾 256 KB（实际 ≈40 KB）；
2. `ChartDataset.parse`（84–127）：文件每秒变（指纹 `size:mtime` 必变，缓存必失效）→ **780 行逐行** `split("\n")`、`split(",")` 得 12 元素 `String[]`、9 次 `parseInt` 装箱，再两次全量平滑（`applyOne`×2）。**≈780 × 24 ≈ 1.9 万临时对象/s**（含子串、数组、装箱）；
3. `ChartWindow.of`（31–71）：`ChartSample[≈780]` + `float[780]`×2 + `boolean[780]` ≈ **13 KB/s**；
4. `ChartView.rebuild`（425–429）：**9 个 `Path`**（`buildPaths` 703；实际开启约 7 条，每条 ≤780 `lineTo`）、`buildPidSingles` 的 `int[780]`+`float[]`×2、`buildRecomputeMarks` 的 `float[]`、`buildMarkers` 两个 `ArrayList` 与 `toArray`；
5. 轴刻度文字：`ChartAxis` 169 用 **`String.format`**，每轴 3–5 段 → **约 8–12 次/s**；末端标签 `ChartSeries.format` 251 再 1–3 次/s；
6. `invalidate()` → 一次整视图重绘（onDraw 本身廉价）。

**日志列表每拍重建多少行**：`REFRESH_INTERVAL_MS=2000`（LogFragment:48），日志页可见时每 2s 一次 `stat`（`AppFiles.probe`），`LogTailReader` 用 `size:mtime` 指纹短路（`unchanged`）——**日志不增长时 0 行重建、不读盘**；增长时 `submit()` 走 `notifyDataSetChanged()`（LogListAdapter:80）——**3000 行的适配器记账 + 可见约 15 行重绑**，而不是 3000 行排版（RecyclerView 虚拟化）。尾读上限 200 KB、行数上限 3000、单行 4096 字符（LogTailReader:30/34/41），都有界。

**有没有在 `onDraw` 里做 IO**：没有（`ChartView` 无 `File`/`Stream`/`Cursor` 引用）。IO 都在 `loadNow()` 起的后台线程里。

**lite（`app.js`）**：`chartPoll` 1s 一次（1793）→ 桥方法 `chartData()` 每次都整份读文件（`WebBridge.tail` 279，尾读上限 204 800 B）并把 ≈40 KB 字符串跨 JNI 传到 JS；`chartIngest`（1477）每秒 `split('\n')` 780 行、每行 `split(',')`+8 次 `parseInt`+对象，**≈1.6 万对象/s**；有新点才 `drawChart()`，一次重绘 6 条系列 × ≤720 点 ≈ **4 300 次 `lineTo`**。日志页 `logPoll` 1s 一次整份读（≤16 KB）+ `split` + 必要时 `textContent = join('\n')`（1868）。

## B 热点评级表

| # | 热点 | 量级（静态估算） | 触发条件 | 评级 |
|---|---|---|---|---|
| 1 | **`am broadcast` fork 链**（tempctrl.c:2631 / ramp 4568） | 每次下发 **1 个 `am` 进程**；一次变化拆 5 拍 → **5 fork/5s**，单次 100–300 ms（代码自述 2511）→ 调节期可占 **10–30% 单核** | 实际值未达目标（温度变化中） | **高** |

## C 采样指引（真机命令）

> 均为只读命令；`<daemon_pid>`=`pidof tempctrl`。凡涉及 `strace`/`perfetto` 的需 root 或 userdebug。

**C-1 验证 A1 的 read/write 总量与 A3 的写盘量**

```sh
su -c 'p=$(pidof tempctrl); a=$(cat /proc/$p/io); sleep 60; b=$(cat /proc/$p/io); echo "$a"; echo "$b"'
```
看 `syscr`/`syscw` 差分：期望 `syscr ≈ 900–1 000/分钟`、`syscw ≈ 60/分钟`（曲线 60 次 flush + 少量日志）。`write_bytes` 差分应≈**5 MB 级别/小时**（含重写）；若 `write_bytes` 远大于逻辑写入量，说明存在块级放大（A3 的 12× 结论成立）。
另：`su -c 'wc -lc /data/data/com.example.waspwingtempctrl/files/tempctrl_webui.data'` 直接给出真实行宽（验证「≈57 B/行、720–780 行」）。

**C-2 验证 A1 的 open/stat/fork 计数与 B-1/B-2**

```sh
su -c 'strace -f -c -p $(pidof tempctrl) -o /data/local/tmp/tc.sum & sleep 120; kill %1'
su -c 'cat /data/local/tmp/tc.sum'
```
看 `openat`、`newfstatat`、`read`、`clone`/`fork` 四行。预期：`openat` 2 500–4 000/分钟（若明显偏低说明 `/proc` 扫描提前命中），`newfstatat` ≈ 200/分钟，`clone` 只在温度变化期出现、呈 5 连发。设备无 `strace` 时用 perfetto + `ftrace/events/syscalls` 统计同名事件。

**C-3 验证 B-1 的 `am` CPU 与 B-3/B-6/B-7 的 app 线程唤醒**

```sh
su -c 'top -H -b -n 5 -d 2 -p $(pidof tempctrl)'
su -c 'top -H -b -n 5 -d 2 -p $(pidof com.flydigi.waspwing)'   # 包名按实际 B6X/B7X app 调整
```
daemon 侧：稳态应 <1% 单核；**调节期（或温度变化时）会出现以 5s 为周期的 CPU 尖峰**——尖峰即 `am` 链。app 侧看线程名/占比：`StatusWriter`（1 Hz）与消费线程应很低，`runFetchLoop` 者由 50ms sleep 决定。

**C-4 验证 A4 的曲线页绘制与重解析代价**

```sh
adb shell dumpsys gfxinfo com.example.waspwingtempctrl reset
# 打开曲线页停留 60s 后
adb shell dumpsys gfxinfo com.example.waspwingtempctrl framestats
adb shell dumpsys meminfo com.example.waspwingtempctrl | head -20
```
`framestats` 的 `Draw`/`Prepare` 时间应稳定（onDraw 无分配）；若每秒出现一次 5–15 ms 的 `Measure/Layout` 尖峰，对应 `rebuildWindow`→`setData` 的重建。`meminfo` 前后对比 Java Heap 无持续上行即证明 A5 无泄漏；GC 频率（`dumpsys gfxinfo` 的 janky 段或 logcat `GC_`）应能解释那 ~1.9 万对象/s。

**C-5 验证 A2 的空闲唤醒与 A5 的线程常驻**

```sh
su -c 'p=$(pidof com.flydigi.waspwing); a=$(grep ctxt /proc/$p/status); sleep 60; b=$(grep ctxt /proc/$p/status); echo "$a"; echo "$b"'
```
`voluntary_ctxt_switches` 差分应≈**1 500–1 800/分钟**（20 Hz SDK 空转 + 1 Hz 状态写 + 4 Hz 消费线程的量级）；若显著更高，说明还有未识别的轮询源。同时 `ls /proc/$p/task | wc -l` 检查线程数是否稳定（A5 的「无累积」结论）。

## D 已核实无问题的地方

1. **`ChartView.onDraw` 零分配、零 IO**（1187–1306）：画笔与几何全部字段复用，`rebuild` 预算；与类注释的「性能硬约束」一致。
2. **曲线/日志/状态三条 UI 轮询链在不可见时确实停**：Chart 走 `onPause`+`setPageHidden`（216/237）、Log 走 `onPause`+页面可见性（229/237）、Status 走 `onPause`+`onPageVisible`（320/329）；ViewPager2 不派发 `onPause` 的坑已被显式处理。
3. **daemon 无常驻内存增长**：无动态容器，唯一 `malloc` 在日志滚动里成对 `free`（1884–1899）；fd 有界且退出显式关闭（5752–5754）。
4. **`am` 子进程有界回收**：`AM_PENDING_MAX=8`，池满杀最旧（2674–2679），每拍 `reap_am_children` 回收（5622），不会 fork 风暴积累。
5. **thermal zone 常驻 fd 的优化真实生效**：周期读取走 `lseek`+`read`（2307–2324），只有重扫时 `open`；`O_CLOEXEC` 防止泄漏给子进程（2299）。
6. **status 文件读写不会读到半截**：模块侧 `tmp` + `rename` 原子替换（527–544），daemon 每秒重开路径（2136），inode 变化不会导致写到旧文件。
7. **日志与操作记录都有界**：daemon 日志 16 256 B 上限并做行首对齐截断（1869–1903）；`LogTailReader` 200 KB/3 000 行/4 096 字符三重上限；`OpLog` 合计 64 KB。
8. **`ChartLoader` 的缓存口径正确**：只缓存解析产物、失败不入缓存、指纹含配置口径（类注释与 `read` 实现一致），不会残留旧口径结果。
9. **`RootShell` 不累积进程/线程**：每次 exec 新建 `su` 进程 + 2 个 gobbler，`finally` 里 `channel.close()`（435–439），线程在 EOF 自行结束。
10. **lite 的三条 `setInterval` 都有对应的 `clearInterval`**（1798/1894/1990），切页即停，没有后台空转。
