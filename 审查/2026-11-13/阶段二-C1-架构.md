## A 五个问题逐条结论

### A1 依赖方向

**结论：编译期方向成立（core 是叶子）；app 未绕过 ConfigStore；app-lite 复用了 core 服务，但在 JS 里二次实现了 core 已有的策略。**

1. **core 是否 import app/ui 的类：零处。**
   - `core/build.gradle.kts:20-24` 只有 `compileOnly` 的 Xposed API，没有 `project(":app")` 之类依赖，编译期不可能反向依赖。
   - core 内唯一的项目内 import 是 `Deployer.java:6` 的 `com.example.waspwingtempctrl.core.R`（core 自己的 R）。
   - 对 `waspwingtempctrl.ui` 的引用只有 Javadoc：`ConfigStore.java:1316`、`StartupTiming.java:164`。
   - `MainHook.java:3111/3128/3138` 的 `enterSetupActivity` 是 `loadClass("com.example.extool.B6ExperimentalActivity")`（被 hook 的宿主 app），不是本仓库的 `:app` 模块，不构成模块依赖。

2. **app 是否绕过 ConfigStore 读写 `profile.conf`：零处。**
   - 写：`ShortcutActionActivity.java:203`、`ConfigWriteQueue.java:156`、`ConfigFormController.java:790/862`、`WebBridge.java:212`（lite）全部走 `ConfigStore.setAll/removeKeys`；部署出厂配置走 `Deployer.java:738 → ConfigStore.writeFactoryIfAbsent`。
   - 读：`SetupActivity.java:52/70/73`、`ChartConfig.java:113-140`、`KiCutData.java:100/142`、`TextCopy.java`、`UiSettingsFragment.java` 等均走 `ConfigStore.get/read/paramsRoot`。
   - 唯一的直接路径访问是 `ConfigDiagnosticsText.java:30-35`：只做 `getConfigFile()` 的 `exists/length` 诊断，不读内容、不写。
   - app 内没有对 `profile.conf` 的 `FileInputStream/FileOutputStream/RandomAccessFile`。

3. **app-lite 是否复制 app 的逻辑而不是复用：服务层复用，策略层二次实现。**
   - 复用：`WebBridge.java:17-19` 直接依赖 core 的 `AppFiles/ConfigStore/Deployer`；`WebBridge.java:87-88/212` 用 ConfigStore 读快照/批量写；`WebBridge.java:229-245` 用 Deployer 动作；`WebBridge.java:279-285` 用 `AppFiles.readTailText`。没有复制 app 的任何 Java UI 类。
   - 二次实现（同一事实多来源）：
     - 参数资产读取：`WebBridge.java:40,70-77` 自己定义 `PARAMS_ASSET="params.json"` 并 `readAsset`，而 `ConfigStore.java:58,163` 已解析同一资产。
     - 配置 schema 语义：`app.js:197-275`（default/factory/序列化/多值缺槽）、`app.js:480-660`（表单与 master 门控）、`app.js:702-750`（min/max 钳制）、`app.js:780-960`（表型键）对应 `ConfigStore.java:978-1031`（assess）、`1297-1562`（KeyMeta）与 `1563-1600`（FieldMeta）与 `ConfigKeyRow.java:1464/1534`。
     - 曲线口径：`app.js:1376-1418` 重新实现 `UI_GAP_SEC` 的 3/15 与 `UI_CHART_VIEW` 槽 0 的 3000，和 `ChartConfig.java:37-46,112-182` 是两套。
     - CSV 列：`app.js:1454-1477` 硬编码 0..7，对应 `ChartDataset.java:53-72`。
     - 分组/键清单：`app.js:18-19` 的 `MAIN_GROUPS/WEBUI_KEYS` 是 `params.json` groups 的第二个来源。
   - 这不是「app→lite 的复制」，而是「core 已有派生逻辑 → JS 第二实现」。后果是改一处口径要同时改 Java 与 JS 两个前端。

### A3 配置入口唯一性

**结论：Java 侧只有 ConfigStore 一层；C 侧是 4 个各自成篇的写回函数；7 条写路径当前全部在 fcntl 锁内。**

写入 `profile.conf` 的路径共 **7 条**：

| 侧 | 入口 | 行 | 锁 |
|---|---|---|---|
| Java | `ConfigStore.setAll` | `ConfigStore.java:691` | `WRITE_LOCK` + `lockForWrite()`（738） |
| Java | `ConfigStore.writeFactoryIfAbsent` | `ConfigStore.java:853` | 同上（865-880） |
| Java | `ConfigStore.removeKeys` | `ConfigStore.java:1083` | 同上（1093-1112） |
| C | `writeback_temp_stop_disabled` | `tempctrl.c:3879` | `config_write_lock`（3880） |
| C | `migrate_pid_cut_config` | `tempctrl.c:4005` | `config_write_lock`（4006） |
| C | `migrate_rescan_unit_config` | `tempctrl.c:4106` | `config_write_lock`（4107） |
| C | `migrate_launch_timing_config` | `tempctrl.c:4171` | `config_write_lock`（4172） |

- **是否同一层**：Java 是（3 个 public 方法共用 `writeChanges/writeChangesLocked`）；C 不是——每个函数各自复制 `lock→fopen→stat→fopen(tmp)→逐行改写→commit→unlock` 约 45-60 行，只有 `commit_config_rewrite`（`tempctrl.c:3764-3785`）是共享的。第 5 条写回路径没有结构性保障，靠人记得调 `config_write_lock`。
- **锁内确认**：Java 的 `lockForWrite` 覆盖「读→写 tmp→rename」全程（`ConfigStore.java:738-770,782-800`）；`removeKeys` 的备份写（`atomicWrite`，1984）也在锁内。C 的 4 个函数都在 `fopen(path)` 之前取锁，`commit_config_rewrite` 之后才 unlock。`b6x-tempctrl.sh:25,147` 只读 `profile.conf`，不写。
- **锁协议一致**：Java 锁文件是 `profile.conf + ".lock"`（`ConfigStore.java:739`，后缀 83），C 是 `"%s.lock"`（`tempctrl.c:3825`）；两边都是 fcntl 记录锁，只有锁同一路径才互斥。当前 `CONFIG_FILE_NAME` 与 C 默认路径都是 `profile.conf`，一致。
- **遗留小坑**：C 先建锁文件、后 `stat(path)`（`tempctrl.c:3823-3861`）。若某次调用时配置不存在，会留下 root:0600 的锁文件，之后 app 打不开（S3-2）。当前 4 个调用点都要求配置已存在，尚未触发。

### A4 flavor 差异

**结论：不是 Gradle flavor，是两个 application 模块。功能差异很小（依赖与少量打包开关），重复约 20-25 行；版本号/applicationId 是真正的双份事实。**

- 规模：`app/build.gradle.kts` 199 行，`app-lite/build.gradle.kts` 60 行；差的 139 行主要是 app 独有的体积优化与两个 `preBuild` 布局检查（`app/build.gradle.kts:58-199`），不是功能配置。
- 共用且重复的片段：
  - `applicationId`（app:10 / lite:11）、`minSdk/targetSdk/versionCode`（app:11-13 / lite:12-14）；
  - signingConfig 的 `storePassword/keyAlias/keyPassword`（两边各一份，keystore 路径因目录不同而不同）；
  - `buildTypes.release` 的 `signingConfig/isMinifyEnabled/isShrinkResources/proguardFiles`（app:32-49 / lite:32-41，app 多一段 baselineProfile 忽略）；
  - `compileOptions`（app:54-57 / lite:44-47）、`dependenciesInfo`（app:84-87 / lite:51-54）。
- app 独有而 lite 不需要的：`resourceConfigurations zh/en`、baseline profile 忽略、`packaging` 排除、密度裁剪、Xposed 依赖、`checkPreInflateThemeAttr/checkNoConstraintReferencedIds`。lite 只有 WebView + framework 主题，这些差异合理。
- lite 独有的：`enableV1Signing=false/enableV2/V3`（CI 对 app 另做重签，lite 由 AGP 直签）。
- 是否抽出：
  - **值得抽出**：`versionCode`/`applicationId`。versionCode 是两处 Gradle + CI；applicationId 是两处 Gradle + `ConfigStore.DAEMON_PRIVATE_DIR` + C（`PRIVATE_DIR`/`HOST_PKG`）+ 脚本 `HOST_PKG`。CI 只断言了两个 APK 的 versionCode 相等（`build.yml:300-313`）和包名（`build.yml:534-543`），C/脚本的副本不在断言内。最小做法是 `gradle.properties` 或根 `build.gradle.kts` 定义单一值，两个模块引用。
  - **可选**：signing/release/dependenciesInfo 抽成 `buildSrc` 约定插件（约 20 行）。以当前 2 个模块的规模，收益主要是防漂移，不是省行数；出现第三个变体时再抽。
  - **不建议**：为了复用把 app 与 app-lite 合成一个模块的 flavor——两边 UI 实现完全不同（Java 布局 vs WebView 资产），合模块只能复用构建配置，还会把 appcompat/material 的依赖隔离变成 flavor 级依赖管理，收益低于成本。

### A5 分层是否还成立

**结论：编译期分层成立；运行期没有「协议定义层」，跨端事实靠三份手抄 + 文档。改一处通常跨 2-3 个模块，成本由「同一事实有几个来源」直接决定。**

现有分层：

```
参数定义/params.def.json ──生成──> core/assets/params.json（UI）
                              ├──> daemon/params_generated.h（C 键表/默认值）
                              └──> daemon/profile.conf（出厂模板）
core（ConfigStore/Deployer/AppFiles/MainHook/RootShell） ← app / app-lite
daemon/tempctrl.c  ←→  core：status 文件、广播、配置文件、部署产物（无编译期依赖）
```

- 好的部分：配置键做到了「定义一处生成四处 + `check_params.py` 三源对账」，是仓库里唯一有生成层和审计的跨端契约。
- 缺的部分：status 字段/路径、广播 action、CSV 列、运行时文件名没有对应的定义/生成层，只有 README 规范与零散 CI 断言。
- 三个最典型的改动：

| 改动 | 要动的文件 | 跨模块数 | 说明 |
|---|---|---:|---|
| 新增一个 daemon 消费的配置键 | `参数定义/params.def.json` → 跑 `gen_params.py` → `core/assets/params.json` + `daemon/params_generated.h`（若进生成表）+ `daemon/tempctrl.c`（行为/手写解析分支）+ 文档 | 3 | app/app-lite 通常 0 改动；若键归 webui 组，lite 的 `WEBUI_KEYS`（`app.js:19`）还要加一行 |
| 曲线 CSV 增列或改列序 | `daemon/tempctrl.c`（宏/格式串/实参）+ `app/ChartDataset.java` + `app/KiCutData.java`（若 7 号列移位）+ `app-lite/app.js` + 文档 + CI 断言 | 3 | 4 个代码文件各有独立下标；漏改读端不报错，曲线静默错位 |
| 状态文件加字段或改落点 | `core/MainHook.java` + `core/Deployer.java`（清理/预创建）+ `core/assets/deploy/b6x-tempctrl.sh` + `daemon/tempctrl.c` + `README.md`；另需重编 `tempctrl-arm64` | 3（core/daemon/资产） | 路径类改动还要同步 3 份清理清单（`Deployer:1663-1668`、`tempctrl.c:4714-4722`、脚本:386-393） |

**判定**：分层在编译期「还成立」，在运行期只到「文档约定」这一层。当前最贵的不是模块耦合，而是同一协议在 Java/C/JS 各有一份字面量。

## C 已核实无害

1. **core 无反向依赖**：`core/build.gradle.kts:20-24` 无 app 依赖；core 源码对 `waspwingtempctrl.ui` 仅有 Javadoc 引用（`ConfigStore.java:1316`、`StartupTiming.java:164`）；`MainHook` 的 `loadClass` 目标是宿主 `com.example.extool.*`，不是本仓库 app 模块。
2. **app/app-lite 全部配置访问都经 ConfigStore**：写入口仅 `setAll/removeKeys/writeFactoryIfAbsent`；唯一直接路径访问 `ConfigDiagnosticsText.java:30-35` 只做 `stat/length` 诊断，不读内容。没有 `profile.conf` 的裸文件 IO。
3. **7 条 `profile.conf` 写路径全在 fcntl 锁内**：Java 的 `setAll/writeFactoryIfAbsent/removeKeys` 均在 `lockForWrite` 内完成「读→临时文件→rename」；C 的 `writeback_temp_stop_disabled` 与三个 `migrate_*` 均在 `config_write_lock` 内；`b6x-tempctrl.sh` 只读不写。锁文件名 Java `profile.conf.lock`（`ConfigStore.java:739`）与 C `"%s.lock"`（`tempctrl.c:3825`）一致。
4. **app-lite 没有复制 app 的 Java 实现**：它复用 core 的 `ConfigStore/Deployer/AppFiles`，自身只有 `WebActivity/WebBridge` 两个类；问题在 JS 二次实现策略（S2-3），不在模块复制。
5. **配置键治理是全仓库最完整的一条链**：`参数定义/params.def.json` 单一手写源 → `gen_params.py` 生成 `params.json`、`params_generated.h`、`profile.conf`、文档表；`check_params.py` 做产物可复现与「定义↔C 接受集↔文档」对账。键名/默认值/范围的漂移有 CI 兜底。
6. **广播 7 个 extra 名当前两端一致**：`MainHook.java:314-320` 与 `tempctrl.c:2505-2507` 的名字/顺序一致，且 `build.yml:96-109` 有 CI 断言（问题只在 action 字符串没有同类断言，见 S2-2）。
