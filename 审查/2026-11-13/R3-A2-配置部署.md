## A. 十条横切判据逐条结论

1. **契约一致性**：定义（`params.def.json`）→ `params.json` → `ConfigStore` 的键名/类型/默认值链路一致；`keyCount()`、`present()`、`rawInt()` 的对外语义与调用点基本一致。发现两处偏差：多值键"存在但无数字 token"时 `ConfigStore` 给 0 而 C 端保持代码默认（S2-8）；`configFile` 固定 `profile.conf` 而 `daemonConfigPath()` 用定义里的 `configFileName`，二者可能分叉（S3-12，当前同值）。
2. **资源生命周期**：`memo` 仅一份、`ASSET_MD5_MEMO` 只在成功时写、IO 流均有界并关闭；未发现泄漏。两处收尾不完全：`atomicWrite` 写异常时不清 `.tmp`（S3-1）；卸载清理清单漏 `tempctrl_coldmax`（S3-2）。后台白名单线程每次部署新建、无回收（S3-7）。
3. **静默失败**：存在多处"步骤无条件宣称成功"（S3-3）、APK 资源缺失被写成"哈希不一致"（S3-5）、`updateScript()` 有警告仍返回成功（S3-4 同类）、KSU 旧版目录误判仍报成功（S2-7）、清理旧键可能删掉迁移源（S2-1）。无 root 时逐项显示"不存在/未安装"由结论行「无 su」兜住，属有意设计。
4. **并发与竞态**：`atomicWrite` 固定临时名 + 部署线程与配置 IO 线程是两个串行域（S2-5）；`RootShell` 超时后设备侧脚本可能续跑，重试可叠加两趟部署（S2-4）；`resetChannel()` 不持锁（S3-10）；`startDaemon` 冷却是非原子的检查后置位（S3-11）；memo 指纹不含 inode（S3-15）。
5. **状态机完整性**：部署只有"完成/未完成"两态，缺"部分就位"态：脚本写失败时二进制已换但 `status=null`、`placementsOk=false`，调用方不拉起（S3-4）。`uninstall()` 的 `ok` 只看 `!deployed`，不看进程是否停稳（S2-2）。部署无回滚副本，且 `startDaemon()` 先杀旧再试新，坏二进制会导致温控离线（S2-9）。`updateScript()` 的 `WD_STARTED=0`/`STARTED=0` 仅写入步骤文本、仍返回成功（S3-4）。
6. **输入边界**：进入 su 命令串的值全部来自可信来源或经校验/转义（`quote()`、`sanitizePids()`、`isMd5()`、`isStat()`、`isScriptPath()` 白名单），未发现可利用注入。两处硬化点：`R.array.xposed_scope` 的包名未 quote 直接拼 shell（S3-8）；`Value.ofText` 允许换行且 `setAll` 不校验，程序化调用可写出多行注入（S3-13 同类，当前调用方均为单行输入）。大文件读取无上限（S3-14）。
7. **旧键兼容层**：`compat.daemonAccept/cleanup/renames` 与 C 端接受集经审计对齐；`present()`/`rawInt()` 两个调用点都带 `size()`/空值回退，语义一致。**缺口**：整键族清理（`APP_LAUNCH_COOLDOWN`/`APP_WATCHDOG`）没有"新键已存在"守卫，而它们仍是 C 端一次性迁移的源（S2-1）。
8. **重复与死代码**：`EXIT_ALREADY_RUNNING` 与 `stopControlApp()`（含 `stopControlAppScript()`）全仓无调用（S3-6）；三处飞智包名常量与 `MainHook`/`arrays.xml` 重复属已记录的有意复制（审计覆盖）；`join` 等小工具在两类中各有一份，无功能风险。
9. **文档偏差**：`ConfigStore.keyCount()` 注释写 55（实际 59）；`Deployer` 类注释把 `stopControlApp()` 列为界面允许入口（实际无调用）；`RootShell.exec` 注释称"失败只更新退避窗口"（实际仅通道失败才更新）；越界发现 app 文档仍写 55/60 键（见 C）。
10. **测试缺口**：`lsp模块` 无任何 `src/test`/`androidTest`；`ConfText` 自述"可在桌面 JVM 直接跑测试"却零用例。`parseKv`、脚本拼装、原子写、出厂配置写出、旧键清理守卫均无回归保护（S3-19）。本次审查的全部结论均为静态核对，未运行时验证。

## C. 越界发现（归属包 + 一句话）

- **参数定义包**：`params.def.json` 的 `compat.cleanup.exact` 把 `APP_LAUNCH_COOLDOWN`/`APP_WATCHDOG` 列为可清理，但它们是 C 端（`tempctrl.c:3876-3932`）仍在永久读的一次性迁移源，且定义侧没有对应 `counterparts` 守卫——与 S2-1 同源，需定义侧补守卫数据。

## D. 已核实无害（可疑但查证不成立）

- **su 命令注入面**：逐处核查 `Deployer` 的脚本拼装——staged 路径经 `quote()`；`binStat/scriptPath/scriptStat/daemonPids/watchdogPids` 分别经 `isStat`/`isScriptPath`/`sanitizePids` 校验后才进脚本；md5 只以 `[0-9a-f]{32}` 缓存值嵌入；`svcd` 只用于回显不再拼命令。未发现未转义的外部值。
- **C 端临时文件冲突**：C 用 `profile.conf.tmpstop` 与 `.mig`，app 用 `profile.conf.tmp`，名字不相交；C 侧写回还对齐原属主/权限。
- **`present()`/`rawInt()` 语义**：仅两个调用点（`ChartConfig:121,169-174`、`ConfigKeyRow:672-677`），都带 `size()>i` 回退与 null 兜底，行为一致；`rawInt` 的"同键多行取后出现者"与 C 端一致。
- **`atomicWrite` 失败语义**：rename 失败会删 tmp 并抛错（1748-1754），目标文件不会出现半截；`fsync` 顺序正确。
- **cp→chmod→mv 链**：`cp` 失败时旧 `$BIN` 保持不变，`BIN_OK=0` 被上层判失败；`rm -f $BIN.new` 不改写 `BIN_OK` 的判定。
- **中转副本保留**：`files/deploy/tempctrl` 不删除是有意为之——同步清单的 `BIN_SRC/SCRIPT_SRC` 指向它，作为脚本侧降级来源（§2.5）。
- **`RootShell` 通道**：双流 EOF 才判死、marker 每次唯一、超时后 `destroyForcibly`、脚本均不含 `exit`；"换候选命令"只限通道失败且非超时，避免重复执行非幂等脚本（当前 deploy/uninstall 幂等）。
- **`ConfText` 与 C 解析对齐**：`lineStartOf`/`configLineEq`/`trimRight` 与 `config_parse_line` 口径一致；`spliceValue` 对 CRLF 与空值片段有专门分支（除 S2-6 的 `#` 情形）。
- **`removeKeys` 迁移源守卫**：在落盘前按当前文件重算 `KI_CUT_<n>` ↔ `PID_CUT_<n>`，任一守卫不过只少删该行；先备份后原子替换。
- **读失败不留档**：`read()` 失败不进 memo；`md5OfAsset` 失败不写 memo。
- **`splitLines`/`removeKeys` 行尾**：末尾换行与 CRLF 均能保留，删行不会产生半行。
- **`configFileName` 分叉**（S3-12）：当前定义与常量同为 `profile.conf`，属潜在问题而非现网缺陷。
- **`keyCount()` 注释键数**：注释写 55、实际 59，仅注释，不影响逻辑。

## E. 未覆盖 / 待真机

1. **SELinux 上下文**：`/data/local/tmp/tempctrl` 与 service.d 脚本均为 root `cp` 创建，未做 `chcon`/`restorecon`；能否执行取决于 root 方案继承的标签，静态无法判定，需真机 `ls -Z` + 执行验证。
2. **工具可用性/格式**：`md5sum`、`stat -c '%s:%Y:%i'`、`toybox`、`ksud -V` 的实际输出格式（S2-3/S2-7 的触发条件）需在 Magisk/KSU 新旧/APatch 上各验一次。
3. **并发部署写坏二进制**（S2-4）：需人为注入 su 超时并用两路重试复现，静态只能确认窗口存在。
4. **原子写断电语义**（S3-1 同类）：只 fsync 文件未 fsync 目录，掉电后 rename 是否可见未验证。
5. **C 端与 app 并发写 `profile.conf`**（S3-12/memo 竞态）：需真机在重启瞬间（UI_TEMP_STOP 写回）反复制造读写交叠。
6. **卸载时 daemon 处于 D 状态**（S2-2）：真机不易构造，建议故障注入（SIGSTOP 后 kill）验证。
