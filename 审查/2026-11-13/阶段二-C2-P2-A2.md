## D 双方一致的结论清单

1. **`am broadcast` 是调节期的最大单项 CPU**：每次下发 1 个 `am` 进程、`RAMP_DISPATCH=1` 拆 5 份（峰值 1 次/s、稳态 0），单次 100–300 ms 量级。
2. **曲线页每秒全量重解析是 UI 侧最大分配源**：原生 ≈1.9 万对象/s + 7–9 个 `Path` + 一次整视图重绘；lite ≈1.7 万对象/s + 2 000–4 300 `lineTo`。仅页面可见时发生。
3. **模块侧 1 Hz status 原子写 + 11 次反射 + 1 Hz 标记文件读**是常驻基线开销；叠加 SDK 队列 50 ms 空转（≈20 唤醒/s）与 250 ms 消费线程。
4. daemon 稳态 1s 拍本身很轻（3 open / 2–4 stat / 13–15 read / 1 write，无 fork），且 thermal zone 常驻 fd、`is_app_alive` 复用 fstat、5s 块复用采集缓存这三处优化确实生效。
5. 曲线 CSV 恒定 720–780 行、1 行/s + 每 60 s 整份重写；12× 放大、60 MB/天量级，长期无磁盘增长。
6. 所有原生 UI 轮询随页面不可见停止；lite 的定时器只在切 tab 停（后台可停未停）。
7. 内存侧无无界增长；唯二需采样的留存点是 `ChartLoader.cached`（有界常量）与 `MainHook.connectedControllers`（可能随重连累积）。
8. `ChartView.onDraw` 零分配零 IO；日志/曲线/oplog 均有硬上限。
9. 默认配置下 `/proc` 看门狗与 15s 仲裁**不生效**（对端结论正确，我方原报告需按 B-1 修正）。
10. 状态页（原生与 lite）均为约 5 s 一趟 root shell（对端正确，我方原报告需按 B-2 修正）。
