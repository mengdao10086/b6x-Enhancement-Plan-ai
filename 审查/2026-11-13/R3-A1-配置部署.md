## A. 十条横切判据逐条结论

1. **契约一致性**：键元数据、默认值、compat 判据均来自 `assets/params.json` 单一来源，`LOG_FILE`/包名/曲线容量有 `crossChecks` 兜底，**未发现漂移**。偏差两处：`CONFIG_FILE_NAME` 硬编码、`params.json` 的 `configFileName` 只进诊断不参与实际落点（S3-1）；键数注释与三份文档已过期（S3-2、S3-3）。
2. **资源生命周期**：流、进程、锁均在 `finally`/`closeQuietly` 收口，未发现泄漏（`RootShell` 的 gobbler 线程为 daemon、进程在超时/结束时销毁）。唯一问题：stderr 收集队列无界（S3-19）。
3. **静默失败**：`read()` 失败时会带回 note，但 `get(key)` 丢弃 note/unknownKeys，调用方拿到默认值而无告警（S3-22）；`cleanPrivateRuntime()` 删除失败不记账却仍报成功（S2-7）；`uninstall()` 的 `ok=!deployed` 在回吐缺失时会把失败当成功（S3-12）；多个失败分支不给状态回吐（S3-13）。
4. **并发与竞态**：配置写入无跨实例/跨进程互斥，共用固定 `.tmp`（S2-1）；应用部署与 `service.d` 自动更新共用 `$BIN.new`（S2-8）；枚举 PID 后直接 kill 存在 PID 复用窗口（S2-6）。su 串行锁、探测缓存双读锁、单例 DCL 均正确。
5. **状态机完整性**：部署/拉起/停止/卸载的状态回吐基本闭合；缺口是「盘面已就位」与「运行映像已换」被混为一谈：`deploy()` 写盘即写 `KEY_BIN_DEPLOYED_MD5`，随后拉起失败时界面仍可能显示“已完成”且不再提示重部署（S2-4）。无回滚路径（S3-14）。
6. **输入边界**：路径值未拒绝换行，可把一行配置拆成多行并注入额外键（S2-2）；表行号在界面往返中丢失去重编号（S2-3）；CRLF 表行尾 `\r` 未清理（S3-7）；Unicode 数字/溢出簇号退化为 0（S3-8）。数值溢出按 C 的 `atoi` 语义跳过，已核实无害。
7. **旧键兼容层**：`KI_CUT_` 有 counterparts 迁移源守卫、`DEBUG_` 豁免与 `daemonAccept` 前缀严格大于判据都正确。缺口：`cleanup.exact` 中 `APP_LAUNCH_COOLDOWN`/`APP_WATCHDOG` 仍被 C 永久读取，却无 `APP_LAUNCH_TIMING` 同源守卫即可删（S3-6）。
8. **重复与死代码**：`EXIT_ALREADY_RUNNING` 无 Java 引用；`Snapshot.notes` 在 `parseText()` 中从不写入（S3-20）。控制 app 三包名与 `MainHook`/`arrays.xml` 的重复属已审计的单一来源派生，未计缺陷。
9. **文档偏差**：键数 60/55（实际 59）、`Deployer` 方法清单多列 `buildDiagnostics`、卸载后私有目录“只剩两项”（实际还留 `tempctrl_coldmax`/`oplog`）、`tryExec` javadoc 与实现措辞不一致（S3-2、S3-3、S3-4、S3-5、S3-17）。
10. **测试缺口**：`lsp模块` 无任何 `test/` 或 `androidTest/`；`ConfText` 自述可在桌面 JVM 跑却无测试；原子写、并发写、解析器与 C 对齐、su 通道协议均无自动化用例（S3-21）。

**本包专属重点的直接回答**

- **su 命令串注入面**：进入脚本的**运行时值**全部受限——`BIN_STAT` 只放行 `[0-9:]+`、md5 只放行 `[0-9a-f]{32}`、脚本路径只认两个常量候选、PID 只留数字；staged 路径经 `quote()`。**未发现命令串注入**。真正的问题是文件系统信任：`/data/local/tmp` 可被 shell uid 写入且脚本跟随符号链接（S1-1）。
- **写入原子性**：目标文件不会半截（临时文件 → `fsync` → `rename`）；中断/磁盘满只留 `.tmp`，读端只认 `profile.conf`。缺目录 `fsync`（掉电后 rename 持久性不保证，但不会半截），且并发写共用一个 tmp（S2-1）。
- **未知键/补默认/present/rawInt**：未知键不进 `values` 且写侧拒绝；缺键补 `default`；`present()` 只表示“文件里真写了”，表行键不映射到逻辑键；`rawInt()` 只取第一整数。调用点（`ChartConfig`、`ConfigKeyRow`）语义一致；唯一偏差是读失败时 `present` 全空、`rawInt` 全 null，界面静默退回默认值（S3-22）。
- **部署权限/SELinux/覆盖回滚**：二进制与脚本均 `chmod 0755`，staging 在 app 私有目录；**无显式 `restorecon`/`chown`**，依赖 `/data/adb/...` 的目录 type_transition（E 节待真机）。覆盖用 `mv` 原子替换，但**无旧版本备份/回滚**（S3-14）。
- **失败回显/重试/并发部署**：多数早退失败不回吐盘面状态、无自动重试（S3-13）；并发部署的两个写入者见 S2-8。

## C. 越界发现（归属包 + 一句话）

1. **归属：部署脚本资产（`core/src/main/assets/deploy/`）** — `b6x-tempctrl.sh:300-306` 同样 `cp -f`/`chmod` 到 `$BIN.new` 后 `mv`，不拒绝符号链接，且由开机看门狗自动触发；S1-1 的修复必须覆盖此处。

3. **归属：UI / 快捷方式** — `ConfigFormController.java:788`（`removeKeys`，各自单线程 executor）与 `ShortcutActionActivity.java:79`（`setAll`）是 `profile.conf` 的另外两个写入者，不共享写锁，是 S2-1 的现实触发来源。

## D. 已核实无害（可疑但查证不成立）

- **设备回吐值回灌进 root 脚本的注入面**：`rememberProbeCaches()`（`Deployer.java:483-534`）对 `BIN_STAT`/md5/脚本路径/PID 分别做 `[0-9:]+`、`[0-9a-f]{32}`、两常量路径、纯数字白名单，之后才拼入脚本；未发现可注入路径。
- **`quote()` 转义**：单引号按 `'\''` 处理，staged 路径全部经它包装（`Deployer.java:1730-1732`）。
- **并发 `stageAsset` 写同一目标**：所有写入者都写同一 APK 资产的同一内容，交错不改变最终字节；且设备侧 md5 与 APK 侧复核会兜底（`Deployer.java:695-700`）。真正有风险的是不同内容的 `$BIN.new`（S2-8）。
- **`cp`→`mv` 原子替换**：避免覆写运行中二进制的 ETXTBSY 和“先删后落”的半成品，行为与文档一致。
- **`writeFactoryIfAbsent` 不覆盖已存在文件（含空文件）**：实现与决策一致（`ConfigStore.java:707-709`）。
- **读失败不留 memo + 登记前复核**：实现正确（`ConfigStore.java:317-331`、`:577-579`）。
- **`atomicWrite` 中途失败**：目标文件保持原样，残留 `.tmp` 不被读端消费，下一次写会截断。
- **未知键写入拒绝**、**表行键不被当未知键**、**`daemonAccept` 裸前缀不算认**：与文档逐条一致。
- **空表哨兵 `PID_CUT_1=`**：与 C 的“值空=清空该簇”语义一致（`tempctrl.c:3399-3410`）。
- **CRLF 对普通键值**：C 的 `trim_value` 与 Java 的 `trimValue` 都去 `\r`，仅表行例外（已列 S3-7）。
- **PID 快路径缓存**：`bin_pid_ok`/`wd_match` 在执行前复核身份，回收 PID 不会被误当成 daemon/看门狗（`Deployer.java:1263-1280`、`:1380-1405`）。
- **`(deleted)` 同口径**：Deployer 的 `bin_pids`/`bin_pid_ok` 与 C/脚本一致，都算“在跑”（`Deployer.java:1256-1267`）。
- **严格 UTF-8 写守卫**：非法字节拒绝改写；读路径用替换解码只影响展示（`ConfigStore.java:319` vs `:1908-1918`）。
- **锁与流收尾**：`RootShell.exec`/`checkAlive` 的锁在 `finally` 释放，`Channel.close` 关闭 stdin 并 destroy 进程；`Deployer` 的缓存读写成对加锁（`:483-534` vs `:1317-1326`）。
- **`tryExec` 失败不 markDead**：只成功时 `markAlive`，不会污染交互路径的退避状态（javadoc 措辞偏严，见 S3-17）。
- **`isPathAlignedWithDaemon`**：规范路径比较正确处理 `/data/data` 与 `/data/user/0` 的符号链接关系。
- **键顺序**：Android `org.json.JSONObject` 内部为 `LinkedHashMap`，`keys` 遍历顺序与 `params.json` 声明一致；此依赖属平台实现细节，非缺陷。
