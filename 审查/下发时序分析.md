# 下发时序分析：重算标记与制冷下发之间的 1 秒

> 只读分析，未改任何代码。分析对象：`lsp模块/daemon/tempctrl.c`（6443 行）与 `lsp模块/app/src/main/java/com/example/waspwingtempctrl/ui/*`。
> 用户观察（2026-11-15）：曲线图上制冷下发都要等重算标记打出来再过一秒才开始。

## 1. 一句话结论

**C：数据文件/曲线的对齐问题，控制层没有问题。**

- 界面上能看到的「目标制冷」是**第 7 列（0 基索引 6）设备回显的设定档**，不是第 8 列「下发目标制冷」；第 8 列界面根本不消费。
- 这一列的值来自**每秒开头、控制块之前**的采集快照；重算标记来自**控制块之后**写行那一刻的 `pid_recompute_pending`。所以标记落在第 N 行，回显变化最早只能落在第 N+1 行——差一行 = 1 秒，是数据行的取样顺序决定的。
- 第 8 列（下发目标制冷）记的是 `actual_cold`（限速后的目标值），**不是** `sent_cold`，也不是 PID 原始目标；它在标记同一行就已经更新。
- 平滑下发的第一份在同一拍（标记行写完之后几毫秒）就送出，**不存在**"等下一个 dispatch 节拍"的额外 1 秒（`tempctrl.c:6404-6407` 的 `timerfd_drain` 就是为此补取）。

### 2.3 列 7 取的是 sent 还是 target

**都不是。** 列 7 取 `actual_cold`，它是"限速后的目标值"：

- `tempctrl.c:375-378`：`// 始终向目标值（PID 目标制冷 / 风扇目标）靠拢，每周期最多变动速率限制的量`，`static int actual_cold = -1; // 当前实际制冷片强度`

- `tempctrl.c:6388-6390`：控制块内先 `rate_limited_execute()`（内部调 `rate_limit_cold`），再在 `:6402` 写行。

所以：**标记行上的列 7 已经是本周期的新目标**。而 `sent_cold`（真正已广播的值）由 `ramp_tick()` 在写行**之后**（`:6407`）才推进，它从来不进数据文件。任务里"如果列 7 取 sent_cold，则值没动是必然"的假设不成立——代码里列 7 不是 sent。

## 3. timerfd 相位（Q2）

- 创建与装载：`tempctrl.c:6231-6239`

```c
int tfd_tick = timerfd_create(CLOCK_MONOTONIC, TFD_CLOEXEC | TFD_NONBLOCK);
int tfd_dispatch = timerfd_create(CLOCK_MONOTONIC, TFD_CLOEXEC | TFD_NONBLOCK);
...
if (use_timerfd && timerfd_arm_periodic(tfd_tick, 1000) != 0) use_timerfd = 0;
if (use_timerfd && sync_dispatch_timer(tfd_dispatch, &dispatch_ms) != 0) use_timerfd = 0;
```

两个 fd 连续创建、连续装载，间隔是两次 `timerfd_settime` 系统调用（微秒级）。tick 先装、dispatch 后装，所以 dispatch 每次到期都略晚于 tick。

- 周期：`tempctrl.c:408-412`，`N=5` 时 `(5000 + 5/2)/5 = 1000` ms；默认 `RAMP_DISPATCH=1`、`RAMP_SLOTS=5`（`参数定义/params.def.json:628`、`:657`）。
- 相位保持：`tempctrl.c:6119-6126`

```c
/** 按当前 RAMP_SLOTS/RATE_LIMIT_FAN 重装下发定时器；间隔未变则不重装（保持节拍相位）。 */
static int sync_dispatch_timer(int fd, int *cur_ms) {
    int ms = ramp_dispatch_interval_ms();
    if (ms == *cur_ms) return 0;
```

稳态间隔恒为 1000ms，`:6275-6279` 每拍核对时 `ms == *cur_ms` 直接返回，**不重装**。两个定时器都按 `CLOCK_MONOTONIC` 绝对到期序列推进（`:6087` 注释「不累积漂移」）。

- 同拍首发保障：`:6404-6406`。tick 到期时 dispatch 还差几微秒，`wait_timer_events` 只取到 tick；控制块执行耗时远超几微秒，末尾 `timerfd_drain` 必然取到已到期的 dispatch，于是 `ramp_tick()` 在同一拍执行。

**结论：两定时器同相位，差值是微秒级且被 drain 吸收；"1 秒"是固定值而不是随机相位漂移。** 唯一会重装 dispatch 的场景是 `RAMP_SLOTS`/限速参数热重载导致间隔变化（`:6277-6278`，同时丢弃未走完的本轮），这不是稳态。

## 4. 「1 秒」到底是什么（Q3）

三种候选逐一排除：

**(a) 设计如此（首份本来在 1000ms 后）——不成立。** 代码明确让首份同拍送出（`:6404-6407` 注释「本拍判定通过的目标同一拍就送出第一份」）。ramp 的 5 份是 0/1000/2000/3000/4000 ms 的"之后各份"，首份在 t≈0。

**(b) 相位错位——不成立。** 见第 3 节：同相位、drain 补取、不会漂。

**(c) 数据文件/曲线的对齐问题——成立。**

一拍内的实际顺序（默认配置）：

| 时刻 | 动作 | 代码 |
|---|---|---|
| 本秒开头 | `sample_webui_inputs()` 读电池/CPU/散热器回传，快照 `cooler_cold_real`（旧回显） | `:6282` |
| 本秒内 | 5s 控制块到期：PID 算出新目标 → `rate_limit_cold` 更新 `actual_cold` → `apply_gear_direct` 登记 ramp，`pid_recompute_pending=1` | `:6380`、`:5240`、`:4939-4953` |
| 同一拍稍后 | `append_webui_row()` 写第 N 行：列 6 = **旧回显**、列 7 = **新目标**、列 9 = 1 | `:6402` |
| 同一拍末尾 | `ramp_tick()` 送出本轮第一份（`send_am_broadcast` fork+exec 非阻塞） | `:6407`、`:2994-3035` |
| 下一秒开头 | `sample_webui_inputs()` 读到设备已接受的新回显 | `:6282` |
| 下一拍 | 写第 N+1 行：列 6 = 新回显、列 9 = 0 | `:6402` |

所以：**标记在第 N 行，回显变化只可能出现在第 N+1 行**。物理首发发生在第 N 行写完之后几毫秒，并不晚 1 秒；晚的是"设备回显被读到并写进数据行"这一步。

**历史原因（为什么"现在看"才发现）**：`git show 0f91a60b`（2026-11-07「曲线行移到控制块之后写，重算标记同拍」）之前，`write_webui_data()` 在每拍**开头**、控制块之前调用：

```
-        write_webui_data();   // 每 1s 采集写数据文件（刚需热数据，WebUI 直接读）
+        sample_webui_inputs();   // 每 1s 采集（控制块用新鲜缓存；写行在 5s 控制块之后）
```

那时标记与控制决策差一行，但设备回显也差一行，两者**恰好同行**，所以看不出错位。该提交把写行移到控制块之后以让"标记与重算同行"，标记前移了一行，回显仍在下一行，于是曲线上露出 1 秒。这是列布局变化的副作用，不是控制行为变化。

**界面消费的是哪一列**（决定用户看到的是哪条线）：

- `app/src/main/java/.../ui/ChartDataset.java:36`：`[7]  下发目标制冷    0.1°C              → 不消费`
- `ChartDataset.java:43-45`：`[7] 下发目标制冷：写端有，读端有意不消费。本界面（图例 + 实时数值列）都不展示下发目标制冷……界面消费的「目标制冷」是 [6] 设备回显的设定档，「实际制冷」是 [10] 运行档。`
- `ChartSeries.java:75-76`：`new ChartSeries("cool", ... R.string.chart_series_cool ...)`；`:227-228`：`case "cool": return d.cool;`，而 `d.cool` 由 `ChartDataset` 的 `COL_COOL = Protocol.WEBUI_COL_COLD_SET`（索引 6）赋值。
- `app/逻辑说明.md:692`：`第 8 列（0 基索引 7）「目标制冷」写端有、读端有意不消费。`

即使 `RAMP_DISPATCH=0`，这个 1 秒也存在（见第 5 节），所以与平滑下发开关无关。

**固定还是随机**：按数据行计**固定 1 行**（1 秒），不是随机相位。下限恒为 1 行；能否恒为 1 行取决于 app/设备回显是否在 1 秒内落地（LSP 每秒写一次 status，`app/逻辑说明.md:524`），若某次跨过采样点，最多看到 2 行。

## 5. 平滑关闭时的对照（Q4）

`tempctrl.c:4954-4958`（`apply_gear_direct` 的 else 分支）：

```c
} else {
    send_am_broadcast(mode, target, send_rpm, cold, wl);
    sent_rpm        = send_rpm;
    sent_cold       = cold;
    ramp_slots_left = 0;
}
```

关闭平滑时，广播在控制块内**立即同步发起**（fork+exec，父进程不等），位置在 `append_webui_row()` 之前。但行的温度/回显快照仍然取自本秒开头（控制之前），所以：

- 设备回显依旧要到下一行才出现——**同一个 1 秒**。
- 列 7 依旧在标记行更新（`rate_limit_cold` 在广播前已更新 `actual_cold`）。

因此"关掉平滑后就没有延迟"不成立；反过来，这正好证明 1 秒与平滑下发无关，是采样/写行顺序造成的。

补充边界：只有 `use_timerfd=0` 的退化路径（`:6240-6246` 日志「定时器 创建或装载失败，退化为 1s 节拍」）下，`next_disp_ms` 的 1 秒分辨率才可能让首份晚 0~1 秒；该路径会写错误日志，不属于正常路径。

## 6. 若为 B：两方案对比

**不适用——结论是 C，不是 B。** 控制层不存在需要修的额外延迟，不建议为目标更新后"立即补发"（现在的代码已经同拍首发，补发只会变成一拍发两份，破坏 5 份分摊的步长语义与限速节奏）。

如果用户仍希望曲线上"标记与制冷变化"看起来同排，属于纯呈现层口径，可选做法（仅供拍板，未实施）：

- **在文档/图例里标明列 6 是"上一秒下发的设备回显"**：零风险、零代码改动，是唯一不歪曲数据的做法。
- **把回显列左移到标记行**（画图时用 N+1 行的回显覆盖 N 行）：会篡改数据语义，且下一行自身又需要下一行的回显，会整条曲线前移；不建议。

## 7. 未验证项

1. 真机实测 `am broadcast` → app 应用 → 设备回传 → LSP 写 status 的总时延（决定回显滞后是恒 1 行还是偶尔 2 行）。本次只读代码，未抓真机曲线/日志。
2. 用户具体看的是「目标制冷」（列 6）还是「实际制冷」（列 10）。结论对两者都成立（都由控制前的采集写入）；列 7 界面不显示，若用户看的是别的工具直读列 7，则那里不存在滞后。
3. `RAMP_SLOTS=3/4`（间隔 1667/1250ms）时 dispatch 与 tick 的相位错位幅度未实测；按代码推算只影响 5 份在 1 秒内的分布，不改变"回显滞后 ≥1 行"。
4. 退化路径（timerfd 创建失败）未实测，只按代码确认它会写错误日志并退化为 1s 粗节拍。
