## 配置文件系统 (profile.conf)

tempctrl 支持运行时配置文件，大部分关键阈值和参数均可外部修改，无需重新编译。

### 配置路径自动检测

1. **`--config` 参数**（最高优先级）：
   ```shell
   tempctrl --config /自定义路径/profile.conf
   ```
2. **自动检测**：通过 `/proc/self/exe` 获取自身路径，在同目录下查找
3. **默认值**：全部使用代码内默认值

### PERF_ENABLED / DEBUG_ENABLED / SYSFS_ENABLED 开关

配置层级：

```
PERF_ENABLED（性能总开关，默认=1）
  ├── =0：不加载性能参数（挡位表、PID、紧急、速率限制等），全部使用代码默认值
  └── =1：正常加载所有性能参数

DEBUG_ENABLED（调试总开关，独立于 PERF_ENABLED，默认=0）
  ├── =0：分区调试日志关闭
  └── =1：各 DEBUG_* 分区开关生效

SYSFS_ENABLED（sysfs 路径与缩放，独立于 PERF_ENABLED，默认=0）
  ├── =0：不加载自定义 sysfs/日志路径，使用代码默认路径
  └── =1：加载 profile.conf 中的 BATT_*/CPU_*/LOG_* 路径与缩放配置
```

这对调试很有用——**设置 `PERF_ENABLED=0` 但 `DEBUG_ENABLED=1` 可关闭性能控制并保留调试输出**；sysfs 路径可独立于性能开关加载（`SYSFS_ENABLED=1`）。

### ⚠️ 常见坑

| 坑 | 说明 |
|----|------|
| **Termux 编译不可用** | Termux 的 `clang -static` 链接的是 Termux 的 libc，非 Android libc。编译出的二进制在真机上 PT_TLS 对齐错误，必须用 NDK 编译。**开发阶段在 Termux 编出来可以看语法错误，但不要拿去真机跑** |
| **`--config` 路径** | service.sh 使用 `--config "$MODDIR/profile.conf"`直接从模块目录读取，不再复制到 `/data/local/tmp/` |

### 配置格式

```
# 注释以 # 开头
KEY=VALUE

# 例：
BATT_BASELINE=350
BATT_BOUNDARY=5 13 25
```

不认识的 key 静默跳过；每个值有范围保护（`clamp`），非法值不会导致进程崩溃。

### 热重载

每轮 `main_loop()`（5 秒间隔）开头 `stat()` 检查配置文件的修改时间（mtime），变了就自动重读所有参数并记日志。**修改配置无需重启 daemon**。

## 温度读取

- **电池温度**：`/sys/class/power_supply/battery/temp`
  - 原生 0.1°C 精度，如 350 = 35.0°C

- **CPU 温度**：`/sys/class/thermal/thermal_zone[N]/temp`
  - 原始值 m°C，÷100 转 0.1°C，如 75321 → 753 (=75.3°C)
  - 首次调用时在 `CPU_ZONE_MIN~CPU_ZONE_MAX` 范围内扫描，记录能读到有效值的 zone
  - 后续只扫描已记录的 zone，取最高值
  - 一阶低通滤波平滑（系数由 `CPU_FILTER_ALPHA` 配置，默认 α=0.25）

### 温度变化检测（v2.8）

- **值比较驱动**：不再依赖 sysfs 文件 mtime 判断温度是否变化（部分内核 mtime 更新不可靠，会导致温度实际在变却被判"未更新"而大量跳过）。改为每次 1s 采集直接读值，值与上次缓存不同才标记"更新"。
- **1s 窗口累积**：5s 控制周期的跳过判定不看"当前采样值 vs 上次控制值"，而是看**自上次控制以来 1s 层是否检测到过值变化**（累积标志，控制周期开始时快照并清零）。温度在窗口内变过又回到原位也不会漏判。
- **最大跳过次数**：值连续未变达 `BATT_SKIP_MAX`（默认 6）周期时强制进入一次 pid/gear 计算，防止温度文件卡死导致控制长期停摆。

## 档位系统

档位 1~12，使用查表法（非公式计算）。默认全部固定功率模式（实测智能温控模式的风扇转速配置非强制生效，
容易突破上限导致噪音突增）。

  -a com.flydigi.SET_TEMPERATURE_B7 \
  --ei mode 1 --ei windOC 6000 --ei coldOC 200

- **智能模式 (mode=0)**：设目标温度和风扇上限，散热器自行调节制冷
- **固定功率 (mode=1)**：直接指定风扇转速和制冷片强度

### GEAR_AUTO_FAN 自动风扇转速（v2.4）

当 `CTRL_MODE=0` 且 `GEAR_AUTO_FAN=1`（默认）时，固定功率模式下风扇转速不再直接使用挡位表配置值，
改用 PID 同款的**冷端强度 + 热端温度双映射平均**逻辑：
1. 从挡位表取出制冷强度 `cold`，计算 `rpm_from_cold_exp(cold)`（冷端指数映射）
2. 从状态文件获取热端温度 `HOT_TEMP`，计算 `rpm_from_hot_end(hot)`（热端线性映射）
3. 两者自加权合并（大者自动主导）
4. 结果受**挡位表风扇转速截断上限**约束：`实际转速 ≤ min(计算值, 挡位表配置值)`

这样挡位表的风扇转速变为了"最高噪音/性能上限"，实际风扇转速根据当前热负荷动态调整。
制冷强度（`cold`）仍直接使用挡位表配置值，不受此参数影响。

## PID 控制模式（v2.3）

`CTRL_MODE=1` 启用 PID 连续无级调节，完全绕过 gear 体系的档位逻辑。

### 控制流

```
main_loop() PID 分支:
  1. 热重载（共享）
  2. 读电池温度
  3. 温度更新时推入方差采样（原始值，非平滑值），环形缓冲区滑动计算
  4. 滤波判定：
     ── 预测过渡期（进入/退出后 6 周期）→ 强制滤波（防跳变）
     ── 否则按 PID_INPUT_FILTER_ENABLED：
         =1 滤波模式：EMA_DIR 方向取整滤波（pid_batt_alpha），每周期全量重算
         =0（默认）无滤波模式：使用原始值直通，温度未更新则跳过本周期
  5. CPU 补偿：
     CPU: clamp(cpu_weighted - batt_raw, 0) ÷ PID_CPU_COMP_DIVISOR
      → EMA_DIR 方向取整平滑（CPU_FILTER_ALPHA）
     总补偿 = CPU（直接加到电池温度输入）
  6. 温度预测（前馈，升温/降温权重任一 >0 时启用）：
     ── 窗口 → 峰/谷定位 → 每周期归一化 delta
     ── 稳定性闸门 ×1：低于闸门不停止，预测增量 × 抑制系数（PID_PREDICT_WEIGHT 第三值）
     ── 仅 2 有效点（1 个 delta）：线性外推 当前温度 + 两窗口间变化速度
     ── 多点：加速度均值迭代外推平衡温度
     ── 预测成功 → ramp-up 渐进钳位 + EMA 平滑（预测结果强制滤波）
     ── 进入/退出预测 → 防跳变平滑 + 开启 6 周期强制滤波
  7. 输入 = 预测值（有效时）｜滤波值或原始值，再 + CPU 补偿
     滤波模式每周期 / 无滤波模式变化时：
     pid_compute(输入) → P + I(方差门控/死区回退) + D(首次跳过)
     → pid_map_output(0~1) → cold(线性)（风扇目标已独立计算，不再在此输出）
     （无输出平滑，直接映射）
  8. return（跳过电池控制/反补/豁免等全部 gear 逻辑）

rate_limited_execute() PID 分支:
  → rate_limit_cold(pid_align_cold) 限速制冷（actual_cold）
  → compute_fan_target() 独立风扇目标（冷端指数 + 热端线性加权，不跟 PID 输出）
  → rate_limit_fan 限速风扇
  → apply_gear_direct(1, 5, send_rpm, actual_cold, 0) 纯下发（去重/日志/广播）
```

### PID 参数配置

详见 `profile.conf` 的 `[5] PID 模式控制` 段，所有参数通过配置热重载，无需重启。

### I 项方差门控（v2.3）

I 项（积分）的累积条件从固定 ±1°C 分离改为**方差门控 + 死区回退**双层逻辑：

| 层级 | 条件 | 效果 |
|------|------|------|
| **方差门控**（首选） | 温度方差 < `PID_KI_VAR_THRESHOLD` | I 项全温度段启用（无死区限制），消除稳态静差 |
| **死区回退**（备选） | 方差门控未激活且 `\|error\| < PID_KI_DEADBAND` | 仅在死区内累积，防 windup |
| **冻结** | 均不满足 | I 项不累积 |

方差计算方式：
- 采样值：原始电池温度（`batt_raw`，非 EMA 平滑值）
- 触发条件：仅 `batt_temp_updated == true` 时推入
- 缓冲区：环形 FIFO，大小 = `PID_KI_VAR_SAMPLES`（默认 6）
- 采样不足（< 2）时回退死区模式

**设计意图**：解决旧 ±1°C 分离导致稳态静差 >1°C 时 I 项永远无法介入的问题。温度稳定时方差小 → I 项跨越大偏差继续累积，把温度拉到目标；温度波动时方差大 → 冻结 I 防 windup。

### 制冷→RPM 映射引擎（双模式共享）

PID 和 DIRECT_COLD（已移除）模式共用同一套映射函数，gear 模式不使用：

| 函数 | 映射方式 | 用途 |
|------|---------|------|
| `rpm_from_hot_end()` | EMA 平滑 + 双向滞回线性映射 | 热端温度 → RPM（需求侧：越高越迫切），输入先经 `RPM_SMOOTH_ALPHA` EMA 平滑（滞回基于平滑值），降温滞回 +1°C，升温不低于上次 RPM；**热端 ≤0（异常/未就绪）时保持上次输出** |
| `rpm_from_cold_exp()` | `cold^exp` 指数 + EMA 平滑 | 冷强度 → RPM（供给侧：越强调速越高），输出经 `RPM_SMOOTH_ALPHA` EMA 平滑 |
| `rpm_combine_weighted()` | 自加权平均 = (a²+b²)/(a+b) | 大者自动主导 |
| `compute_fan_target()` | `rpm_from_cold_exp(actual_cold)` + 热端加权合并 | 独立风扇目标：PID/Gear 每周期下发前统一计算，与 PID/Gear 输出解耦（禁降钉死时风扇保持高转速，热端过温直接拉满） |

### EMA 方向取整

所有整数 EMA 平滑（CPU 温度、电池电流、PID 电池滤波）使用 `EMA_DIR` 宏替代标准 `EMA`。
标准整数 EMA 因截断存在渐进问题（如 `α=33%` 时 `old=449 + raw=450` 永远到不了 450），
`EMA_DIR` 基于原始值方向做取整：原始值升高→向上取整，原始值降低→自然截断（按需方向），
确保滤波值能实际到达目标温度。

## 主循环逻辑

**决策执行分离 + 限速统一下沉**：`main_loop()` 纯计算不下发，`rate_limited_execute()` 分发。**PID 模式：`rate_limit_cold()` 限速制冷 → `compute_fan_target()` 独立计算风扇目标（基于限速后实际制冷，不跟 PID 输出）→ `rate_limit_fan()` 限速风扇 → `apply_gear_direct()` 纯下发**；Gear 模式：限速内建在 `apply_gear()` 内部（`rate_limit_cold` → `GEAR_AUTO_FAN` 分支 `compute_fan_target` → `rate_limit_fan`）。所有计算层（PID / 电池控制）只传递目标值，不限速。风扇目标基于限速后制冷（而非目标制冷），禁降钉死时风扇保持高转速。

```
 ┌─ 主循环（1 秒节拍；控制每 5s）───────────────────────────────┐
 │  每 1s：write_webui_data() 采集电池/CPU/散热器 → 缓存+数据文件（滚动480行）│
 │  每 5s（时间判定）执行下方控制节拍：                        │
 │                                                          │
 │  1. 连接检测（双重检查：status 文件 mtime + BLE=1）         │
 │     ├─ 断联 → 实际值保持（丢弃未执行变化量）               │
 │     │       → 重连后三值对齐匹配挡位，不立即下发，          │
 │     │       → 由 rate_limited_execute 按正常速率逐步过渡   │
 │     │       → continue（跳过本轮）                        │
 │     │       ⚡ 重连后首次温度读取不计入任何判断，          │
 │     │          数据正常更新后直接进入冷却期               │
 │     └─ 存活 → 继续                                        │
 │                                                          │
 │  2. main_loop() 纯计算                                    │
 │     紧急干预（CPU 温度）→                          │
 │     if current_gear_override() → 跳过电池控制              │
 │     else → 电池控制（反补+豁免，REV_COMP 配置）                    │
 │     → 保存 target                                          │
 │                                                          │
 |  3. ★ 速率限制执行（替代逐档变动 + RPM 平滑跟踪）          │
 │     rate_limited_execute() 对每个物理参数独立限速：        │
 │     ├─ 风扇转速：升速 = FAN_UP + d × FAN_MULT / 10，降速 = RATE_LIMIT_FAN_DOWN │
 │     ├─ 制冷强度：升速 = COLD_BASE + dev × COLD_MULT / 10，降速 = COLD_BASE − dev × COLD_MULT / 10（dev 有符号，负值禁方向）│
 │     └─ 目标温度：每周期最多 ±RATE_LIMIT_TEMP              │
 │     溢出自然累积下周期；目标变化时从当前值重新计算         │
 │                                                          │
 │  4. sleep(1)；原"5 秒间隔对齐"（按 status mtime 调整 sleep）已删除 │
 └───────────────────────────────────────────────────────────┘
```

### 关键说明

- **`target_level`**：控制逻辑计算出的目标档位，由 `main_loop` 末尾设置，供下轮执行
- **`battery_fan_level`**：电池控制的逻辑基准值（同步到 `final_level`），不是实际档位
- **限速统一下沉 vs 强制下发**：正常运行时限速由 `apply_gear()` / `apply_gear_direct()` 内建执行，计算层只管传目标值
- **三参数独立速率限制**（v2.3+ 动态温差修正 + 0.1°C 精度）：风扇升速（`RATE_LIMIT_FAN_UP + d × RATE_LIMIT_FAN_MULT / 10`，d=|0.1°C 温差|）和降速（`RATE_LIMIT_FAN_DOWN` 固定值）独立配置；制冷片强度升降速独立且有符号（升速 = `RATE_LIMIT_COLD + d × RATE_LIMIT_COLD_MULT / 10`，降速 = `RATE_LIMIT_COLD − d × RATE_LIMIT_COLD_MULT / 10`，d = 有符号温差(电池温度 − BATT_BASELINE)）。不再取绝对值：负值表示禁止该方向变化（电池 ≥37.5°C 禁止降制冷强度、≤32.5°C 禁止升制冷强度）。使用 `d × mult / 10` 保留 0.1°C 精度，避免先截断到 °C 再乘倍率造成的精度损失。目标温度（`RATE_LIMIT_TEMP`，仅智能温控模式）在发送函数内各自独立限速，互不影响。溢出自然累积下周期，目标变化时从当前实际值重新计算
- **重连安全对齐**：断联后实际值保持不动（丢弃未执行变化量）。重连时三个实际值（RPM/制冷/温度）都调到匹配挡位，不下发，由 `apply_gear` 按正常速率逐步过渡。防止部分执行期间断联导致参数组合不协调（如风扇低+制冷高→危险，或风扇高+制冷低→噪音），以及防止基准值错误导致异常操作
- **溢出累积**：每周期差值若超过速率限制，超出部分自然保留至下周期，不做丢弃。目标档位变化时从当前实际值重新计算差值，实现"没变完也能继续增加/减少"
- **重连温度跳过**：重连后首次 `battery_control` 的电池温度读数不参与反补、趋势豁免、常规升降档等任何判断，仅更新记录后直接进入档位变动冷却（`batt_cooldown = BATT_COOLDOWN_CYCLES`），防止断联期间积累的温度差引发异常调整
- **冷却期不影响执行**：`batt_cooldown` 只阻止电池控制做新决策，速率限制执行不受影响（已累积的差值照常消耗）

### main_loop() 内部详细逻辑（每 5s 控制节拍执行一次）

0. **检查配置更新** → `stat()` 检测 `profile.conf` 修改时间，变了就热重载
1. **紧急干预** → 读 CPU 温度（低通滤波）→ 判定紧急等级 (0~3)，设 `forced_min_level`
2. **电池控制** → 读电池温度 → 计算温度变化量 + 常规档位调整量
   - 首次读取（`last_batt_reading < 0`，启动后或重连后第一次）跳过所有判断，仅更新记录后直接进入冷却
   - 温度读数不变则跳过
   - **反补查表**（Sheet3 三区×双向×三级阈值）：
     - 三区：冷外区(≤基准-ZONE2) / 内区(±ZONE2内) / 热外区(≥基准+ZONE2)
     
     | 方向 | 区域 | 反补T1 | 反补T2 | 反补T3 |
     |------|------|--------|--------|--------|
     | 升温 | 冷外区 | 0.4°C/周期 | — | — |
     | 升温 | 内区 | 0.3°C/周期 | 0.4°C/周期 | — |
     | 升温 | 热外区 | 0.2°C/周期 | 0.3°C/周期 | 0.4°C/周期 |
     | 降温 | 冷外区 | 0.2°C/周期 | 0.3°C/周期 | 0.4°C/周期 |
     | 降温 | 内区 | 0.3°C/周期 | 0.4°C/周期 | — |
     | 降温 | 热外区 | 0.4°C/周期 | — | — |
   - **趋势豁免**（温度向基准方向变动时跳过调整，防振荡）：豁免生效阈值随速率提高而抬高
     - rate < T1（无阈值触发）→ 豁免区间 [0, T1)（原行为）
     - T1 ≤ rate < T2（T1已触发）→ 豁免区间 [T1, T2)（豁免提至T1以上）
     - T2 ≤ rate < T3（T2已触发）→ 豁免区间 [T2, T3)（豁免提至T2以上）
     - rate ≥ T3（T3已触发）→ 不豁免
   - **温度锚点复位机制**（替代原计数上限）：首次豁免记录当前电池温度为锚点。以当前区间中间值（steps=0→T1/2, steps=1→(T1+T2)/2, steps=2→(T2+T3)/2）为偏移量：降温方向用锚点-偏移量为复位下限，升温方向用锚点+偏移量为复位上限。电池温度越过复位阈值后豁免计数器复位，下轮以新锚点重新开始
   - 反补按每周期速率查表（温差÷空闲周期数），冷却期累积不执行，到期后合并计算

   - 未被豁免/反补时执行常规升降档（偏差四区策略：死区/±1档/±2档/±3档，阈值由 BATT_BOUNDARY_1/2/3 配置）
3. **合最终档位** = `max(battery_fan_level, forced_min_level)`
4. **同步逻辑目标**：`battery_fan_level = final_level`（下轮电池控制以此为基础）
5. **保存执行目标**：`target_level = final_level`（供下轮 `rate_limited_execute()` 使用）
6. **退出紧急限制**：如果刚退出紧急等级，根据降档模式处理档位
   - 模式 0（钳制）：硬 cap 到 `EMERG_FORCED_X + EMERG_EXIT_CAP_OFFSET`
   - 模式 1（降档）：`battery_fan_level -= EMERG_STEP`（固定步数）
   - 退出条件已在紧急干预中由 AND 逻辑保证，但仍受电池温度约束：
     - 电池温度 < 基准 + `EMERG_EXIT_BATT_THRESHOLD` → 全效退出（正常降档/钳制）
     - 电池温度 < 基准 + `EMERG_EXIT_BATT_THRESHOLD` × 2 → 半效退出（档位/钳制量减半，向下取整）
     - 电池温度 ≥ 基准 + `EMERG_EXIT_BATT_THRESHOLD` × 2 → 不退出（保持当前档位）

## 进程检测机制

使用 **双重检查**：状态文件 mtime 心跳检查 + BLE 连接状态。B6X 文件 BLE=0/1/2（0=未连接，1=老 app 连接，2=新 app 连接），B7X 文件 BLE=0/6/7 设备型号编码。只要有一个出问题就算断联。

```
 启动 → 创建 status 文件（0666，所有用户可写）
      → 等待 status 文件出现 BLE≠0（模块就绪 + BLE 已连；B6X 文件 BLE=1/2，B7X 文件 BLE=6/7）
 
 工作模式中，每 5 秒：
   连接检测 → 双 app 存活仲裁 → main_loop（纯计算）→ 速率限制执行
   
   1. 读 status 文件内容 → BLE（B6X 文件：0=未连接/1=老 app 连/2=新 app 连；B7X 文件：0/6/7 型号）
   
   2. 双重检查存活检测（任一不满足即算断联）：
      ├─ stat(status 文件).mtime 距现在 ≤ 5秒？      → 模块在写心跳?
      └─ status 文件内容 BLE≠0?                       → BLE 已连接?
      
      ├─ 全部 OK → 存活
      └─ 任一失败  → 模块/BLE 失联
                          ↓
                      等待复活子循环（每 5 秒检测，同时查 BLE）
                          ↓
                      模块+BLE 都重新就绪 → 三值对齐匹配挡位 → 按正常速率过渡

 模块侧（LSPosed）：
   ────────────────────────────────
   onDeviceConnected / disconnect 钩子 → 更新 bleConnected + connectedModel
   每 1 秒线程（后台 BLE 重连保持 5s 节奏）+ 连接/断连事件：FileOutputStream 写 "BLE=0/1/2\n"（B6X）或 "BLE=0/6/7\n"（B7X）+ CONNECTED_AT + BLE_OWNER_LAST=<值> <时间> 到 status 文件
   （BLE_OWNER_LAST 连接时写入、断连保留，标识"上次连接者"，供 app 存活仲裁）
   （直接 Java 文件 I/O，不走 su，无 KSU 命名空间问题）
```

### 文件详情

| 项目 | 说明 |
|------|------|
| 路径（B6X） | `/data/local/tmp/tempctrl_b6x.status` |
| 路径（B7X） | `/data/local/tmp/tempctrl_b7x.status` |
| 创建者 | tempctrl 启动时 `fopen("a")` + `chmod 0666`（两个文件） |
| 写入者 | LSPosed 模块每 1 秒覆写 + 连接/断连事件即时覆写对应设备的 status（含散热器全参数回传 + `CONNECTED_AT` + `BLE_OWNER_LAST=<值> <时间>`；`BOOT_AT` 已删除） |
| 读取者 | tempctrl 主循环开头 `read_status_ble_both()` 逐行解析双文件 |
| 心跳超时 | 3 秒（`STATUS_TIMEOUT` 硬编码，LSP 每 1s 写，超 3s 判死） |
| 温控仲裁 | `select_active_device()` — 先连者优先：比较 `CONNECTED_AT` 时间戳，连入较早的设备获得控制权 |
| 限幅切换 | `update_active_limits()` — 按 status 回传的实际设备型号切换上限（B6X 文件 BLE=1/2 → 型号兜底 6 → 制冷 194/风扇 6000；B7X 文件 BLE=6/7 → 制冷/风扇默认与 B6X 一致，由 FAN_RPM/PID_COLD 第三值配置），非按包名猜测 |

### 双检测互补

| 场景 | 文件 mtime | BLE≠0? | 结果 |
|------|-----------|--------|------|
| App 正常运行，BLE 已连 | ✅（新鲜） | ✅ | 存活 |
| App 正常运行，BLE 断联 | ✅（新鲜） | ❌ | 断联（等 BLE） |
| App 被 kill | ❌（无写入） | ❌ | 断联 |
| App 卡死/ANR | ❌（无写入） | - | 断联 |
| 文件被意外删除 | ❌（stat 失败） | - | 断联（daemon 会重建） |

### 三方 app 存活仲裁（v2.7）

三个 app 最多一个后台存活：老 B6X app（`com.flydigi.waspwing.experimental`）+ 新 B6X app（`com.flydigi.waspwing.experimentanliuliu`）+ farsef（B7X 游戏厅）。由 `arbitrate_apps()` 每 5 秒在读取双 status 后调用。

farsef 只在**最近连接的是 B6X 散热器**（`BLE_OWNER_LAST`=6）时参与仲裁——它控制同一台 B6X 散热器才与两个 B6X app 竞争；连的是 B7X 设备（=7）时不参与（控制另一台设备，不应被杀）。

```
存活参与者 = {老B6X, 新B6X} ∪（farsef 存活 && BLE_OWNER_LAST==6 ? {farsef} : ∅）
参与者 < 2 → 不仲裁
保留优先级：
  1. BLE_OWNER_LAST 值代表的 app（标识"上次连接者"，连接时写入、断连保留）：
     =1 → 保留老 B6X app
     =2 → 保留新 B6X app
     =6 → 候选保留 farsef
  2. 无 BLE_OWNER_LAST → 回退当前连接者 BLE 字段（=1 老 / =2 新）
  3. 兜底保留老 app

保留者涉及 farsef 时：比较 farsef 的 BLE_OWNER_LAST 时间与另一方（B6X app）的
CONNECTED_AT，保留时间更晚（最近使用）的那个。

被淘汰者非前台时 am force-stop（dumpsys window mCurrentFocus 优先判断，
被淘汰者在前台则等下一周期再试）
```

**与温控仲裁的关系**：`arbitrate_apps()` 只管 app 存活，`select_active_device()` 只管散热器控制权。两个 B6X app 共写同一 B6X status 文件；`BLE_OWNER_LAST` 由 LSP 连接事件写入、断连保留，标识"上次连接者"；farsef 连 B6X 设备时写 B7X status 文件（BLE=6 + `BLE_OWNER_LAST`=6）。都未连接时 arbitrate 保留上次连接者（或老 app）在后台待命（LSP 后台自动重连会恢复连接）。

**v2.8 自动拉起**：`arbitrate_apps()` 扩展——当**没有任何散热器 app 存活**时自动拉起上次使用的 app（`launch_last_app()`，复用 `BLE_OWNER_LAST` 选择逻辑：2→新 B6X app、6/7→farsef、其余/无记录→老 B6X app；目标 B6X app 未安装时回退另一个）。拉起用 `am start` + `b6x_auto_launch` 标志，LSP 读到后连接完成自动 `moveTaskToBack` 后台化（几乎无感）。带 60s 冷却；由 `APP_LAUNCH_ENABLED` 开关控制（默认 0 关闭，刷入时音量±选择）。调用时机：启动等待设备循环 + 主循环每 5s 节拍 + **断联（连接丢失）时**（存活检测失败路径；无 app 存活时真正拉起，app 存活时记 debug「已在运行」；开关关闭也会记 debug「开关关闭，跳过」，便于排查）。

**LSP 侧配合（v2.9）**：连接成功时把散热器 MAC 持久化到 `/data/local/tmp/tempctrl_last_dev`。冷启动打开 app 时，LSP 检测到引导页（MainActivity）即**自动进入参数设置界面**（等效自动点「开始设置」，`autoStartSetup()`），由 B6ExperimentalActivity.onResume 的 `tryConnect()` 主动发起连接——不再需要手动点「开始设置」。已进入过设置界面（`enteredSetup`）或已连接时跳过；后台重连线程仍保留（断开后每 5s 兜底）；`am start` 携带 `b6x_auto_launch=1` 时 LSP 将 Activity 切回后台。

## 电池控制细节

- **基准温度**：35.0°C（`BATT_BASELINE=350`，可配置）
- **四级策略**（diff = 当前温度 - 基准温度）：
  - `|diff| ≤ BATT_BOUNDARY_1` → 不动，属于正常范围
  - `BATT_BOUNDARY_1 < |diff| ≤ BATT_BOUNDARY_2` → 升/降 1 档
  - `BATT_BOUNDARY_2 < |diff| ≤ BATT_BOUNDARY_3` → 升/降 2 档
  - `|diff| > BATT_BOUNDARY_3` → 升/降 3 档

- **档位同步机制**（逻辑跟踪 vs 实际执行分离）：
  - `battery_fan_level = final_level` → 逻辑基准值（供下轮电池控制计算起点）
  - `target_level = final_level` → 执行目标（供下轮逐步执行使用）
  - 电池控制始终从上次计算的逻辑目标开始调整，不受逐步执行滞后影响
  - 紧急退出后不会暴跌——`battery_fan_level` 继承了紧急期间的档位
  - 退出紧急限制在逻辑同步之后执行：根据模式选择钳制或降档

- **反补查表（Sheet3 三区×双向×三级阈值）**：
  - **三区分类**（基于电池温度相对基准的位置）：
    - **冷外区**：`batt ≤ BASELINE - ZONE_2`（显著低于基准）
    - **内区**：`|batt - BASELINE| < ZONE_2`（基准附近）
    - **热外区**：`batt ≥ BASELINE + ZONE_2`（显著高于基准）
  - 反补档位数 = 跨越几个阈值门槛就补几档（见上表）
  - **趋势豁免**：温度向基准方向变动时跳过调整。豁免生效阈值随速率抬高：T1触发时 [0, T1) 可豁免，T2触发时 [T1, T2) 可豁免，T3触发时 [T2, T3) 可豁免，T3+不豁免
  - **温度锚点复位**（替代原计数上限）：首次豁免记录当前电池温度为锚点，以当前区间中间值（steps=0→T1/2, steps=1→(T1+T2)/2, steps=2→(T2+T3)/2）为偏移量。降温方向（温度向基准降温）用锚点-偏移量为复位下限，升温方向用锚点+偏移量为复位上限。电池温度越过复位阈值后豁免计数器复位，下轮以新锚点重新开始
  - 最高/最低档位时不记日志（避免刷屏）
  - 反补、趋势豁免、常规升降档在 batt_cooldown 冷却期内均不做调整。反补独立冷却（REV_COMP_COOLDOWN）期间累积温差，到期后与下周期合并计算

- **防重复（mtime 检测）**：
  - 通过 `stat()` 检测电池温度 sysfs 文件的修改时间（mtime）
  - mtime 未变化时跳过本周期控制逻辑，仅递增空闲周期计数（`batt_idle_cycles`）
  - mtime 变化时立即更新缓存值，正常执行控制逻辑
  - 相比原值比较：sysfs 文件由内核驱动在 ADC 采样后更新 mtime，比数值比较更可靠

- **档位变动冷却期**：每次任何原因导致的档位变动后冻结 `BATT_COOLDOWN_CYCLES` 个周期
  - 冻结期间跳过因电池温度触发的常规升降档、趋势豁免和反补
  - 紧急干预不受冷却限制（反补、趋势豁免、常规升降档在冷却期内均跳过）

- **紧急退出恢复期**（阈值放大）：紧急等级降低后，BATT_BOUNDARY 阈值倍率逐步衰减恢复全灵敏度：
  - P1：×`EMERG_RECOVERY_MULT` 第一值（默认 6），持续 `EMERG_RECOVERY_PHASE_CYCLES`（默认 6）周期
  - P2：×`EMERG_RECOVERY_MULT` 第二值（默认 4），持续 `EMERG_RECOVERY_PHASE_CYCLES` 周期
  - P3：×`EMERG_RECOVERY_MULT` 第三值（默认 2），持续 `EMERG_RECOVERY_PHASE_CYCLES` 周期
  - P4：×1（恢复正常，全灵敏度）
  - 各倍率和周期数可通过 `profile.conf` 的 `EMERG_RECOVERY_MULT`（三值：6 4 2）和 `EMERG_RECOVERY_PHASE_CYCLES` 配置
  - 恢复期内反补不受影响（继续正常执行）
  - 连续退出紧急时从 M1 重新开始；重新进入紧急时立即取消恢复期，恢复全灵敏度以快速响应
  - 此机制防止退出紧急后电池温度仍偏高导致立即升降档，造成档位反复跳动

## 紧急干预细节（CPU 温度单源）

紧急干预监测 **CPU 温度** 单一来源，直接比较阈值判定等级。

### CPU 温度处理
- 一阶低通滤波：`weighted = raw × CPU_FILTER_ALPHA% + old × (100-CPU_FILTER_ALPHA)%`
- 首次运行直接赋值，不做滤波
- 滤波系数默认 25 (α=0.25)，可通过 `CPU_FILTER_ALPHA` 配置

### 紧急等级与强制档位

| 等级 | 触发条件 | 恢复条件 | 模式0 最低档 | 模式1 最低档 (EMERG_STEP=2) |
|------|---------|---------|-------------|---------------------------|
| 0 | — | — | 无 | 无 |
| 1 | CPU ≥ 65°C | CPU < 55°C | 6（固定 3050RPM/75） | level_min + 2 = 3 |
| 2 | CPU ≥ 75°C | CPU < 65°C | 8（固定 4000RPM/125） | level_min + 4 = 5 |
| 3 | CPU ≥ 85°C | CPU < 75°C | 10（固定 5000RPM/165） | level_min + 6 = 7 |

**退出紧急时**根据降档模式处理：
- **模式 0（钳制最高档）**：限制 `battery_fan_level` 上限（在同步之后执行，保证生效）
  - 退出等级 3 → `battery_fan_level ≤ EMERG_FORCED_3 + EMERG_EXIT_CAP_OFFSET`
  - 退出等级 2 → `battery_fan_level ≤ EMERG_FORCED_2 + EMERG_EXIT_CAP_OFFSET`
  - 退出等级 1 → `battery_fan_level ≤ EMERG_FORCED_1 + EMERG_EXIT_CAP_OFFSET`
  - `EMERG_EXIT_CAP_OFFSET` 默认 1，退出时高一级强制档位 + 此偏移作为档位上限，防止 `battery_control` 立即拉升
- **模式 1（降档）**：直接减去档位
  - `battery_fan_level -= EMERG_STEP`（全效）或 `EMERG_STEP/2`（半效，受电池温度约束），不乘下降级数
  - 默认 EMERG_STEP=2：全效退出时降 2 档，半效退出时降 1 档

## 电流-挡位映射 + 温度调整融合模式

融合设计：电流 → EMA 平滑 → 推荐挡位（基础），温度 → 在推荐挡位基础上累积偏移（带冷却期）。
当 `CURRENT_GEAR_MODE` 对应方向开启时生效。

### 控制流

```
main_loop 中第 2 步：
  先尝试 current_gear_override()
  ├─ 返回 1（已融合）→ 电流推荐挡位 + 温度偏移，跳过 battery_control
  └─ 返回 0（未覆盖）→ 回退到 battery_control 常规电池温度控制
```

未覆盖条件：传感器读取失败、方向开关关闭、推荐档位低于 `CURRENT_GEAR_MIN`。

### 计算流程

1. 读取带符号 `current_now`（µA），÷10000 转 0.01A 单位
2. 判断方向：负值 = 充电，正值 = 放电（用户约定）
3. 查 `CURRENT_GEAR_MODE`：第一位=充电开关，第二位=放电开关，未开则跳过
4. **EMA 平滑**（α=`CURRENT_GEAR_SMOOTH_ALPHA`，默认 0.25）
5. **推荐档位** = 平滑值(0.01A) × `CURRENT_GEAR_MULT_*` ÷ 100
   - 充电倍率默认 ×2（如 3A→6 档）
   - 放电倍率默认 ×6（如 8A→48→clamp 到 max 档）
6. 低于 `CURRENT_GEAR_MIN`（默认 6）→ 复位轨迹、回退基准模式
7. **偏移继承**：推荐挡位变化时 `curr_gear_temp_offset` 自动保留，跨过渡不丢失
8. **温度累积偏移**（带冷却期 `BATT_COOLDOWN_CYCLES`）：
   - 冷却中 → 递减、不更新偏移
   - 冷却结束 → 温度 delta = 同 `battery_control` 的偏差四区计算，累积到 `curr_gear_temp_offset`
   - 偏移量无上限（由 `level_min`/`level_max` 钳位）
9. **最终档位** = `clamp(推荐 + 温度偏移, level_min, level_max)`

### 特点
- **有冷却期**：温度偏移同方向累积冻结 `BATT_COOLDOWN_CYCLES` 周期（反方向调整不受阻挡，温度回归时立即响应）
- **无趋势豁免、无反补**（温度部分仅做纯 delta 偏移累积）
- **推荐挡位变化时偏移继承**：温度贡献的偏移在推荐挡位变化后保持，不归零

## 日志系统

- **默认日志路径**：`/cache/<二进制名>.log`（自动根据二进制文件名生成）
  - 例：`tempctrl` → `/cache/tempctrl.log`
- 可通过 `profile.conf` 的 `LOG_FILE` 覆盖
- **日志滚动**：超 `LOG_MAX`（默认 7936 字节）后自动删除最早 N 行（由 `LOG_TRIM_LINES` 配置，默认 3 行）
- **日志关闭**：`LOG_MAX=0` 完全关闭日志写入
- **格式**：`[日 时:分:秒] 日志内容`
  - 例：`[15 14:30:22] 档位3 +2`
- **调试日志**：`[DEBUG]` 前缀，按功能区分 8 个分区（传感器/紧急/电池/执行/连接/配置/主循环/PID），通过 `DEBUG_ENABLED` + 分区开关控制。开启调试时自动关闭日志体积限制

- **主要日志含义**：

| 日志 | 含义 |
|------|------|
| `挡位5（+1）` | 电池常规升降档，从 4→5 升了 1 档（正负号表示方向） |
| `35+0.6° b6x 冷40 热34° RPM2000` | PID 状态：基准温度+偏差，设备标签（b6x/b7x=当时实际连接的散热器），冷端强度，热端温度，风扇转速 |
| `过冲0.4 挡位9（+1）` | 峰值过冲抑制，温度骤变 0.4°C，从 8→9 升了 1 档 |
| `趋势豁免 7` | 温度趋势反向，本周期跳过升降档（停留在 7 档） |
| `紧急2（+1）cpu69.0 cur5.2` | 紧急等级变化，CPU 加权 ≈69.0°C，电流 ≈5.2A |
| `App 不存在，等待连接...`（末尾空行） | status 文件超时（模块停止心跳），进程失联 |
| `BLE 已断开，等待连接...`（末尾空行） | BLE 连接断开但进程仍存活 |
| `脚本启动成功` | 守护程序启动完成 |

### 布局

### 折叠逻辑（开关驱动 + 控制模式）

分组顺序（schema.js，从上到下）：[0] 日志 & 调试 → [1] 总开关 → [2] 控制模式 → [3] sysfs 路径与缩放 → [4] 自动拉起散热器 app（最底）。

- **[0] 日志 & 调试**：组头开关 = `DEBUG_ENABLED`，关闭时子面板折叠（折叠整组 body，无底部空白残留）
- **[1] 总开关**：组头开关 = `PERF_ENABLED`，子面板收纳通用参数（速率限制、冷/热端→RPM 映射、风扇转速范围、基准温度）；`PERF_ENABLED=0` → 其余性能分区折叠 + 「未生效」徽标
- **[2] 控制模式**（PID 与 Gear 两侧横滑）：组头开关 = `CTRL_MODE` **仅切换模式**（1=PID / 0=Gear），**不控制折叠**；组内 PID / Gear 两个参数面板**横向并排滑动切换**（类似顶部实时曲线/日志），CTRL_MODE=1 滑到 PID、=0 滑到 Gear，手动滑动**滚动停止后**同步更新 CTRL_MODE（不打断惯性滑动）；整组展开/折叠由 `PERF_ENABLED` 总开关驱动
- **[3] sysfs 路径与缩放**：独立大类（组头开关 = `SYSFS_ENABLED`）；=1 加载子面板路径与缩放配置，=0 折叠 + 使用代码默认路径
- **[4] 自动拉起散热器 app**：独立分组（组头开关 = `APP_LAUNCH_ENABLED`），开关**常显在组头**；**无折叠内容**（无小三角、组头点击无动作），说明区常显
- 拨总开关 → 对应分区**即时展开/折叠**（保存才落盘）；开关驱动组（日志/sysfs）折叠时**整个 body 隐藏**，不残留空 body 的 padding
- 手动展开折叠分区**不会**自动打开总开关，仅查看/编辑对应参数；**不持久**，刷新回到开关驱动状态
- **保存不重置手动状态**：改即存写配置时只重置 dirty 标记，**不清空手动展开/折叠状态**（否则总开关关着时切换模式会触发保存→清空→面板自动折叠回去）
- **总开关幂等**：拨总开关时控制模式（[2]）展开跟随总开关（开→确保展开、关→确保折叠），清除历史手动折叠/展开残留；总开关不变时手动折叠/展开仍生效

### 改即存（无保存条）

- **无保存按钮**：任何值变更（含档位增删/排序）**防抖 600ms 自动写配置**，toast「已保存」；daemon 每 5s 热重载生效
- 写入：`echo <base64> | base64 -d > profile.conf`，保留 0644/root 权限
- **注释与未改动行逐字保留**；schema 未收录的未知键原样保留（防 schema 漂移丢参数）

### 状态页数据源（C 每 1s 写数据文件）

daemon 每 1s 采集电池/CPU/散热器回传/目标制冷：**同一份采集同时写入内存缓存（`cached_batt_raw`/`cached_cpu_now`/`cooler_*`）**，5s 控制块直接读缓存、不再重复读 sysfs/状态文件（读取频率从每 5s 多次降到每秒一次，截断竞争窗口减半，采集失败保留上次成功值抗抖）；采集结果追加到 `/data/local/tmp/tempctrl_webui.data`（**滚动保留 480 行** = 曲线最大挡位秒数），WebUI 每 1s 只读这一个文件 → **exec 次数从每 5s 七次降到每秒一次**，消除卡顿（每次 exec 都会新建 root shell，是主要延迟来源）。

行格式：`epoch,电池(0.1°C),CPU(0.1°C),热端(0.1°C),冷端(0.1°C),实际转速,实际制冷,目标制冷`（未就绪为 -1）

### 曲线

- 每秒读数据文件更新一次；窗口时长按钮 **60/90/120/180/240/360/480s**，默认 **240s**（存 localStorage），只显示最近 N 行
- **双纵轴**：左轴 **℃/百rpm**（温度 ℃ 一位小数 + 风扇转速 ÷100 共轴，标题靠左绘制可向右突出到曲线区内，不挤压曲线空间），右轴 **cold**（制冷强度独立刻度）
- 系列开关（电池/制冷/风扇/冷端/热端/CPU℃），**默认除 CPU℃ 外全显示**；CPU℃ 置于系列最后（实时数值列顺序由实时行独立维护，不受系列顺序影响）
- 实时数值列：电池 · CPU · 制冷 · 风扇 · 冷端 · 热端（不含目标制冷）

### 日志页

- 读 `LOG_FILE`（默认 `/cache/tempctrl.log`），`tail -c 400KB`
- 默认吸附底部自动跟随，上滑暂停；5s 刷新（增量缓存，不常变内容不重拉）；关键词过滤
- 时间戳 / `[DEBUG]` / `[PID]` / 错误着色

### 桥接

- 探测注入全局并归一化：`window.kernelsu.console.exec` / `window.kernelsu.exec` / `window.ksu.exec` / `window.mMRL.console.exec`
- **KSU 管理器真实形态**：`window.ksu.exec(cmd)` 同步（实测只返回最后一行）→ 自动切到 `exec(cmd, 全局函数名字符串)` 异步回调拿完整输出；传 JS 函数对象会被强转成字符串而永不回调

## 启动流程

1. 设定默认日志路径（根据二进制文件名）
2. 加载配置（`--config` 参数 > 自动检测 > 全部默认值。`PERF_ENABLED=0` 时仅 `DEBUG_ENABLED=1` 的调试子项生效，其余全部使用代码默认值；`PERF_ENABLED=1` 正常加载全部）
3. 创建 status 文件，读取存档制冷强度（无存档回退默认挡位 LEVEL_INIT=5：Gear 模式查最近挡位，PID 模式直接对齐初始制冷值）
4. 等待模块就绪 + BLE 已连（status 文件读到 `BLE=1`）；等待期间无散热器 app 存活时自动拉起上次使用的 app（`APP_LAUNCH_ENABLED`，冷却 60s）
5. 进入工作模式后每 5 秒：连接检测 → `main_loop`（纯计算）→ 速率限制执行
   - 每轮循环开头通过双重检查检测 App 存活（status 文件 mtime + BLE=1）
   - 断联时实际值保持不动（丢弃未执行变化量），进入等待复活子循环
   - 重连时三个实际值（RPM/制冷/温度）都调到匹配挡位，不下发，由 `rate_limited_execute` 按正常速率逐步过渡；同时重置电池温度跟踪，重连后首次温度读取不计入任何判断，直接进入冷却期

## 实测说明

### 智能温控模式的风扇转速限制非强制生效

经实测，**智能温控模式（mode=0）的风扇转速配置疑似并非强制生效**，经常会突破设定的上限很多，尤其是刚切换过去的时候。这会导致噪音突然变大，体验非常差。

**原因推测**：`setRunMode` 的 `windLevel` 参数在散热器固件中被解释为"建议上限"而非"硬上限"。散热器内部有独立的 PID 或逻辑控制算法，在刚切换模式或温差较大时，会以更高转速运行来快速达到目标温度，忽略应用层设定的风扇上限。

**解决方案**：全部改用**固定功率模式（mode=1）**，直接指定风扇转速和制冷片强度。v2.1 的默认档位表已全部采用固定功率模式，避免了此问题。如果要恢复某档为智能温控，可通过 `profile.conf` 的 `GEAR_B6X_N`（B6X）/ `GEAR_B7X_N`（B7X）自定义覆盖（设模式=0）。

## 注意事项

- **CPU 温度扫描范围** 通过 `CPU_ZONE_MIN/MAX` 配置（默认 0~99 全扫），K60 机型推荐 30~40 
- **温度传感器路径** `thermal_zone[N]` 是 Linux 通用接口，不同 SoC 的 zone 编号不同。全自动扫描无需手动配置，但如果扫描范围过大（0~99）首次可能稍慢（约 1 秒），可通过 `CPU_ZONE_MIN/MAX` 缩小范围
- **去重逻辑**：`apply_gear()` / `apply_gear_direct()` 缓存上次参数，连续相同不下发，但 App 复活时强制清除缓存重发
- **`patch_tls.py`**：NDK 静态编译后需要执行，修复 PT_TLS 对齐；无 TLS 段时返回非零，需要 `|| echo "skipped"` 容忍
- **`#include <stdarg.h>`**：`write_log()` 用了 `va_list`，NDK clang 下不是隐式包含的
- **KernelSU noexec**：KernelSU 模块目录挂载了 `noexec`，`service.sh` 会将二进制复制到 `/data/local/tmp/` 执行
