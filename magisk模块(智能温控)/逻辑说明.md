## 配置文件系统 (profile.conf)

tempctrl 支持运行时配置文件，大部分关键阈值和参数均可外部修改，无需重新编译。

### 配置路径自动检测

1. **`--config` 参数**（最高优先级）：
   ```shell
   tempctrl --config /自定义路径/profile.conf
   ```
2. **自动检测**：通过 `/proc/self/exe` 获取自身路径，在同目录下查找
3. **默认值**：全部使用代码内默认值

### PERF_ENABLED / DEBUG_ENABLED / SYSFS_ENABLED 开关

配置层级：

```
PERF_ENABLED（性能总开关，默认=1）
  ├── =0：不加载性能参数（PID、速率限制、热端过温削减等），全部使用代码默认值
  └── =1：正常加载所有性能参数

DEBUG_ENABLED（调试总开关，独立于 PERF_ENABLED，默认=0）
  ├── =0：分区调试日志关闭
  └── =1：各 DEBUG_* 分区开关生效

SYSFS_ENABLED（sysfs 路径与缩放，独立于 PERF_ENABLED，默认=0）
  ├── =0：不加载自定义 sysfs/日志路径，使用代码默认路径
  └── =1：加载 profile.conf 中的 BATT_*/CPU_*/LOG_* 路径与缩放配置
```

这对调试很有用——**设置 `PERF_ENABLED=0` 但 `DEBUG_ENABLED=1` 可关闭性能控制并保留调试输出**；sysfs 路径可独立于性能开关加载（`SYSFS_ENABLED=1`）。

### ⚠️ 常见坑

| 坑 | 说明 |
|----|------|
| **Termux 编译不可用** | Termux 的 `clang -static` 链接的是 Termux 的 libc，非 Android libc。编译出的二进制在真机上 PT_TLS 对齐错误，必须用 NDK 编译。**开发阶段在 Termux 编出来可以看语法错误，但不要拿去真机跑** |
| **`--config` 路径** | service.sh 使用 `--config "$MODDIR/profile.conf"`直接从模块目录读取，不再复制到 `/data/local/tmp/` |

### 配置格式

```
# 注释以 # 开头
KEY=VALUE

# 例：
BATT_BASELINE=350
PID_GAIN=300 20 240
```

不认识的 key 静默跳过；每个值有范围保护（`clamp`），非法值不会导致进程崩溃。

### 热重载

每轮 `main_loop()`（5 秒间隔）开头 `stat()` 检查配置文件的修改时间（mtime），变了就自动重读所有参数并记日志。**修改配置无需重启 daemon**。

## 温度读取

- **电池温度**：`/sys/class/power_supply/battery/temp`
  - 原生 0.1°C 精度，如 350 = 35.0°C

- **CPU 温度**：`/sys/class/thermal/thermal_zone[N]/temp`
  - 原始值 m°C，÷100 转 0.1°C，如 75321 → 753 (=75.3°C)
  - 首次调用时在 `CPU_ZONE_MIN~CPU_ZONE_MAX` 范围内扫描，记录能读到有效值的 zone
  - 后续只扫描已记录的 zone，取最高值
  - 一阶低通滤波平滑（系数由 `CPU_FILTER_ALPHA` 配置，默认 α=0.25）

### 温度变化检测

- **值比较 + mtime 双信号**：以值比较为主（部分内核 sysfs 温度文件 mtime 更新不可靠，会导致温度实际在变却被判"未更新"而大量跳过）；**同时检测文件 mtime**——mtime 更新时（即使值相同）也视为温度数据刷新，触发 PID 重算以保持积分累积与 dt 新鲜。mtime 恒不变的内核自动退化为纯值比较。
- **1s 窗口累积**：5s 控制周期的跳过判定不看"当前采样值 vs 上次控制值"，而是看**自上次控制以来 1s 层是否检测到过值/mtime 变化**（累积标志 `batt_changed_since_ctrl`，控制周期开始时快照 `batt_window_changed` 并清零）。温度在窗口内变过又回到原位也不会漏判。
- **两条跳过（pid_cycle 重算判定）**：仅**温度窗口变化** 或 **CPU 补偿变化**（`total_comp_10 != pid_last_comp_10`）才触发重算；两者均未变则本轮冻结 `acc`/`kdp`/`target`/`last_ch` 等控制状态。两条跳过：
  1. **温度未变（仅补偿变化触发）** → `kdp` 沿用上次值（`batt_window_changed=0` 时 `pid_kdp` 不更新），避免补偿突变带动 KDP 跳变；
  2. **温度未变且上次 `|ch| ≤ PID_CH_THRESHOLD`** → 整轮冻结（`acc`/`kdp`/`target`/`last_ch` 一律不动），仅推进补偿书签 `pid_last_comp_10`（防补偿反复变化反复触发导致死锁）。
- **电池温度输入滤波（改动2：加回）**：电池温度进 PID `ch` 前先经 EMA 滤波（`pid_batt_filtered`），**仅温度更新时（值/mtime 变化，即 `batt_window_changed`）才滤波并输出**；动态 α = `0.2 + 0.05 × 间隔周期数`（间隔 = 距上次温度更新的 5s 控制周期，钳 0~16 → α 0.2~1.0，时间越长新值权重越高）。**停机（`batt_window_changed=0`）且滤波未收敛**（`pid_batt_filtered != batt_raw`）时，首个周期**优先恢复原始值强制重算**（改动2优先于此节第②条整轮冻结），`pid_batt_filtered = batt_raw`（= 未更新的电池温度），进 PID 用原始电池 + 新 CPU 滤波补偿 → "半新 ch"；snap 一次后 `pid_batt_filtered==batt_raw` 滤波态消失，回正常冻结。`pid_batt_filtered` 在 `pid_reset_core`（切模式/重连）重置为 -1 直取初值。

## 控制下发模式

本实现**仅保留 PID 连续无级调节**。Gear 档位表（`gear_cycle` / `battery_control` / `gear_from_current` /
反补 / 趋势豁免 / 紧急干预 等）与旧 `CTRL_MODE` 切换开关已随 Gear 一并删除，下发统一走 `apply_gear_direct()`。

> **制冷上限口径**：194 = SDK/硬件上限（散热器固件最大制冷）；190 = 温控默认下发上限（`PID_COLD` 可调）。

控制指令通过 `am broadcast` 发送（Action 由 `active_device` 决定），广播 Action、完整 7 参数格式与示例**协议详见 [lsp模块 README](../lsp模块(apk修复+温控接口)/README.md)**（唯一规范处）。

- **智能模式 (mode=0)**：设目标温度和风扇上限，散热器自行调节制冷
- **固定功率 (mode=1)**：直接指定风扇转速和制冷片强度（本实现 PID 下发使用 mode=1）

风扇转速不直接由 PID 输出决定，而是每周期由 `compute_fan_target()` 基于**限速后的实际制冷强度**（`actual_cold`）
+ 散热器热端温度独立计算（冷端指数映射 + 热端线性映射自加权合并），与 PID 输出解耦——见「制冷→RPM 映射引擎」节。

## PID 控制模式

本实现**仅 PID 单模式**（Gear 已删除），采用**单累积器**结构：`OUTPUT = clamp(acc + kdp, 0, 1)`。
`acc` 为积分累积（`pid_ki`），`kdp` 为融合 P+D 项（`pid_kdp`，无记忆）。`error` 只取纯电池误差；
CPU 补偿与速度项同地位进入 `ch`，再进入积分与 KDP。

### 控制流

```
main_loop()（纯计算，不下发）:
  0. 温度窗口快照：batt_window_changed = batt_changed_since_ctrl；清零使开启新窗口
  1. 热重载（共享）：stat() 检测 profile.conf mtime，变了重读并 update_active_limits()
  2. update_hot_derate()：热端过温 → 制冷上限削减（本周期即生效）
  3. update_active_cold_range()：当前有效制冷范围（供下发/去重/映射统一使用）
  4. pid_cycle()：CPU 补偿 → 两条跳过判定 → pid_compute() → 映射制冷

pid_cycle()（每 5s）:
  1. cpu 温度读入 → update_cpu_filtered()（CPU_FILTER_ALPHA EMA 滤波）
  2. cpu_comp = cpu_comp_now(batt_raw)：CPU 补偿（EMA 平滑，门控滞回，始终生效）
  3. 重算判定：batt_window_changed || total_comp_10 != pid_last_comp_10
     ── 两条跳过（见「温度变化检测」节）：①温度未变→kdp 沿用 ②|last_ch|≤阈值→整轮冻结
  4. dt = (now − pid_last_change_time)/5，钳位 0.6~6（1 = 5s）
  5. pid_compute(batt_raw, dt, cpu_comp, batt_window_changed) → 归一化输出 0~1
  6. 映射：pid_align_cold = clamp(pid_cold_min + (int)(out×range), pid_cold_min, active_cold_eff_max)

rate_limited_execute()（执行段）:
  → rate_limit_cold(pid_align_cold)：限速制冷（actual_cold；每周期最大变化量限制，取代原 PID_OUT_FILTER 的输出平滑）
  → compute_fan_target()：独立风扇目标（冷端指数 + 热端线性加权，不跟 PID 输出）
  → rate_limit_fan：限速风扇
  → apply_gear_direct(1, 5, send_rpm, actual_cold, 0)：纯下发（去重/日志/广播）
```

### 单累积器公式

```
error   = (batt_raw − BATT_BASELINE) / 10             # 纯电池，单位 °C（batt_raw 为 0.1°C）
v       = (error − pid_last_error) / dt                # 速度（°C/周期）；首算无常值历史 v=0
sc      = PID_GAIN 速度倍率 / 1000
ch      = error + v×sc + cpu_comp                      # 用于积分
ch_kdp  = error + v×sc×0.33 + cpu_comp                 # 用于 KDP（速度按 0.33 衰减）

raw_target = clamp(error×PID_TARGET 目标系数/1000, ±0.5)   # 动态目标（±0.5°C 界）
pid_target_f += α_dir × (raw_target − pid_target_f)   # 方向性 EMA：PID_TARGET_DIR 开关=1 时，远离基线用"远离alpha"/回归基线用"回归alpha"；开关=0 时 α=PID_TARGET 平滑%/100

pid_ki += PID_GAIN 积分增益/1000 × (ch − pid_target_f)   # acc 累积，不乘 dt
budget  = max(0, 1 − pid_kdp)                          # 预算钳制（防 acc+kdp 超 1 被末端硬截断）
pid_ki  = clamp(pid_ki, 0, budget)

pid_kdp = PID_GAIN KDP系数/1000 × ch_kdp               # 无记忆；温度未变（batt_window_changed=0）沿用上次
out     = clamp(pid_ki + pid_kdp, 0, 1)
```

- **error 纯电池**：不含 CPU 补偿；CPU 补偿（`cpu_comp`）与速度项同地位进 `ch`（用于积分）。KDP 用的 `ch_kdp` 中速度项按 0.33 衰减（≈1/3），CPU 补偿不衰减。
- **速度 v**：以 `dt`（5s 周期数）归一化，只乘 `PID_GAIN` 速度倍率系数，不乘 dt。
- **动态目标 `pid_target_f`**：`raw_target` 随时间 EMA 平滑，使积分逼近"误差×目标系数"包络，防静态过冲。
- **KDP 无记忆靠预算**：`pid_kdp` 每周期重算（温度未变时沿用），`acc` 钳到 `1−kdp`，避免 `acc+kdp` 超 1 被末端硬截断（抗 windup）。
- **两条跳过**：见「温度变化检测」节；跳过时控制状态（`acc`/`kdp`/`target`/`last_ch`）不动，仅推进补偿书签。

### PID 参数配置

当前 PID 键：`PID_GAIN` / `PID_TARGET` / `PID_TARGET_DIR` / `PID_CH_THRESHOLD` / `PID_COLD` / `PID_CPU_COMP` / `PID_SPD_RECALL`（多值/单值混合，走 `parse_pid_cfg` 分段）；`PID_CH_THRESHOLD` 单值走 `INT_CFG_KEYS` 表驱动。`PID_OUT_FILTER`（输出端自适应滤波）已删除——输出平滑改由 `RATE_LIMIT_COLD` 每周期限速承担。全部通过配置热重载，无需重启。

### CPU 补偿（PID_CPU_COMP）

`comp = clamp(cpu_filtered_temp − batt_raw − 偏移, 0) ÷ divisor`，按补偿专属滤波系数 EMA 平滑（独立于
`CPU_FILTER_ALPHA`，首次上次值用 0 从 0 爬升）。门控滞回：`raw>0` 进入补偿，条件消失后平滑值继续向 0
收敛归零才退出（不瞬间跳变）。始终生效，与 PID 单累积器一同作用于 `ch`。

### 制冷→RPM 映射引擎

PID 模式使用（本实现仅 PID）：

| 函数 | 映射方式 | 用途 |
|------|---------|------|
| `rpm_from_hot_end()` | EMA 平滑 + 双向滞回线性映射 | 热端温度 → RPM（需求侧：越高越迫切），输入先经 `RPM_SMOOTH_ALPHA` EMA 平滑（滞回基于平滑值），降温滞回 +1°C，升温不低于上次 RPM；**热端 ≤0（异常/未就绪）时保持上次输出** |
| `rpm_from_cold_exp()` | `cold^exp` 指数 + EMA 平滑 | 冷强度 → RPM（供给侧：越强调速越高），输出经 `RPM_SMOOTH_ALPHA` EMA 平滑 |
| `compute_fan_target()` | `rpm_from_cold_exp(actual_cold)` + 热端线性映射自加权合并（自加权逻辑已内联于本函数） | 独立风扇目标：PID 每周期下发前统一计算，与 PID 输出解耦（禁降钉死时风扇保持高转速，热端过温直接拉满） |

### 热端过温制冷上限削减

散热器热端过温时降低制冷强度上限（PID 模式专用，`main_loop` 每 5s 周期入口先执行），保护散热器硬件：

| 场景 | 行为 |
|------|------|
| 热端 > 阈值 | 每次削减上限 `(热端-阈值)×倍率`，削减后冷却周期内不再削减 |
| 热端 ≤ 阈值 | 每次恢复 `倍率`（固定值），恢复后冷却周期内不再恢复 |
| 削减/恢复冷却 | 独立计数，互不影响 |

- **削减基准上限**：`active_pid_cold_max`（`PID_COLD` 上限，B6X/B7X 取对应值），由 `update_active_cold_range()` 计算。
- **生效上限** = 基准上限 - `hot_derate`，下限不低于冷端最小强度。
- **下发边界强制生效（硬钳制）**：除压低目标上限外，还在每次下发前对制冷强度做硬钳制（`min(期望, 生效上限)`），直接绕过 `RATE_LIMIT_COLD` 的禁降限速——电池 ≥37.5°C 禁降期间也能把已升高的制冷强度一步压回上限内。钳制不改变 `actual_cold`，仅作用于本次下发值。
- 削减量按原始读数直算（不加滤波），一次 55°C 读数可削减 50，恢复按每 `冷却+1` 周期 +5 逐级回满（约 200s）。
- 热端数据无效（<0，断联/未就绪）时保持当前削减量不动。
- 削减仅下调制冷强度上限，不直接干预 CPU 档位/CU 风扇（旧"CPU 紧急干预强制升档"已随 Gear 删除）。
- **已知边界**：热端在阈值附近来回时（≤45 / ≥46 交替）可能"削减→恢复→削减"每 2 周期交替，属规格固有行为；真机热端温变慢，实际振荡概率低。若需消除可加滞回带。
- **风扇联动（刻意不同步）**：边界钳制**故意不修改** `actual_cold`，风扇目标仍由 `actual_cold` 推算保持高转速——过温时只降制冷片强度、不拉低风扇，避免"火上浇油"；散热器实际制冷以回传值为准。钳制生效瞬间制冷强度一步跳至上限内，恢复时从被压值按正常升速爬回。

### EMA 方向取整

所有整数 EMA 平滑（CPU 温度、热端温度→RPM、冷端 RPM）使用 `EMA_DIR` 宏替代标准 `EMA`。
标准整数 EMA 因截断存在渐进问题（如 `α=33%` 时 `old=449 + raw=450` 永远到不了 450），
`EMA_DIR` 基于原始值方向做取整：原始值升高→向上取整，原始值降低→自然截断（按需方向），
确保滤波值能实际到达目标温度。

## 主循环逻辑

**决策执行分离 + 限速统一下沉**：`main_loop()` 纯计算不下发，`rate_limited_execute()` 分发。
执行段：`rate_limit_cold()` 限速制冷 → `compute_fan_target()` 独立计算风扇目标（基于限速后实际制冷，
不跟 PID 输出）→ `rate_limit_fan()` 限速风扇 → `apply_gear_direct()` 纯下发（去重/日志/广播）。
计算层（`pid_cycle`）只传目标值，不限速。风扇目标基于限速后制冷（而非目标制冷），禁降钉死时风扇保持高转速。

```
 ┌─ 主循环（1 秒节拍；控制每 5s）───────────────────────────────┐
 │  每 1s：write_webui_data() 采集电池/CPU/散热器 → 追加+读删写（每60行压缩）│
 │  每 5s（时间判定）执行下方控制节拍：                        │
 │                                                          │
 │  1. maybe_rescan_cpu_zones()：CPU zone 首扫建名单/周期重扫   │
 │  2. 双设备仲裁 select_active_device()：                    │
 │     ├─ 读双 status → BLE 连接状态 / 连接者（BLE_OWNER_LAST）│
 │     ├─ arbitrate_apps()（ARBITRATE_INTERVAL 节流）          │
 │     ├─ 设备切换/断联 → reconnect_align() 或 continue        │
 │     └─ is_app_alive() + BLE 存活检测 → 断联则 continue      │
 │                                                          │
 │  3. main_loop() 纯计算                                    │
 │     窗口快照 → 热重载 → update_hot_derate() →              │
 │     update_active_cold_range() → pid_cycle()               │
 │                                                          │
 |  4. ★ 速率限制执行                                        │
 │     rate_limited_execute()：                            │
 │     ├─ 风扇转速：升速 = RATE_LIMIT_FAN_UP + d×MULT/10       │
 │     │           降速 = RATE_LIMIT_FAN_DOWN                 │
 │     ├─ 制冷强度：升速/降速 = RATE_LIMIT_COLD ± dev×MULT/10  │
 │     │             （dev 有符号，负值禁方向）                 │
 │     └─ watchdog_check()：本次实际下发制冷变化后判定          │
 │                                                          │
 │  5. sleep(1)                                             │
 └───────────────────────────────────────────────────────────┘
```

### 关键说明

- **风扇目标独立于 PID 输出**：风扇转速不跟 PID 输出，每周期由 `compute_fan_target()` 基于限速后 `actual_cold`
  （冷端指数映射）+ 热端温度（线性映射）自加权合并计算；热端过温时只降制冷强度、不拉低风扇（避免"火上浇油"）。
- **三参数独立速率限制**（含动态温差修正 + 0.1°C 精度）：风扇升速（`RATE_LIMIT_FAN_UP + d × RATE_LIMIT_FAN_MULT / 10`，
  d=有符号 0.1°C 温差）和降速（`RATE_LIMIT_FAN_DOWN` 固定值）独立配置；制冷片强度升降速独立且有符号
  （升速 = `RATE_LIMIT_COLD + d × RATE_LIMIT_COLD_MULT / 10`，降速 = `RATE_LIMIT_COLD − d × RATE_LIMIT_COLD_MULT / 10`，
  d = 有符号温差(电池温度 − BATT_BASELINE)）。负值表示禁止该方向变化（电池 ≥37.5°C 禁止降制冷强度、≤32.5°C 禁止升制冷强度）。
  使用 `d × mult / 10` 保留 0.1°C 精度。溢出自然累积下周期，目标变化时从当前实际值重新计算。
- **去重 + 最小变化幅度**：`apply_gear_direct()` 以散热器实际回传为准判定是否下发（`should_skip_dispatch`）：
  要播发值与实际回传一致视为已到位、跳过下发；回传异常退化用 `last_*` 缓存对比。另含最小变化幅度
  （目标与制冷实际 `|差值|` ≤ `RATE_LIMIT_COLD` 第三值、距极值 ≥ 死区×2 时上升下降都不下发）。
- **短断联保留状态（`RECONNECT_KEEP_CYCLES`）**：断联时长 < `RECONNECT_KEEP_CYCLES`×5 秒（默认 3×5=15s）时，
  **跳过 `pid_reset_core()`**——`acc`/`kdp`/`target`/误差等 PID 学习状态保留，输出连续不跳变；仅仍以散热器回传实际值
  对齐 `actual_cold`/`actual_rpm`。长断联或配置=0 时完整重置（防陈旧状态误入）。该规则按断联时长统一生效，
  跨设备切换（B6X→B7X）若未记录断联起点也走保留分支（电池共享、状态连续合理）。
- **锁死自动重启（APP_WATCHDOG）**：仅在本次实际下发制冷变化后判定——实际制冷停滞（=上周期实际）且未达目标
  （≠上周期下发）连续 N 次时 kill 散热器 app 并重新拉起（散热器重启无效，需重建 App 进程恢复连接栈）；
  仅 BLE 已连、实际回传可用、watchdog 开启时启用；kill 后冷却 300s 防风暴。

### main_loop() 内部详细逻辑（每 5s 控制节拍执行一次）

> **结构**：`main_loop` 为骨架，直接分发到 `pid_cycle()`（本实现仅 PID，无 CTRL_MODE / gear_cycle 分支）。
> 配置解析为表驱动 + 分段函数（`INT_CFG_KEYS` 表 + `parse_debug/sysfs/pid/common`），与单函数行为等价。

0. **温度窗口快照**：`batt_window_changed = batt_changed_since_ctrl`；清零开启新窗口（供 pid_cycle 跳过判定）
1. **检查配置更新** → `stat()` 检测 `profile.conf` 修改时间，变了就热重载（`update_active_limits()`）
2. **热端过温削减** → `update_hot_derate()`：按散热器热端温度更新制冷上限削减量
3. **有效制冷范围** → `update_active_cold_range()`：`active_cold_eff_min/max`（含热端过温削减）
4. **PID 周期** → `pid_cycle()`：CPU 补偿 → 两条跳过判定 → `pid_compute()` → 映射 `pid_align_cold`

（旧 Gear 电池控制 / 反补 / 趋势豁免 / 紧急干预 / 电流-挡位映射等步骤已随 Gear 删除。）

## 进程检测机制

使用 **双重检查**：状态文件 mtime 心跳检查 + BLE 连接状态。B6X 文件 BLE=0/1/2（0=未连接，1=老 app 连接，2=新 app 连接），B7X 文件 BLE=0/6/7 设备型号编码。只要有一个出问题就算断联。

> **STATUS_TIMEOUT**：状态文件心跳超时判死秒数，**硬编码 3**（不再可配置，故不列入参数表）——LSP 每 1s 写一次，超 3s 判死。

```
 启动 → 创建 status 文件（0666，所有用户可写）
      → 脚本启动成功 → 延迟 30s 再开始（等待系统/蓝牙就绪，避开开机初期拉起 app 闪烁）
      → 等待 status 文件出现 BLE≠0（模块就绪 + BLE 已连；B6X 文件 BLE=1/2，B7X 文件 BLE=6/7）
 
 工作模式中，每 5 秒：
   连接检测 → 双 app 存活仲裁 → main_loop（纯计算）→ 速率限制执行
   
   1. 读 status 文件内容 → BLE（B6X 文件：0=未连接/1=老 app 连/2=新 app 连；B7X 文件：0/6/7 型号）
   
   2. 双重检查存活检测（任一不满足即算断联）：
      ├─ stat(status 文件).mtime 距现在 ≤ 5秒？      → 模块在写心跳?
      └─ status 文件内容 BLE≠0?                       → BLE 已连接?
      
      ├─ 全部 OK → 存活
      └─ 任一失败  → 模块/BLE 失联
                          ↓
                      等待复活子循环（每 5 秒检测，同时查 BLE）
                          ↓
                      模块+BLE 都重新就绪 → 实际制冷/转速以散热器回传为准 → 按正常限速过渡

 模块侧（LSPosed）：
   ────────────────────────────────
   onDeviceConnected / disconnect 钩子 → 更新 bleConnected + connectedModel
   每 1 秒线程（后台 BLE 重连保持 5s 节奏）+ 连接/断连事件：FileOutputStream 写 "BLE=0/1/2\n"（B6X）或 "BLE=0/6/7\n"（B7X）+ CONNECTED_AT + BLE_OWNER_LAST=<值> <时间> 到 status 文件
   （BLE_OWNER_LAST 连接时写入、断连保留，标识"上次连接者"，供 app 存活仲裁）
   （直接 Java 文件 I/O，不走 su，无 KSU 命名空间问题）
```

> 字段级协议（status 文件字段名/含义/单位/编码）详见 [lsp模块 README](../lsp模块(apk修复+温控接口)/README.md)（唯一规范处）。制冷上限口径见 `PID_COLD`（`active_pid_cold_max`）：194=SDK/硬件上限，190=温控默认下发上限（B7X 由第三值指定）。

### 三方 app 存活仲裁

三个 app 最多一个后台存活：老 B6X app（`com.flydigi.waspwing.experimental`）+ 新 B6X app（`com.flydigi.waspwing.experimentanliuliu`）+ farsef（B7X 游戏厅）。由 `arbitrate_apps()` 每 5 秒在读取双 status 后调用。

farsef 只在**最近连接的是 B6X 散热器**（`BLE_OWNER_LAST`=6）时参与仲裁——它控制同一台 B6X 散热器才与两个 B6X app 竞争；连的是 B7X 设备（=7）时不参与（控制另一台设备，不应被杀）。

```
存活参与者 = {老B6X, 新B6X} ∪（farsef 存活 && BLE_OWNER_LAST==6 ? {farsef} : ∅）
参与者 < 2 → 不仲裁
保留优先级：
  1. BLE_OWNER_LAST 值代表的 app（标识"上次连接者"，连接时写入、断连保留）：
     =1 → 保留老 B6X app
     =2 → 保留新 B6X app
     =6 → 候选保留 farsef
  2. 无 BLE_OWNER_LAST → 回退当前连接者 BLE 字段（=1 老 / =2 新）
  3. 兜底保留老 app

保留者涉及 farsef 时：比较 farsef 的 BLE_OWNER_LAST 时间与另一方（B6X app）的
CONNECTED_AT，保留时间更晚（最近使用）的那个。

被淘汰者非前台时 am force-stop（dumpsys window mCurrentFocus 优先判断，
被淘汰者在前台则等下一周期再试）
```

**与温控仲裁的关系**：`arbitrate_apps()` 只管 app 存活，`select_active_device()` 只管散热器控制权。两个 B6X app 共写同一 B6X status 文件；`BLE_OWNER_LAST` 由 LSP 连接事件写入、断连保留，标识"上次连接者"；farsef 连 B6X 设备时写 B7X status 文件（BLE=6 + `BLE_OWNER_LAST`=6）。都未连接时 arbitrate 保留上次连接者（或老 app）在后台待命（LSP 后台自动重连会恢复连接）。

**自动拉起**：`arbitrate_apps()` 扩展——当**没有任何散热器 app 存活**时自动拉起上次使用的 app（`launch_last_app()`，复用 `BLE_OWNER_LAST` 选择逻辑：2→新 B6X app、6/7→farsef、其余/无记录→老 B6X app；目标 B6X app 未安装时回退另一个）。拉起用 `am start`（**显式 launcher 组件 `-n <包名>/<Activity>`**；这些 app 的 launcher 未导出/非标准 filter，隐式 `-p` 解析不到）+ `b6x_auto_launch` 标志，LSP 读到标志后在**离开引导页、进入设置界面时**（第一个非引导页 Activity 的 `onResume`）执行 `moveTaskToBack` 后台化（几乎无感；引导页 onResume 不切，等自动跳转到设置界面后再切，避免"没进界面就退后台"；读取后清除标志避免用户手动打开又被切走；附 2s 兜底超时，自动进入设置失败时仍退后台）。按 `APP_LAUNCH_COOLDOWN` 冷却；由 `APP_LAUNCH_ENABLED` 开关控制（默认 0 关闭，刷入时音量±选择）。调用时机：启动等待设备循环 + 主循环每 5s 节拍 + **断联（连接丢失）时**（存活检测失败路径；无 app 存活时真正拉起，app 存活时记 debug「已在运行」；开关关闭也会记 debug「开关关闭，跳过」，便于排查）。进程存活检测**直读 `/proc/<pid>/cmdline` 精确比对包名**（整参=包名或 `--nice-name=<包名>`），不经 shell——避免 `system("pgrep -f <包名>")` 时临时 shell 自身命令行含包名造成的自匹配误判（曾导致 app 已死仍被判"已在运行"、拉起被跳过）。

**LSP 侧配合**：连接成功时把散热器 MAC 持久化到 `/data/local/tmp/tempctrl_last_dev`。冷启动打开 app 时，LSP 检测到引导页（MainActivity）即**自动进入参数设置界面**（等效自动点「开始设置」，`autoStartSetup()`），由 B6ExperimentalActivity.onResume 的 `tryConnect()` 主动发起连接——不再需要手动点「开始设置」。已进入过设置界面（`enteredSetup`）或已连接时跳过；后台重连线程仍保留（断开后每 5s 兜底）；`am start` 携带 `b6x_auto_launch=1` 时 LSP 将 Activity 切回后台。

## 日志系统

- **默认日志路径**：`/cache/<二进制名>.log`（自动根据二进制文件名生成）
  - 例：`tempctrl` → `/cache/tempctrl.log`
- 可通过 `profile.conf` 的 `LOG_FILE` 覆盖
- **日志滚动**：超 `LOG_MAX`（默认 7936 字节）后 `ftruncate` 截断保留尾部（从完整行首起），零读零写只改文件 size，不依赖 `LOG_TRIM_LINES`（已删除）
- **日志关闭**：`LOG_MAX=0` 完全关闭日志写入
- **格式**：`[日 时:分:秒] [PID] 日志内容`（PID 专属日志统一带 `[PID]` 前缀）
  - 例：`[15 14:30:22] [PID] e=-0.35 v=0.12 ch=0.48 tgt=0.20 ki=0.30 kdp=0.15 out=0.45 win=1`
- **调试日志**：`[DEBUG]` 前缀，按功能区分 7 个分区（传感器/执行/连接/配置/主循环/PID/自动拉起；原始"档位"分区已随 Gear 删除），通过 `DEBUG_ENABLED` + 分区开关控制。开启调试时自动关闭日志体积限制

- **主要日志含义**：

| 日志 | 含义 |
|------|------|
| `[PID] e=-0.35 v=0.12 ch=0.48 tgt=0.20 ki=0.30 kdp=0.15 out=0.45 win=1` | PID 计算输出：偏差 e、速度项 v、综合量 ch、动态目标 tgt、积分 ki、融合项 kdp、最终输出 out、温度窗口标志 win |
| `[PID] epoch=123 Tbatt=350+comp+0.7(cpu)=Tinp357 Ttgt=353 Thot=450 dt=1.0周期` | PID 周期状态：原始电池温度 + CPU 补偿 → PID 输入温度、动态目标、热端温度、距上次重算的周期数 dt |
| `PID 跳过重算（温度/补偿未变）` | （debug）温度窗口未变且 CPU 补偿未变，本轮复用上次 PID 状态 |
| `PID 整轮冻结（[last_ch]=0.30 ≤阈值1.0）` | （debug）触发跳过②：温度未变且上次 [ch] 低于稳态阈值，整轮冻结防抖 |
| `过热钳制冷 180→120（上限削减 40）` | 热端过温，制冷强度被钳到上限 - 削减量 |
| `App 不存在，等待连接...`（末尾空行） | status 文件超时（模块停止心跳），进程失联 |
| `BLE 已断开，等待连接...`（末尾空行） | BLE 连接断开但进程仍存活 |
| `脚本启动成功` | 守护程序启动完成；之后延迟 30s 才开始工作（等待系统/蓝牙就绪） |

分组顺序（schema.js，从上到下）：[0] 日志 & 调试 → [1] 性能参数 → [2] sysfs 路径与缩放 → [3] 自动拉起散热器 app → [4] WebUI 界面（最底）。

- **[1] 性能参数**（总开关 + PID，合并原 [1] 总开关 与 [2] PID 控制）：组头开关 = `PERF_ENABLED`，子面板收纳通用参数（速率限制、冷/热端→RPM 映射、风扇转速范围、基准温度）+ PID 参数（`PID_GAIN` / `PID_TARGET` / `PID_TARGET_DIR` / `PID_CH_THRESHOLD` / `PID_CPU_COMP` / `PID_SPD_RECALL` / `PID_COLD`）；=0 时标题置灰 + 「未生效」徽标

### 改即存（无保存条）

- **无保存按钮**：任何值变更**防抖 600ms 自动写配置**，toast「已保存」；daemon 每 5s 热重载生效
- 写入：`echo <base64> | base64 -d > profile.conf`，保留 0644/root 权限
- **注释与未改动行逐字保留**；schema 未收录的未知键原样保留（防 schema 漂移丢参数）

### 状态页数据源（C 每 1s 写数据文件）

daemon 每 1s 采集电池/CPU/散热器回传/目标制冷：**同一份采集同时写入内存缓存（`cached_batt_raw`/`cached_cpu_now`/`cooler_*`）**，5s 控制块直接读缓存、不再重复读 sysfs/状态文件（读取频率从每 5s 多次降到每秒一次，截断竞争窗口减半，采集失败保留上次成功值抗抖）；采集结果追加到 `/data/local/tmp/tempctrl_webui.data`（**滚动保留 720 行** = 曲线最大窗口秒数 720s），WebUI 每 1s 只读这一个文件 → **exec 次数从每 5s 七次降到每秒一次**，消除卡顿（每次 exec 都会新建 root shell，是主要延迟来源）。

行格式：`epoch,电池(0.1°C),CPU(0.1°C),热端(0.1°C),冷端(0.1°C),实际转速,实际制冷,目标制冷`（未就绪为 -1）

### 曲线

- 系列开关（电池/制冷/风扇/热端/冷端/CPU℃），**默认除 CPU℃ 外全显示**；热端在冷端之前（实时数值列顺序由实时行独立维护，不受系列顺序影响）
- 实时数值列：电池 · CPU · 制冷 · 风扇 · 冷端 · 热端（不含目标制冷）
- **时间窗口 + 图例打包成子窗口**（`.ct-inner`）：内部全部保持固定值，超宽时整个子窗口 `transform: scale()` 等比缩放（裁切在父级 `.chart-tools` 的 `overflow:hidden`，与 transform 不同坐标系，缩放后内容必然落在可用区内；规避 WebView 对子元素单独缩放——calc 乘法/zoom——的兼容性问题）。**实时数值栏**：单行完整显示、不可滑动，文本宽度用隐藏探针测量（如实反映 tabular-nums 定宽，探针不可用退 canvas 加 5% 保险），超宽字号缩小（**0.1px 步进**，最小 7px，**4% 缓冲余量**），每帧重算但同字符数宽度一致不抖动，数值内容变化不改变显示长度。UI 诊断日志输出 `[fit] chartTools / liveRow` 行：可用宽/内容宽/字号/缩放百分比/跳过原因）

## 启动流程

1. 设定默认日志路径（根据二进制文件名）
2. 加载配置（`--config` 参数 > 自动检测 > 全部默认值。`PERF_ENABLED=0` 时仅 `DEBUG_ENABLED=1` 的调试子项生效，其余全部使用代码默认值；`PERF_ENABLED=1` 正常加载全部）
3. 创建 status 文件。读 LSP 回传实际制冷对齐初始制冷值（`active_cold_eff_*` 初始化；不可用回退代码默认 `pid_cold_min`）
4. 输出「脚本启动成功」后延迟 30 秒再开始（等待系统/蓝牙就绪，避开开机初期拉起 app 闪烁）
5. 等待模块就绪 + BLE 已连（status 文件读到 `BLE=1`）；等待期间无散热器 app 存活时自动拉起上次使用的 app（`APP_LAUNCH_ENABLED`，按 `APP_LAUNCH_COOLDOWN` 冷却）
6. 进入工作模式后每 5 秒：连接检测 → `main_loop`（纯计算）→ 速率限制执行
   - 每轮循环开头通过双重检查检测 App 存活（status 文件 mtime + BLE=1）
   - 断联时实际值保持不动（丢弃未执行变化量），进入等待复活子循环
   - 重连时实际制冷/转速以散热器实际回传为准初始化（不做档位匹配），由 `rate_limited_execute` 按正常限速逐步调节，抑制突变；重连后按 `RECONNECT_KEEP_CYCLES` 决定将 PID 状态保留还是完整重置（见 [主循环逻辑](#主循环逻辑)）

## 实测说明

### 智能温控模式的风扇转速限制非强制生效

经实测，**智能温控模式（mode=0）的风扇转速配置疑似并非强制生效**，经常会突破设定的上限很多，尤其是刚切换过去的时候。这会导致噪音突然变大，体验非常差。

**原因推测**：`setRunMode` 的 `windLevel` 参数在散热器固件中被解释为"建议上限"而非"硬上限"。散热器内部有独立的 PID 或逻辑控制算法，在刚切换模式或温差较大时，会以更高转速运行来快速达到目标温度，忽略应用层设定的风扇上限。

**解决方案**：全部改用**固定功率模式（mode=1）**，直接指定风扇转速和制冷片强度。daemon 下发均按固定功率模式指定实际制冷/风扇值，避免"建议上限被固件忽略"的问题。

## 注意事项

- **CPU 温度扫描范围** 通过 `CPU_ZONE_MIN/MAX` 配置（默认 0~99 全扫），K60 机型推荐 30~40 
- **温度传感器路径** `thermal_zone[N]` 是 Linux 通用接口，不同 SoC 的 zone 编号不同。首次真全量扫描无需手动配置（范围过大 0~99 约 1 秒），可通过 `CPU_ZONE_MIN/MAX` 缩小；后续周期重扫只在首次有效名单内、不再发现新 zone，保留数由 `CPU_ZONE_RESCAN` 第二值控制
- **去重逻辑**：`apply_gear_direct()` 以散热器实际回传为准——要播发值与散热器实际值一致视为已到位不下发（解决"日志已变化但实际未成功导致达不到最高/最低制冷"）；回传异常退化用 `last_*` 缓存对比。另含最小变化幅度：目标与制冷实际 `|差值|` ≤ `RATE_LIMIT_COLD` 第三值（最小变化幅度）时上升下降都不下发（距最高/最低 < 阈值×2 时失效）
- **am 广播可靠性**：`send_am_broadcast()` 用绝对路径 `/system/bin/am` 执行（不依赖 daemon PATH），并在 `waitpid` 后检查子进程退出码——`am` 未找到（127）或广播失败时 `write_log` 明确报错。排查"日志显示下发但散热器不动"时，先看日志里有没有 `am broadcast 失败` 行；开启 `DEBUG_ENABLED=1`+`DEBUG_EXEC=1` 可看到 `am broadcast 已发送` / `apply_gear_direct 跳过下发` 明细
- **`patch_tls.py`**：NDK 静态编译后需要执行，修复 PT_TLS 对齐；无 TLS 段时返回非零，需要 `|| echo "skipped"` 容忍
- **`#include <stdarg.h>`**：`write_log()` 用了 `va_list`，NDK clang 下不是隐式包含的
- **KernelSU noexec**：KernelSU 模块目录挂载了 `noexec`，`service.sh` 会将二进制复制到 `/data/local/tmp/` 执行
