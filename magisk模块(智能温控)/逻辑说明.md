# tempctrl 智能温控守护程序 — 设计说明

对应实现：[tempctrl.c](tempctrl.c)
配置文件：[magisk模块框架/profile.conf](magisk模块框架/profile.conf)
本文件只说明运行逻辑，不追求代码级精细。

## 整体架构

```
 ┌──────────────────┐               ┌──────────────────┐
 │ LSPosed 模块     │  am broadcast │ tempctrl 守护进程 │
 │ (MainHook.java)  │ ←──────────── │ (本 C 程序)      │
 │                  │   mode/temp/  │                  │
 │ 收到广播 → 调用   │   windOC/     │ pgrep → 检测 App │
 │ WaspWingManager  │   coldOC/     │ 存活状态          │
 │ .setRunMode()    │   windLevel   │ 每 5s main_loop()│
 │      ↓           │               │                  │
 │ BLE → 散热器     │               │ 热重载 profile.   │
 └──────────────────┘               │ conf 配置        │
                                    └──────────────────┘
```

**通信方式变更（v2.1）**：~~FIFO 写入~~ → 已废弃，~~pgrep~~ → 已移除，改为 status 文件 mtime 心跳 + BLE=1 双重检查存活检测。

**执行机制变更（v2.0）**：档位决策（`main_loop` 纯计算）→ 与执行（逐级 ±1 档）分离，每轮最多变动 1 档压制噪音突变。

## 配置文件系统 (profile.conf)

tempctrl 支持运行时配置文件，大部分关键阈值和参数均可外部修改，无需重新编译。

### 配置路径自动检测

1. **`--config` 参数**（最高优先级）：
   ```shell
   tempctrl --config /自定义路径/profile.conf
   ```
2. **自动检测**：通过 `/proc/self/exe` 获取自身路径，在同目录下查找
3. **默认值**：全部使用代码内默认值

### CONFIG_ENABLED 开关

配置文件第一行必须是 `CONFIG_ENABLED=1` 才能加载，否则所有参数使用代码默认值。
这对调试很有用——**设置 `CONFIG_ENABLED=0` 可快速排除配置文件问题**。

### ⚠️ 常见坑

| 坑 | 说明 |
|----|------|
| **Termux 编译不可用** | Termux 的 `clang -static` 链接的是 Termux 的 libc，非 Android libc。编译出的二进制在真机上 PT_TLS 对齐错误，必须用 NDK 编译。**开发阶段在 Termux 编出来可以看语法错误，但不要拿去真机跑** |
| **`--config` 路径** | service.sh 使用 `--config "$MODDIR/profile.conf"`直接从模块目录读取，不再复制到 `/data/local/tmp/` |

### 配置格式

```
# 注释以 # 开头
KEY=VALUE

# 例：
BATT_BASELINE=350
BATT_ZONE_1=7
```

不认识的 key 静默跳过；每个值有范围保护（`clamp`），非法值不会导致进程崩溃。

### 热重载

每轮 `main_loop()`（5 秒间隔）开头 `stat()` 检查配置文件的修改时间（mtime），变了就自动重读所有参数并记日志。**修改配置无需重启 daemon**。

## 温度读取

- **电池温度**：`/sys/class/power_supply/battery/temp`
  - 原生 0.1°C 精度，如 350 = 35.0°C

- **CPU 温度**：`/sys/class/thermal/thermal_zone[N]/temp`
  - 原始值 m°C，÷100 转 0.1°C，如 75321 → 753 (=75.3°C)
  - 首次调用时在 `CPU_ZONE_MIN~CPU_ZONE_MAX` 范围内扫描，记录能读到有效值的 zone
  - 后续只扫描已记录的 zone，取最高值
  - 一阶低通滤波平滑（系数由 `CPU_FILTER_ALPHA` 配置，默认 α=0.25）

## 主循环逻辑

**决策与执行分离**：`main_loop()` 先做纯计算（不下发），计算完成后立即逐步执行（±1 档）。

```
 ┌─ 主循环（每 5 秒）────────────────────────────────────────┐
 │                                                          │
 │  1. 连接检测（双重检查：status 文件 mtime + BLE=1）         │
 │     ├─ 断联 → actual_level = target_level（清零待执行     │
 │     │       → 等待复活，重连后对齐强制下发                  │
 │     │       → continue（跳过本轮）                        │
 │     └─ 存活 → 继续                                        │
 │                                                          │
 │  2. main_loop() 纯计算                                    │
 │     紧急干预（CPU+电流综合等级）→ 电池控制 → 保存 target   │
 │                                                          │
 │  3. ★ 逐步执行 ±1 档（计算后立即执行）                    │
 │     actual_level < target_level → ++/直跳, apply_level() │
 │     actual_level > target_level → --, apply_level()      │
 │     actual_level == target_level → 跳过                  │
 │                                                          │
 │  4. sleep(5)                                              │
 └───────────────────────────────────────────────────────────┘
```

### 关键说明

- **`actual_level`**：散热器当前实际运行的档位，每轮最多 ±1 变动
- **`target_level`**：控制逻辑计算出的目标档位，由 `main_loop` 末尾设置，供下轮执行
- **`battery_fan_level`**：电池控制的逻辑基准值（同步到 `final_level`），不是实际档位
- **逐步执行 vs 强制下发**：正常运行时逐级变动；断联重连时 `actual_level = target_level` 对齐后强制下发（不走逐步执行）
- **断联清零**：断联时 `actual_level = target_level` 抛弃所有待执行步伐，避免重连后执行过时指令
- **冷却期不影响执行**：`batt_cooldown` 只阻止电池控制做新决策，逐步执行不受影响（已积压的步伐照常消耗）

### main_loop() 内部详细逻辑，每5秒循环一次

0. **检查配置更新** → `stat()` 检测 `profile.conf` 修改时间，变了就热重载
1. **紧急干预** → 读 CPU 温度（低通滤波）+ 读电池电流（进入不平滑，退出用 EMA 平滑）→ 双源 OR 入 AND 出判定紧急等级 (0~4)，设 `forced_min_level`
2. **电池控制** → 读电池温度 → 计算温度变化量 + 常规档位调整量
   - 温度读数不变则跳过
   - **反补查表**（Sheet3 三区×双向×三级阈值）：
     - 三区：冷外区(≤基准-ZONE2) / 内区(±ZONE2内) / 热外区(≥基准+ZONE2)
     
     | 方向 | 区域 | 趋势豁免 | +1 档 | +2 档 | +3 档 |
     |------|------|---------|-------|-------|-------|
     | 升温 | 冷外区 | ≤0.8°C | >0.8°C | — | — |
     | 升温 | 内区 | ≤0.5°C | >0.5°C | >0.8°C | — |
     | 升温 | 热外区 | ≤0.3°C | >0.3°C | >0.5°C | >0.8°C |
     | 降温 | 冷外区 | ≤0.3°C | >0.3°C | >0.5°C | >0.8°C |
     | 降温 | 内区 | ≤0.5°C | >0.5°C | >0.8°C | — |
     | 降温 | 热外区 | ≤0.8°C | >0.8°C | — | — |
     - 趋势豁免仅当温度向基准方向变动时触发，防振荡
     - 反补跨越几个门槛就补几档（冷却期也执行，安全机制）
   - 未被豁免/反补时执行常规升降档（偏差三区策略）
3. **合最终档位** = `max(battery_fan_level, forced_min_level)`
4. **同步逻辑目标**：`battery_fan_level = final_level`（下轮电池控制以此为基础）
5. **保存执行目标**：`target_level = final_level`（供下轮逐步执行使用）
6. **退出紧急限制**：如果刚退出紧急等级且档位过高 → 硬 cap 到 `EMERG_FORCED_X`
   - 退出条件已在紧急干预中由 AND 逻辑保证，此处不再额外判断

## 进程检测机制

使用 **双重检查**：状态文件 mtime 心跳检查 + BLE=1 状态。只要有一个出问题就算断联。

```
 启动 → 创建 status 文件（0666，所有用户可写）
      → 等待 status 文件出现 BLE=1（模块就绪 + BLE 已连）
 
 工作模式中，每 5 秒：
   连接检测 → 逐步执行（±1 档）→ main_loop（纯计算）
   
   1. 读 status 文件内容 → BLE=0/1（模块上报的 BLE 连接状态）
   
   2. 双重检查存活检测（任一不满足即算断联）：
      ├─ stat(status 文件).mtime 距现在 ≤ 16秒？     → 模块在写心跳?
      └─ status 文件内容 BLE=1?                      → BLE 已连接?
      
      ├─ 全部 OK → 存活
      └─ 任一失败  → 模块/BLE 失联
                          ↓
                      等待复活子循环（每 5 秒检测，同时查 BLE）
                          ↓
                      模块+BLE 都重新就绪 → actual_level = target_level 对齐 → 强制下发

 模块侧（LSPosed）：
   ────────────────────────────────
   onDeviceConnected / disconnect 钩子 → 更新 bleConnected
   每 5 秒线程：FileOutputStream 写 "BLE=0/1\n" 到 status 文件
   （直接 Java 文件 I/O，不走 su，无 KSU 命名空间问题）
```

### 文件详情

| 项目 | 说明 |
|------|------|
| 路径 | `/data/local/tmp/tempctrl.status` |
| 创建者 | tempctrl 启动时 `fopen("a")` + `chmod 0666` |
| 写入者 | LSPosed 模块每 5 秒覆写 `BLE=0\n` 或 `BLE=1\n` |
| 读取者 | tempctrl 主循环开头 `read_status_ble()` |
| 心跳超时 | 11 秒（STATUS_TIMEOUT，写死后约 2 轮检测判死） |

### 双检测互补

| 场景 | 文件 mtime | BLE=1? | 结果 |
|------|-----------|--------|------|
| App 正常运行，BLE 已连 | ✅（新鲜） | ✅ | 存活 |
| App 正常运行，BLE 断联 | ✅（新鲜） | ❌ | 断联（等 BLE） |
| App 被 kill | ❌（无写入） | ❌ | 断联 |
| App 卡死/ANR | ❌（无写入） | - | 断联 |
| 文件被意外删除 | ❌（stat 失败） | - | 断联（daemon 会重建） |

## 电池控制细节

- **基准温度**：35.0°C（`BATT_BASELINE=350`，可配置）
- **三级策略**（diff = 当前温度 - 基准温度）：
  - `|diff| ≤ BATT_ZONE_1` → 不动，属于正常范围
  - `BATT_ZONE_1 < |diff| ≤ BATT_ZONE_2` → 升/降 1 档
  - `|diff| > BATT_ZONE_2` → 升/降 2 档

- **档位同步机制**（逻辑跟踪 vs 实际执行分离）：
  - `battery_fan_level = final_level` → 逻辑基准值（供下轮电池控制计算起点）
  - `target_level = final_level` → 执行目标（供下轮逐步执行使用）
  - 电池控制始终从上次计算的逻辑目标开始调整，不受逐步执行滞后影响
  - 紧急退出后不会暴跌——`battery_fan_level` 继承了紧急期间的档位
  - 退出紧急限制在逻辑同步之后执行：如果逻辑档位过高则硬 cap

- **反补查表（Sheet3 三区×双向×三级阈值）**：
  - **三区分类**（基于电池温度相对基准的位置）：
    - **冷外区**：`batt ≤ BASELINE - ZONE_2`（显著低于基准）
    - **内区**：`|batt - BASELINE| < ZONE_2`（基准附近）
    - **热外区**：`batt ≥ BASELINE + ZONE_2`（显著高于基准）
  - 反补档位数 = 跨越几个阈值门槛就补几档（见下表）
  - 趋势豁免仅当温度向基准方向变动时触发（`trend_rev`），防振荡
  - 最多连续豁免 `OVERRIDE_MAX` 次（默认 6 次 ≈ 30 秒），之后强制执行
  - 最高/最低档位时不记日志（避免刷屏）
  - 反补冷却期也执行（安全机制）

- **防重复**：
  - 记录上次读取的电池温度（`last_batt_reading`）
  - 温度连续不变时计数跳过，超 `BATT_SKIP_MAX` 次（默认 6）后强制进入一次
  - 温度有变化时重置计数，避免因传感器精度不足反复调整

- **档位变动冷却期**：每次任何原因导致的档位变动后冻结 `BATT_COOLDOWN_CYCLES` 个周期
  - 冻结期间跳过因电池温度触发的常规升降档和趋势豁免
  - 反补和紧急干预不受冷却限制

## 紧急干预细节（CPU 温度 + 电池电流双源）

紧急干预同时监测 **CPU 温度** 和 **电池电流** 两个来源，使用**OR 入 AND 出**逻辑：

- **进入紧急（OR）**：CPU 温度或电池电流任意一个超过阈值即触发对应等级
- **退出紧急（AND）**：CPU 温度 AND 电池电流都低于恢复阈值才允许降级

### CPU 温度处理
- 一阶低通滤波：`weighted = raw × CPU_FILTER_ALPHA% + old × (100-CPU_FILTER_ALPHA)%`
- 首次运行直接赋值，不做滤波
- 滤波系数默认 25 (α=0.25)，可通过 `CPU_FILTER_ALPHA` 配置

### 电池电流处理
- 读取 `/sys/class/power_supply/battery/current_now`（µA）
- 取绝对值（充放电都算），**不平滑、不滤波**，原始值直接比较

### 紧急等级与强制档位

| 等级 | 触发条件（综合 = cpu + 电流，各自 0~3） | 恢复条件（AND） | 强制最低档位 |
|------|----------------------------------------|----------------|-------------|
| 0 | cpu=0 AND 电流=0 | — | 无 |
| 1 | 综合 ≥ 1（单源最低级） | CPU < 55°C AND 电流(平滑) < 4A | 6（固定 3050RPM/75） |
| 2 | 综合 ≥ 2 | CPU < 65°C AND 电流(平滑) < 5A | 8（固定 4000RPM/125） |
| 3 | 综合 ≥ 3（单源最高级） | CPU < 75°C AND 电流(平滑) < 6A | 10（固定 5000RPM/160） |
| 4 | 综合 ≥ 4（需双源叠加） | CPU < 75°C AND 电流(平滑) < 6A | 12（固定 6000RPM/185） |

**退出紧急时**限制电池档位上限（在同步之后执行，保证生效）：
- 退出条件已由 AND 逻辑保证（CPU 和电流都低于恢复阈值），此处直接钳制，不再额外判断
- 退出等级 4 → `battery_fan_level ≤ EMERG_FORCED_4 + EMERG_EXIT_CAP_OFFSET`
- 退出等级 3 → `battery_fan_level ≤ EMERG_FORCED_3 + EMERG_EXIT_CAP_OFFSET`
- 退出等级 2 → `battery_fan_level ≤ EMERG_FORCED_2 + EMERG_EXIT_CAP_OFFSET`
- 退出等级 1 → `battery_fan_level ≤ EMERG_FORCED_1 + EMERG_EXIT_CAP_OFFSET`
- `EMERG_EXIT_CAP_OFFSET` 默认 1，退出时高一级强制档位 + 此偏移作为档位上限，防止 `battery_control` 立即拉升

## 日志系统

- **默认日志路径**：`/cache/<二进制名>.log`（自动根据二进制文件名生成）
  - 例：`tempctrl` → `/cache/tempctrl.log`
- 可通过 `profile.conf` 的 `LOG_FILE` 覆盖
- **日志滚动**：超 `LOG_MAX_KB`（默认 7KB）后自动删除最早日志行
- **日志关闭**：`LOG_MAX_KB=0` 完全关闭日志写入
- **格式**：`[日 时:分:秒] 日志内容`
  - 例：`[15 14:30:22] 档位3 +2`
- **主要日志含义**：

| 日志 | 含义 |
|------|------|
| `挡位5（+1）` | 电池常规升降档，从 4→5 升了 1 档（正负号表示方向） |
| `过冲0.4 挡位9（+1）` | 峰值过冲抑制，温度骤变 0.4°C，从 8→9 升了 1 档 |
| `趋势豁免 7` | 温度趋势反向，本周期跳过升降档（停留在 7 档） |
| `紧急2（+1）cpu69.0 cur5.2` | 紧急等级变化，CPU 加权 ≈69.0°C，电流 ≈5.2A |
| `App 不存在，等待连接...`（末尾空行） | status 文件超时（模块停止心跳），进程失联 |
| `BLE 已断开，等待连接...`（末尾空行） | BLE 连接断开但进程仍存活 |
| `脚本启动成功` | 守护程序启动完成 |

## 启动流程

1. 设定默认日志路径（根据二进制文件名）
2. 加载配置（`--config` 参数 > 自动检测 > 全部默认值，`CONFIG_ENABLED=0` 跳过）
3. 创建 status 文件，读取存档档位（无存档为 LEVEL_INIT=5）
4. 等待模块就绪 + BLE 已连（status 文件读到 `BLE=1`）
5. 进入工作模式后每 5 秒：连接检测 → 逐步执行（±1 档）→ `main_loop`（纯计算）
   - 每轮循环开头通过双重检查检测 App 存活（status 文件 mtime + BLE=1）
   - 断联时 `actual_level = target_level`（清零待执行步伐），进入等待复活子循环
   - 重连时 `actual_level = target_level` 对齐后强制下发

## 实测说明

### 智能温控模式的风扇转速限制非强制生效

经实测，**智能温控模式（mode=0）的风扇转速配置疑似并非强制生效**，经常会突破设定的上限很多，尤其是刚切换过去的时候。这会导致噪音突然变大，体验非常差。

**原因推测**：`setRunMode` 的 `windLevel` 参数在散热器固件中被解释为"建议上限"而非"硬上限"。散热器内部有独立的 PID 或逻辑控制算法，在刚切换模式或温差较大时，会以更高转速运行来快速达到目标温度，忽略应用层设定的风扇上限。

**解决方案**：全部改用**固定功率模式（mode=1）**，直接指定风扇转速和制冷片强度。v2.1 的默认档位表已全部采用固定功率模式，避免了此问题。如果要恢复某档为智能温控，可通过 `profile.conf` 的 `GEAR_N` 自定义覆盖（设模式=0）。

## 注意事项

- **CPU 温度扫描范围** 通过 `CPU_ZONE_MIN/MAX` 配置（默认 0~99 全扫），K60 机型推荐 30~40 
- **温度传感器路径** `thermal_zone[N]` 是 Linux 通用接口，不同 SoC 的 zone 编号不同。全自动扫描无需手动配置，但如果扫描范围过大（0~99）首次可能稍慢（约 1 秒），可通过 `CPU_ZONE_MIN/MAX` 缩小范围
- **去重逻辑**：`apply_level()` 缓存上次参数，连续相同不下发，但 App 复活时强制清除缓存重发
- **`patch_tls.py`**：NDK 静态编译后需要执行，修复 PT_TLS 对齐；无 TLS 段时返回非零，需要 `|| echo "skipped"` 容忍
- **`#include <stdarg.h>`**：`write_log()` 用了 `va_list`，NDK clang 下不是隐式包含的
- **KernelSU noexec**：KernelSU 模块目录挂载了 `noexec`，`service.sh` 会将二进制复制到 `/data/local/tmp/` 执行
