### 通用1 飞智生态与包名体系

飞智（Flydigi）生态由散热器（WaspWing 系列）、手柄（Cyberfox / Gaia 系列）、游戏厅 / 社区 / 商城 / 账号等模块组成；各 app 只是这套生态的不同裁剪。

**包名前缀两套体系**：

| 前缀 | 含义 | 用于 |
|---|---|---|
| `com.flydigi.*` | 飞智自研业务包（账号、社区、设备管理、`sdk`） | B7X、B8X 的业务代码根包 |
| `com.fdg.flashplay.*` | 发行 / 渠道侧包名 | B7X（`farsef`）、B8X（`farb8x`）的 manifest 包名 |

段义（B8X 文档的还原）：`fdg` = 飞迪 / 飞智游戏，`flashplay` = 飞智体系，`far` = 风扇（Fan），末段 = 设备型号或系列（`farsef` 系列通用、`farb8x` = B8X）。

**四个 app 的包名与产物**（完整清单见 [索引](#索引)）：`com.flydigi.waspwing.experimental` = 飞智散热器开发者工具（别名：老 app）、`com.flydigi.waspwing.experimentanliuliu` = B6 B6X 超频工具 V2（别名：新 app）、`com.fdg.flashplay.farsef` = B7 B7X超频 V3 Max、`com.fdg.flashplay.farb8x` = B8X 超频工具 V2。

**命名空间口径**：反编译产物内部的 Java 命名空间为 `com.example.extool`（工具作者自建，不是 APK 包名），与上表包名不同，比对 / 引用时一律以 APK 包名为准。

### 通用4 BLE 与 GATT 流程

**总体链路**（各 app 共用同一套 SDK 流程）：

```
扫描: AbstractBluetoothController.startScan(activity, scanMode)
        ├─ scanMode == 2 → BluetoothAdapter.startLeScan()（已废弃 API）
        └─ 否则         → BluetoothLeScanner.startScan()
      过滤：RSSI 阈值（默认 -90）+ 设备名称匹配

连接: onDeviceFound(device) → stopScan() → connect(device)
        → WaspWingManager.connectGattWith(device)
          → LeDataInteractionController.connectGattWith(device)
            → BluetoothDevice.connectGatt(context, false, gattCallback)

服务发现: onConnectionStateChange(CONNECTED)
        → onGattConnected(gatt)
          → checkBluetoothPermission()          [⚠️ 关键检查点，失败即中断]
            → gatt.discoverServices()
              → onServicesDiscovered(status=0)
                → initCharacteristic(gatt)
                  → setCharacteristicNotification(targetUUID, true) + 写入 CCCD

数据通道: onCharacteristicChanged(gatt, characteristic)
        → 解析 0x13 数据包 → onReceiveDataFromDevice(WaspWingInfo)
          → SDK.onDeviceInfoUpdate(info) → _waspWingInfo.postValue(info)
            → DataBinding.executeBindings() → UI 重绘
```

**GATT 服务与特征值 UUID**（逆向自 B7X 的 `WaspWingDataInteractionController`）：

| UUID | 用途 |
|---|---|
| `0000ffe0-0000-1000-8000-00805f9b34fb` | 服务 UUID |
| `0000ffe1-0000-1000-8000-00805f9b34fb` | 数据写入特征值 |
| `0000ffe4-0000-1000-8000-00805f9b34fb` | 数据通知特征值 |
| `00002902-0000-1000-8000-00805f9b34fb` | CCCD（客户端特征配置描述符） |

**上报模式**：设备主动上报（Notify），非 App 轮询。智能温控模式下约每秒一个 `0x13` 数据包，固定功率模式下频率较低。

| 状态字段 | 更新时机 | 说明 |
|---|---|---|
| `temperature` | 每个 `0x13` 数据包 | 智能温控模式每秒更新 |
| `realWindLevel` | 风扇转速变化时 | 档位变动后下一数据包 |
| `realColdLevel` | 制冷强度变化时 | 指令生效后下一数据包 |
| `runMode` | 模式切换响应后 | App 主动查询或设备确认 |
| `experimentalRunModeValue` | 智能温控模式 | 设备反馈的运行状态值 |

> `onCharacteristicChanged` 在 BLE 回调线程执行，`postValue` 把数据切到主线程更新 LiveData，因此 UI 更新比数据到达晚一帧。

**BLE 层的 app 差异**：B6X 两包与 B7X 都走 WaspWing SDK（B7X 为混淆版）；B8X 改为 `cyberfox.h1.services.GAIAGATTBLEService` / `GAIABREDRService`（Cyberfox/Gaia 手柄蓝牙栈），架构完全不同，现有 LSPosed 钩子（针对 `setRunMode`、`AbstractBluetoothController`）无法复用。

**证据**：飞智散热器开发者工具 §三 蓝牙连接流程（3.1–3.4 全链）、§五 5.2 数据包解析、§五 5.3 散热器状态同步；B6 B6X 超频工具 V2 §二「废弃扫描 API 分支」行（保留 `startLeScan`/`stopLeScan` 分支）；B7 B7X超频 V3 Max §（3）BLE 连接流程（UUID 表 + 扫描/连接/通知流程）；B8X 超频工具 V2 §六 与 B6X/B7X 的关键差异（BLE 层）。

### 通用5 控制 API 与 setRunMode 掩码协议

所有控制指令都经 `WaspWingManager`（SDK 单例）的**同一个 7 参数入口**下发：

```java
setRunMode(int mode, int targetTemperature,
           int windLevelOverclock, int coldLevelOverclock,
           int windLevel, int modeCustom, int extra)
```

| 模式 | 生效参数 | 说明 |
|---|---|---|
| mode=0（智能温控） | targetTemperature + windLevel | 设目标温度和风扇上限，散热器自行管理制冷 |
| mode=1（固定功率） | windLevelOverclock + coldLevelOverclock | 直接指定风扇转速和制冷片强度 |
| mode=2（超频，B7X 有） | 超频档位 | B7X 追加 |

**更新掩码**（由 B6X smali 调用点还原）：`0x5c` = 制冷、`0x7c` = 温度、`0x6c` = 风速。

**各 app 的同一 API 对照**：

| app | 入口写法 | 备注 |
|---|---|---|
| 飞智散热器开发者工具 / B6 B6X 超频工具 V2 | `WaspWingManager.setRunMode(...)` | 未混淆 |
| B7 B7X超频 V3 Max | `WaspWingManager.W(...)` → `WaspWingDataInteractionController.E2(...)` | 同名 7 参数；单例 `t9.j.f50990a`；追加 B7 专有 `0x20` 9 字节命令格式 |
| B8X 超频工具 V2 | ❓ 未知 | 加固不可见 |

**底层命令字节**（逆向自 B7X `E2()`）：通用设备 `0x21`（智能）/ `0x22`（手动）/ `0x23`（超频）；B7/B7X 另一套 9 字节 `0x20` 格式。

**证据**：飞智散热器开发者工具 §4.3 模式切换逻辑与掩码协议（签名 + 参数映射 + 掩码）、§4.4 设备控制逻辑（掩码列）、§七 对比表「控制 API」行；B6 B6X 超频工具 V2 §一（`setExperimentalRunMode` 7 参数调用）+ §二 尾注（「两包的 `setRunMode` 掩码协议…一致，因此不重复记录」）；B7 B7X超频 V3 Max §（2）核心控制方法 `W()` → `E2()` + BLE 控制协议命令；B8X 超频工具 V2 §七 对比表「控制 API ❓ 未知」。

**实用技巧**：

- 同源包判定：忽略调试行号后**逐字节 / 逐文件比对**（B6X 两包即此法判定 19 类差异）

### 通用9 加固与静态可分析性

| app | 加固 / 混淆 | 静态可分析性 |
|---|---|---|
| 飞智散热器开发者工具 | ❌ 无加固（另有作者插桩版构建，见其文档） | ✅ 完整 |
| B6 B6X 超频工具 V2 | ❌ 无加固 | ✅ 完整 |
| B7 B7X超频 V3 Max | ❌ 无商业加固壳，仅 ProGuard / DexGuard 轻度混淆（类名 / 方法名 / 变量名单字母化，资源文件名混淆） | ✅ 完整（jadx 可反编译全部 dex） |
| B8X 超频工具 V2 | ✅ **爱加密 + 自定义 JNI 双重加固** | ❌ 静态不可分析，需动态脱壳 |

**加固的三类形态**：

1. **爱加密**：`assets/libjiagu.so` / `libjiagu_a64.so`；壳入口 `com.stub.StubApp`（Application）+ `com.stub.stub01.StartActivity`（Launcher）
2. **自定义 JNI 壳**：`com.tianyu.util.DtcLoader` 静态块 `System.loadLibrary("jgdtc")` → 加载 `/data/data/<pkg>/lib/libjgdtc.so`；关键字符串 XOR / 移位加密（`com.tianyu.util.a`），`Class.forName` 反射加载真实入口类
3. **纯混淆**（非加固）：只改名字，反编译后逻辑仍完整可读 —— 与加固必须区分

**判定方法**：jadx / baksmali 能完整反编译所有 dex 且无 `libjiagu` 等壳 so = 无加固；`classes.dex` 里只有几个壳类 + `assets/` 有壳 so = 已加固，业务 dex 由 native 层运行时解密注入。

**加固后的处理**：静态只能拿到 Manifest 架构（AXML 字符串表可解码出组件清单）、assets 配置与 lib；真实代码需 Frida 内存 dump dex / 脱壳机（BlackDex、Youpk）——具体方案与工具见 [b8x/反编译分析.md §八](b8x/反编译分析.md)。

**证据**：飞智散热器开发者工具 §七 对比表「加固」行；B6 B6X 超频工具 V2 §二（未加固）+ §三 备注（B8X 加固一句话）；B7 B7X超频 V3 Max §（4）加固/混淆评估（无商业加固壳、有 `libSignatureKiller.so`）；B8X 超频工具 V2 §一 结论先行、§三 加固机制拆解、§五 为什么静态分析不可行。
