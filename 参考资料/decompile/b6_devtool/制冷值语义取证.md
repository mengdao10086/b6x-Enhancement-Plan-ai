# 制冷值语义取证 — `realColdLevel` 到底是"设定回显"还是"实际运行档"

> **取证对象**：`参考资料/apk_original/飞智散热器开发者工具.apk`（包名 `com.example.extool`）
> **证据基准**：`./devtool/smali/`（原 APK 的 `classes.dex` 反编译；**不是** `./smali_merged/` 的插桩版）
> **辅助核对**：同 SDK 的 B7 包 Java 反编译 `../b7_overclock_v3/sources/com/flydigi/sdk/waspwing/a.java`、`WaspWingInfo.java`；布局/资源用 apktool 解到临时目录只做视图对应，未改动仓库
> **结论强度**：Q1–Q4 为**确证**；Q5"设定值 vs 实际运行档"为**强推断**（缺原始 0x13 抓包）

---

## 0. 结论摘要

设备通过 `0x13` 通知包同时上报**至少三个不同的"冷"字段**，SDK 把它们分别存进三个私有字段：

| 字段 | B6/B6X 的字节 | 含义（本取证结论） | App 里的显示位置 |
|---|---|---|---|
| `coldLevel` | `byte[7]` | 普通制冷设定档 | 控制区滑块 + 滑块上方读数（经 `getRealColdLevel()` 选择） |
| `coldLevelOverclock` | `byte[0x0d]` | 超频/实验制冷设定档 | 同上 |
| `coldRunLevel` | `byte[0x0f]` | 运行档（实际输出侧） | **顶部四宫格**的「制冷片强度」 |

`getRealColdLevel()` **不是字段**，而是计算属性：

```
runMode == 0 && overClockUsable ? coldLevelOverclock : coldLevel
```

**所以我们的曲线第 7 列取到的是"设备回显的设定值"（更准确说：设备上报的当前设定档/超频档），不是设备实际运行档 `coldRunLevel`。**

关键反差的正解：飞智 App 里"逐渐爬到 180"的那个数字，按代码应是**顶部四宫格**的「制冷片强度」= `getColdRunLevel()`（`byte[0x0f]`）；而滑块上方那行「制冷片强度：xxx」和滑块位置绑定的是 `getRealColdLevel()`，与我们的曲线同源。两处文案相同、取值不同，这是本次现象最容易误判的地方。

## 1. Q1：`realColdLevel` 的数据来源

### 1.1 0x13 包识别与设备分支

`WaspWingDataInteractionController.onReceiveDataFromDevice(UUID, byte[])` 取 `value[0]` 判断包类型：

- `./devtool/smali/com/flydigi/sdk/waspwing/WaspWingDataInteractionController.smali:1108`（`aget-byte v3, v1, 0`）
- `:1124-1126`（`const/16 v11, 0x13`；`if-ne v3, v11`）
- `:1241-1261`（`deviceCode` 等于 `"b6"` 或 `"b6x"` 才进入 B6/B6X 解析分支 `:cond_a1`）

### 1.2 B6/B6X 分支的逐字节解析

| 字段 | 字节 | 证据行 |

| `ipType` | `value[1] & 0xff` | `:1266-1274` |

解析完不新建对象，直接改 `deviceInfo` 这个复用实例，然后遍历回调：

- 复用实例：`:1128`（`iget-object ... deviceInfo`）、构造时的默认实例 `:235-301`
- 回调：`:1673-1700`（遍历 `gattCallbacks`，逐个 `onDeviceInfoUpdate(deviceInfo)`）
- App 侧再接 `postValue`：`./devtool/smali/com/example/extool/WaspWingViewModel.smali:487-496`

### 1.3 `getRealColdLevel()` 的计算

`./devtool/smali/com/flydigi/sdk/waspwing/WaspWingInfo.smali:2402-2421`：

```smali
.method public final getRealColdLevel()I
    .registers 2

    iget v0, p0, Lcom/flydigi/sdk/waspwing/WaspWingInfo;->runMode:I

    if-nez v0, :cond_b

    iget-boolean v0, p0, Lcom/flydigi/sdk/waspwing/WaspWingInfo;->overClockUsable:Z

    if-eqz v0, :cond_b

    iget v0, p0, Lcom/flydigi/sdk/waspwing/WaspWingInfo;->coldLevelOverclock:I

    goto :goto_d

    :cond_b
    iget v0, p0, Lcom/flydigi/sdk/waspwing/WaspWingInfo;->coldLevel:I

    :goto_d
    return v0
.end method
```

字段定义：`WaspWingInfo.smali:250-258`（`coldLevel`、`coldLevelOverclock`、`coldRunLevel` 三个独立私有字段）；对应 setter 为 `:2986-2998`，getter `getColdRunLevel` 在 `:2080`、`getColdLevelOverclock` 在 `:2064`。

`runMode` 的取值：`0` = 智能温控（`rb_smart`），`2` = 固定功率（`WaspWingViewModel.smali:898-915`，`0x7f080161` 对应 `rb_smart`）。因此：

- 固定功率（`runMode=2`）：`getRealColdLevel()` 取 `coldLevel = byte[7]`；
- 智能温控（`runMode=0`）且 `overClockUsable=true`：取 `coldLevelOverclock = byte[0x0d]`。

### 1.4 为什么搜不到 `setRealColdLevel`

因为 `realColdLevel` **不是存储字段**，没有 setter；smali 里只有 `setColdLevel` / `setColdLevelOverclock`。这两者在本 APK 中的调用点**只有 0x13 解析器**：

- `WaspWingDataInteractionController.smali:1180`（B3 分支）
- `:1359`（B6/B6X 的 `coldLevel`）
- `:1431`（B6/B6X 的 `coldLevelOverclock`）
- `:1568`、`:1641`（B5/B5P 分支；注意 B5/B5P 的 overclock 冷量来自 `byte[0x0c]`，与 B6/B6X 的 `byte[0x0d]` 不同）

### 1.5 交叉验证（同 SDK 的 B7 包 Java 反编译）

`../b7_overclock_v3/sources/com/flydigi/sdk/waspwing/a.java` 的同一段解析是逐行对应的：

- `:326`、`:340`、`:371` → `setColdLevel(value[7] & 255)`
- `:350`、`:376` → `setColdLevelOverclock(value[13] & 255)`
- `:353`、`:378` → `setWindRunLevel(value[14] & 255)`
- `:356`、`:378` → `setColdRunLevel(value[15] & 255)`

`../b7_overclock_v3/sources/com/flydigi/sdk/waspwing/WaspWingInfo.java:463-464` 也是同一个三目表达式。

**Q1 证据强度：确证。**

## 2. Q2：是不是"设备回显"——有没有本地乐观更新

### 2.1 拖动滑块路径

`WaspWingViewModel.updateColdPwm(IZ)`（`WaspWingViewModel.smali:850-895`）：

- `:853-855`：`if (fromUser == false) return`
- `:868-892`：读取当前 `runMode`、`targetTemperature`，把 `p1`（滑块值）放在第 6 个参数位，掩码 `0x5c`，调用 `WaspWingManager.setRunMode$default(...)`
- 整个方法**没有** `setColdLevel`、没有 `postValue`、没有 `iput` 到 `WaspWingInfo`

掩码 `0x5c` 的含义（`WaspWingManager.smali:969-1063`）：第 3/4/5/7 个参数取默认 0，实际生效参数是 `(runMode, targetTemperature, 0, 0, 0, coldValue, 0)`。

滑块回调入口：`ActivityExperimentalB6BindingImpl.smali:780-818`（callback id 10 → `updateColdPwm(progress, fromUser)`），`fromUser` 为 false 时不下发。

### 2.2 下发链路是否改写本地对象

`WaspWingManager.setRunMode(IIIIIII)`（`WaspWingManager.smali:1598-1630`）只是转发给
`WaspWingDataInteractionController.setRunMode(IIIIIII)`（`:2819-3162`）。

后者全方法只做两件事：

1. 按 `deviceCode` 和 `runMode` 组装 `byte[]`（`:2822-3151`，命令字 `0x21/0x22/0x23`）
2. `addCommandToQueue` 入队（`:3153-3160`）

全方法内**没有**任何 `iput` 到 `deviceInfo` 的字段、没有 `setColdLevel`。`AbstractDataInteractionController.addCommandToQueue`（`./devtool/smali/com/flydigi/sdk/bluetooth/AbstractDataInteractionController.smali:639-666`）也只做队列封装，该类里搜不到 `WaspWingInfo`。

SDK 另一个 `WaspWingDataInteractionController.setColdLevel(I)`（`:2287-2314`，命令 `0x12`）同样只入队；本 App 也**没有调用**它（app 只调 `setRunMode`）。

### 2.3 全量反例排查

| 排查项 | 结果 |
|---|---|
| 全 APK `setColdLevel(` 调用点 | 仅 `WaspWingDataInteractionController` 的 4 处解析分支（1180/1359/1568/1641）+ 定义处 |
| 全 APK `setColdLevelOverclock(` 调用点 | 仅 `:1431`、`:1641`（解析分支） |
| `WaspWingInfo.copy(...)` 调用点 | App 仅 `WaspWingViewModel.smali:472`，发生在 `onDeviceDisconnected`，用默认值清空，不涉及"用户拖动后的本地回填" |
| ViewModel 的 `postValue` | 仅 `:482`（断连清空）、`:496`（SDK 回传原对象）、`:845`（`update()`，全 APK 未找到调用方） |
| 下发方法内 `iput` / `setValue` | 无 |

### 2.4 结论

**没有本地乐观更新。** 两条路径都查清：

- 拖动 → `updateColdPwm` → `setRunMode` → BLE 入队，**本地字段不变**；
- `coldLevel`/`coldLevelOverclock` 的唯一写入源是**设备 0x13 通知包**。

因此，设定 219 后我们的曲线能在约 1 秒内看到 219，只能是**设备在下一包 0x13 里把新设定值回显出来**，不可能是 App/SDK 自己写的。约 5 秒后被"打回"，则是我们的 daemon 控制周期下发自己的值，设备再回显该值。

**Q2 证据强度：确证（"无本地写入"部分）。**

## 3. Q3：UI 上"制冷片强度"绑的是谁

这个界面有**两处**文案都叫「制冷片强度」，绑定的是不同字段。

### 3.1 控制区：滑块上方的「制冷片强度：xxx」→ `getRealColdLevel()`

- getter：`ActivityExperimentalB6BindingImpl.smali:935`（`invoke-virtual ... WaspWingInfo->getRealColdLevel()I`）
- 文案拼接：`:1223-1227`（`const-string v15, "制冷片强度："` → `concat(String.valueOf(realColdLevel))`）
- 赋给 `mboundView22`：`:1702-1706`（`TextViewBindingAdapter->setText`）；`mboundView22` 即布局里的 `binding_22`——位于 `sb_cold`（`binding_25`）正上方（apktool 临时解出的 `res/layout/activity_experimental_b6.xml:43-48`；该布局文件不在仓库内，`apk_raw/res` 为混淆目录）
- 滑块进度：`:1237`（`move/from16 v35, v27`）+ `:1792-1796`（`SeekBarBindingAdapter->setProgress(sbCold, v35)`）
- 注：smali 的寄存器在 `executeBindings` 里大量复用；用 jadx 对**同一 APK** 反编译复核，表达式明确为 `"制冷片强度：".concat(String.valueOf(waspWingInfo.getRealColdLevel()))`，赋给 `mboundView22`；`setProgress(this.sbCold, realColdLevel)`。

### 3.2 顶部四宫格：「制冷片强度」→ `getColdRunLevel()`（`byte[0x0f]`）

- getter：`:1527`（`WaspWingInfo->getColdRunLevel()I`）
- 文案拼接：`:1601-1605`（`const-string v2, "制冷片强度\r\n"` → `concat(v0)`）
- 赋给 `mboundView8`：`:1768-1770`（`mboundView8` = `binding_8`，布局 `:16`）
- 同一块的四项分别是：冷面温度（`binding_5`）、热面温度（`binding_6`）、风扇转速（`binding_7`）、**制冷片强度 = `coldRunLevel`（`binding_8`）**

### 3.3 结论

- **滑块与滑块上方读数**：`getRealColdLevel()`（`coldLevel` 或 `coldLevelOverclock`）。
- **顶部四宫格的「制冷片强度」**：`getColdRunLevel()`（`byte[0x0f]`），**不是** `realColdLevel`。
- 没有独立的进度条/指示条控件；唯一的"指示条"是 `sbCold` 这个 SeekBar，它的位置同样绑 `getRealColdLevel()`。

**Q3 证据强度：确证。**

## 5. Q5：综合结论与"219 vs 180"的成因

### 5.1 三个"冷值"不要混

| 概念 | 数据源 | 我们在哪看到 |
|---|---|---|
| **A. 我们的下发目标** | daemon PID 输出 `actual_cold` | 曲线/文件**第 8 列**（`daemon/tempctrl.c:4531-4535`，`WEBUI_ROW_FMT` 第 8 个字段） |
| **B. 设备回显的设定值** | 0x13 的 `byte[7]`（或 `byte[0x0d]`），经 `getRealColdLevel()` 选择 | 曲线**第 7 列** `COLD_REAL`（LSPosed `MainHook.java:433`；daemon `tempctrl.c:2034-2035`） |
| **C. 设备实际运行档** | 0x13 的 `byte[0x0f]`，`getColdRunLevel()` | 飞智 App **顶部四宫格**的「制冷片强度」 |

### 5.2 现象解释

1. 在飞智 App 把制冷设成 219 → App 走 `updateColdPwm(219,true)` → `setRunMode(...,0x5c)` 下发；**App 本地不改任何字段**（Q2）。
2. 设备接受命令后的下一包 0x13（约 1 秒）在 `byte[7]` 或 `byte[0x0d]` 回显 219 → SDK `setColdLevel`/`setColdLevelOverclock` → `onDeviceInfoUpdate` → 我们的钩子读到 `getRealColdLevel()=219` → 曲线第 7 列**瞬间跳到 219**。
3. 我们的 daemon 按 5 秒控制周期下发自己的目标 → 设备再回显该值 → 曲线第 7 列被"打回"。
4. 飞智 App 顶部四宫格显示的是 `coldRunLevel`（`byte[0x0f]`），它是设备的运行档侧数值，按设备内部节奏爬升；代码里它**与设定值完全独立存储**，因此不会跟着 219 跳变，表现为"逐渐爬到 180"。

### 5.3 明确回答

**我们的曲线第 7 列 = `getRealColdLevel()` = 设备回显的设定值（当前设定档/超频设定档），不是设备实际运行档 `coldRunLevel`。**

"实际档位"若指设备真正输出/运行的档，则答案是：**我们取到的不是它**；我们取到的是设备对"当前设定"的回显。若"实际档位"仅指"设备真实上报的值（而非我们本地伪造）"，则答案是：**是设备上报的，但不是运行档**。

### 5.4 证据强度与缺口

- "无本地乐观更新、值只能来自 0x13"：**确证**。
- "`byte[7]/byte[0x0d]` 是设定值、`byte[0x0f]` 是运行档"：**强推断**。依据是：字段命名（`coldLevel`/`coldLevelOverclock` vs `coldRunLevel`）、滑块（设定控件）绑 `getRealColdLevel()` 而遥测四宫格绑 `getColdRunLevel()`、以及 App 自修复逻辑把 `getRealColdLevel()+1` 当作**要重新下发的参数**（`WaspWingViewModel.smali:487-556`）。旁证（同 SDK 的 B7 App）：预设档位判断用的是 `getColdLevel() == 104/149/155/254`（`../b7_overclock_v3/sources/com/flydigi/device_manager/ui/detail/waspwing/b7/RunModeItem.java:307-310`，属于"设定"语义），而统计页展示的是 `getColdRunLevel()`（`.../statistics/StatisticsActivity.java:63`，属于"运行统计"语义）。
- **仍缺的证据**：
  1. 在设 219 的同时抓一包原始 0x13，直接对照 `byte[7]/byte[0x0d]/byte[0x0f]` 的数值；
  2. 同时记录 `getRealColdLevel()` 与 `getColdRunLevel()`（后者可在钩子里加一次 getter 调用），确认"跳 219 的是前者、爬 180 的是后者"；
  3. 确认当时的 `runMode` 与 `overClockUsable`，才能判定 219 来自 `byte[7]` 还是 `byte[0x0d]`。
- **现场一分钟判别法**：看飞智 App 里"逐渐到 180"的数字在哪个位置——若是**滑块上方那行「制冷片强度：」**，按代码它应与我们的曲线同跳 219（若不同，说明观看的不是这个控件或 App 版本不一致）；若是**顶部四宫格**，则它就是 `coldRunLevel`，与代码完全吻合。

**Q5 证据强度：强推断（设定/运行字段区分）；"180 的物理上限成因"证据不足，代码只能证明它是另一个设备上报字段，不能证明设备为何停在 180。**
