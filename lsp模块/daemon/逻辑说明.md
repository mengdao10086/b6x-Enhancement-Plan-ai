## 配置文件系统 (profile.conf)

tempctrl 支持运行时配置文件，大部分关键阈值和参数均可外部修改，无需重新编译。

### 配置路径自动检测

1. **`--config` 参数**（最高优先级）：仅用于临时覆盖，正常部署不传
   ```shell
   tempctrl --config /自定义路径/profile.conf
   ```
2. **自动检测**：应用私有目录 `/data/data/com.example.waspwingtempctrl/files/profile.conf`
3. **默认值**：配置不存在时全部使用代码内默认值，并记一行日志（不再静默）

> 该路径由 C 端 `PRIVATE_DIR` 宏决定，必须与 `app/build.gradle.kts` 的 `applicationId`、`参数定义/params.def.json` 的 `LOG_FILE` 默认值**三处一致**；`python 参数定义/check_params.py` 会自动核对（宏改成跨行拼接时降级为 INFO，不假通过）。

### PERF_ENABLED / DEBUG_ENABLED / SYSFS_ENABLED 开关

配置层级：

```
PERF_ENABLED（性能总开关，默认=1）
  ├── =0：不加载性能参数（PID、速率限制、热端过温削减等），全部使用代码默认值
  └── =1：正常加载所有性能参数

DEBUG_ENABLED（调试总开关，独立于 PERF_ENABLED，默认=0）
  ├── =0：分区调试日志关闭
  └── =1：各 DEBUG_* 分区开关生效

SYSFS_ENABLED（sysfs 接口与外围，独立于 PERF_ENABLED，默认=0）
  ├── =0：不加载自定义 sysfs/日志路径，使用代码默认路径
  └── =1：加载 profile.conf 中的 BATT_*/CPU_*/LOG_* 路径与缩放配置
```

**运行中关闭开关的语义**：上表「使用代码默认值」是**运行期**语义——开关由 1 改为 0（或删掉该键），该层已加载的参数会在下一次热重载（5 秒内）**立即回落代码默认值**，等同该层配置不存在；**profile.conf 内容不动**，开关改回 1 后文件里的值立刻恢复生效。默认值表由 `params_generated.h` 的 `CFG_PERF_DEFAULTS` / `CFG_SYSFS_DEFAULTS` 生成（`参数定义/params.def.json` 单一来源，与上表「默认值」一致）：路径键走 `CFG_DEFAULT_*` 宏，`LOG_FILE` 走 `set_default_log_path()`（私有目录不可用时仍兜底 `/cache`）。层总开关自身不复位；热端削减量与其冷却计数一并清零，PID 运行态（积分、动态目标）不重置。

这对调试很有用——**设置 `PERF_ENABLED=0` 但 `DEBUG_ENABLED=1` 可关闭性能控制并保留调试输出**；sysfs 路径可独立于性能开关加载（`SYSFS_ENABLED=1`）。

### ⚠️ 常见坑

| 坑 | 说明 |
|----|------|
| **Termux 编译不可用** | Termux 的 `clang -static` 链接的是 Termux 的 libc，非 Android libc。编译出的二进制在真机上 PT_TLS 对齐错误，必须用 NDK 编译。**开发阶段在 Termux 编出来可以看语法错误，但不要拿去真机跑** |
| **配置路径** | 部署脚本（`assets/deploy/b6x-tempctrl.sh`，落 `/data/adb/service.d/`）**不传 `--config`**：daemon 自行按上文私有目录定位；`--config` 仅用于临时覆盖。**不复制的是 profile.conf**——二进制仍按 KSU noexec 约束复制到 `/data/local/tmp/tempctrl` 执行（见「注意事项」末条） |

### 配置格式

```
# 注释以 # 开头
KEY=VALUE

# 例：
BATT_BASELINE=350
PID_KI_RATE=20 30
```

不认识的 key 静默跳过；每个值有范围保护（`clamp`），非法值不会导致进程崩溃。

### 热重载

每轮 `main_loop()`（5 秒间隔）开头 `stat()` 检查配置文件的修改时间（mtime），变了就自动重读所有参数并记日志。**修改配置无需重启 daemon**。

**`CPU_AFFINITY` 的生效时机**（与其它键不同，要落到进程的 `sched_setaffinity` 与 cgroup cpuset 组上）：只在两处应用 —— `main()` 启动时（日志就绪后、等待设备循环之前）与上面这个热重载块（`load_config()` 之后）。因此：① 等待设备阶段改配置不会立即生效（该循环不查 mtime）；② 无 `profile.conf` 时永不热重载，但亲和仍按代码默认 `0 5` 无条件生效（该键缺失、或 `SYSFS_ENABLED=0` 时同样按默认生效——配置值只有一个来源，不会被开关关掉）；③ 值非法（非双值、起始核 > 结束核）或与本机 `/sys/devices/system/cpu/present` 交集为空时回落默认 `0 5` 并记日志；④ 迁 cpuset 组失败时只设亲和，实际生效核一律以日志读回的 `Cpus_allowed_list` 为准（cpuset 的 cpus 是硬上限、组内只能收窄不能放宽，故顺序是先迁组、后设亲和；只写 `cgroup.procs` 迁自己，绝不改任何组的 `cpus`）。

**`CPU_AFFINITY` 的已知限制**：① cpuset 挂载点硬编码 `/dev/cpuset`（依真机 mountinfo 取证：`/dev/cpuset rw,cpuset,noprefix`），不在运行期探测——挂载布局不同的设备只会走到「只设亲和」的降级路径；② 本机核号取自 `/sys/devices/system/cpu/present`，只解析**首个连续区间**（写成 `0-3,4-7` 会被当成 `0-3`），偏保守、不会把范围放宽；③ 亲和只在启动与热重载两处应用，迁组后若被 ROM 改回**不会低频重申**；④ 该键只在 `SYSFS_ENABLED=1` 时按键值取用，缺键或该组未启用时按默认 `0 5` 生效。

## 温度读取

- **电池温度**：`/sys/class/power_supply/battery/temp`
  - 原生 0.1°C 精度，如 350 = 35.0°C

- **CPU 温度**：`/sys/class/thermal/thermal_zone[N]/temp`
  - 原始值 m°C，÷100 转 0.1°C，如 75321 → 753 (=75.3°C)
  - 首次调用时在 `CPU_ZONE` 指定的范围内扫描，记录能读到有效值的 zone
  - 后续只扫描已记录的 zone，取最高值
  - 一阶低通滤波平滑（系数由 `CPU_FILTER_ALPHA` 配置，默认 α=0.25）

### 温度变化检测

- **值比较 + mtime 双信号**：以值比较为主（部分内核 sysfs 温度文件 mtime 更新不可靠，会导致温度实际在变却被判"未更新"而大量跳过）；**同时检测文件 mtime**——mtime 更新时（即使值相同）也视为温度数据刷新，触发 PID 重算以保持积分累积与 dt 新鲜。mtime 恒不变的内核自动退化为纯值比较。
- **1s 窗口累积**：5s 控制周期的跳过判定不看"当前采样值 vs 上次控制值"，而是看**自上次控制以来 1s 层是否检测到过值/mtime 变化**（累积标志 `batt_changed_since_ctrl`，控制周期开始时快照 `batt_window_changed` 并清零）。温度在窗口内变过又回到原位也不会漏判。
- **两条跳过（pid_cycle 重算判定）**：仅**温度窗口变化** 或 **CPU 补偿变化**（`total_comp_10 != pid_last_comp_10`）才触发重算；两者均未变则本轮冻结 `acc`/`kdp`/`target`/`last_ch` 等控制状态。两条跳过：
  1. **温度未变（仅补偿变化触发）** → `kdp` 沿用上次值（`batt_window_changed=0` 时 `pid_kdp` 不更新），避免补偿突变带动 KDP 跳变；
  2. **温度未变且上次 `|ch| ≤ PID_CH_THRESHOLD`** → 整轮冻结（`acc`/`kdp`/`target`/`last_ch` 一律不动），仅推进补偿书签 `pid_last_comp_10`（防补偿反复变化反复触发导致死锁）。
- **电池温度输入滤波（改动2：加回）**：电池温度进 PID `ch` 前先经 EMA 滤波（`pid_batt_filtered`），**仅温度更新时（值/mtime 变化，即 `batt_window_changed`）才滤波并输出**；动态 α = `0.2 + 0.05 × 间隔周期数`（间隔 = 距上次温度更新的 5s 控制周期，钳 0~16 → α 0.2~1.0，时间越长新值权重越高）。**停机（`batt_window_changed=0`）且滤波未收敛**（`pid_batt_filtered != batt_raw`）时，首个周期**优先恢复原始值强制重算**（改动2优先于此节第②条整轮冻结），`pid_batt_filtered = batt_raw`（= 未更新的电池温度），进 PID 用原始电池 + 新 CPU 滤波补偿 → "半新 ch"；snap 一次后 `pid_batt_filtered==batt_raw` 滤波态消失，回正常冻结。`pid_batt_filtered` 在 `pid_reset_core`（切模式/重连）重置为 -1 直取初值。

## PID 控制模式

本实现**仅 PID 单模式**（Gear 已删除），采用**单累积器**结构：`OUTPUT = clamp(acc + kdp, 0, 1)`。
`acc` 为积分累积（`pid_ki`），`kdp` 为融合 P+D 项（`pid_kdp`，无记忆）。`error` 只取纯电池误差；
CPU 补偿与速度项同地位进入 `ch`，再进入积分与 KDP。

### 控制流

```
main_loop()（纯计算，不下发）:
  0. 温度窗口快照：batt_window_changed = batt_changed_since_ctrl；清零使开启新窗口
  1. 热重载（共享）：stat() 检测 profile.conf mtime，变了重读并 update_active_limits()
  2. update_hot_derate()：热端过温 → 制冷削减（本周期即生效）
  3. update_active_cold_range()：当前有效制冷范围（供下发/去重/映射统一使用）
  4. pid_cycle()：CPU 补偿 → 两条跳过判定 → pid_compute() → 映射制冷

pid_cycle()（每 5s）:
  1. cpu 温度读入 → update_cpu_filtered()（CPU_FILTER_ALPHA EMA 滤波）
  2. cpu_comp = cpu_comp_now(batt_raw)：CPU 补偿（EMA 平滑，门控滞回，始终生效）
  3. 重算判定：batt_window_changed || total_comp_10 != pid_last_comp_10
     ── 两条跳过（见「温度变化检测」节）：①温度未变→kdp 沿用 ②|last_ch|≤阈值→整轮冻结
  4. dt = (now − pid_last_change_time)/5，钳位 0.6~6（1 = 5s）
  5. pid_compute(batt_raw, dt, cpu_comp, batt_window_changed) → 归一化输出 0~1
  6. 映射：pid_align_cold = clamp(pid_cold_min + (int)(out×range), pid_cold_min, active_cold_eff_max)

rate_limited_execute()（执行段）:
  → rate_limit_cold(pid_align_cold)：限速制冷（actual_cold；每周期最大变化量限制，取代原 PID_OUT_FILTER 的输出平滑）
  → compute_fan_target()：独立风扇目标（冷端指数 + 热端线性加权，不跟 PID 输出）
  → rate_limit_fan：限速风扇
  → apply_gear_direct(1, 5, send_rpm, actual_cold, 0)：纯下发（去重/日志/广播）
```

### 单累积器公式

```
error   = (batt_raw − BATT_BASELINE) / 10             # 纯电池，单位 °C（batt_raw 为 0.1°C）
v       = (error − pid_last_error) / dt                # 速度（°C/周期）；首算无常值历史 v=0
L,q     = PID_SPEED_NL_THR/100, PID_SPEED_NL_EXP/100   # 速度非线性：阈值 L（°C/周期）与强度 q
v       = |v|≥L ? v : sign(v)·|v|·s^q                  # 映射：t=|v|/L、s=t²(3−2t)；保号、|v| 不增、v=±L 连续
sc      = PID_SPEED / 10                               # 100=速度×10，0=关闭
ch      = error + v×sc + cpu_comp                      # 用于积分
ch_kdp  = error + v×sc×0.33 + cpu_comp                 # 用于 KDP（速度按 0.33 衰减）

raw_target = clamp(error×PID_TARGET 目标系数/1000, ±PID_TARGET 第三值/10)   # 动态目标（默认 ±1.5°C 界）
pid_target_f += α_dir × (raw_target − pid_target_f)   # 方向性 EMA：PID_TARGET_DIR 开关=1 时，远离基线用"远离alpha"/回归基线用"回归alpha"；开关=0 时 α=PID_TARGET 平滑%/100

integrand = ch − pid_target_f                          # 被积项，符号决定用哪个速率
ki_rate   = (integrand ≥ 0) ? PID_KI_RATE 升速率/1000 : PID_KI_RATE 降速率/1000
ki_rate  *= 冷值动态倍率 升/降（见下）                  # 升降各自乘算，1.0 = 不干预
pid_ki   += ki_rate × integrand                        # acc 累积，不乘 dt
budget  = max(0, 1 − pid_kdp)                          # 预算钳制（防 acc+kdp 超 1 被末端硬截断）
pid_ki  = clamp(pid_ki, 0, budget)

pid_kdp = PID_KDP/1000 × ch_kdp × 冷值动态倍率 KDP      # 无记忆；温度未变（batt_window_changed=0）沿用上次
out     = clamp(pid_ki + pid_kdp, 0, 1)
```

### 冷值动态倍率（逻辑2）

只有温度窗口有更新（`batt_window_changed=1`）的周期才重算；取样值 = **上次 PID 重算**算出的目标冷值 `pid_align_cold`，两次重算之间沿用同一取样值与三个倍率。

```
冷值 cold → 抽象值 s（两段线性 + 两端平台）
  cold ≤ 下界            → 0（不干预）
  下界 < cold ≤ 拐点      → −om × (cold − 下界) / (拐点 − 下界)
  拐点 < cold < 上界      → −om − (1 − om) × (cold − 拐点) / (上界 − 拐点)
  cold ≥ 上界            → −1（最大降幅）

倍率 = U^(sign(s)·|s|^γ)                               # 取整三位；s = 0 → 1.000，s = −1 → 1/U
作用点 s_k = clamp(s × 权重, −1, 0) → 各自映射倍率       # KDP / KI 升速率 / KI 降速率
```

- **单位与默认值**：冷值三点为**码**（零换算，`PID_COLD_DYN_IN` 默认 `40 100 190`）；拐点降幅 `om`、三作用点权重、`U`、`γ` 为配置整数（均 ×100：`PID_COLD_DYN_OUT` 默认 `50`、`PID_COLD_DYN_W` 默认 `100 100 100`、`PID_COLD_DYN_MAP` 默认 `200 100`）。配置里输出轴存**正数**（默认 50 = 拐点处降幅 0.50），C 内变换成抽象值 −0.5。
- **三个作用点**：倍率分别乘进 KI 升速率、KI 降速率与 `pid_kdp`（KDP 为本次新增作用点）；倍率 ∈ [1/U, 1]，只降不升。
- **除零保护**：归一化辅助函数在分母 ≤ 0（配置乱序）时返回 1——配置不拒绝、只做内部保护，保证 `s` 恒落 [−1, 0]、不产 NaN/Inf。
- **诊断日志**（`DEBUG_PID=1`，每重算周期一行）：`[PID] 冷值动态 in=170 om=0.50 s=-0.889 | 加权 sk=-0.889 su=-0.889 sd=-0.889 | 倍率 rkdp=0.540 rup=0.540 rdn=0.540`（取样冷值 / 拐点降幅 / 抽象值 / 三作用点加权后抽象值 / 三作用点最终倍率）。

> **已删除**：动态 KI 抑制机制（窗口散布评估器、三个配置键 `PID_KI_DYN_T` / `PID_KI_DYN_GATE` / `PID_KI_DYN_WIN`、结构体 `ki_dyn_cfg` 及其全部实现）——积分速率不再按窗口散布削减，改由本节冷值动态倍率调制。

- **error 纯电池**：不含 CPU 补偿；CPU 补偿（`cpu_comp`）与速度项同地位进 `ch`（用于积分）。KDP 用的 `ch_kdp` 中速度项按 0.33 衰减（≈1/3），CPU 补偿不衰减。
- **速度 v**：以 `dt`（5s 周期数）归一化，乘 `PID_SPEED`/10 系数，不乘 dt。计算后先做**非线性映射**：幅度达到阈值 `L`（`PID_SPEED_NL_THR`/100，°C/周期）时**严格恒等**（1:1、无恒定偏置），低于 `L` 时按 `t²(3−2t)` 平滑阶跃取 `q` 次幂降权（`q` = `PID_SPEED_NL_EXP`/100，`q=0` 即完全线性）。映射保号（奇函数）、处处 `|输出| ≤ |v|`、单调不减、在 `±L` 处连续；差分得到的 v 与回溯注入的 v **汇聚到同一处映射、各恰好施加一次**，映射后的同一个 v 供 `ch` 与 `ch_kdp` 共用。
- **动态目标 `pid_target_f`**：`raw_target` 随时间 EMA 平滑，使积分逼近"误差×目标系数"包络，防静态过冲。
- **KDP 无记忆靠预算**：`pid_kdp` 每周期重算（温度未变时沿用），`acc` 钳到 `1−kdp`，避免 `acc+kdp` 超 1 被末端硬截断（抗 windup）。
- **两条跳过**：见「温度变化检测」节；跳过时控制状态（`acc`/`kdp`/`target`/`last_ch`）不动，仅推进补偿书签。

### PID 参数配置

当前 PID 键：`PID_KDP` / `PID_SPEED` / `PID_SPEED_NL_THR` / `PID_SPEED_NL_EXP` / `PID_KI_RATE` / `PID_TARGET` / `PID_TARGET_DIR` / `PID_CH_THRESHOLD` / `PID_COLD_RANGE` / `PID_CPU_COMP` / `PID_SPEED_RECALL` / `PID_COLD_DYN_IN` / `PID_COLD_DYN_OUT` / `PID_COLD_DYN_W` / `PID_COLD_DYN_MAP`。多值键（`PID_KI_RATE` / `PID_TARGET` / `PID_TARGET_DIR` / `PID_COLD_RANGE` / `PID_CPU_COMP` / `PID_SPEED_RECALL` / `PID_COLD_DYN_IN` / `PID_COLD_DYN_W` / `PID_COLD_DYN_MAP`，连同单值键 `PID_COLD_DYN_OUT`）走 `parse_pid_cfg` 分段；单值键（`PID_KDP` / `PID_SPEED` / `PID_SPEED_NL_THR` / `PID_SPEED_NL_EXP` / `PID_CH_THRESHOLD`）走 `INT_CFG_KEYS` 表驱动。`PID_GAIN`（原增益组合）已拆分为 `PID_KDP` / `PID_KI_RATE` / `PID_SPEED`；`PID_OUT_FILTER`（输出端自适应滤波）已删除——输出平滑改由 `RATE_LIMIT_COLD` 每周期限速承担。全部通过配置热重载，无需重启。

### CPU 补偿（PID_CPU_COMP）

`comp = clamp(cpu_filtered_temp − batt_raw − 偏移, 0) ÷ divisor`，按补偿专属滤波系数 EMA 平滑（独立于
`CPU_FILTER_ALPHA`，首次上次值用 0 从 0 爬升）。门控滞回：`raw>0` 进入补偿，条件消失后平滑值继续向 0
收敛归零才退出（不瞬间跳变）。始终生效，与 PID 单累积器一同作用于 `ch`。

### 制冷→RPM 映射引擎

PID 模式使用（本实现仅 PID）：

| 函数 | 映射方式 | 用途 |
|------|---------|------|
| `rpm_from_hot_end()` | 输入 EMA 平滑 + 双向滞回线性映射 | 热端温度 → RPM（需求侧：越高越迫切），**输入先经 `MAP_INPUT_SMOOTH_ALPHA` EMA 平滑**（滞回基于平滑值），降温滞回 +1°C，升温不低于上次 RPM；**热端 ≤0（异常/未就绪）时保持上次输出** |
| `rpm_from_cold_exp()` | `cold^exp` 指数映射（输入侧 EMA 平滑） | 冷强度 → RPM（供给侧：越强调速越高），**制冷强度先经 `MAP_INPUT_SMOOTH_ALPHA` EMA 平滑再进指数映射，映射后不再滤波**（与热端共用系数，首次直取） |
| `compute_fan_target()` | `rpm_from_cold_exp(actual_cold)` + 热端线性映射自加权合并（自加权逻辑已内联于本函数） | 独立风扇目标：PID 每周期下发前统一计算，与 PID 输出解耦（禁降钉死时风扇保持高转速，热端过温直接拉满） |

### 热端过温制冷削减

散热器热端过温时**就地压低**制冷强度上限（PID 模式专用，`main_loop` 每 5s 周期入口先执行），保护散热器硬件：

| 场景 | 行为 |
|------|------|
| 热端 > 阈值 | 单次削减量 = `(热端-阈值)×倍率/10`；**首次触发**把生效上限压到「当前实际制冷值 − 削减量」（回传未就绪时按配置上限算），**之后每次触发在当前生效上限上继续累减（不回看历史触发值）**；削减后冷却周期内不再削减 |
| 热端 ≤ 阈值 | 有削减时生效上限每次 +`倍率`（固定值）逐级上爬，削减量归零即**封顶配置上限**；恢复后冷却周期内不再恢复 |
| 削减/恢复冷却 | 独立计数，互不影响 |

- **配置上限**：`active_pid_cold_max`（`PID_COLD_RANGE` 上限，B6X/B7X 取对应值），由 `update_active_cold_range()` 计算。
- **生效上限** = 配置上限 − 削减量，下限不低于冷端最小强度。
- **下发边界强制生效（硬钳制）**：除压低目标上限外，还在每次下发前对制冷强度做硬钳制（`min(期望, 生效上限)`），直接绕过 `RATE_LIMIT_COLD` 的禁降限速——电池 ≥37.5°C 禁降期间也能把已升高的制冷强度一步压回上限内。钳制不改变 `actual_cold`，仅作用于本次下发值。
- 削减量按原始读数直算（不加滤波），一次 55°C 读数可削减 50；恢复按每冷却周期 +5（=倍率）逐级上爬，回到配置上限为止。
- 热端数据无效（<0，断联/未就绪）时保持当前削减量不动。
- 削减仅下调制冷强度上限，不直接干预 CPU 档位/CU 风扇（旧"CPU 紧急干预强制升档"已随 Gear 删除）。
- **已知边界**：热端在阈值附近来回时（≤45 / ≥46 交替）可能"削减→恢复→削减"每 2 周期交替，属规格固有行为；真机热端温变慢，实际振荡概率低。若需消除可加滞回带。
- **风扇联动（刻意不同步）**：边界钳制**故意不修改** `actual_cold`，风扇目标仍由 `actual_cold` 推算保持高转速——过温时只降制冷片强度、不拉低风扇，避免"火上浇油"；散热器实际制冷以回传值为准。钳制生效瞬间制冷强度一步跳至上限内，恢复时从被压值按正常升速爬回。

### EMA 方向取整

所有整数 EMA 平滑（CPU 温度、热端映射输入、冷端映射输入）使用 `EMA_DIR` 宏替代标准 `EMA`。
标准整数 EMA 因截断存在渐进问题（如 `α=33%` 时 `old=449 + raw=450` 永远到不了 450），
`EMA_DIR` 基于原始值方向做取整：原始值升高→向上取整，原始值降低→自然截断（按需方向），
确保滤波值能实际到达原始值。

## 主循环逻辑

**决策执行分离 + 限速统一下沉**：`main_loop()` 纯计算不下发，`rate_limited_execute()` 分发。
执行段：`rate_limit_cold()` 限速制冷 → `compute_fan_target()` 独立计算风扇目标（基于限速后实际制冷，
不跟 PID 输出）→ `rate_limit_fan()` 限速风扇 → `apply_gear_direct()` 纯下发（去重/日志/广播）。
计算层（`pid_cycle`）只传目标值，不限速。风扇目标基于限速后制冷（而非目标制冷），禁降钉死时风扇保持高转速。

```
 ┌─ 主循环（1 秒节拍；控制每 5s）───────────────────────────────┐
 │  每 1s：write_webui_data() 采集电池/CPU/散热器 → 追加+读删写（每60行压缩）│
 │  每 5s（时间判定）执行下方控制节拍：                        │
 │                                                          │
 │  1. maybe_rescan_cpu_zones()：CPU zone 首扫建名单/周期重扫   │
 │  2. 双设备仲裁 select_active_device()：                    │
 │     ├─ 读双 status → BLE 连接状态 / 连接者（BLE_OWNER_LAST）│
 │     ├─ arbitrate_apps()（ARBITRATE_INTERVAL 节流）          │
 │     ├─ 设备切换/断联 → reconnect_align() 或 continue        │
 │     └─ is_app_alive() + BLE 存活检测 → 断联则 continue      │
 │                                                          │
 │  3. main_loop() 纯计算                                    │
 │     窗口快照 → 热重载 → update_hot_derate() →              │
 │     update_active_cold_range() → pid_cycle()               │
 │                                                          │
 |  4. ★ 速率限制执行                                        │
 │     rate_limited_execute()：                            │
 │     ├─ 风扇转速：升/降步长=RATE_LIMIT_FAN 第一值+防抖(第二值)│
 │     ├─ 制冷强度：升速/降速 = RATE_LIMIT_COLD ± dev×MULT/10  │
 │     │             （dev 有符号，负值禁方向）                 │
 │     └─ watchdog_check()：本次实际下发制冷变化后判定          │
 │                                                          │
 │  5. sleep(1)                                             │
 └───────────────────────────────────────────────────────────┘
```

### 关键说明

- **风扇目标独立于 PID 输出**：风扇转速不跟 PID 输出，每周期由 `compute_fan_target()` 基于限速后 `actual_cold`
  （冷端指数映射）+ 热端温度（线性映射）自加权合并计算；热端过温时只降制冷强度、不拉低风扇（避免"火上浇油"）。
- **升降速率限制**（0.1°C 精度）：风扇升速与降速**共用同一组步长与阈值**（单键双值 `RATE_LIMIT_FAN`：第一值=每周期最大变化量、第二值=防抖阈值），
  且两个方向各带一段**幅度阈值防抖**（本周期变化量 ≤ 阈值就整步不做——升速方向保持当前值不升、降速方向保持当前值不降，
  升速时距最高转速 / 降速时距最低转速 < 阈值×1.5 时该方向防抖失效）；制冷片强度升降速独立且有符号
  （升速 = `RATE_LIMIT_COLD + d × RATE_LIMIT_COLD_MULT / 10`，降速 = `RATE_LIMIT_COLD − d × RATE_LIMIT_COLD_MULT / 10`，
  d = 有符号温差(电池温度 − BATT_BASELINE)）。负值表示禁止该方向变化（电池 ≥37.5°C 禁止降制冷强度、≤32.5°C 禁止升制冷强度）。
  制冷方向的 `d × mult / 10` 保留 0.1°C 精度。溢出自然累积下周期，目标变化时从当前实际值重新计算。
- **去重 + 最小变化幅度**：`apply_gear_direct()` 以散热器实际回传为准判定是否下发（`should_skip_dispatch`）：
  要播发值与实际回传一致视为已到位、跳过下发；回传异常退化用 `last_*` 缓存对比。另含最小变化幅度
  （目标与制冷实际 `|差值|` ≤ `RATE_LIMIT_COLD` 第三值、距极值 ≥ 死区×2 时上升下降都不下发）。
- **短断联保留状态（`RECONNECT_KEEP_CYCLES`）**：断联时长 < `RECONNECT_KEEP_CYCLES`×5 秒（默认 3×5=15s）时，
  **跳过 `pid_reset_core()`**——`acc`/`kdp`/`target`/误差等 PID 学习状态保留，输出连续不跳变；仅仍以散热器回传实际值
  对齐 `actual_cold`/`actual_rpm`。长断联或配置=0 时完整重置（防陈旧状态误入）。该规则按断联时长统一生效，
  跨设备切换（B6X→B7X）若未记录断联起点也走保留分支（电池共享、状态连续合理）。
- **锁死自动重启（APP_WATCHDOG）**：仅在本次实际下发制冷变化后判定——实际制冷停滞（=上周期实际）且未达目标
  （≠上周期下发）连续 N 次时 kill 散热器 app 并重新拉起（散热器重启无效，需重建 App 进程恢复连接栈）；
  仅 BLE 已连、实际回传可用、watchdog 开启时启用；kill 后冷却 300s 防风暴。

### main_loop() 内部详细逻辑（每 5s 控制节拍执行一次）

> **结构**：`main_loop` 为骨架，直接分发到 `pid_cycle()`（本实现仅 PID，无 CTRL_MODE / gear_cycle 分支）。
> 配置解析为表驱动 + 分段函数（`INT_CFG_KEYS` 表 + `parse_debug/sysfs/pid/common`），与单函数行为等价。

0. **温度窗口快照**：`batt_window_changed = batt_changed_since_ctrl`；清零开启新窗口（供 pid_cycle 跳过判定）
1. **检查配置更新** → `stat()` 检测 `profile.conf` 修改时间，变了就热重载（`update_active_limits()`）
2. **热端过温削减** → `update_hot_derate()`：按散热器热端温度更新制冷上限削减量
3. **有效制冷范围** → `update_active_cold_range()`：`active_cold_eff_min/max`（含热端过温削减）
4. **PID 周期** → `pid_cycle()`：CPU 补偿 → 两条跳过判定 → `pid_compute()` → 映射 `pid_align_cold`

（旧 Gear 电池控制 / 反补 / 趋势豁免 / 紧急干预 / 电流-挡位映射等步骤已随 Gear 删除。）

## 进程检测机制

使用 **双重检查**：状态文件 mtime 心跳检查 + BLE 连接状态。status 双文件的路径与 `BLE=` 字段的取值编码（B6X 文件区分两个 app、B7X 文件记实际散热器型号）见 [lsp模块 README](../README.md)（唯一规范处）。只要有一个出问题就算断联。

> **STATUS_TIMEOUT**：状态文件心跳超时判死秒数，**硬编码 3**（不再可配置，故不列入参数表）——LSP 每 1s 写一次，超 3s 判死。

```
 启动 → 创建 status 文件（0666，所有用户可写）
      → 脚本启动成功 → 延迟 30s 再开始（等待系统/蓝牙就绪，避开开机初期拉起 app 闪烁）
      → 等待 status 文件出现 BLE≠0（模块就绪 + BLE 已连）
 
 工作模式中，每 5 秒：
   连接检测 → 双 app 存活仲裁 → main_loop（纯计算）→ 速率限制执行
   
   1. 读 status 文件内容 → BLE（编码见 lsp模块 README）
   
   2. 双重检查存活检测（任一不满足即算断联）：
      ├─ stat(status 文件).mtime 距现在 ≤ 3秒？      → 模块在写心跳?
      └─ status 文件内容 BLE≠0?                       → BLE 已连接?
      
      ├─ 全部 OK → 存活
      └─ 任一失败  → 模块/BLE 失联
                          ↓
                      等待复活子循环（每 5 秒检测，同时查 BLE）
                          ↓
                      模块+BLE 都重新就绪 → 实际制冷/转速以散热器回传为准 → 按正常限速过渡

 模块侧（LSPosed）：
   ────────────────────────────────
   onDeviceConnected / disconnect 钩子 → 更新 bleConnected + connectedModel
   每 1 秒线程（后台 BLE 重连保持 5s 节奏）+ 连接/断连事件：FileOutputStream 写 "BLE=<编码>\n" + CONNECTED_AT + BLE_OWNER_LAST=<值> <时间> 到 status 文件（字段名与编码见 lsp模块 README）
   （BLE_OWNER_LAST 连接时写入、断连保留，标识"上次连接者"，供 app 存活仲裁）
   （直接 Java 文件 I/O，不走 su，无 KSU 命名空间问题）
```

### 三方 app 存活仲裁

三个 app 最多一个后台存活：**飞智散热器开发者工具**（别名：老 app，包名 `com.flydigi.waspwing.experimental`，参数定义里的键名沿用 `B6X_OLD`）+ **B6 B6X 超频工具 V2**（别名：新 app，包名 `com.flydigi.waspwing.experimentanliuliu`，键名沿用 `B6X_NEW`）+ farsef（`com.fdg.flashplay.farsef`，B7X 游戏厅）。由 `arbitrate_apps()` 每 5 秒在读取双 status 后调用。

```
参与者 < 2 → 不仲裁
保留优先级：
  1. BLE_OWNER_LAST 值代表的 app（标识"上次连接者"，连接时写入、断连保留）：
     =1 → 保留飞智散热器开发者工具（老 app）
     =2 → 保留 B6 B6X 超频工具 V2（新 app）
     =6 → 候选保留 farsef
  2. 无 BLE_OWNER_LAST → 回退当前连接者 BLE 字段（=1 飞智散热器开发者工具 / =2 B6 B6X 超频工具 V2）
  3. 兜底保留飞智散热器开发者工具（老 app）

保留者涉及 farsef 时：比较 farsef 的 BLE_OWNER_LAST 时间与另一方（B6X app）的
CONNECTED_AT，保留时间更晚（最近使用）的那个。

被淘汰者非前台时 am force-stop（dumpsys window mCurrentFocus 优先判断，
被淘汰者在前台则等下一周期再试）
```

**与温控仲裁的关系**：`arbitrate_apps()` 只管 app 存活，`select_active_device()` 只管散热器控制权。两个 B6X app 共写同一 B6X status 文件；`BLE_OWNER_LAST` 由 LSP 连接事件写入、断连保留，标识"上次连接者"；farsef 连 B6X 设备时写 B7X status 文件（BLE=6 + `BLE_OWNER_LAST`=6）。都未连接时 arbitrate 保留上次连接者（或飞智散热器开发者工具）在后台待命（LSP 后台自动重连会恢复连接）。

**自动拉起**：`arbitrate_apps()` 扩展——当**没有任何散热器 app 存活**时自动拉起上次使用的 app（`launch_last_app()`，复用 `BLE_OWNER_LAST` 选择逻辑：2→B6 B6X 超频工具 V2、6/7→farsef、其余/无记录→飞智散热器开发者工具；目标 app 未安装时回退另一个）。拉起用 `am start`（**显式 launcher 组件 `-n <包名>/<Activity>`**；这些 app 的 launcher 未导出/非标准 filter，隐式 `-p` 解析不到）+ `b6x_auto_launch` 标志，LSP 读到标志后在**离开引导页、进入设置界面时**（第一个非引导页 Activity 的 `onResume`）执行 `moveTaskToBack` 后台化（几乎无感；引导页 onResume 不切，等自动跳转到设置界面后再切，避免"没进界面就退后台"；读取后清除标志避免用户手动打开又被切走；附 2s 兜底超时，自动进入设置失败时仍退后台）。按 `APP_LAUNCH_COOLDOWN` 冷却；由 `APP_LAUNCH_ENABLED` 开关控制（默认 0 关闭，需在界面中开启）。调用时机：启动等待设备循环 + 主循环每 5s 节拍 + **断联（连接丢失）时**（存活检测失败路径；无 app 存活时真正拉起，app 存活时记 debug「已在运行」；开关关闭也会记 debug「开关关闭，跳过」，便于排查）。进程存活检测**直读 `/proc/<pid>/cmdline` 精确比对包名**（整参=包名或 `--nice-name=<包名>`），不经 shell——避免 `system("pgrep -f <包名>")` 时临时 shell 自身命令行含包名造成的自匹配误判（曾导致 app 已死仍被判"已在运行"、拉起被跳过）。

**开销收敛（2026-09-25）**：本链在启动等待循环、主循环 5s 节拍与断联路径上都会被反复调用，故四处做了收敛——① 屏幕门禁前移到最贵的探测（安装探测 `pm`、全量 `/proc` 扫描）**之前**，息屏期间整条链停跑、每 10 秒才复核一次屏幕（常量非配置键；代价：息屏→亮屏最长滞后 10 秒，息屏期间散热器 app 被回收时自动拉起最多晚 10 秒开始）；② 安装状态一次开机周期内只问一次并缓存，命令跑不起来时不写缓存；③ 调用方已扫出「三方全灭」时把该结论传给拉起链，免去重复的全量扫描；④ 屏检自己不再走 `sh | awk` 管线，只 fork 一个 `dumpsys`（命中即关管道让子进程提前退出）—— 一次探测从 3 个进程、两段管道降到 1 个进程、一段。

**LSP 侧配合**：连接成功时把散热器 MAC 持久化到**宿主 app 自己的私有目录** `/data/data/<宿主包名>/files/tempctrl_last_dev`（**各包各记**，不再四包共用一个文件；代价是同一台散热器在另一个飞智 app 里需重新选一次）。该文件由 LSP 侧（`MainHook`）自建自读自写，**tempctrl daemon 不参与**（原 daemon 侧在 `/data/local/tmp/` 预创建 0666 的兜底块已删除）。冷启动打开 app 时，LSP 检测到引导页（MainActivity）即**自动进入参数设置界面**（等效自动点「开始设置」，`autoStartSetup()`），由 B6ExperimentalActivity.onResume 的 `tryConnect()` 主动发起连接——不再需要手动点「开始设置」。已进入过设置界面（`enteredSetup`）或已连接时跳过；后台重连线程仍保留（断开后每 5s 兜底，**息屏时放慢到 10s**）；`am start` 携带 `b6x_auto_launch=1` 时 LSP 将 Activity 切回后台。

## 日志系统

- **默认日志路径**：`/data/data/com.example.waspwingtempctrl/files/<二进制名>.log`（应用私有目录，自动根据二进制文件名生成）
  - 例：`tempctrl` → `/data/data/com.example.waspwingtempctrl/files/tempctrl.log`
  - 私有目录不可用时兜底回 `/cache/<二进制名>.log` 并写 stderr（不静默失败）
- 可通过 `profile.conf` 的 `LOG_FILE` 覆盖
- **日志滚动**：超 `LOG_MAX`（默认 16256 字节）后 `ftruncate` 截断保留尾部（从完整行首起），零读零写只改文件 size，不依赖 `LOG_TRIM_LINES`（已删除）
- **日志关闭**：`LOG_MAX=0` 完全关闭日志写入
- **格式**：`[日 时:分:秒] [PID] 日志内容`（PID 专属日志统一带 `[PID]` 前缀）
  - 例：`[15 14:30:22] [PID] e=-0.35 v=0.12 ch=0.48 tgt=0.20 ki=0.30 kdp=0.15 out=0.45 win=1`
- **调试日志**：`[DEBUG]` 前缀，按功能区分 7 个分区（传感器/执行/连接/配置/主循环/PID/自动拉起；原始"档位"分区已随 Gear 删除），通过 `DEBUG_ENABLED` + 分区开关控制。开启调试时自动关闭日志体积限制

- **主要日志含义**：

| 日志 | 含义 |
|------|------|
| `[PID] e=-0.35 v=0.12 ch=0.48 tgt=0.20 ki=0.30 kdp=0.15 out=0.45 win=1` | PID 计算输出：偏差 e、速度项 v、综合量 ch、动态目标 tgt、积分 ki、融合项 kdp、最终输出 out、温度窗口标志 win |
| `[PID] epoch=123 Tbatt=350+comp+0.7(cpu)=Tinp357 Ttgt=353 Thot=450 dt=1.0周期` | PID 周期状态：原始电池温度 + CPU 补偿 → PID 输入温度、动态目标、热端温度、距上次重算的周期数 dt |
| `[PID] 冷值动态 …` | 冷值动态倍率重算诊断：取样冷值、拐点降幅、抽象值、三作用点加权后抽象值与最终倍率（字段含义与样例见 [冷值动态倍率](#冷值动态倍率逻辑2)节） |
| `PID 跳过重算（温度/补偿未变）` | （debug）温度窗口未变且 CPU 补偿未变，本轮复用上次 PID 状态 |
| `PID 整轮冻结（[last_ch]=0.15 ≤阈值0.2）` | （debug）触发跳过②：温度未变且上次 [ch] 低于稳态阈值，整轮冻结防抖（阈值 = `PID_CH_THRESHOLD` 默认 2 ÷ 10 = 0.2°C） |
| `过热钳制冷 180→120（削减量 40）` | 热端过温，制冷强度被钳到生效上限（配置上限 − 削减量） |
| `热端过温 49.0°C 削减制冷上限 190→140（削减量 50）` | 热端超阈值触发削减：生效上限从 190 就地压低到 140 |
| `热端回落 44.0°C 恢复制冷上限 140→145（恢复量 5）` | 热端回落到阈值内，生效上限逐级上爬（本周期 +5） |
| `App 不存在，等待连接...`（末尾空行） | status 文件超时（模块停止心跳），进程失联 |
| `BLE 已断开，等待连接...`（末尾空行） | BLE 连接断开但进程仍存活 |
| `脚本启动成功` | 守护程序启动完成；之后延迟 30s 才开始工作（等待系统/蓝牙就绪） |

## 原生配置界面（APK 内）

配置界面在 APK 里（原生 Android + androidx Material），**Magisk 的 KSU 模块网页入口已随路线 A 删除**。三个页签：**状态**、**配置 · 曲线**、**日志**（标题栏右侧设置按钮另开界面参数设置页）。

界面与 daemon 之间**没有直连通道**，各自只碰文件：

| 方向 | 介质 | 说明 |
|---|---|---|
| 界面 → daemon | 私有目录的 `profile.conf` | 界面经 `ConfigStore` 直读直写（同 uid，普通 File IO，**不需要 root**）。写必须**原子替换**（同目录 `.tmp` + fsync + `renameTo`），因 C 端是 5s `mtime` 轮询、半截文件会被读到；改单键**逐字节保留**注释/空行/行序，键不存在则追加。`stat` 的 mtime 只有秒级精度，故界面防抖需 ≥1s |
| daemon → 界面 | 私有目录的 `tempctrl_webui.data` | C 每 1s 追加一行，界面每秒读一次 |
| daemon → 钩子 | `/data/local/tmp/tempctrl_uiprefs` | 界面与钩子分属两个进程、不共享内存，`UI_BACK_HIDE` 由 daemon 转写进该文件供钩子读取。**方向与 status 文件相反**，是本工程第二条跨进程通道；路径/内容编码/写入与读取方/读取失败默认值见 [lsp模块 README](../README.md)「界面开关文件协议」（唯一规范处） |
| 部署 / 拉起 / 停止 | su | 经 `RootShell`（零依赖 `Runtime.exec`）。部署完成判定看「二进制与脚本的 md5 是否与 APK 内 assets 一致」；部署只到"盘上就位"为止、**不重启进程**，拉起由界面接在部署结果上屏之后自动再走一次（独立的一段：自己的忙态文案、操作记录与进度条），部署判定失败则不拉。**拉起先看 `service.d` 看门狗在不在**：在则只停/起 daemon，不在（例如刚点过「停止daemon」）则先把看门狗拉起来、由它停旧起新。**「停止daemon」先停看门狗再停 daemon**（只杀进程，不删文件）；卸载用同一段停止序列，停稳之后才删文件 |
| 卸载 → 自清 | 宿主 APK 的父数据目录 + `pm path`（二级复核，节流） | 宿主 APK 被卸载后 daemon 自行清掉落盘产物并停止运行。**两级判据必须都过**：一级判「父数据目录 `/data/data/<包名>` 不存在」（取**父目录**而非 `files/`——app「清除数据」只清 contents、父目录由系统保留，故可抗误判），命中后二级走 `pm path` 复核（**60s 节流**，`fork`+`pm` 的开销不许进每轮热路径），再叠**连续 2 次一级命中**才判真（滤掉重装中、挂载抖动等瞬态）。落点分工：**C 端为主**（判据挂在「等设备就绪」等待循环与 5s 控制块两处，故无 BLE 时不漏检），**`service.d` 脚本看门狗兜底**（判据同构 + 隔 5s 复核一次，**能删自己**，最坏 300s 一轮） |

> **卸载自清的清理清单有三份实现，必须同源同步**（本轮发现的漂移风险）：C 端 `cleanup_artifacts_on_uninstall()`、`service.d` 脚本的 `cleanup_all()`、`Deployer.uninstallScript()` 各存一份，改一处须同步另两处（`Deployer` 那份本轮已补齐 `tempctrl_uiprefs`）。清单固定为：`/data/local/tmp` 下的二进制与运行文件（status 双文件、`tempctrl_uiprefs`、`tempctrl_service.log`）、两个候选路径的 `service.d` 脚本（`/data/adb/service.d/` 与 `/data/adb/ksu/service.d/`）、`/cache/tempctrl.log`。**不显式删 `profile.conf`**：系统卸载会连带删掉整个 `/data/data/<包名>`，与「卸载部署 ≠ 删配置」的既有口径一致。**已知局限**：`tempctrl_b6x/b7x.status` 只要飞智 app 进程还活着就被其 LSPosed 钩子每秒重写，unlink 后可能被立刻重建、删不干净（须重启 app 或设备才彻底消失）；脚本那一侧全程静默——那一路的任何写盘都会把刚删掉的日志文件重新建出来。

**表单由定义动态生成**：读 `assets/params.json`（键数见 `参数定义/check_params.py` 的 `EXPECTED_KEY_COUNT`）拿类型、label、范围、默认值、分组与 `requires` 前置键，不手抄任何参数元数据。`multi` 组内标了 `bool` 的子字段（`fields[].bool`）渲成开关；每个参数独占一行（同一参数下的多个值仍并排、放不下在该行内换行）；分组默认收起，组头即该组的总开关，关闭时置灰 + 组头一处「未生效」标记。界面参数组（`webui` 组，`UI_*` 键）不在配置页，在标题栏设置按钮进入的 `SettingsActivity`。

### 参数落点

各部署产物与运行文件（`profile.conf`、日志、曲线数据、锁、status 双文件、`tempctrl_last_dev`、二进制与 `service.d` 脚本）的落点与写入方见 [lsp模块 README](../README.md)「文件落点」（唯一规范处）。

> **已知代价**：app「清除数据」会把私有目录里的配置、日志、曲线数据与锁文件一并删掉，而 `service.d` 脚本与 `/data/local/tmp/tempctrl` 不受影响 → 会出现"守护进程还在跑、配置已空"。靠部署脚本的开机自检 + C 端回退默认值兜底；锁文件被删的那一次锁会失效（新旧实例锁到不同 inode）。这是私有目录落点最大的代价。

### 状态页数据源（C 每 1s 写数据文件）

daemon 每 1s 采集电池/CPU/散热器回传/目标制冷：**同一份采集同时写入内存缓存（`cached_batt_raw`/`cached_cpu_now`/`cooler_*`）**，5s 控制块直接读缓存、不再重复读 sysfs/状态文件（读取频率从每 5s 多次降到每秒一次，截断竞争窗口减半，采集失败保留上次成功值抗抖）；采集结果追加到私有目录的 `tempctrl_webui.data`（**滚动保留 720 行** = 曲线最大窗口秒数 720s），界面每秒只读这一个文件（直读私有目录，不再经 root shell）。

行格式：`epoch,电池(0.1°C),CPU(0.1°C),热端(0.1°C),冷端(0.1°C),实际转速,实际制冷,目标制冷`（未就绪为 -1）

### 曲线

- 每秒读数据文件更新一次；窗口时长按钮 **120/180/240/360/480/720s**，默认 **360s**（档位数组与默认档位取自 `params.json` 的 `chart.windowOptionsSec` / `windowDefaultSec`），只显示最近 N 行
- **双纵轴**：左轴 **℃/百rpm**（温度 ℃ 一位小数 + 风扇转速 ÷100 共轴，标题收在刻度数字块上——左标题左沿与左侧数字左沿平齐、右标题右沿与右侧数字右沿平齐，横向可越进曲线区内，不挤压曲线空间；绘图区左右内边距按该侧最宽的那条数字现算，不留固定空白），右轴 **制冷**（制冷强度**下限恒为 1**＝C 端 `COLD_MIN`；**上限浮动**＝当前可见窗口内 `coldReal` 最高值，夹进 `[COLD_RPM_MAP` 第一值（映射起始强度，默认 40），`PID_COLD_RANGE` 第二值（B6X 制冷上限，默认 190）`]`——两值均在总开关 PERF_ENABLED=1 开启时取配置实际值，否则用默认；窗口口径与左轴同一套，无有效数据时上限回落制冷上限）。**整图只保留一套横线，位置由左轴刻度决定**：右轴不再自算刻度、不再单独画线，只在每条左轴横线的高度上标一个制冷强度整数（= 该高度线性映射进 `[1, 当前上限]` 后四舍五入）。左轴全部系列关闭时无横线可依，右侧不标数字。左轴取值排除风扇转速低于 `UI_RPM_AXIS_MIN`（默认 3000）的样本，该段画到图外；过滤后左轴无有效数据时退回不过滤
- **曲线头部数值标签取实际物理值**：温度 ℃ 一位小数；风扇转速显示**实际 rpm**（如 `3500rpm`），纵轴单位文本仍为「百rpm」（纵轴数值仍是 ÷100）
- **数值标签以背景色描边（halo）**：先用背景色描边再填充，故曲线穿过字形时不会与同色标签糊在一起。描边色 = 卡片底色 `app_surface_container`（halo 与圆点外圈共用它）；**描边字号必须与标签同字号**——曾漏设，`new Paint()` 的 textSize 默认为 0，导致描边根本画不出来
- **曲线头部标记**：只有**风扇转速**系列的头部圆点允许向下越出绘图区、落到「接缝」（实时数值栏顶边）处、被展示栏盖住下半——表示转速已降出图表范围；其余曲线（含右轴制冷）一律钳制在作图区下沿
- **标签摆放规则**（已与原 WebUI 末版逐项对齐）：端点取每条系列**最后一个有效样本**；端点 y 钳在 `[padT, rpm ? seamY : padT+H]`；标签与端点水平间距 6dp，贴近右沿时翻到左侧、左界 2dp；按 y 距离小于合并阈值（配置键 `UI_LABEL_MERGE_PX`，默认 9px）**聚类成一行**，行内用 `' / '` 分隔、分隔符用 `#888888`；**选边判据** = 比较「簇顶端到绘图区上沿」与「绘图区下沿到簇底端」，**空间更大的一侧**放标签，上方空间不足时落到下方一行高
- **标签摆放相对 WebUI 的两处有意偏离**：① Java 额外多一条「画布高 − descent」的下沿钳制（本 app 画布下沿即视觉下沿、其下紧贴 8dp 拖柄触控带，只钳一条会让最低那行文字被裁）；② Java 的 `fSeamY` 落在绘图区下沿**之上**，所以 WebUI 那条「簇最低点越界 → 改放上方」的分支在 Java 恒不成立，贴底的簇由「上方空间更大」判定得到同样结果
- **色号**：六个系列色 = 原 WebUI 的 Material 500（batt `#F44336` / cool `#4CAF50` / rpm `#9C27B0` / hot `#E91E63` / cold `#2196F3` / cpu `#FF9800`），**明暗两套资源同值**；刻度 / 轴标题 / 合并分隔符 = `#888888`（明暗同值）。网格与卡片底色**不走** `chart_*`，用全主题共用的 `app_outline_variant` / `app_surface_container`（与 WebUI 的白底 + 淡灰网格不同，属有意偏离，避免连带其他页面）。图例色在切明暗时由 `ChartFragment.onResume` 重取（此前只在建视图时取一次、切换不跟随）
- **热端与电池曲线滤波**（两条曲线**共用**同一对参数，均由 `UI_CURVE_FILTER` 配置）：对每段连续有效样本做**零相位双向平滑**（前向一遍 EMA + 反向一遍同一 EMA，等价 filtfilt，每遍权重 α 默认 0.15）——阶跃响应为对称 S 形、稳态等于原始值，无滞后、无稳态偏置；反向一遍以段末前向值为初值做边界延拓，故**段内为完整零相位**，段末沿用前向值、不引入跳变。平滑后再做一遍**最小步长格点吸附**（默认步长 0.05，偏差 ≥ **0.9×最小步长** 才吸附到最近整格，一次可跨多格），消灭平滑后残留的亚格点微挪
- **滤波关闭语义**（`UI_CURVE_FILTER` 双值均 ×100）：每遍权重 α = **0 或 100**（100=1.0 恒等变换）都视为**关闭滤波**；最小步长 = **0** 视为**关闭格点吸附**。两个子步骤**各自独立开关**（可只关其中一个）
- **「平滑」的口径**：格点吸附使输出只取最小步长的整数倍，故曲线必为阶梯、导数不连续——平滑只在**包络**意义上成立（台阶密度沿对称 S 形分布：起段稀、中段密、末段又稀），不是逐点连续平滑
- **实时数值栏显示原始值**：电池/热端的实时数值栏取 C 端**原始读数**，与曲线（滤波值）**刻意不同步**——该栏语义是「C 端当前读数」而非「曲线上的点」；且零相位滤波在阶跃处会「先动」，属算法固有现象
- **分段处理**：热端、电池**各自**按自己的连续有效样本**独立分段**（各自无效处断档、各段独立平滑），处理顺序固定、与显示窗口无关，同一份数据每次得到同一曲线
- **断联空白**：C 端断联时不写曲线数据行，相邻采样时间差 > `UI_GAP_SEC` **第一值**（默认 2s）视为一次断联：曲线在该处断开，并按**真实断开时长**插入等比空白（空白宽度 = 正常绘制该秒数的宽度），封顶 `UI_GAP_SEC` **第二值**（默认 15s）——短断联窄空白、长断联封顶，直观反映断联长短
- 系列开关（电池/制冷/风扇/热端/冷端/CPU℃），**默认除 CPU℃ 外全显示**；热端在冷端之前（实时数值列顺序由实时行独立维护，不受系列顺序影响）
- 实时数值列（**WebUI 规格**：电池 · CPU · 制冷 · 风扇 · 冷端 · 热端，不含目标制冷）：**原生界面不设独立数值栏**，当前值以曲线头部标注呈现；`ChartView` 里为它预留的接缝几何量（`fSeamY`）只用于"转速圆点允许下越界"这一处
- **时间窗口 + 图例分两行自然尺寸排布**（第一行档位按钮、第二行图例网格），**不缩放、不裁切**——原 WebUI 的"打包成子窗口 + 超宽时整体等比缩放"已废除（它会把图例压成窄条并裁掉右端）。**实时数值栏**（WebUI 规格，原生未实现）：单行完整显示、不可滑动，文本宽度用隐藏探针测量（如实反映等宽数字定宽），超宽字号缩小（**0.1px 步进**，最小 7px，**4% 缓冲余量**），每帧重算但同字符数宽度一致不抖动

## 部署与 Root 调用

### 为什么守护进程不能由 APK 直接拉起（三条硬阻断）

APK 侧有界面、也有 root 能力，但**不能自己把 daemon 拉成常驻进程**：

1. **stopped state** — 全新安装未打开过、或被用户强停过的 app 收不到 `BOOT_COMPLETED`（Android 3.1 起广播默认带 `FLAG_EXCLUDE_STOPPED_PACKAGES`，Android 15 进一步收紧）
2. **cgroup 连带杀** — 从 app 里 `su` 起的常驻进程仍留在该 app 的 cgroup 内，app 一死就一起被杀；`nohup`/`setsid` 无效（只改父子/会话关系）
3. **LSPosed 钩子域** — 钩子以宿主 app 的 `untrusted_app` 域与 uid 运行，读不了 thermal sysfs、用不了 `am`/`dumpsys`/`pm`

> 若硬走前台服务路线：Android 15+ 的 `BOOT_COMPLETED` FGS 类型白名单只有 location / connectedDevice / remoteMessaging / health / systemExempted / **specialUse**，且启动调用**必须写在 `BroadcastReceiver.onReceive()` 里**（放 `Application.onCreate` 在 Android 16 实测被拒）。

因此拉起的实际做法是 **`service.d` 脚本开机先起 + app 内手动拉起入口**，两处都直接执行启动命令，由 C 端单实例锁保证幂等（见 [文件落点](../README.md#文件落点) 里的 `tempctrl.lock`）。

### root 调用（照 Scene，出处 `../scene相关/decompiled`）

**照搬**：

1. 零依赖，只用 `Runtime.getRuntime().exec()`（Scene 全仓库无 libsu、无 Shizuku Java API）
2. su 命令行按表选：先 `su -v` 嗅探 root 类型，再按表定——SDK<30 → `su`；SDK≥30 时 **MAGISK → `su`**、KernelSU → `su -M`、其余 → `magisk su -mm`。（出处 `a/a70.java` 的 `f()`；类型串由 `d()` 产出，取值 `MAGISK` / `KernelSU` / `apd` / `mqsas` / `xsu`，**未识别时 Scene 兜底为 KernelSU**。小米专用的 `mqsas` / `xsu` 未照搬。）结果持久化、用户可手动切换；失败时给「当前模式 / SU CMD / 当前用户 / 日志」诊断对话框
3. 资源落盘与授权**全用 Framework 的 File API**（`setExecutable(true, false)` 并沿父目录链逐级向上），不调外部 `chmod` 二进制
4. **判活看通道连通性，不看进程**，配退避重连
5. 部署时跑一遍省电白名单批处理（`dumpsys deviceidle whitelist +`、`appops set RUN_IN_BACKGROUND allow`、`am set-standby-bucket active`、`am unfreeze --sticky`），对象是**已安装的散热器控制 app**（不是界面自身——界面 manifest 里没有任何 service/receiver/provider，没有后台职责）；`renice -n -20` 与白名单无关，由开机自启脚本对守护进程自己做

**不照搬**：rish/Shizuku 整条通路（Scene v9.3.1 里它的启动函数全库无调用点，是残留）；签名派生密钥 + AES + 长度前缀的 socket 协议（单 app 自用多余，换签名即全废）；Scene 那个"存了 `Process` 字段却只用一次"的半常驻 shell（无结束标记、无超时、无重连——本项目做成带结束标记 + 读超时 + 退出码回传的真常驻）；UPX 加壳。

## 启动流程

1. 设定默认日志路径（根据二进制文件名）
2. 加载配置（`--config` 参数 > 自动检测 > 全部默认值。`PERF_ENABLED=0` 时仅 `DEBUG_ENABLED=1` 的调试子项生效，其余全部使用代码默认值；`PERF_ENABLED=1` 正常加载全部）
3. 创建 status 文件。读 LSP 回传实际制冷对齐初始制冷值（`active_cold_eff_*` 初始化；不可用回退代码默认 `pid_cold_min`）
4. 输出「脚本启动成功」后**立即**进入等待设备阶段（无启动延时；历史上曾有固定 30 秒延时，已删除，详见 [CHANGELOG](../../CHANGELOG.md)）
5. 等待模块就绪 + BLE 已连（status 文件读到 `BLE≠0`）；等待期间无散热器 app 存活时自动拉起上次使用的 app（`APP_LAUNCH_ENABLED`，按 `APP_LAUNCH_COOLDOWN` 冷却）
6. 进入工作模式后每 5 秒：连接检测 → `main_loop`（纯计算）→ 速率限制执行
   - 每轮循环开头通过双重检查检测 App 存活（status 文件 mtime + BLE≠0）
   - 断联时实际值保持不动（丢弃未执行变化量），进入等待复活子循环
   - 重连时实际制冷/转速以散热器实际回传为准初始化（不做档位匹配），由 `rate_limited_execute` 按正常限速逐步调节，抑制突变；重连后按 `RECONNECT_KEEP_CYCLES` 决定将 PID 状态保留还是完整重置（见 [主循环逻辑](#主循环逻辑)）

## 实测说明

### 智能温控模式的风扇转速限制非强制生效

经实测，**智能温控模式（mode=0）的风扇转速配置疑似并非强制生效**，经常会突破设定的上限很多，尤其是刚切换过去的时候。这会导致噪音突然变大，体验非常差。

**原因推测**：`setRunMode` 的 `windLevel` 参数在散热器固件中被解释为"建议上限"而非"硬上限"。散热器内部有独立的 PID 或逻辑控制算法，在刚切换模式或温差较大时，会以更高转速运行来快速达到目标温度，忽略应用层设定的风扇上限。

**解决方案**：全部改用**固定功率模式（mode=1）**，直接指定风扇转速和制冷片强度。daemon 下发均按固定功率模式指定实际制冷/风扇值，避免"建议上限被固件忽略"的问题。

## 注意事项

- **CPU 温度扫描范围** 通过 `CPU_ZONE` 配置（双值：起始 zone 结束 zone，默认 `0 99` 全扫），K60 机型推荐 `30 40`
- **温度传感器路径** `thermal_zone[N]` 是 Linux 通用接口，不同 SoC 的 zone 编号不同。首次真全量扫描无需手动配置（范围过大 0~99 约 1 秒），可通过 `CPU_ZONE` 缩小；后续周期重扫只在首次有效名单内、不再发现新 zone，保留数由 `CPU_ZONE_RESCAN` 第二值控制
- **去重逻辑**：`apply_gear_direct()` 以散热器实际回传为准——要播发值与散热器实际值一致视为已到位不下发（解决"日志已变化但实际未成功导致达不到最高/最低制冷"）；回传异常退化用 `last_*` 缓存对比。另含最小变化幅度：目标与制冷实际 `|差值|` ≤ `RATE_LIMIT_COLD` 第三值（最小变化幅度）时上升下降都不下发（距最高/最低 < 阈值×2 时失效）
- **am 广播可靠性**：`send_am_broadcast()` 用绝对路径 `/system/bin/am` 执行（不依赖 daemon PATH），并在 `waitpid` 后检查子进程退出码——`am` 未找到（127）或广播失败时 `write_log` 明确报错。排查"日志显示下发但散热器不动"时，先看日志里有没有 `am broadcast 失败` 行；开启 `DEBUG_ENABLED=1`+`DEBUG_EXEC=1` 可看到 `am broadcast 已发送` / `apply_gear_direct 跳过下发` 明细
- **`patch_tls.py`**：NDK 编译后按需执行，修复 PT_TLS 对齐；当前程序无 PT_TLS 段，脚本空操作并返回成功——只有真正的修补错误才返回非零（CI 直接失败）
- **`#include <stdarg.h>`**：`write_log()` 用了 `va_list`，NDK clang 下不是隐式包含的
- **KernelSU noexec**：`/data/adb` 下的模块目录挂载了 `noexec`，故二进制**不放在 `service.d` 目录**，而是由部署流程落到 `/data/local/tmp/tempctrl` 执行（`service.d` 里只放拉起脚本）
