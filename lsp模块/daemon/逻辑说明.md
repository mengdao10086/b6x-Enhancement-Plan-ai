## 配置文件系统 (profile.conf)

tempctrl 支持运行时配置文件，大部分关键阈值和参数均可外部修改，无需重新编译。

### 配置路径自动检测

1. **`--config` 参数**（最高优先级）：仅用于临时覆盖，正常部署不传
   ```shell
   tempctrl --config /自定义路径/profile.conf
   ```
2. **自动检测**：应用私有目录 `/data/data/com.example.waspwingtempctrl/files/profile.conf`
3. **默认值**：配置不存在时全部使用代码内默认值，并记一行日志（不再静默）

> 该路径由 C 端 `PRIVATE_DIR` 宏决定，必须与 `app/build.gradle.kts` 的 `applicationId`、`参数定义/params.def.json` 的 `LOG_FILE` 默认值**三处一致**；`python 参数定义/check_params.py` 会自动核对（宏改成跨行拼接时降级为 INFO，不假通过）。

### PERF_ENABLED / DEBUG_ENABLED / SYSFS_ENABLED 开关

配置层级：

```
PERF_ENABLED（性能总开关，默认=1）
  ├── =0：不加载性能参数（PID、速率限制、热端过温削减等），全部使用代码默认值
  └── =1：正常加载所有性能参数

DEBUG_ENABLED（调试总开关，独立于 PERF_ENABLED，默认=0）
  ├── =0：分区调试日志关闭
  └── =1：各 DEBUG_* 分区开关生效

SYSFS_ENABLED（sysfs 接口与外围，独立于 PERF_ENABLED，默认=0）
  ├── =0：不加载自定义 sysfs/日志路径，使用代码默认路径
  └── =1：加载 profile.conf 中的 BATT_*/CPU_*/LOG_* 路径与缩放配置
```

**运行中关闭开关的语义**：上表「使用代码默认值」是**运行期**语义——开关由 1 改为 0（或删掉该键），该层已加载的参数会在下一次热重载（5 秒内）**立即回落代码默认值**，等同该层配置不存在；**profile.conf 内容不动**，开关改回 1 后文件里的值立刻恢复生效。默认值表由 `params_generated.h` 的 `CFG_PERF_DEFAULTS` / `CFG_SYSFS_DEFAULTS` 生成（`参数定义/params.def.json` 单一来源，与上表「默认值」一致）：路径键走 `CFG_DEFAULT_*` 宏，`LOG_FILE` 走 `set_default_log_path()`（私有目录不可用时仍兜底 `/cache`）。层总开关自身不复位；热端削减量与其冷却计数一并清零，PID 运行态（积分、动态目标）不重置。

这对调试很有用——**设置 `PERF_ENABLED=0` 但 `DEBUG_ENABLED=1` 可关闭性能控制并保留调试输出**；sysfs 路径可独立于性能开关加载（`SYSFS_ENABLED=1`）。

### ⚠️ 常见坑

| 坑 | 说明 |
|----|------|
| **Termux 编译不可用** | Termux 的 `clang -static` 链接的是 Termux 的 libc，非 Android libc。编译出的二进制在真机上 PT_TLS 对齐错误，必须用 NDK 编译。**开发阶段在 Termux 编出来可以看语法错误，但不要拿去真机跑** |
| **配置路径** | 部署脚本（`assets/deploy/b6x-tempctrl.sh`，落 `/data/adb/service.d/`）**不传 `--config`**：daemon 自行按上文私有目录定位；`--config` 仅用于临时覆盖。**不复制的是 profile.conf**——二进制仍按 KSU noexec 约束复制到 `/data/local/tmp/tempctrl` 执行（见「注意事项」末条） |

### 配置格式

```
# 注释以 # 开头
KEY=VALUE

# 例：
BATT_BASELINE=350
PID_KI_RATE=20 30
```

不认识的 key 静默跳过；每个值有范围保护（`clamp`），非法值不会导致进程崩溃。

### 热重载

每轮 `main_loop()`（5 秒间隔）开头 `stat()` 检查配置文件的修改时间（mtime），变了就自动重读所有参数并记日志。**修改配置无需重启 daemon**。

**未加载成功时的自愈（2026-09-28 起）**：启动时探测不到 `profile.conf`（开机早期私有目录尚不可读）不再一锤定音——改记「未加载」并按 `CONFIG_RETRY_INTERVAL`=60s 周期重试探测与加载，成功时记「配置 延迟加载成功」，并补一次 `CPU_AFFINITY`（`main_loop` 那条另补 `update_active_limits()`）。自愈挂在**两个循环**上：等设备循环（只补亲和——那时还没有有效设备，故不刷设备上限）与 `main_loop` 步骤 0。故**一直没连设备也会补加载**；从目录可读起算，滞后上界 = 重试间隔 + 等设备循环的 `sleep(5)` = **65 秒**。已加载过立即短路，原 mtime 热重载路径一字未改。

**`CPU_AFFINITY` 的生效时机**（与其它键不同，要落到进程的 `sched_setaffinity` 与 cgroup cpuset 组上）：只在两处应用 —— `main()` 启动时（日志就绪后、等待设备循环之前）与上面这个热重载块（`load_config()` 之后）。取值是**一个输入位**，按首字符分派：首字符 `c`（只认小写）= 簇模式，`c` 后**每一位数字**是一个簇号（`c0` = 只用 0 号簇、`c123` = 簇 1/2/3 的并集）；否则按核号（单值 `0`、区间 `0-1`、列表 `0,2-3`，旧写法 `0 5` 仍按区间 0~5 解释）。因此：① 等待设备阶段改配置不会立即生效（该循环不查 mtime）；② 无 `profile.conf` 时没有可热重载的对象（文件稍后出现由上面那条自愈补上），但亲和仍按代码默认 `c0` 无条件生效（该键缺失、或 `SYSFS_ENABLED=0` 时同样按默认生效——配置值只有一个来源，不会被开关关掉）；③ 值非法（簇语法里含非数字、簇号超出本机簇数、核号区间反向或为负、空值以外的其它畸形串）或与本机 `/sys/devices/system/cpu/present` 的核集合交集为空时回落默认 `c0` 并记日志；④ 迁 cpuset 组失败时只设亲和，实际生效核一律以日志读回的 `Cpus_allowed_list` 为准（cpuset 的 cpus 是硬上限、组内只能收窄不能放宽，故顺序是先迁组、后设亲和；迁组与跳过迁组的判据都是「组 cpus ⊇ 目标核集合」；只写 `cgroup.procs` 迁自己，绝不改任何组的 `cpus`）。簇边界**从内核拓扑现算、不写死机型核数表**：含 cpu0 的簇是 `c0`，其余按各簇首核号升序依次编号；探测源依次为 `cpufreq/policy*/related_cpus`（每个 policy 一个频率域）→ `cpuN/cpu_capacity` 等值分组 → `cpuN/topology/physical_package_id` 等值分组。每次应用都把「探测源 + 每个簇的核集合 + 本次请求集合 + 读回值」写进日志，供真机核对。

**`CPU_AFFINITY` 的已知限制**：① cpuset 挂载点硬编码 `/dev/cpuset`（依真机 mountinfo 取证：`/dev/cpuset rw,cpuset,noprefix`），不在运行期探测——挂载布局不同的设备只会走到「只设亲和」的降级路径；② 内核侧的核集合文本（`present`、cpuset 的 `cpus`、`related_cpus`）按**完整 cpulist** 解析（`0-3,7` 不再被截断成 `0-3`），并额外容忍空白分隔与含 `a`~`f` 的十六进制位掩码；**纯数字的掩码与核号无法区分**，故只有含 `a`~`f` 的 token 才按掩码读，误读交给下一条兜住；③ 每级探测源都要求「各簇两两不相交、并集恰好等于本机 `present`」，不满足即判该源不可信并退到下一级；全部不可用时按**单簇**降级（`c0` = 全部核，等于不限制）并记日志——探测不出就不管，不会把进程限到错误的核上；④ 簇划分**未在真机验证**（本机无设备），实际结果依赖上面那条日志核对；⑤ 亲和只在启动与热重载两处应用，迁组后若被 ROM 改回**不会低频重申**；⑥ 该键只在 `SYSFS_ENABLED=1` 时按键值取用，缺键或该组未启用时按默认 `c0` 生效；⑦ **值内不能带行内注释**——`config_parse_line()` 只跳过 `#` 开头的整行、不剥离行内注释，故 `CPU_AFFINITY=0 5  # 大核` 会整串判非法并回落默认 `c0`（旧实现的 `sscanf("%d %d")` 会忽略尾串，这是本次改成文本键后的一处行为回归）。生成器与界面都把注释写在单独一行，只有手写配置才会遇到。

> **默认值核对的一处硬约束**：`affinity_spec` 的静态初值**必须写字面量** `"c0"`（不能写宏）——默认值审计按字面量逐位比对它与定义 `default`，写成宏会被当成「C 内未找到初值」而**跳过核对**（洞会变哑）。运行期的「回落默认」另用生成头宏 `CFG_DEFAULT_CPU_AFFINITY`（由定义 `default`/`factory` 派生），故改默认值时只须同步这两处（本行字面量 + 定义）。

## 温度读取

- **电池温度**：`/sys/class/power_supply/battery/temp`
  - 原生 0.1°C 精度，如 350 = 35.0°C

- **CPU 温度**：`/sys/class/thermal/thermal_zone[N]/temp`
  - 原始值 m°C，÷100 转 0.1°C，如 75321 → 753 (=75.3°C)
  - 首次调用时在 `CPU_ZONE` 指定的范围内扫描，记录能读到有效值的 zone
  - 后续只扫描已记录的 zone，取最高值
  - 一阶低通滤波平滑（系数由 `CPU_FILTER_ALPHA` 配置，默认 α=0.25）

### 温度变化检测

- **值比较 + mtime 双信号**：以值比较为主（部分内核 sysfs 温度文件 mtime 更新不可靠，会导致温度实际在变却被判"未更新"而大量跳过）；**同时检测文件 mtime**——mtime 更新时（即使值相同）也视为温度数据刷新，触发 PID 重算以保持积分累积与 dt 新鲜。mtime 恒不变的内核自动退化为纯值比较。
- **1s 窗口累积**：5s 控制周期的跳过判定不看"当前采样值 vs 上次控制值"，而是看**自上次控制以来 1s 层是否检测到过值/mtime 变化**（累积标志 `batt_changed_since_ctrl`，控制周期开始时快照 `batt_window_changed` 并清零）。温度在窗口内变过又回到原位也不会漏判。
- **两条跳过（pid_cycle 重算判定）**：仅**温度窗口变化** 或 **CPU 补偿变化**（`total_comp_10 != pid_last_comp_10`）才触发重算；两者均未变则本轮冻结 `acc`/`kdp`/`target`/`last_ch` 等控制状态。两条跳过：
  1. **温度未变（仅补偿变化触发）** → `kdp` 沿用上次值（`batt_window_changed=0` 时 `pid_kdp` 不更新），避免补偿突变带动 KDP 跳变；
  2. **温度未变且上次 `|ch| ≤ PID_CH_THRESHOLD`** → 整轮冻结（`acc`/`kdp`/`target`/`last_ch` 一律不动），仅推进补偿书签 `pid_last_comp_10`（防补偿反复变化反复触发导致死锁）。
- **电池温度输入滤波（改动2：加回）**：电池温度进 PID `ch` 前先经 EMA 滤波（`pid_batt_filtered`），**仅温度更新时（值/mtime 变化，即 `batt_window_changed`）才滤波并输出**；动态 α = `0.2 + 0.05 × 间隔周期数`（间隔 = 距上次温度更新的 5s 控制周期，钳 0~16 → α 0.2~1.0，时间越长新值权重越高）。**停机（`batt_window_changed=0`）且滤波未收敛**（`pid_batt_filtered != batt_raw`）时，首个周期**优先恢复原始值强制重算**（改动2优先于此节第②条整轮冻结），`pid_batt_filtered = batt_raw`（= 未更新的电池温度），进 PID 用原始电池 + 新 CPU 滤波补偿 → "半新 ch"；snap 一次后 `pid_batt_filtered==batt_raw` 滤波态消失，回正常冻结。`pid_batt_filtered` 在 `pid_reset_core`（切模式/重连）重置为 -1 直取初值。

## 控制下发模式

本实现**仅保留 PID 连续无级调节**。Gear 档位表（`gear_cycle` / `battery_control` / `gear_from_current` /
反补 / 趋势豁免 / 紧急干预 等）与旧 `CTRL_MODE` 切换开关已随 Gear 一并删除，下发统一走 `apply_gear_direct()`。

> **制冷上限口径**：194 = SDK/硬件上限（散热器固件最大制冷）；190 = 温控默认下发上限（`PID_COLD_RANGE` 可调）。

控制指令通过 `am broadcast` 发送（Action 由 `active_device` 决定），广播 Action、完整 7 参数格式与示例**协议详见 [lsp模块 README](../README.md)**（唯一规范处）。

- **智能模式 (mode=0)**：设目标温度和风扇上限，散热器自行调节制冷
- **固定功率 (mode=1)**：直接指定风扇转速和制冷片强度（本实现 PID 下发使用 mode=1）

风扇转速不直接由 PID 输出决定，而是每周期由 `compute_fan_target()` 基于**限速后的实际制冷强度**（`actual_cold`）
+ 散热器热端温度独立计算（冷端指数映射 + 热端线性映射自加权合并），与 PID 输出解耦——见「制冷→RPM 映射引擎」节。

## PID 控制模式

本实现**仅 PID 单模式**（Gear 已删除），采用**单累积器**结构：`OUTPUT = clamp(acc + kdp, 0, 1)`。
`acc` 为积分累积（`pid_ki`），`kdp` 为融合 P+D 项（`pid_kdp`，无记忆）。`error` 只取纯电池误差；
CPU 补偿与速度项同地位进入 `ch`，再进入积分与 KDP。

### 控制流

```
main_loop()（纯计算，不下发）:
  0. 温度窗口快照：batt_window_changed = batt_changed_since_ctrl；清零使开启新窗口
  1. 热重载（共享）：stat() 检测 profile.conf mtime，变了重读并 update_active_limits()
  2. update_hot_derate()：热端过温 → 制冷削减（本周期即生效）
  3. update_active_cold_range()：当前有效制冷范围（供下发/去重/映射统一使用）
  4. pid_cycle()：CPU 补偿 → 两条跳过判定 → pid_compute() → 映射制冷

pid_cycle()（每 5s）:
  1. cpu 温度读入 → update_cpu_filtered()（CPU_FILTER_ALPHA EMA 滤波）
  2. cpu_comp = cpu_comp_now(batt_raw)：CPU 补偿（EMA 平滑，门控滞回，始终生效）
  3. 重算判定：batt_window_changed || total_comp_10 != pid_last_comp_10
     ── 两条跳过（见「温度变化检测」节）：①温度未变→kdp 沿用 ②|last_ch|≤阈值→整轮冻结
  4. dt = (now − pid_last_change_time)/5，钳位 0.6~6（1 = 5s）
  5. pid_compute(batt_raw, dt, cpu_comp, batt_window_changed) → 归一化输出 0~1
  6. 映射：pid_align_cold = clamp(pid_cold_min + (int)(out×range), pid_cold_min, active_cold_eff_max)

rate_limited_execute()（执行段）:
  → rate_limit_cold(pid_align_cold)：限速制冷（actual_cold；每周期最大变化量限制，取代原 PID_OUT_FILTER 的输出平滑）
  → compute_fan_target()：独立风扇目标（冷端指数 + 热端线性加权，不跟 PID 输出）
  → rate_limit_fan：限速风扇
  → apply_gear_direct(1, 5, send_rpm, actual_cold, 0)：纯下发（去重/日志/广播）
```

### 单累积器公式

```
error   = (batt_raw − BATT_BASELINE) / 10             # 纯电池，单位 °C（batt_raw 为 0.1°C）
v       = (error − pid_last_error) / dt                # 速度（°C/周期）；首算无常值历史 v=0
L,q     = PID_SPEED 第二值/100, PID_SPEED 第三值/100         # 速度非线性：阈值 L（°C/周期）与强度 q
v       = |v|≥L ? v : sign(v)·|v|·s^q                  # 映射：t=|v|/L、s=t²(3−2t)；保号、|v| 不增、v=±L 连续
sc      = PID_SPEED 第一值 / 10                             # 100=速度×10，0=关闭
ch      = error + v×sc + cpu_comp                      # 用于积分
ch_kdp  = error + v×sc×0.33 + cpu_comp                 # 用于 KDP（速度按 0.33 衰减）

raw_target = clamp(error×PID_TARGET 目标系数/1000, ±PID_TARGET 第三值/10)   # 动态目标（默认 ±1.5°C 界）
pid_target_f += α_dir × (raw_target − pid_target_f)   # 方向性 EMA：PID_TARGET_DIR 开关=1 时，远离基线用"远离alpha"/回归基线用"回归alpha"；开关=0 时 α=PID_TARGET 平滑%/100

integrand = ch − pid_target_f                          # 被积项，符号决定用哪个速率
ki_rate   = (integrand ≥ 0) ? PID_KI_RATE 升速率/1000 : PID_KI_RATE 降速率/1000
ki_rate  *= KI 削减倍率 升/降（见下）                  # 升降各自乘算，1.0 = 不削
pid_ki   += ki_rate × integrand                        # acc 累积，不乘 dt
budget  = max(0, 1 − pid_kdp)                          # 预算钳制（防 acc+kdp 超 1 被末端硬截断）
pid_ki  = clamp(pid_ki, 0, budget)

pid_kdp = PID_KDP/1000 × ch_kdp × (PID_CUT 的 KDP倍率/100)   # 无记忆；温度未变（batt_window_changed=0）沿用上次；KDP倍率默认 100=不削
out     = clamp(pid_ki + pid_kdp, 0, 1)
```

### PID 分段倍率表

只有温度窗口有更新（`batt_window_changed=1`）的周期才重算；取样值 = **上次 PID 重算**算出的目标冷值 `pid_align_cold`，两次重算之间沿用同一组倍率。倍率口径 ×100（100 = 不削、0 = 完全压死），作用于 KDP 融合项与 KI 升/降速率。

```
每个簇独立求值（簇 = PID_CUT_1 / PID_CUT_2 … 的每一行；行值 = 重复四元组「冷值,KDP倍率,升倍率,降倍率」）
  1) 簇内点按冷值升序；同一冷值只保留先出现者
  2) 折线 L(x)：相邻点线性插值；x < 最小冷值取首点值、x > 最大冷值取末点值（两端平推）
     三轴（KDP/升/降）各自独立按折线求值，**无滤波**
  3) 该簇输出 (L_kdp(cold), L_升(cold), L_降(cold))
所有簇逐轴取最小（倍率更小 = 削减更大）；无任何有效簇 → 三轴均返回 100
```

- **单位与默认值**：`PID_CUT_1` 默认 `1,100,100,50,40,100,100,100,100,100,70,80,190,100,50,65`（一个簇、四个点：冷值 1 / 40 / 100 / 190）。冷值 0~255、三倍率 0~200（均 ×100）。
- **作用点**：KDP 倍率乘进 `pid_kdp`（融合 P+D 项）；升倍率乘进 KI 升速率、降倍率乘进 KI 降速率（即上面的 `ki_rate`）。
- **键名与容错**：`PID_CUT_1` / `PID_CUT_2` …（簇号从 1 起、连续）；某行值个数非 4 的整数倍或簇号非法时**整行忽略**（保持该簇上次值）；排序与同冷值取舍在求值内部做，配置乱序不拦。层关闭（`PERF_ENABLED=0`）或启动时回落默认表。
- **旧键迁移**：旧键 `KI_CUT_<簇号>`（三元组、无 KDP 倍率）仍被识别——每点补 KDP 倍率 = 100（不削）后按四元组口径装载；并触发**一次性迁移写回**，把配置里的旧行就地改名为 `PID_CUT_<簇号>`（四元组）、删除已废弃的 `KI_CUT_SMOOTH` 行。写回失败则保留原文件、继续按读兼容工作（行为不丢）。
- **诊断日志**（`DEBUG_PID=1`，每重算周期一行）：`[PID] PID削减 冷值=170 KDP=100.0 升=54.0 降=62.0 簇=2`（取样冷值 / KDP倍率 / 升倍率 / 降倍率 / 参与求值的簇数）。

> **已删除**：动态 KI 抑制机制（窗口散布评估器、三个配置键 `PID_KI_DYN_T` / `PID_KI_DYN_GATE` / `PID_KI_DYN_WIN`、结构体 `ki_dyn_cfg` 及其全部实现）——积分速率不再按窗口散布削减，改由本节 PID 分段倍率表调制。原「冷值动态倍率」四键（`PID_COLD_DYN_IN` / `_OUT` / `_W` / `_MAP`）连同 `cold_dyn_*` 实现也已被 `KI_CUT` / `KI_CUT_SMOOTH` 取代；本轮再删除 `KI_CUT_SMOOTH`（平滑系数）并停用滤波——求值为纯折线（「平坦段过冲」问题随之消失），`KI_CUT` 更名 `PID_CUT` 并扩为四元组（增 KDP 倍率）。

- **error 纯电池**：不含 CPU 补偿；CPU 补偿（`cpu_comp`）与速度项同地位进 `ch`（用于积分）。KDP 用的 `ch_kdp` 中速度项按 0.33 衰减（≈1/3），CPU 补偿不衰减。
- **速度 v**：以 `dt`（5s 周期数）归一化，乘 `PID_SPEED` 第一值/10 系数，不乘 dt。计算后先做**非线性映射**：幅度达到阈值 `L`（`PID_SPEED` 第二值/100，°C/周期）时**严格恒等**（1:1、无恒定偏置），低于 `L` 时按 `t²(3−2t)` 平滑阶跃取 `q` 次幂降权（`q` = `PID_SPEED` 第三值/100，`q=0` 即完全线性）。映射保号（奇函数）、处处 `|输出| ≤ |v|`、单调不减、在 `±L` 处连续；差分得到的 v 与回溯注入的 v **汇聚到同一处映射、各恰好施加一次**，映射后的同一个 v 供 `ch` 与 `ch_kdp` 共用。
- **动态目标 `pid_target_f`**：`raw_target` 随时间 EMA 平滑，使积分逼近"误差×目标系数"包络，防静态过冲。
- **KDP 无记忆靠预算**：`pid_kdp` 每周期重算（温度未变时沿用），`acc` 钳到 `1−kdp`，避免 `acc+kdp` 超 1 被末端硬截断（抗 windup）。
- **两条跳过**：见「温度变化检测」节；跳过时控制状态（`acc`/`kdp`/`target`/`last_ch`）不动，仅推进补偿书签。

### PID 参数配置

当前 PID 键：`PID_KDP` / `PID_SPEED` / `PID_KI_RATE` / `PID_TARGET` / `PID_TARGET_DIR` / `PID_CH_THRESHOLD` / `PID_COLD_RANGE` / `PID_CPU_COMP` / `PID_SPEED_RECALL` / `PID_CUT`。多值键（`PID_SPEED` / `PID_KI_RATE` / `PID_TARGET` / `PID_TARGET_DIR` / `PID_COLD_RANGE` / `PID_CPU_COMP` / `PID_SPEED_RECALL`）走 `parse_pid_cfg` 分段；`PID_CUT` 是表键（`PID_CUT_<簇号>` 按行前缀在 `parse_pid_cfg` 内解析，行数可变、逐字段边界取自生成头），旧键 `KI_CUT_<簇号>` 走 `parse_legacy_pidcut_cfg` 兼容并触发一次性迁移写回；单值键（`PID_KDP` / `PID_CH_THRESHOLD`）走 `INT_CFG_KEYS` 表驱动。`PID_GAIN`（原增益组合）已拆分为 `PID_KDP` / `PID_KI_RATE` / `PID_SPEED`；`PID_OUT_FILTER`（输出端自适应滤波）已删除——输出平滑改由 `RATE_LIMIT_COLD` 每周期限速承担；「冷值动态倍率」四键（`PID_COLD_DYN_*`）已删除，改由 `PID_CUT` 承担；`KI_CUT_SMOOTH`（平滑系数）已删除，求值不再滤波。全部通过配置热重载，无需重启。

### CPU 补偿（PID_CPU_COMP）

`comp = clamp(cpu_filtered_temp − batt_raw − 偏移, 0) ÷ divisor`，按补偿专属滤波系数 EMA 平滑（独立于
`CPU_FILTER_ALPHA`，首次上次值用 0 从 0 爬升）。门控滞回：`raw>0` 进入补偿，条件消失后平滑值继续向 0
收敛归零才退出（不瞬间跳变）。始终生效，与 PID 单累积器一同作用于 `ch`。

### 制冷→RPM 映射引擎

PID 模式使用（本实现仅 PID）：

| 函数 | 映射方式 | 用途 |
|------|---------|------|
| `rpm_from_hot_end()` | 输入 EMA 平滑 + 双向滞回线性映射 | 热端温度 → RPM（需求侧：越高越迫切），**输入先经 `MAP_INPUT_SMOOTH_ALPHA` EMA 平滑**（滞回基于平滑值），降温滞回 +1°C，升温不低于上次 RPM；**热端 ≤0（异常/未就绪）时保持上次输出** |
| `rpm_from_cold_exp()` | `cold^exp` 指数映射（输入侧 EMA 平滑） | 冷强度 → RPM（供给侧：越强调速越高），**制冷强度先经 `MAP_INPUT_SMOOTH_ALPHA` EMA 平滑再进指数映射，映射后不再滤波**（与热端共用系数，首次直取） |
| `compute_fan_target()` | `rpm_from_cold_exp(actual_cold)` + 热端线性映射自加权合并（自加权逻辑已内联于本函数） | 独立风扇目标：PID 每周期下发前统一计算，与 PID 输出解耦（禁降钉死时风扇保持高转速，热端过温直接拉满） |

### 热端过温制冷削减

散热器热端过温时**就地压低**制冷强度上限（PID 模式专用，`main_loop` 每 5s 周期入口先执行），保护散热器硬件：

| 场景 | 行为 |
|------|------|
| 热端 > 阈值 | 单次削减量 = `(热端-阈值)×倍率/10`；**首次触发**把生效上限压到「当前实际制冷值 − 削减量」（回传未就绪时按配置上限算），**之后每次触发在当前生效上限上继续累减（不回看历史触发值）**；削减后冷却周期内不再削减 |
| 热端 ≤ 阈值 | 有削减时生效上限每次 +`倍率`（固定值）逐级上爬，削减量归零即**封顶配置上限**；恢复后冷却周期内不再恢复 |
| 削减/恢复冷却 | 独立计数，互不影响 |

- **配置上限**：`active_pid_cold_max`（`PID_COLD_RANGE` 上限，B6X/B7X 取对应值），由 `update_active_cold_range()` 计算。
- **生效上限** = 配置上限 − 削减量，下限不低于冷端最小强度。
- **下发边界强制生效（硬钳制）**：除压低目标上限外，还在每次下发前对制冷强度做硬钳制（`min(期望, 生效上限)`），直接绕过 `RATE_LIMIT_COLD` 的禁降限速——电池 ≥37.5°C 禁降期间也能把已升高的制冷强度一步压回上限内。钳制不改变 `actual_cold`，仅作用于本次下发值。**该下压优先级最高**：削减生效且本轮确被钳制压低时（`hot_forced_down`），去重里的制冷变化死区一律放行、当周期即下发，不受任何去重判定拦阻（死区、已到位、升降速限等均不拦）。
- 削减量按原始读数直算（不加滤波），一次 55°C 读数可削减 50；恢复按每冷却周期 +5（=倍率）逐级上爬，回到配置上限为止。
- 热端数据无效（<0，断联/未就绪）时保持当前削减量不动。
- 削减仅下调制冷强度上限，不直接干预 CPU 档位/CU 风扇（旧"CPU 紧急干预强制升档"已随 Gear 删除）。
- **已知边界**：热端在阈值附近来回时（≤45 / ≥46 交替）可能"削减→恢复→削减"每 2 周期交替，属规格固有行为；真机热端温变慢，实际振荡概率低。若需消除可加滞回带。
- **风扇联动（刻意不同步）**：边界钳制**故意不修改** `actual_cold`，风扇目标仍由 `actual_cold` 推算保持高转速——过温时只降制冷片强度、不拉低风扇，避免"火上浇油"；散热器实际制冷以回传值为准。钳制生效瞬间制冷强度一步跳至上限内，恢复时从被压值按正常升速爬回。

### EMA 方向取整

所有整数 EMA 平滑（CPU 温度、热端映射输入、冷端映射输入）使用 `EMA_DIR` 宏替代标准 `EMA`。
标准整数 EMA 因截断存在渐进问题（如 `α=33%` 时 `old=449 + raw=450` 永远到不了 450），
`EMA_DIR` 基于原始值方向做取整：原始值升高→向上取整，原始值降低→自然截断（按需方向），
确保滤波值能实际到达原始值。

## 主循环逻辑

**决策执行分离 + 限速统一下沉**：`main_loop()` 纯计算不下发，`rate_limited_execute()` 分发。
执行段：`rate_limit_cold()` 限速制冷 → `compute_fan_target()` 独立计算风扇目标（基于限速后实际制冷，
不跟 PID 输出）→ `rate_limit_fan()` 限速风扇 → `apply_gear_direct()` 纯下发（去重/日志/广播）。
计算层（`pid_cycle`）只传目标值，不限速。风扇目标基于限速后制冷（而非目标制冷），禁降钉死时风扇保持高转速。

 │  2. 双设备仲裁 select_active_device()：                    │

### 关键说明

- **风扇目标独立于 PID 输出**：风扇转速不跟 PID 输出，每周期由 `compute_fan_target()` 基于限速后 `actual_cold`
  （冷端指数映射）+ 热端温度（线性映射）自加权合并计算；热端过温时只降制冷强度、不拉低风扇（避免"火上浇油"）。
- **升降速率限制**（0.1°C 精度）：风扇升速与降速**共用同一组步长与阈值**（单键三值 `RATE_LIMIT_FAN`：第一值=每周期最大变化量、第二值=防抖阈值、第三值=下发转速的就近取整单位），
  且两个方向各带一段**幅度阈值防抖**（本周期变化量 ≤ 阈值就整步不做——升速方向保持当前值不升、降速方向保持当前值不降，
  升速时距最高转速 / 降速时距最低转速 < 阈值×1.5 时该方向防抖失效）；制冷片强度升降速独立且有符号
  （升速 = `RATE_LIMIT_COLD + d × RATE_LIMIT_COLD_MULT / 10`，降速 = `RATE_LIMIT_COLD − d × RATE_LIMIT_COLD_MULT / 10`，
  d = 有符号温差(电池温度 − BATT_BASELINE)）。负值表示禁止该方向变化（电池 ≥37.5°C 禁止降制冷强度、≤32.5°C 禁止升制冷强度）。
  制冷方向的 `d × mult / 10` 保留 0.1°C 精度。溢出自然累积下周期，目标变化时从当前实际值重新计算。
- **风扇防抖阈值 ×1.5 取整口径**：`(RATE_LIMIT_FAN_DEBOUNCE * 3 + 1) / 2`（先乘后除且**向上取整**）。写成 `/2*3`（阈值 51 得 75）或截断式 `x*3/2`（阈值 51 得 76）都会差 1 RPM，即移动 `>=` 边界；与冷端死区豁免带宽 `ceil(死区×1.5)` 同一口径。
- **风扇 `actual_rpm` 恒不低于 `fan_rpm_min`**：否则风扇目标偏低时 `actual_rpm` 跌破下界，`rate_limited_execute` 的就绪守卫（`actual_rpm < fan_rpm_min`）会误判「未就绪」而永久跳过下发（死锁）。故内部 `actual_rpm` 与下发值 `send_rpm` 对齐，均钳在设备范围内。
- **去重 + 最小变化幅度**：`apply_gear_direct()` 以散热器实际回传为准判定是否下发（`should_skip_dispatch`）：
  要播发值与实际回传一致视为已到位、跳过下发；回传异常退化用 `last_*` 缓存对比。另含最小变化幅度
  （目标与制冷实际 `|差值|` < `RATE_LIMIT_COLD` 第三值时不升不降；**豁免有方向**——要升只看「距上限」、
  要降只看「距下限」，该方向余量 < `ceil(死区×1.5)` 时才豁免，故「贴近上限的下降」「贴近下限的上升」不豁免）。
  **热端过温削减的下压（硬钳制）优先级最高**：本轮 cold 确被钳制压低时跳过死区、一律下发，不受去重其余判定拦阻。
- **短断联保留状态（`RECONNECT_KEEP_CYCLES`）**：断联时长 < `RECONNECT_KEEP_CYCLES`×5 秒（默认 3×5=15s）时，
  **跳过 `pid_reset_core()`**——`acc`/`kdp`/`target`/误差等 PID 学习状态保留，输出连续不跳变；仅仍以散热器回传实际值
  对齐 `actual_cold`/`actual_rpm`。长断联或配置=0 时完整重置（防陈旧状态误入）。该规则按断联时长统一生效，
  跨设备切换（B6X→B7X）若未记录断联起点也走保留分支（电池共享、状态连续合理）。
- **锁死自动重启（APP_WATCHDOG）**：仅在本次实际下发制冷变化后判定——实际制冷停滞（=上周期实际）且未达目标
  （≠上周期下发）连续 N 次时 kill 散热器 app 并重新拉起（散热器重启无效，需重建 App 进程恢复连接栈）；
  仅 BLE 已连、实际回传可用、watchdog 开启时启用；kill 后冷却 300s 防风暴。

### main_loop() 内部详细逻辑（每 5s 控制节拍执行一次）

> **结构**：`main_loop` 为骨架，直接分发到 `pid_cycle()`（本实现仅 PID，无 CTRL_MODE / gear_cycle 分支）。
> 配置解析为表驱动 + 分段函数（`INT_CFG_KEYS` 表 + `parse_debug/sysfs/pid/common`），与单函数行为等价。

0. **温度窗口快照**：`batt_window_changed = batt_changed_since_ctrl`；清零开启新窗口（供 pid_cycle 跳过判定）
1. **检查配置更新** → `stat()` 检测 `profile.conf` 修改时间，变了就热重载（`update_active_limits()`）
2. **热端过温削减** → `update_hot_derate()`：按散热器热端温度更新制冷上限削减量
3. **有效制冷范围** → `update_active_cold_range()`：`active_cold_eff_min/max`（含热端过温削减）
4. **PID 周期** → `pid_cycle()`：CPU 补偿 → 两条跳过判定 → `pid_compute()` → 映射 `pid_align_cold`

（旧 Gear 电池控制 / 反补 / 趋势豁免 / 紧急干预 / 电流-挡位映射等步骤已随 Gear 删除。）

## 看门狗反向保活（WD_KEEPALIVE）

**方向**：既有链路是「`service.d` 脚本（看门狗）→ 守护进程」（脚本每 `RESTART_INTERVAL`=300s 看一眼 daemon 在不在，不在就拉起）；本节是反方向——**daemon → 看门狗**：每 `WD_KEEPALIVE_INTERVAL`=60s 探测看门狗是否存活，不在就把它拉起来。开关 `WD_KEEPALIVE`（**默认开**，见参数表与本节末尾〈默认值〉）；关掉则退回只有单向链路的原状。

**两侧统一为「先查后拉、存在即不重复拉起」**（这是本轮的核心约束，缺任一半都会成环）：

| 侧 | 规则 | 判据 |
|---|---|---|
| daemon → 看门狗 | 探测到看门狗实例存在 → **不拉起** | 扫 `/proc/*/cmdline`，**某个参数恰好等于**两条候选脚本路径之一、或恰好等于脚本名 `b6x-tempctrl.sh`（逐参数整等；app 侧 `wd_pids()` 已统一到同一口径，只剩 daemon 侧额外接受裸脚本名，见本节下方注记）。**不经 shell、不 fork `pgrep`** |
| 看门狗 → daemon | `start()` 内先查 daemon 存在 → 跳过拉起；**脚本启动时不再先杀 daemon** | `/proc/<pid>/exe` 是否指向 `/data/local/tmp/tempctrl`（**紧判据**，见下） |

> **判据口径（2026-09-28 起 daemon 侧改为「逐参数整等」）**：daemon 侧不用 `/proc/*/exe`——脚本的 exe 是 `/system/bin/sh`，与一切 shell 共享，据此无法识别；故改判「`/proc/<pid>/cmdline` 里有没有一个参数**整等于**脚本路径（两条候选之一）或脚本名」。**app 侧 `wd_pids()` 已统一到同一口径（2026-09-28 起）**：那边原来有一道 `grep -l '^sh$' /proc/[0-9]*/comm` 前置过滤，把 `comm=busybox` 的开机看门狗整条漏掉（判活恒空 → 「停止daemon」静默失效并假报成功、重复拉起导致双看门狗并存）；现已改为「comm 白名单（`sh|ash|busybox|mksh|dash|toybox`）**只做省 fork 的快筛**，一个都没命中时全量兜底扫一轮（兜底已由"逐 pid fork 一次 `tr`"改为一次 `grep -l` 扫全部 cmdline、再对候选逐个精确确认——判据不变，只省掉真机数百~上千次 fork）」，身份判据与 daemon 侧一样只剩「某个参数**整等于**候选完整路径」。**仍存的一处差异**：daemon 侧额外接受裸脚本名，故 `sh b6x-tempctrl.sh` 在 daemon 侧算「在」（app 侧不算）——只让该轮不拉，无停摆风险。**这里踩过一次坑**：早期 daemon 侧用 `strstr()` 在 cmdline 缓冲区里做子串搜索，而该文件是 **NUL 分隔**的、`strstr()` 在第一个 NUL 处就结束——实际**只搜到了 `argv[0]`**；而看门狗的真实形态是 `sh <脚本路径>`（路径落在 `argv[1]`），于是判活**恒为「未见」**，去抖与冷却全被绕开、"拉起"每次都会发生。反过来，若对整段字节做子串搜索，`cp`/`rm`/`md5sum <脚本>` 这类命令行里出现过路径名的临时进程又会被认成看门狗（假阳 → 那一轮不拉，长期存在就永远不拉）。逐参数整等把这两个坑一起避开；口径收紧后的假阴（非常规包装，例如参数不是裸路径的 `sh -c 'sh <路径>'`）代价可控——多拉一个站岗实例，由拉起冷却与"存在即不重复拉起"封顶。
> 脚本侧必须紧：那边的假阳（把别的进程认成 daemon）会让**真正的 daemon 永远起不来**（模块静默失效），而 `pgrep -f /data/local/tmp/tempctrl` 有可证的假阳路径——它匹配的是 cmdline 子串，而该路径同时是 `tempctrl_service.log` / `tempctrl_uiprefs` / `tempctrl_*.status` 等一串兄弟文件名的前缀（仓库自带的 `diagnose_status.sh` 在设备上就会跑出 `ls -l /data/local/tmp/tempctrl` 这类命令行含该串的临时进程）；假阴最多多起一个（C 端单实例锁让它立刻以退出码 2 退出，且现在已不再先杀，故不会误杀）。二进制在运行中被替换（app 部署正是 `rm -f` 后 `cp`）时 exe 显示 `(deleted)`，而该实例**仍持着单实例锁**：**两侧（脚本的 `bin_pids()` 与 app `Deployer` 的 `bin_pids()`）必须同口径、都算"在跑"**（2026-09-30 起统一；此前脚本侧按"不在"处理）。脚本侧若漏判，它会以为没有 daemon 而反复起新实例（全被锁以退出码 2 顶掉），而这个旧实例谁也停不掉、盘上的新二进制永不生效——**两侧只要一侧漏判，"这个实例替换不掉"就成立**。假阳（把别的进程认成 daemon）的代价由"先查后拉"与 C 端单实例锁兜住。

**为什么"先查后拉"能断环**：看门狗脚本被 daemon 拉起时，daemon 必然在跑 → 脚本查到 daemon 存在 → 不杀不起 → daemon 一次都不会被重启（天真实现"无条件先杀后起"会让每次误判都白重启一次 daemon：温控空窗 + PID 学习状态清零 + BLE 重新对齐）。

**三重节流**（都是为了让误判的代价有界）：

1. **连续两次未见才拉**（`WD_MISS_CONFIRM`=2，两轮相隔 60s）——单次采样可能撞上瞬态（`/proc` 抖动、看门狗正在启动或正在重部署）。顺带把「app 先杀看门狗、再杀 daemon」那段约 8~13 秒的窗口挡掉：凑不齐两次 → **「停止daemon」不会被这条新链路顶回来**。
2. **拉起冷却** `WD_SPAWN_MIN_INTERVAL`=300s，且**持久化**到私有目录 `tempctrl_wd_spawn`（内容=上次拉起时刻的 epoch 秒）→ 冷却跨 daemon 重启有效，把"两侧判据同时假阴"这种最坏情况从"每分钟多一个"压到"每 5 分钟多一个"。
3. **连续失败退避**：连续失败 ≥ `WD_SPAWN_BACKOFF_FAILS`=3 次后，退避到 `WD_SPAWN_BACKOFF`=600s。（只统计"拉起动作本身没交出去"，**不**统计"交出去了但孙层没起来"——后者由下一轮判活复查并记一条日志，不叠加退避，免得把脚本启动慢误判成失败。）

**拉起形态（double-fork）**：父 `fork` → 中间层 `setsid`（脱离会话，避免连带）后**立刻退出** → 孙层 stdio 全重定向 `/dev/null` → `execv("/system/bin/sh", {sh, <脚本路径>})`，随后被 `init` 收养。**必须是 `sh <脚本>`**：`/data/adb` 是 noexec 挂载，脚本不能直接 exec；**绝对路径、不经 PATH**（同 `am`/`dumpsys` 的既有教训）。

> **为什么必须只回收「中间层」（2026-09-28 修）**：脚本第 3 节是常驻循环，子进程**永不退出**；旧实现让父进程直接 `waitpid` 它，而 3s 定时打不断 `waitpid`（本文件的 `signal()` 是 BSD 语义带 SA_RESTART，会被自动重启）→ 父进程**永久阻塞**在主循环里（进程还在、日志与曲线停更、不下发 BLE，而两个方向的判活都只看"进程在不在"，谁也发现不了）。改成 double-fork 后父进程只回收必然速退的中间层，且用 `WNOHANG` 轮询（上界 `WD_REAP_TRIES`×`WD_REAP_STEP_US`≈3s）而非阻塞等待。**exec 是否成功无法在拉起处观测**（父进程不再回收孙层，拿不到它的退出码）——由下一轮判活复查：仍「未见」时记一条「脚本存在但看门狗未起来」。这是刻意的取舍：不为一条更早的日志引入阻塞或额外复杂度。

**降级（一律只记日志，不影响温控主链）**：`/proc` 读不到 → 按未见处理但受冷却约束；两条候选脚本路径都不存在 → 记日志（≥`WD_LOG_MIN_INTERVAL`=600s 一行）且**不重建脚本内容**（等 app 重新部署）；拉起失败 → 记日志 + 退避。脚本路径优先 `/data/adb/service.d/`（与 `Deployer` 的默认一致）。

**调用点（两处，且必须排在各 `continue` 之前）**：①`main()` 的「等设备就绪」等待循环内 ②主循环 5s 控制块开头（与 `host_app_uninstalled()` 并列）。理由与卸载自清同构：两处循环体在无 BLE / 无设备时会 `continue`，放后面就会出现"最需要它的时候它不跑"。

**代价（如实记录）**：看门狗脚本启动时不再无条件替换在跑的 daemon → 开机时若已有实例在跑（例如用户开机后抢先点了「拉起daemon」，那个实例活在 app 的 cgroup 内），不再被替换成 `service.d` 拉起的规范实例；它会随 app 一起被杀，随后由看门狗循环在 ≤300s 内重建。

**默认值（2026-09-29 起为默认开）**：开关 `WD_KEEPALIVE` 的默认值由 0 改回 1 —— `params.def.json` 的 `default`/`factory` 与 C 侧初值一并改，两者一致由 `check_params.py` 的逐键默认值审计强制（改一侧不改另一侧直接红）。**注意**：`profile.conf` 里已写入的旧值**优先于**默认值——若设备上曾被写过 `WD_KEEPALIVE=0`，改默认值不会自动打开它，要在界面里开启（或删掉该行）才生效。

## 进程检测机制

使用 **双重检查**：状态文件 mtime 心跳检查 + BLE 连接状态。status 双文件的路径与 `BLE=` 字段的取值编码（B6X 文件区分两个 app、B7X 文件记实际散热器型号）见 [lsp模块 README](../README.md)（唯一规范处）。只要有一个出问题就算断联。

> **STATUS_TIMEOUT**：状态文件心跳超时判死秒数，**硬编码 3**（不再可配置，故不列入参数表）——LSP 每 1s 写一次，超 3s 判死。

```
 启动 → 创建 status 文件（0666，所有用户可写）
      → 脚本启动成功 → 立即开始（无启动延时；历史 30s 延时已删，见「启动流程」）
      → 等待 status 文件出现 BLE≠0（模块就绪 + BLE 已连）
 
 工作模式中，每 5 秒：
   连接检测 → 双 app 存活仲裁 → main_loop（纯计算）→ 速率限制执行
   
   1. 读 status 文件内容 → BLE（编码见 lsp模块 README）
   
   2. 双重检查存活检测（任一不满足即算断联）：
      ├─ stat(status 文件).mtime 距现在 ≤ 3秒？      → 模块在写心跳?
      └─ status 文件内容 BLE≠0?                       → BLE 已连接?
      
      ├─ 全部 OK → 存活
      └─ 任一失败  → 模块/BLE 失联
                          ↓
                      等待复活子循环（每 5 秒检测，同时查 BLE）
                          ↓
                      模块+BLE 都重新就绪 → 实际制冷/转速以散热器回传为准 → 按正常限速过渡

 模块侧（LSPosed）：
   ────────────────────────────────
   onDeviceConnected / disconnect 钩子 → 更新 bleConnected + connectedModel
   每 1 秒线程（后台 BLE 重连保持 5s 节奏）+ 连接/断连事件：FileOutputStream 写 "BLE=<编码>\n" + CONNECTED_AT + BLE_OWNER_LAST=<值> <时间> 到 status 文件（字段名与编码见 lsp模块 README）
   （BLE_OWNER_LAST 连接时写入、断连保留，标识"上次连接者"，供 app 存活仲裁）
   （直接 Java 文件 I/O，不走 su，无 KSU 命名空间问题）
```

### 文件详情

status 双文件的**路径、字段名/含义/单位/编码、写入节奏与心跳超时**等协议细节一律见 [lsp模块 README](../README.md)「status 文件协议」（唯一规范处），此处不重复。

C 端消费侧（协议之外的行为）：主循环开头 `read_status_ble_both()` 逐行解析双文件；`select_active_device()` 按 `CONNECTED_AT` 做「先连者优先」的设备仲裁；`update_active_limits()` 按回传的设备型号切换制冷/风扇上限（B6X 型号兜底 6 → 制冷 194/风扇 6000；B7X 默认与 B6X 一致，由 `FAN_RPM_RANGE`/`PID_COLD_RANGE` 第三值配置），非按包名猜测。

> **`service.d` 脚本侧的进程判据（`bin_pids()`）**：脚本判「daemon 在不在跑」的唯一来源。读 `/proc/[0-9]*/exe`，按**末端锚定**匹配 `/data/local/tmp/tempctrl`——末端锚定故不会命中 `tempctrl_service.log` / `tempctrl_uiprefs` / `tempctrl_*.status` 这些兄弟文件；`running()` / `stop_old()` / `start()` 都从这一个判据取，故「判有没有在跑」与「停哪些 / 给谁改优先级」不可能给出不同结论。**不用 `pkill -f "$BIN"`**：那是 cmdline 子串匹配，凡命令行里出现过该路径的临时进程（诊断脚本里的 `ls -l /data/local/tmp/tempctrl`、`grep tempctrl` 等）都会被误杀（2026-09-28 修）。**两侧对 `"(deleted)"` 必须同口径（都算「在跑」）**：二进制在运行中被替换（app 部署正是 `rm` 后 `cp`）时 exe 显示 `<路径> (deleted)`，而该实例仍持着单实例锁——脚本侧若按「不在」处理，会以为没有 daemon 而反复起新实例（全被锁以退出码 2 顶掉），且这个旧实例谁也停不掉、盘上的新二进制永不生效。app 侧 `Deployer` 的 `bin_pids` 与本处同为 exe 末端锚定、且都接受 `<路径> (deleted)`（2026-09-30 起统一）。

> 制冷上限口径见 `PID_COLD_RANGE`（`active_pid_cold_max`）：194=SDK/硬件上限，190=温控默认下发上限（B7X 由第三值指定）。

### 三方 app 存活仲裁

三个 app 最多一个后台存活：**飞智散热器开发者工具**（别名：老 app，包名 `com.flydigi.waspwing.experimental`，参数定义里的键名沿用 `B6X_OLD`）+ **B6 B6X 超频工具 V2**（别名：新 app，包名 `com.flydigi.waspwing.experimentanliuliu`，键名沿用 `B6X_NEW`）+ farsef（`com.fdg.flashplay.farsef`，B7X 游戏厅）。由 `arbitrate_apps()` 按 `ARBITRATE_INTERVAL`（15 秒）节流、在读取双 status 后调用。

farsef 只在**最近连接的是 B6X 散热器**（`BLE_OWNER_LAST`=6）时参与仲裁——它控制同一台 B6X 散热器才与两个 B6X app 竞争；连的是 B7X 设备（=7）时不参与（控制另一台设备，不应被杀）。

```
存活参与者 = {飞智散热器开发者工具（老 app）, B6 B6X 超频工具 V2（新 app）} ∪（farsef 存活 && BLE_OWNER_LAST==6 ? {farsef} : ∅）
参与者 < 2 → 不仲裁
保留优先级：
  1. BLE_OWNER_LAST 值代表的 app（标识"上次连接者"，连接时写入、断连保留）：
     =1 → 保留飞智散热器开发者工具（老 app）
     =2 → 保留 B6 B6X 超频工具 V2（新 app）
     =6 → 候选保留 farsef
  2. 无 BLE_OWNER_LAST → 回退当前连接者 BLE 字段（=1 飞智散热器开发者工具 / =2 B6 B6X 超频工具 V2）
  3. 兜底保留飞智散热器开发者工具（老 app）

保留者涉及 farsef 时：比较 farsef 的 BLE_OWNER_LAST 时间与另一方（B6X app）的
CONNECTED_AT，保留时间更晚（最近使用）的那个。

被淘汰者非前台时 am force-stop（dumpsys window mCurrentFocus 优先判断，
被淘汰者在前台则等下一周期再试）
```

**与温控仲裁的关系**：`arbitrate_apps()` 只管 app 存活，`select_active_device()` 只管散热器控制权。两个 B6X app 共写同一 B6X status 文件；`BLE_OWNER_LAST` 由 LSP 连接事件写入、断连保留，标识"上次连接者"；farsef 连 B6X 设备时写 B7X status 文件（BLE=6 + `BLE_OWNER_LAST`=6）。都未连接时 arbitrate 保留上次连接者（或飞智散热器开发者工具）在后台待命（LSP 后台自动重连会恢复连接）。

**自动拉起**：`arbitrate_apps()` 扩展——当**没有任何散热器 app 存活**时自动拉起上次使用的 app（`launch_last_app()`，复用 `BLE_OWNER_LAST` 选择逻辑：2→B6 B6X 超频工具 V2、6/7→farsef、其余/无记录→飞智散热器开发者工具；目标 app 未安装时回退另一个）。拉起用 `am start`（**显式 launcher 组件 `-n <包名>/<Activity>`**；这些 app 的 launcher 未导出/非标准 filter，隐式 `-p` 解析不到）+ `b6x_auto_launch` 标志，LSP 读到标志后在**离开引导页、进入设置界面时**（第一个非引导页 Activity 的 `onResume`）执行 `moveTaskToBack` 后台化（几乎无感；引导页 onResume 不切，等自动跳转到设置界面后再切，避免"没进界面就退后台"；读取后清除标志避免用户手动打开又被切走；附 2s 兜底超时，自动进入设置失败时仍退后台）。按 `APP_LAUNCH_COOLDOWN` 冷却；由 `APP_LAUNCH_ENABLED` 开关控制（默认 0 关闭，需在界面中开启）。调用时机：启动等待设备循环 + 主循环每 5s 节拍 + **断联（连接丢失）时**（存活检测失败路径；无 app 存活时真正拉起，app 存活时记 debug「已在运行」；开关关闭也会记 debug「开关关闭，跳过」，便于排查）。进程存活检测**直读 `/proc/<pid>/cmdline` 精确比对包名**（整参=包名或 `--nice-name=<包名>`），不经 shell——避免 `system("pgrep -f <包名>")` 时临时 shell 自身命令行含包名造成的自匹配误判（曾导致 app 已死仍被判"已在运行"、拉起被跳过）。

**开销收敛（2026-09-25）**：本链在启动等待循环、主循环 5s 节拍与断联路径上都会被反复调用，故四处做了收敛——① 屏幕门禁前移到最贵的探测（安装探测 `pm`、全量 `/proc` 扫描）**之前**，息屏期间整条链停跑、隔一定间隔才复核一次屏幕；② 安装状态一次开机周期内只问一次并缓存，命令跑不起来时不写缓存；③ 调用方已扫出「三方全灭」时把该结论传给拉起链，免去重复的全量扫描；④ 屏检自己不再走 `sh | awk` 管线，只 fork 一个 `dumpsys`（命中即关管道让子进程提前退出）—— 一次探测从 3 个进程、两段管道降到 1 个进程、一段。

**开销收敛（2026-10 增补）**：⑤ 入口新增**独立探测节流**——整条链（屏检 + `/proc` 扫描 + 拉起判定）限到 ≤1 次/间隔，与 `am start` 冷却（`APP_LAUNCH_COOLDOWN`=60s）解耦，`last_launch_probe_at` 与 `last_launch_attempt` 各管一摊。间隔**两档**：常态 `APP_LAUNCH_PROBE_INTERVAL`=12s；**断联后 `APP_LAUNCH_PROBE_FAST_WINDOW`=60s 内收窄到 `APP_LAUNCH_PROBE_FAST_INTERVAL`=5s**（计时起点＝`last_disconnect_time`，重连时由 `reconnect_align` 清零），使「App 真死了」能更快被发现并拉起——**只加快既有探测节奏，不新增任何拉起/重启动作**（该链本就只在 App 已死时才真正 `am start`）。**代价**：app 死亡后的重新拉起检测延迟上限 = 12 秒（断联初期 60s 内为 5 秒）；息屏→亮屏感知最长滞后 ≈12 秒（入口节流与息屏退避 `APP_LAUNCH_PROBE_OFF_INTERVAL`=10s 取较大者；断联初期入口为 5s，此时由上闸门的 10s 决定）——**息屏仍按 10s 退避，不被 5s 快探测覆盖**。⑥ `/proc` 扫描列表按安装缓存过滤：仅剔除「已确认未安装」（缓存值 0）的包，使 `app_process_scan` 的 `found_all` 提前退出；`unknown` 一律保留在扫描列表（不漏判）。因默认配置（`APP_LAUNCH_ENABLED=0`）下拉起链不跑、缓存不会被填充，故在**等待设备循环内做有界预热**（对三个候选包各探一次，无法判定者最多重试 3 轮后放弃，绝不周期性 fork `pm`）。屏检结果**不再单独缓存**——其频率已由 ⑤ 统一限流，单一限流点。

**屏幕状态解析（`wakefulness_value`）对旧 `sh|awk` 管线的两处有意偏离**（都只在 dumpsys 输出非标准格式时显形；AOSP 每字段独占一行、用 println 拼接，故实际不可达）：
① **取值起点以 `mWakefulness=` 之后为界**，旧 awk 取全行第 1、2 个 `=` 之间——仅当该行在标记之前还有 `=` 时不同，而那种情况下旧实现取到的是别人的值；
② **首尾空白（空格 / 制表符 / `\r`）一并裁掉**，旧 awk 只裁行尾 `\n`——仅当值两侧带空白时不同，裁掉更贴近字段真实值（旧实现会把 `" Awake"` 判成灭屏，白跳过一轮拉起）。
其余各点（作用于整行、含 `mWakefulness=` 且不含 `Override` 才入选、`Override` 行继续往下扫、超 31 字符截断、1/2/0/-1 的取值映射）与旧 awk 核对等价。

**包安装探测的退出码口径（`app_installed_probe`，走 `pm path`）**：只有 `pm` **明确回答「包未找到」（退出码 1）**才判「确实未安装」；其余一切非 0 —— 命令跑不起来（126 无执行权限 / 127 找不到 `pm`）、被信号杀死（`WIFEXITED` 假）、binder 调用失败（rc=2）、package 服务未就绪（rc=20，2026-09-30 真机实测于开机未解锁窗口，六种调用全部 rc=20 + `cmd: Can't find service: package`）—— 一律按「无法判定」处理。把「无法判定」当「不存在」会在开机早期误判成已卸载（→ 清产物 + 自删二进制，不可逆）；而 pm 长期不可用的最坏后果只是「永不自动清理」，是安全的降级方向。**安装状态在一次开机周期内缓存**（进程生命周期、无过期、不落盘；无法判定不写缓存），故探测链上不要直接调用 `app_installed_probe`，一律走带缓存的 `app_installed()`；只有需要实时结论的宿主卸载探测（`host_app_uninstalled`，自带 60s 节流）才直接用它。**2026-10 增补**：缓存另有两条写入途径——(a) `/proc` 命中的正向证据（`install_cache_mark`：进程在跑即标「已安装」=1，**只写 1、永不写 0**，可自纠重装）；(b) 启动预热（`install_cache_warmup`，见上文「开销收敛」⑥）。`app_installed_cached()` 只读缓存、绝不 fork `pm`，供 `/proc` 扫描列表过滤使用。

**LSP 侧配合**：连接成功时把散热器 MAC 持久化到**宿主 app 自己的私有目录** `/data/data/<宿主包名>/files/tempctrl_last_dev`（**各包各记**，不再四包共用一个文件；代价是同一台散热器在另一个飞智 app 里需重新选一次）。该文件由 LSP 侧（`MainHook`）自建自读自写，**tempctrl daemon 不参与**（原 daemon 侧在 `/data/local/tmp/` 预创建 0666 的兜底块已删除）。冷启动打开 app 时，LSP 检测到引导页（MainActivity）即**自动进入参数设置界面**（等效自动点「开始设置」，`autoStartSetup()`），由 B6ExperimentalActivity.onResume 的 `tryConnect()` 主动发起连接——不再需要手动点「开始设置」。已进入过设置界面（`enteredSetup`）或已连接时跳过；后台重连线程仍保留（断开后每 5s 兜底，**息屏时放慢到 10s**）；`am start` 携带 `b6x_auto_launch=1` 时 LSP 将 Activity 切回后台。

## 部署与 Root 调用

### 为什么守护进程不能由 APK 直接拉起（三条硬阻断）

APK 侧有界面、也有 root 能力，但**不能自己把 daemon 拉成常驻进程**：

1. **stopped state** — 全新安装未打开过、或被用户强停过的 app 收不到 `BOOT_COMPLETED`（Android 3.1 起广播默认带 `FLAG_EXCLUDE_STOPPED_PACKAGES`，Android 15 进一步收紧）
2. **cgroup 连带杀** — 从 app 里 `su` 起的常驻进程仍留在该 app 的 cgroup 内，app 一死就一起被杀；`nohup`/`setsid` 无效（只改父子/会话关系）
3. **LSPosed 钩子域** — 钩子以宿主 app 的 `untrusted_app` 域与 uid 运行，读不了 thermal sysfs、用不了 `am`/`dumpsys`/`pm`

> 若硬走前台服务路线：Android 15+ 的 `BOOT_COMPLETED` FGS 类型白名单只有 location / connectedDevice / remoteMessaging / health / systemExempted / **specialUse**，且启动调用**必须写在 `BroadcastReceiver.onReceive()` 里**（放 `Application.onCreate` 在 Android 16 实测被拒）。

因此拉起的实际做法是 **`service.d` 脚本开机先起 + app 内手动拉起入口**，两处都直接执行启动命令，由 C 端单实例锁保证幂等：先拿 `/data/local/tmp/tempctrl.lock`（DE 存储，开机解锁前也可用），再拿私有目录的主锁 `tempctrl.lock`，**两把任一被占即以退出码 2 退出**——私有目录不可用时单实例保护不再整段消失（见 [文件落点](../README.md#文件落点)）。

### root 调用（照 Scene，出处 `../scene相关/decompiled`）

**照搬**：

1. 零依赖，只用 `Runtime.getRuntime().exec()`（Scene 全仓库无 libsu、无 Shizuku Java API）
2. su 命令行按表选：先 `su -v` 嗅探 root 类型，再按表定——SDK<30 → `su`；SDK≥30 时 **MAGISK → `su`**、KernelSU → `su -M`、其余 → `magisk su -mm`。（出处 `a/a70.java` 的 `f()`；类型串由 `d()` 产出，取值 `MAGISK` / `KernelSU` / `apd` / `mqsas` / `xsu`，**未识别时 Scene 兜底为 KernelSU**。小米专用的 `mqsas` / `xsu` 未照搬。）结果持久化、用户可手动切换；失败时给「当前模式 / SU CMD / 当前用户 / 日志」诊断对话框。**每次 `exec` 都新起一个 su 进程、跑完即关**（非常驻会话），同一时刻只允许一个会话（串行锁）；命令失效时按「实测可用 → 推荐 → 裸 `su`」**有界回退重试**（只在该命令"通道失败且非超时"时换下一条），且用户主动点部署/拉起会复位失败退避——"缓存命令失效后只能重启 app"那条无自愈路径已消除（口径详见 [app/逻辑说明.md](../app/逻辑说明.md) §4.1、§4.2）
3. 资源落盘与授权**全用 Framework 的 File API**（`setExecutable(true, false)` 并沿父目录链逐级向上），不调外部 `chmod` 二进制
4. **判活看通道连通性，不看进程**，配退避重连
5. 省电白名单批处理（`dumpsys deviceidle whitelist +`、`appops set RUN_IN_BACKGROUND allow`、`am set-standby-bucket active`、`am unfreeze --sticky`），对象是**已安装的散热器控制 app**（不是界面自身——界面 manifest 里没有任何 service/receiver/provider，没有后台职责）。**已移出部署主链**：部署结果先上屏、白名单随后后台 best-effort 补跑（拿不到通道就跳过本轮，下次部署时补），可能挂住的命令用 `toybox timeout` 包一层；`renice -n -20` 与白名单无关，由开机自启脚本对守护进程自己做

**不照搬**：rish/Shizuku 整条通路（Scene v9.3.1 里它的启动函数全库无调用点，是残留）；签名派生密钥 + AES + 长度前缀的 socket 协议（单 app 自用多余，换签名即全废）；Scene 那个"存了 `Process` 字段却只用一次"的半常驻 shell（无结束标记、无超时、无重连——本项目改成**每次调用新起一个 su 进程**，配结束标记 + 读超时 + 退出码回传 + 串行锁 + 失败有界回退）；UPX 加壳。

### 开蓝牙命令链（断连自动开蓝牙）

钩子在「确认蓝牙未开启」时写请求文件（`/data/local/tmp/tempctrl_bt_req`，一行 `REQ=<epoch秒>`），
守护进程在**等待设备循环与主循环两处**读取，token 变大才执行一次命令链（**成功即停**）：
`svc bluetooth enable` → `cmd bluetooth_manager enable`（前者在 Android 14+ 内部即转调后者）。
限频（两次之间至少间隔的秒数，0=关闭）在钩子侧完成；**守护进程侧也复核 0**——值为 0 时直接消费掉请求、
不执行，避免钩子 30s 配置缓存留下的漏窗。首拍只记下 token（畸形值记 -1）、不执行，避免重启后对旧请求补执行。
开关为 `BT_AUTO_ENABLE_SEC`（`[3] 自动拉起 app` 组，默认 300，热重载生效）。命令均以 root 上下文执行，
与目标 app 的 targetSdk 无关；`svc`/`cmd` 两条在 Android 13–16 上对 root 放行（不看前台用户）。

## 启动流程

1. 设定默认日志路径（根据二进制文件名）
2. 加载配置（`--config` 参数 > 自动检测 > 全部默认值。`PERF_ENABLED=0` 时仅 `DEBUG_ENABLED=1` 的调试子项生效，其余全部使用代码默认值；`PERF_ENABLED=1` 正常加载全部）
3. 创建 status 文件。读 LSP 回传实际制冷对齐初始制冷值（`active_cold_eff_*` 初始化；不可用回退代码默认 `pid_cold_min`）
4. 输出「脚本启动成功」后**立即**进入等待设备阶段（无启动延时；历史上曾有固定 30 秒延时，已删除，详见 [CHANGELOG](../../CHANGELOG.md)）
5. 等待模块就绪 + BLE 已连（status 文件读到 `BLE≠0`）；等待期间无散热器 app 存活时自动拉起上次使用的 app（`APP_LAUNCH_ENABLED`，按 `APP_LAUNCH_COOLDOWN` 冷却）
6. 进入工作模式后每 5 秒：连接检测 → `main_loop`（纯计算）→ 速率限制执行
   - 每轮循环开头通过双重检查检测 App 存活（status 文件 mtime + BLE≠0）
   - 断联时实际值保持不动（丢弃未执行变化量），进入等待复活子循环
   - 重连时实际制冷/转速以散热器实际回传为准初始化（不做档位匹配），由 `rate_limited_execute` 按正常限速逐步调节，抑制突变；重连后按 `RECONNECT_KEEP_CYCLES` 决定将 PID 状态保留还是完整重置（见 [主循环逻辑](#主循环逻辑)）
7. **回传就绪对齐（不直接采用瞬时回传）**：重启/重连瞬间 `lastWaspWingInfo` 为空 → `COLD_REAL`/`RPM_REAL` 缺失（读到 -1）或设备未下发前回占位 1，拿它初始化 `actual_cold` 会被兜底成 1（WebUI 显示 1），且后续快速限速一步拉到 PID 目标（125/4500）。故改为等待 `REPORT_OK_N`(=2) 帧**连续真实回传**（`RUN_MODE` 存在 + 冷/rpm 值合法）再对齐；超时 `ALIGN_WAIT_TIMEOUT`(=15s) 用保守值（`pid_cold_min`/`fan_rpm_min`）起步，防回传长期缺失（旧机型）导致永久停摆。短断连保留 PID 状态、沿用内存实际值（断联期间未被改仍准确），长断连走本对齐。

## 实测说明

### 智能温控模式的风扇转速限制非强制生效

经实测，**智能温控模式（mode=0）的风扇转速配置疑似并非强制生效**，经常会突破设定的上限很多，尤其是刚切换过去的时候。这会导致噪音突然变大，体验非常差。

**原因推测**：`setRunMode` 的 `windLevel` 参数在散热器固件中被解释为"建议上限"而非"硬上限"。散热器内部有独立的 PID 或逻辑控制算法，在刚切换模式或温差较大时，会以更高转速运行来快速达到目标温度，忽略应用层设定的风扇上限。

**解决方案**：全部改用**固定功率模式（mode=1）**，直接指定风扇转速和制冷片强度。daemon 下发均按固定功率模式指定实际制冷/风扇值，避免"建议上限被固件忽略"的问题。

## 注意事项

- **CPU 温度扫描范围** 通过 `CPU_ZONE` 配置（双值：起始 zone 结束 zone，默认 `0 99` 全扫），K60 机型推荐 `30 40`
- **温度传感器路径** `thermal_zone[N]` 是 Linux 通用接口，不同 SoC 的 zone 编号不同。首次真全量扫描无需手动配置（范围过大 0~99 约 1 秒），可通过 `CPU_ZONE` 缩小；后续周期重扫只在首次有效名单内、不再发现新 zone，保留数由 `CPU_ZONE_RESCAN` 第二值控制
- **去重逻辑**：`apply_gear_direct()` 以散热器实际回传为准——要播发值与散热器实际值一致视为已到位不下发（解决"日志已变化但实际未成功导致达不到最高/最低制冷"）；回传异常退化用 `last_*` 缓存对比。另含最小变化幅度：目标与制冷实际 `|差值|` < `RATE_LIMIT_COLD` 第三值（最小变化幅度）时不升不降；豁免有方向（要升只看距上限、要降只看距下限，该方向余量 < `ceil(死区×1.5)` 才豁免）；热端过温削减下压优先级最高，不受死区拦
- **am 广播可靠性**：`send_am_broadcast()` 用绝对路径 `/system/bin/am` 执行（不依赖 daemon PATH），并在 `waitpid` 后检查子进程退出码——`am` 未找到（127）或广播失败时 `write_log` 明确报错。排查"日志显示下发但散热器不动"时，先看日志里有没有 `am broadcast 失败` 行；开启 `DEBUG_ENABLED=1`+`DEBUG_EXEC=1` 可看到 `am broadcast 已发送` / `apply_gear_direct 跳过下发` 明细
- **`patch_tls.py`**：NDK 编译后按需执行，修复 PT_TLS 对齐；当前程序无 PT_TLS 段，脚本空操作并返回成功——只有真正的修补错误才返回非零（CI 直接失败）
- **`#include <stdarg.h>`**：`write_log()` 用了 `va_list`，NDK clang 下不是隐式包含的
- **KernelSU noexec**：`/data/adb` 下的模块目录挂载了 `noexec`，故二进制**不放在 `service.d` 目录**，而是由部署流程落到 `/data/local/tmp/tempctrl` 执行（`service.d` 里只放拉起脚本）
