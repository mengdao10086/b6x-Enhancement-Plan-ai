## 1. 钩子与跨进程（MainHook）

`MainHook` 是 LSPosed 模块入口，宿主是飞智散热器 app（B6X 两个包、B7X/farsef 一个包，共三包）。它做两件事：**改宿主行为**（各 `hookXxx`）与**与守护进程 `tempctrl` 交换状态**。跨进程不共享内存：钩子 → 守护进程走 **status 文件**（每秒写），界面/守护进程 → 钩子走 **开关标志文件**；两者都是 `/data/local/tmp/` 下的小文件。

> 协议字段与行格式见 [../README.md](../README.md)；写入端（守护进程）见 [../daemon/逻辑说明.md](../daemon/逻辑说明.md)。

### 1.1 钩子清单与注册时机

模块不修改 APK，全部通过 Xposed 钩子在运行期改写行为。`handleLoadPackage` 按固定顺序注册以下分区（**顺序影响 Xposed 回调执行次序，不可随意调整**）：

| 分区 | 作用 | 适用 |
|---|---|---|
| `hookControllerStopScan` | 设备连接后停扫描（保底） | 双设备 |
| `hookB6ViewModelFix` | ViewModel 层连接后更新 LiveData（不创建中间态 `WaspWingInfo`） | 仅 B6X |
| `hookB6Diagnostics` | 强制 `checkBluetoothPermission` 返回 true + 诊断钩子 | 仅 B6X |
| `hookCommonDisconnect` | `BluetoothGatt.disconnect` 公共断连检测 | 双设备 |
| `hookRunFetchLoopCpuFix` | 修复 `runFetchLoop` 空转占满一个核心 | 双设备 |
| `hookB6Activity` | 记录 `onResume` BLE 状态 + 冷启动自动进入设置界面 | 仅 B6X |
| `hookWaspWingManagerCapture` | 捕获 `WaspWingManager` 实例（供下发 `setRunMode`） | 双设备 |
| `hookSyncConnectedController` | 把 static `dataInteractionController` 同步到当次连接的实例 | 仅 B6X |
| `hookB7Obfuscated` | B7X 混淆适配（见 §1.5） | 仅 B7X |
| `hookApplicationCreate` | 注册广播接收器 + 启动定时状态写入 | 双设备 |
| `hookAutoLaunch` / `hookBackToBackground` | 自动拉起后台化 / 返回键收后台（见 §1.4） | 双设备 |

**静态初始化不得依赖主线程 Looper**：`mainHandler()` 懒加载，因为 fork 阶段主线程 Looper 尚未创建，此刻取 `Looper.getMainLooper()` 会拿到 null。凡在主线程钩子回调之外（如静态初始化、fork 早期）要 post 主线程任务，都必须走这个懒加载入口。

### 1.2 BLE 重连节奏与息屏退避

后台重连由 `startPeriodicStatusWrite` 的 1Hz tick 线程承担。节奏：**亮屏 5 秒一次**（原节奏），**息屏 10 秒一次**。

- **为什么息屏可以拉长**：屏灭＝宿主不在前台＝没有实时控温需求，此时重连只是「等散热器开机」，每 5 秒打一次射频是浪费（`connectGattWith` / B7X 的 `t9.j.E` 都是**真实**蓝牙连接尝试）。10s 为用户拍板值。
- **屏幕状态的取法与缓存**：用 `Application.onCreate` 钩子拿到的宿主 Context 取 `PowerManager`。`isInteractive()` 是一次到 `system_server` 的调用、不便宜，故按 tick 缓存，最多 `SCREEN_PROBE_TICKS`(5) 秒探一次；且**只在本方法被调用时探**（调用点在三个重连条件之后，连接正常时一次都不问）。缓存最坏过期 5 秒，两个方向都无害。
- **失败兜底**：Context/PowerManager 取不到、或调用抛异常，一律**按亮屏**——宁可维持原来的 5 秒节奏，也不许因探测坏掉把重连拉长甚至变成永不重连。
- **线程归属**：`reconnectIntervalTicks` 只在 tick 线程内被调用与读写，故 `screenProbedAtTick` / `screenInteractive` 无需 volatile；`appContext` 由主线程写、tick 线程读，故 volatile。
- **设备锁死**：多次重连仍无回传时停止自动重连，等用户强制重启 app（见 §1.3 ③）。
- **重连验收与自愈**：每轮重连在发令后延迟约 1 秒复查 SDK 控制器状态（B6X `mDataConnectState`、B7X `E`）。若判定「本次未发起」——发令抛异常、发令后状态仍为空闲(0)、或发令前后状态纹丝不动（被 SDK 自身状态门禁静默挡住，见 §1.3 第 4 点）——则把该状态清成 0 并断开其 gatt，等下一周期重试。任一反射失败只记录并按限频输出，退回原有行为，绝不让重连块整体抛异常。
- **日志限频与心跳**：重连尝试日志由「每断联只记一条」改为按时间限频（5 分钟一条）；断连期间每 5 分钟输出一条「重连循环心跳」。二者共同使「循环在跑但没发起」与「循环停了」在日志上可区分（这是本模块排查「久置后台不再自动连接」的关键可观测性）。
- **关键连接事件豁免预算**：真发起连接 / 连接失败（含断联）这类关键事件不再受连接诊断日志「每连 1 条」的预算限制，改按 5 分钟限频，跨重连周期仍可见。

**B7X 的重连接口**：B7X 无 `connectGattWith`（仅 B6X 有），其等价入口是 `t9.j.E(device)`（内部 `f50991b.o0(device)`），与 B6X 走同一 SDK 静态注册表；直接用 `lastDevice` 发起连接，避免依赖冷启动必丢的控制器实例。

### 1.3 静默丢弃的点与自愈

**问题**：重连时 static 控制器 / `currentValidGatt` 常指向「最后连接成功」的实例，而未必是**当前在收包**的实例。命令写进失效 gatt 会被 SDK **静默丢弃**（不报错），设备停在固件默认（如 125 / 4500）。

**三个静默丢弃点**：① static `dataInteractionController` 指向失效实例；② `currentValidGatt` 指向已断连 gatt；③ `runFetchLoop` 空转/崩溃导致队列不再被消费。

**三类自愈**：

1. **`ensureUsableController`（下发前校验）**——`setRunMode` 下发前校验 static 指向实例的 gatt 是否 == `currentValidGatt`；失效时从 `connectedControllers` 找回 `currentValidGatt` 对应的实例重同步，仍找不到则 `forceReconnect()`。字段缺失/不可访问时**保守放行**（保持原行为，不影响主流程）。
2. **收包者定基准**——在真实收包点（B6X 的 `onCharacteristicChanged`、B7X 的 `captureInfoFromController`）把 `currentValidGatt` 重绑到**真在通信**的 gatt，作为下发基准。这样即便 static 指向旧实例，下一轮 `ensureUsableController` 会按收包基准把它重同步，消除「命令写进失效 gatt」的窗口。
3. **`checkCommandStall` + 守护消费线程**——双信号并行、独立处置：
   - ① 命令队列堆积 > `QUEUE_STALL_THRESHOLD`(6，≈30s 下发量) → 判定 `runFetchLoop` 疑似崩溃，启动**守护消费线程**接管消费（`state==2` 才消费；`peek` 只取一次存局部变量，消除「判断后二次 peek」的双消费窗口；仅当同一队首停留超过 `QUEUE_TAKEOVER_MS`(5s) 才接管）。
   - ② 回传停滞且累计 `DISPATCH_STALL_LIMIT`(3) 次下发未生效 → 判定连接/设备问题，`forceReconnect()`。
   - 另有**回传新鲜度验证**（先于值停滞判定）：重连后 `INFO_STALE_AFTER_MS`(6s) 无新回传 → 判设备无响应，走 `handleDeviceNoResponse`（唤醒序列 → 重连上限 `STALL_RECONNECT_MAX`(3) → 设备锁死提示强制重启）。
   - 守护消费线程轮询间隔 **250ms**（原 50ms）：接管判据是 5 秒级阈值，20Hz 轮询比它密两个数量级；粒度放粗只让最坏接管晚 200ms（5s 阈值下不可感知），换来唤醒次数与反射读字段开销降到 1/5。语义不变：仍是「同一队首停留超阈值才接管」。

**重连路径的第 4 个静默点（SDK `connectWith()` 的状态门禁）**：SDK 的连接入口 `connectWith()` 在控制器状态停在「连接中(1)」或「已连接(2)」时**只写自己的日志后 `return`**，模块侧零输出——因此「后台重连发令后仍连不上」也可能只是被该门禁挡住，而非重连循环停了。自愈手段即 §1.2 的「重连验收与自愈」：判定本次未发起时把该状态清成 0、断开其 gatt，下一周期以空闲状态重新发起。日志侧另配 §1.2 的限频尝试与心跳，使「被门禁挡住」与「循环停了」可区分。

### 1.4 命名空间后台化（返回键 / 自动拉起收后台）

宿主 app 的返回键与自动拉起都不真正退出，而是把任务**收进后台**（保进程、BLE 不断），并从「最近任务」隐藏。

- **返回键接管判据（三条件全成立）**：开关开（`readBackHideEnabled`）、未在结束中（`!isFinishing()`）、当前 Activity 在接管范围内。
- **「在范围内」= `isTaskRoot()` 或 `isBackHideTargetActivity`**（两者并列，任一成立即可）。**为何不再硬要求 `isTaskRoot()`**：宿主只有引导页 `MainActivity` 与设置界面 `B6ExperimentalActivity`，而**设置界面并非任务根**（launcher 是 MainActivity，且跳转不 finish 引导页）；若硬要求任务根，用户在设置界面按返回就完全不生效（这正是「开关无效」的主因）。
- **排除表**：宿主 APK 内含若干**透明转发页**（借壳启动第三方界面、代替 `startActivityForResult` 取结果），它们不是用户可见页面，按返回不该收后台，故按类名前缀排除（`BACK_HIDE_SKIP_ACTIVITIES`）。
- **必须挂两处、但一次返回只生效其一**：宿主 Activity 全部继承 `AppCompatActivity`，androidx 的 `ComponentActivity` 已重写 `onBackPressed`（转 `OnBackPressedDispatcher`），虚拟派发永远落到这个重写版——只挂 `android.app.Activity` 那份时它从不被调用，钩子静默空挂。故主钩子挂 `androidx.activity.ComponentActivity.onBackPressed`，`android.app.Activity` 那份留作兜底（覆盖未走 androidx 的页面）；两者是同一继承链上的重写关系，同一次返回只走一个。
- **预测性返回不在覆盖范围**：宿主 `targetSdk=33` 且未声明 `android:enableOnBackInvokedCallback`，走 legacy `onBackPressed`；若将来 `targetSdk ≥ 35` 或显式开启该属性，两种挂法都会失效，届时须改挂 `OnBackPressedDispatcher`。
- **开关文件读取**：`readBackHideEnabled` 每次返回键都读一次 `/data/local/tmp/tempctrl_uiprefs` 的 `BACK_HIDE=0/1`——返回键是低频事件，一次小文件读取代价可忽略，换来「改了立即生效」。读不到（无文件/无该行/值异常）一律返回 true，与界面默认值一致（默认开启）。
- **`excludeFromRecents`**：把本任务从「最近任务」列表摘掉，只影响任务列表显示、不改变进程存活，与 `moveTaskToBack` 各管一半（一个保进程、一个不留痕）；属附加动作，取不到 `ActivityManager` 或没匹配到本任务时只打一行日志，绝不影响调用方。
- **自动拉起路径同源**：`hookAutoLaunch` 读到 `b6x_auto_launch` 标志后，在离开引导页时一并将任务收后台；开关开启时也从最近任务隐藏，与返回键路径做同样两件事。

### 1.5 字段名常量表按 app 类型分派（B6X/B7X 混淆差异）

B6X 用 SDK 原名、B7X 反编译产物已混淆，故字段名按 `appKind` 分派：

| 用途 | B6X | B7X |
|---|---|---|
| static 控制器字段 | `dataInteractionController` | `f50991b` |
| 连接状态字段 | `mDataConnectState` | `E` |
| gatt 字段 | `mBluetoothGatt` | `I` |

**B7X 混淆类 `com.flydigi.sdk.waspwing.a`**（controller）的方法映射：

- `a.S1(BluetoothGatt)`：GATT 连接成功点 → 置连接状态 + 型号识别；
- `a.T1(BluetoothGatt)`：断连统一入口（远程 + 本地）；
- `a.Z0(UUID, byte[])`：特征分发（`this.X` = 最新 `WaspWingInfo`）→ 刷新回传 + 型号修正。

另：B7X 连接失败修复——`c0.s1()` 检查 `BLUETOOTH_CONNECT` 权限，Android 16 返回 false，故强制其返回 true 以让连接流程走完；`WaspWingManager` 在 B7X 混淆为 `t9.j`，其 Kotlin 单例字段为 `f50990a`（反编译确认），兜底解析实例时使用。

### 1.6 上次设备持久化与自动进入设置界面

- **上次设备 MAC 落点**：宿主 app 私有目录 `/data/data/<包名>/files/tempctrl_last_dev`，**各包各记**。因为包名常量有 3 个（B6X / B6X_NEW / B7X）而 `appKind` 只有 6、7 两值，**必须按命中的包名常量拼**——按 `appKind` 拼会把两个 B6X 包合并成同一个文件。冷启动时本方法可能早于 `Application` 挂载运行、`getFilesDir()` 拿不到 context，故直接按包名拼死路径，写前先建父目录。
- **冷启动恢复**：`restoreLastDevice` 读回上次 MAC 得到 `lastDevice`，使后台重连在启动后即可工作（无需等用户手动连接）。
- **自动进入设置界面**：引导页 `MainActivity` 可见且 BLE 已连、本进程未进过设置界面时，`autoEnterSetup` 自动跳到设置界面；冷启动时 `autoStartSetup` 直接进设置界面（其 `onResume` 会 `tryConnect()` 自动连接）。`enteredSetup` 防重入：已进入过 / 从设置返回时不再自动跳。

## 2. 部署链路（Deployer）

`Deployer` 一次性把 APK 内的 C 二进制与 service.d 脚本部署到设备，并负责后续的启用/停止/更新/卸载。界面只经它动手（调用边界见 §2.1）；本节讲清「怎么算部署完成」「为什么不重启不算完」「看门狗怎么认」「卸载清什么」「文件落在哪」五件事。

### 2.1 部署完成判定（I4）

**I4 判据**（只用 APK 侧可得的信息）：

```
deployed = su 通道可用
         ∧ /data/local/tmp/tempctrl 存在
         ∧ 可执行
         ∧ md5 与 APK 内 assets/tempctrl-arm64 一致
         ∧ service.d 脚本存在
         ∧ md5 与 APK 内 assets/deploy/b6x-tempctrl.sh 一致    ← 脚本逐字节部署，故可直接比哈希
```

- **为什么只用 APK 侧可得的信息**：加 `--version` 之类要给 C 端加开关，而旧二进制不支持——那会让"判定"依赖"先更新"，成死循环。故判据全在 APK 侧算。
- **配置存在、守护进程在跑不算完成判据**：配置允许缺失（C 端有默认值）、进程允许未起，二者只作状态展示，不进 `deployed`。
- **调用边界（I5 的一半）**：界面只允许调本类的 `probe()`/`deploy()`/`uninstall()`/`startDaemon()`/`stopDaemon()`/`buildDiagnostics()`，**不得自己拼 shell、不得直接碰文件**；root 调用一律走 `RootShell`（见 §4）。

**落页判定（`needsRedeploy`，只读缓存、不跑 su）**：判据是「设备侧上次已知的二进制 md5」与 APK 内不一致。该缓存由两条路径写入——`deploy()` 成功就位后读回、或状态页探测到哈希一致时；它表达的是"上次看到的设备侧内容"，不保证此刻仍如此（实时状态仍以 `probe()` 为准）。

- **无缓存时退化为"首启判据"`!root_tried`**：从没部署过（也没试过 root）＝需要去状态页，让首次授权/部署入口仍可达；已经试过 root 却仍无缓存（被拒、或部署从未成功）＝不再自动引导。
- **APK 内取不到二进制**（本地构建没有 CI 注入的 asset）→ 无从比对，一律 false。
- **求值顺序**：先读 `SharedPreferences`、后算资产哈希。资产哈希（解压 + 哈希）是这条路上最贵的一步，而"已试过 root 却无缓存"这一支的结果与资产无关，故那条路上不再白算它。（只调换顺序，判据逐分支不变。）

**`ASSET_MD5_MEMO`：asset 哈希的进程级 memo**（key = asset 路径）。APK 内 asset 在进程存活期间不可能变，一次算过的哈希可一直用；两处调用点（`needsRedeploy` 的落页判定、`probe()` 每动作收尾）代价都不轻，memo 把「每动作数份」降成「每进程各一份」。用 `ConcurrentHashMap` 而非 HashMap：两侧各在自己的后台线程调用、会并发写；撞同一路径只是重复算一次（结果幂等），故不加锁。**只在成功时写**——否则一次瞬时失败会被永久记住、连重试机会都没有；不随 APK 更新失效（覆盖安装会杀进程，新进程自然是空表）。这一「读失败不留档」的口径与 §3.5 同源。

**超时按步骤分级（2026-10-02）**：`PROBE_EXEC_TIMEOUT_MS`(15s) 给 `probe()`（只读、不等进程退出）；`DEPLOY_WRITE_TIMEOUT_MS`(60s) 给部署写盘趟；`RESTART_TIMEOUT_MS`(30s) 给停旧起新趟与只重推脚本；`ALLOWLIST_TIMEOUT_MS`(20s) 给后台省电白名单。`EXEC_TIMEOUT_MS`(120s) 只留给非主链的 `uninstall()`/`stopDaemon()`。**为什么不再一刀切 120s**：任一步在设备上"挂住"都会把整个一键部署拖成分钟级等待（六步各撞满上限合计 ≈512s），而写盘只剩 `cp`+`md5sum`、停旧起新最多 8 秒——给它们 120s 等于把"慢"和"挂住"混为一谈。

### 2.2 停旧起新为什么单列

**部署只动盘、不重启进程**：盘上换了新二进制，不重启它就一直跑旧映像，"等于没更新"。故"换完盘立刻拉起一次"**接在部署之后**，由调用方（状态页）在部署结果上屏后自动调一次 `startDaemon()`，与手动点「拉起daemon」走同一条路径。`deploy()` 本身不重启。**部署趟末尾自带状态回吐**（`deployScript()` 末尾接 `probeTail()`）：写完盘的那一趟 su 顺便把存在性/md5/进程状态一起报回来，**不再另起一趟 su 探测**；回吐缺失（脚本被截断等）时 `deploy()` 才退回独立 `probe()`。`startDaemon()` 同理（`restartScript()` 末尾接 `probeTail()`）。

**`Result.placementsOk` 为什么与 `ok` 单列**：`ok` 还要求收尾自检（一次读回）也通过；而读回可能因与设备侧另一写者（脚本的自动更新）撞窗、或本次会话被超时打断而为假。若调用方只按 `ok` 决定接不接换进程，一次读回失败就会留下「盘上已换新、进程还在跑旧映像」且**没有任何补偿**的状态（旧映像会一直跑到下次手动动作）。故单列这一位：**盘面已就位就仍值得尝试换进程**。`deploy()` 成功时还会清掉拉起冷却（`lastStartAtMs = 0`），否则"防连点"会挡下紧随其后的自动拉起。

**`startDaemon()`：先停再起**。C 端用非阻塞 `flock` 做单实例锁，旧实例还在时新实例会立刻以退出码 2 退出，所以"已在运行"不能当作"无需拉起"——那正是"点了没反应"的原因。停止序列同 `uninstall()`：`kill` → 轮询 ≤`KILL_WAIT_LOOPS`(5) 秒 → `kill -9` → 再轮询 ≤`KILL9_WAIT_LOOPS`(3) 秒；仍未退出则**放弃启动**并如实回吐（抢锁必然失败，静默失败比报错更难查）。

- **`KILL_WAIT_LOOPS` 取 5**：C 端装了 SIGTERM 处理器——收到只置退出标志，要等当前一轮跑完、一轮最长约 5 秒（同部署脚本 `WAIT_LOOPS` 的注记），5 轮即够；实测用不到那么久，原为 30 轮。`KILL9_WAIT_LOOPS` 取 3：`-9` 已不可被忽略，只需一小段收尾时间。
- **失败重试改在设备侧同一趟内做（2026-10-02）**：`restartCore()` 里"起新 + 等 2s + 查活"最多跑两轮，不再由 app 侧整趟重来一次（省一趟 su 与 `RETRY_PAUSE_MS` 的 2s）。确定性失败仍不重试——冷却是拒绝而非失败（先于重试返回）、二进制不存在重试必然同样失败。`RETRY_PAUSE_MS` 已删除。
- **代价**：一次点击约 0~8 秒温控空窗（只等旧实例退出；设备侧重试再叠一轮 ≤2s）。冷却 `START_COOLDOWN_MS`(10s) 保留（防连点）。

**`stopDaemon()`：先停看门狗 shell、再停 daemon**。看门狗每 `RESTART_INTERVAL` 秒检查「daemon 不在就拉起」，只杀 daemon 的话最多 5 分钟被它拉回来，「停止」不成立。代价是看门狗要重启手机才会回到常驻；期间恢复靠 `startDaemon()`（会发现看门狗不在并把它一起拉起）或重新 `deploy()`。与 `uninstall()` 的区别：两者停的是同一对进程（共用停止片段），但卸载停稳后还要删文件，这里什么都不删。

**`restartCore()`：按看门狗在不在分两条路**——看门狗在（常态）→ 只停/起 `$BIN`（看门狗自己的 tick 会兜住后续进程级死亡，杀了它常驻保障就没了）；看门狗不在（如刚 `stopDaemon()`，或 `updateScript()` 刚把它停掉）→ 把 service.d 脚本拉起来、由它把 daemon 带回来（脚本启动时**不再**先杀 daemon："先杀"由 `killAndWaitSnippet` 负责，脚本内是"存在即不重复拉起"，见 §2.3 与 C 侧「看门狗反向保活」）。看门狗脚本第一步是**等亮屏**，灭屏时会一直等到亮屏才启动 daemon，故第二条路要等。第三条路（看门狗在、旧实例已停稳、二进制可执行）里"起新"改成一个最多两轮的循环：每轮 `sleep 2` 后查 `bin_pids`，没起来就再起一次；若第一轮其实起了只是慢，第二轮会因单实例锁立刻退出、不影响结果。

**`killAndWaitSnippet` 是停止序列的唯一出处**：`kill`(SIGTERM) → 轮询 ≤5s → `kill -9` → 再轮询 ≤3s；等待期内每轮重新取一次 pid 并再杀一遍。目标 pid 由 `pidSource`（`bin_pids`/`wd_pids`）提供，**不再用 `pkill -f`**（子串匹配会牵连无关进程，且"杀"与"等"会用两套判据）。

**`updateScript()` 为什么必须连看门狗一起重启**：脚本本身就是常驻的看门狗 shell，只换盘上文件、不重起它，那一层仍跑旧脚本的内存映像——新脚本里改掉的判别逻辑要等重启手机才生效。故先停看门狗 shell，再由 `restartCore()` 用**磁盘上的新脚本**把它拉起来。脚本换完用 `scriptInstallSnippet` 的「先落 `.new` 再 `mv`」：覆写它正在读的文件会让 sh"边写边读"读到半截，`mv` 换的是目录项、正在跑的 shell 继续持旧 inode。

### 2.3 看门狗识别

**身份判据只有一条**：「某个参数**整等于**候选脚本路径」。

- **comm 白名单只是省 fork 的快筛、不是判据**：真机上 service.d 拉起的看门狗 comm 是 `busybox`（`/data/adb/ksu/bin/busybox sh <脚本>`），app 自己拉起的是 `sh`；**曾经只认 `sh` 就把前者整条漏掉**（「停止daemon」静默失效且假报成功）。而枚举必然再撞墙（换个 root 方案就换个壳），故白名单一个都没命中时由 `wd_pids()` 全量兜底一轮。
- **与 C 侧、脚本侧同口径**：`wd_pids()`/`wd_match()` 与 `tempctrl.c` 的 `cmdline_has_script_arg()` 都只认「某参数整等于候选脚本路径」，两侧都不拿 comm 定身份；`bin_pids()` 则与脚本 `running()` 同源（`/proc/<pid>/exe` 的指向）。**两侧对 `(deleted)` 必须同口径（都算"在跑"）**：部署用 `mv` **原子替换** `$BIN`（先写 `$BIN.new` 再改名），旧实例此时 exe 显示成 `<路径> (deleted)` 却仍持单实例锁；任一侧漏判它，"这个实例谁也替换不掉"就成立（脚本会以为没在跑、反复起新实例又被锁以退出码 2 顶掉，盘上新二进制永不生效）。（原子替换同时消除了"先删后落"被打断留下"二进制不存在"半成品的那条路径。）

**为什么替掉 `pgrep -f`**：那是 cmdline 子串匹配，凡命令行里出现过该串的进程都被算进来。对 `$BIN` 尤其糟——该路径同时是 `tempctrl_service.log`/`tempctrl_uiprefs`/`tempctrl_*.status` 等一串兄弟文件名的前缀；后果不只是"多杀一个无关进程"：等待循环会永远等不到"已退出"（无关进程不受我们的 signal 影响），`<TAG>_STOPPED` 恒 0，「拉起daemon」直接判「旧实例未退出，已放弃启动」——一次无关进程就能让该功能硬失败。故改手写 `bin_pids()`（exe 末端锚定 `$BIN`）与 `wd_match()`/`wd_pids()`（整行相等，不依赖 grep 的二进制文件语义）。`bin_pids()`/`wd_pids()` 是**判据的唯一出处**，停（`killAndWaitSnippet`）与判活/取 PID（`restartCore`）共用，故"判有没有在跑"与"判停没停稳"不可能给出不同结论。

**看门狗上屏**：`probeScript()` 一并回吐看门狗个数与 PID（`WD_COUNT`/`WD_PIDS`），使「停机时它仍在跑」「同时有两个」在界面上可见；不输出它这两件事就完全不可观测。

### 2.4 卸载清理的本类边界与唯一例外

卸载部署 = 停进程 → 删脚本/二进制/锁/status 双文件 → 删私有目录里的运行时产物。清完后 `/data/local/tmp/` 侧不再有本次部署的残留；私有目录里只剩 `profile.conf`（用户配置）。

**故意不清的东西**（每条都有理由）：

- 私有目录的 `profile.conf` —— 用户配置，卸载部署≠删配置，重装后仍在。
- 省电白名单（deviceidle/appops/standby bucket）—— 下发对象是**散热器控制 app**（不是本界面 app）。对它仍然有益：钩子跑在散热器 app 进程里，那个进程被冻结/回收即断链；用户也可在系统设置里自行撤销。
- `tempctrl_last_dev` 的**新落点**（飞智 app 自己的私有目录 `/data/data/<飞智包名>/files/`，各包各记）—— 既不属本次部署的产物，也不在我们有权清理的目录里，**本类不碰**。

**唯一例外**是 `tempctrl_last_dev` 的**旧落点** `/data/local/tmp/tempctrl_last_dev`：它是老版本的迁移残留（daemon 侧预创建已删、现已无人读写），不会自己消失，故卸载时顺手清掉——这与"不碰新落点"并不矛盾。

**宿主 APK 被卸载后的 daemon 自清**（C 端 / `service.d` 脚本侧，**不属本类**）：宿主 APK 被卸载后 daemon 自行清掉落盘产物并停止运行。**两级判据必须都过**：一级判「父数据目录 `/data/data/<包名>` 不存在」（取**父目录**而非 `files/`——app「清除数据」只清 contents、父目录由系统保留，故可抗误判），命中后二级走 `pm path` 复核（**60s 节流**，`fork`+`pm` 的开销不许进每轮热路径），再叠**连续 2 次一级命中**才判真（滤掉重装中、挂载抖动等瞬态）。落点分工：**C 端为主**（判据挂在「等设备就绪」等待循环与 5s 控制块两处，故无 BLE 时不漏检），**`service.d` 脚本看门狗兜底**（判据同构 + 隔 5s 复核一次，**能删自己**，最坏 300s 一轮）。

### 2.5 文件落点与三份清理清单的同步义务

**三份清理清单必须同源同步**：卸载自清的清理清单有三份实现——C 端 `cleanup_artifacts_on_uninstall()`、`service.d` 脚本的 `cleanup_all()`、本类 `Deployer.uninstallScript()`，各存一份，改一处须同步另两处（`Deployer` 那份本轮已补齐 `tempctrl_uiprefs`）。清单固定为：`/data/local/tmp` 下的二进制与运行文件（status 双文件、`tempctrl_uiprefs`、`tempctrl_service.log`）、两个候选路径的 `service.d` 脚本（`/data/adb/service.d/` 与 `/data/adb/ksu/service.d/`）、`/cache/tempctrl.log`。**不显式删 `profile.conf`**：系统卸载会连带删掉整个 `/data/data/<包名>`，与「卸载部署 ≠ 删配置」的既有口径一致。**已知局限**：`tempctrl_b6x/b7x.status` 只要飞智 app 进程还活着就被其 LSPosed 钩子每秒重写，unlink 后可能被立刻重建、删不干净（须重启 app 或设备才彻底消失）；脚本那一侧全程静默——那一路的任何写盘都会把刚删掉的日志文件重新建出来。

**为什么二进制/脚本要经私有目录中转**：`/data/local/tmp` 与 `/data/adb` 都不是 app 能写的目录，故先用 Framework 的 File API 把 APK 内资源落到私有目录并授权（照 Scene 的做法），再由 root 的 `cp` 就位。`chmod` 只出现在 root 侧、作用于 root 拥有的路径；app 自己的落盘一律 `setExecutable(true,false)` + 沿父目录链逐级向上。

**落点常量**：二进制落 `/data/local/tmp/tempctrl`（沿用 noexec 规避：模块目录挂载了 noexec，不能直接执行）；service.d 脚本落 `SERVICE_D_MODERN`（Magisk/APatch/KSU≥`KSU_MODERN_VER_CODE`(10683)）或 `SERVICE_D_KSU_LEGACY`（KSU 旧版）两候选目录。

**预创建运行时文件（防御性、未经真机验证）**：`preCreateRuntimeFiles()` 在不存在时用 app 自己的 uid 先建 `tempctrl.log` / `tempctrl_webui.data`。前提是一个未经验证的假设：这两个文件原本由 root 的守护进程在 app 私有目录里创建，权限层面 app 大概率读得到（0644/目录 0771），但 **SELinux 标签层面未必**（非 app 域创建的文件不一定是 `app_data_file`）。由 app 先建，属主与标签就是对的；守护进程之后是**追加写既有文件**与**原地 ftruncate 轮转**（不 rename、不重建），因此不会把标签改回 root。刻意不用 `RootShell`（由 root 创建就回到要规避的标签问题）。边界：只在不存在时创建、失败不阻断部署。详见 §10。

**同步清单**：`writeSyncManifestIfNeeded()` 刷新一份 `KEY=VALUE` 清单（`APK_MTIME`/`BIN_MD5`/`SCRIPT_MD5`/`BIN_SRC`/`SCRIPT_SRC`），是 service.d 脚本在设备上找不到解压工具（`busybox`/`toybox`/`unzip` 三选一）时的**降级来源**。**时间戳是这份清单的保鲜期**：脚本只在「清单里的 `APK_MTIME` 与当前 APK 文件一致」时才用它——否则清单描述的是旧 APK，照它装就是装旧内容。只在 APK 换了才刷新（判据是一次 `stat`）；清单不存在（老版本升上来/刚清过数据）也走刷新。

**`cleanPrivateRuntime()` 为什么连清单/时间戳一起删**：它们描述的是"部署产物当前是什么样"。卸载后不清掉，脚本侧那份「上次核对通过」的记录会让 service.d 认为"本机部署过"，下次开机把刚卸载掉的东西又装回来。

**`powerAllowlistScript()`（2026-10-02 起移出部署主链）**：省电白名单**逐包**下发给已安装的散热器控制 app，四段命令（deviceidle/appops/standby/unfreeze）共处同一个 su 会话。**部署结果先上屏，白名单随后由 `submitPowerAllowlistAsync()` 后台 best-effort 补跑**：用 `RootShell.tryExec()`——只在"串行锁空闲且距最近一次交互动作 ≥5s"时取锁，拿不到就跳过本轮（下次部署时补），不会在"部署刚返回、界面紧接着拉起 daemon"的空档里抢锁。可能挂住的命令用 `toybox timeout 5` 包一层（无 toybox 则前缀为空，等同现状）。

- **为什么目标不是本 app**：本 app 是纯界面（manifest 里零 service/receiver/provider），没有后台职责；控制链路两端是守护进程与**跑在散热器 app 进程里的钩子**，那个进程被冻结/回收才真会断链。
- **包名从哪来**：`R.array.xposed_scope`（老 B6X/新 B6X/B7X-farsef）。Java 侧就这一份（`MainHook` 里的同名常量是 private，且那个类只由 LSPosed 在宿主进程里加载）；C 端另有自己的 `APP_PKG_*` 宏。复用作用域数组而不另写字面量，作用域增删与此处目标同步。
- **只对装了的下发**：判据 `[ -d /data/data/$PKG ]`（零 fork 的廉价判据，与守护进程自己判「已安装」的一级 stat 判据同源）；为此起一次 `pm` 不划算。**每次部署照旧无条件下发**（不做"先判后发"），与卸载不清理白名单的口径一致；差别只是这趟下发不再阻塞部署返回。

**`PREFS_ROOT_PROBE` 为什么集中在 `Deployer`**：写读这两处的类分处两个包（`Deployer` 在根包、`ui/StatusFragment` 在 ui 包），键名与文件名只在根包收口，避免同一字面量写两份。

**`KEY_UI_AUTO_UPDATE`（自动更新开关）**：键定义在 `params.def.json` 的 webui 组（`daemonConsumes=false`，界面自用），值落在 `profile.conf`：之所以不另写一份标记文件，是为了让**脚本侧读同一个键**（`b6x-tempctrl.sh` 直接 grep `profile.conf`），避免"界面写一处、脚本读另一处"的双份真相。读不到即按默认值【开】处理（与定义的 `default` 一致，口径同 `SetupActivity#isDeployEntryEnabled`）。

**已知代价（私有目录落点）**：app「清除数据」会把私有目录里的配置、日志、曲线数据与锁文件一并删掉，而 `service.d` 脚本与 `/data/local/tmp/tempctrl` 不受影响 → 会出现"守护进程还在跑、配置已空"。靠部署脚本的开机自检 + C 端回退默认值兜底；锁文件被删的那一次锁会失效（新旧实例锁到不同 inode）。这是私有目录落点最大的代价。

**操作记录归档**：状态页「操作记录」落盘在私有目录 `<files>/oplog/` 子目录（一次启动一个文件，无记录不建文件）。它不属部署产物、不与三份清单的判据耦合，故**三份同步清单无需改动**（app 卸载时系统连带删除整个 `/data/data/<包名>`）。

## 3. 配置存储与文件访问（ConfigStore / AppFiles）

`ConfigStore` 是界面读写 `profile.conf` 的唯一入口。配置落在 app 私有目录 `<filesDir>/profile.conf`；键的元数据（类型 / min / max / 默认值 / 分组 / label / enum 取值域）全部来自 `assets/params.json`（I1 单一来源），本类不手抄任何键定义。前四节讲 `ConfigStore` 与写队列 `ConfigWriteQueue`，最后一节讲守护进程产物的直读 `AppFiles`。

### 3.1 边界（I3）

**I3（已冻结）：配置读写归属** —— 界面只用 `ConfigStore` 读写 `profile.conf`，不得自己拼 shell 命令或直接碰文件。

**为什么是普通 Java File IO**：配置落私有目录，app 对自己的私有目录有读写权，**整条读写链路不需要 root**（C 端按绝对路径读同一个文件）。

**跨端落点一致性护栏**：`DAEMON_PRIVATE_DIR` 是手抄的 C 端 `PRIVATE_DIR` 宏（跨语言无法共享同一常量）。C 端按这个绝对路径找 `profile.conf`，而 app 只能写自己的 `Context.getFilesDir()`；两者不同名时配置互不可见 → `isPathAlignedWithDaemon()` 返回 false，界面必须如实告警。**改 `applicationId` 或改 C 端 `PRIVATE_DIR` 宏时，两边都要同步。**

`isPathAlignedWithDaemon()` 不能只做字面比较：设备上 `getFilesDir()` 通常是 `/data/user/0/<包名>/files`，而 C 端硬编码 `/data/data/<包名>/files`——`/data/data` 是前者的符号链接（同一目录）。故先取两者的规范路径比较，取不到规范路径再退回字面比较。

**出厂配置写出（`writeFactoryIfAbsent`）**：**仅当文件不存在时**才写；已存在则一个字都不覆盖（包括空白文件）。值取自 `params.json` 的 `factory` 字段（不是 `default`）。**由 `Deployer` 在部署时调用，界面不要自己调。** `LOG_FILE` 的 factory 已与 C 端默认对齐（同在私有目录），由 `参数定义/check_params.py --audit` 的 `crossChecks` 钉住；该键与 C 端 `PRIVATE_DIR` 宏、Gradle `applicationId` 的三方一致要求见其 `desc`。

写出厂配置时，**组总开关不在 `group.keys` 里**，必须先单独写出来（否则生成的配置里没有总开关行）；没被任何分组覆盖的键也要兜底写出（否则出厂配置静默缺键，C 端会退回代码默认值）。

### 3.2 原子写

`profile.conf` 是**带注释的文本**（整段说明、分组标题、行内注释 "值  # 说明"），不是 key=value 转储。故 **不能整文件重写**：改单键只替换该行的**值片段**，其余字节逐字节保持原样（注释、空行、行序、行内注释、CRLF 均不动）。

**为什么必须原子替换**：C 端每 5 秒 `stat()` + `st_mtime` 轮询热重载；半截文件会被读到。因此写入一律「同目录临时文件 → `fsync` → `renameTo`」。`rename` 失败（极少见）时不留下半截文件，删掉临时文件并明确报错。

**`ConfText` 是纯文本改写层**（不引用任何 Android API，可在桌面 JVM 上直接跑测试）：它是「改单键逐字节可复现」的唯一实现点。`spliceValue()` 把一行的值片段换成新值，保留 `=` 之前的全部内容、值前后的空白（含行内注释前的对齐空格）与 `#` 之后的注释原文；值片段全为空白（原值为空）时整段当作「值之后的对齐空白」处理，否则 CRLF 行会变成 `KEY=\r值`、行内注释也会跑到值前面。

**`setAll()`：批量改键合并为一次 rename** —— 全部改动合并为**一次** rename，避免多次 mtime 触发多轮 C 端重载。同键出现多行时全部替换（C 端按行顺序覆盖，只改第一行会不生效）；文件中没有该键时追加到文件尾部（带一行注释头）。**未知键（params.json 未定义）拒绝写入**，避免拼错键名写出一个永远不生效的配置项。值未变化时直接跳过、不触碰 mtime。改前先校验文件是合法 UTF-8（不是就拒绝改写，以免损坏内容）。

**写队列（`ConfigWriteQueue`：改即存的防抖层）**：C 端 `st_mtime` 只有**秒级**精度——两次写入间隔 < 1 秒时 C 端可能不重载。故连续改动合并成一次落盘，防抖窗口 `DEBOUNCE_MS` 取 **1200ms**（> 1000ms，留出写盘与时钟粒度余量）；多个键的改动合并为一次 `setAll`，只触发一次临时文件 + rename、只碰一次 mtime。队列只在**主线程**调用（Handler 定时 + `pending` 表），落盘跑在外部传入的单线程 executor 上、结果回主线程回调；`pending` 保留到写结果返回为止，避免写盘期间界面回退到旧值。写盘期间被改成新值的键继续留在待写表里，等下一轮冲刷（`finish()` 只摘掉「提交时的那一份」）。**`flushNow()` 在 onPause / onDestroyView / 页面隐藏时必须调**：被隐藏的 Fragment 生命周期仍是 RESUMED、onPause 不会来，不主动冲刷就会把改动留在内存里。

### 3.3 解析口径与 C 端 `config_parse_line()` 的对齐

解析口径照 C 端 `config_parse_line()`：跳过前导空白后以 `#` 开头的行、以及不含 `=` 的行不认；键尾空白 trim；值 = `=` 之后的**全部**内容（**行内注释不剥离**——数值键靠 `atoi/sscanf` 自然截断，路径键会把注释一起当成路径，C 端同样如此）。同键多行时**后出现的覆盖先出现的**（C 端按行顺序覆盖）。

`ConfText.lineStartOf()` 与 C 端 `trim_line()` 同口径；`ConfText.configLineEq()` 与 C 端 `config_parse_line()` 同口径。`parseValue()` 按类型解析一行值（数值取前 N 个整数 token，文本型 path / enum 取 trim 后原文）；超出 int 范围的 token 按 C 端 `atoi` 的未定义行为处理：跳过。

**多值键的字段数**：文件里给出的字段数少于定义时，C 端只应用给出的前几个字段，其余字段保持**代码默认值**（不是文件里的值）。

**读的快照 `Snapshot`**：`values` 中缺键用 `KeyMeta.defaultValue` 补齐（对外按 params.json 顺序输出，与界面表单顺序一致）；`unknownKeys` 是文件里存在但 params.json 未定义的键（界面应提示，不得静默忽略）。文件不存在 → 全部取 `KeyMeta.defaultValue`（与 C 端「未找到配置 → 用代码默认值」一致）。

**`parseText()` 不碰磁盘**：故写盘成功后可以拿刚写进去的那段文本直接走它（见 §3.5 的 `rememberWritten`），省掉一次读盘，且与「再读一遍盘」逐字同源（同一段字节、同一套解析）。

### 3.4 校验语义与告警分级

**`assess()`：把用户输入折算成「界面能接受的值」** —— 数值键按 `params.json` 的 min/max 逐字段钳制；文本键按自己的值域收敛（path 只 trim，enum 只认 `options` 里的字面量、表外回落出厂值）。

- **路径为空**：C 端会跳过该键、保持代码默认值。
- **路径含 `#`**：C 端不剥离行内注释，`#` 之后会被当成路径的一部分。
- **enum 取值域是文本的闭合集合**，没有「区间可钳制」一说：只认表里的字面量，表外一律回落出厂值（出厂值由定义保证在取值域内），并记一条 note。
- **数值钳制发生时**加一条 note（「已按定义 min/max 钳制」）。

`OptionMeta.value` 是写进配置的**字面量**（文本，原样落盘），`label` 是界面上的文案；取值域是闭合的（不在表里的值界面不接受）。界面的渲染落在 `ui.ConfigKeyRow` 的分段开关上，本类只提供数据。

`FieldMeta.bool` = 布尔子开关（值只有 0/1）：界面据此把该字段渲染成**开关**而不是数字输入框（定义里 `PID_TARGET_DIR[0]` / `PID_SPEED_RECALL[0]` / `APP_LAUNCH_SCREEN_GATE[0..1]` 为 true）；C 端的逐字段 clamp 边界生成时也**跳过**这些字段。

**诊断串（`describeState`）**：输出路径 / 定义 / 一致性三类信息。重载 `describeState(Snapshot)` 是给「已经读过一次盘」的调用方用的：配置页每次刷新都是「读一次 → 上屏值 → 上屏诊断」，让它再读一次只为拿「未定义键/提示」是白读一遍整个配置文件。

### 3.5 读写失败不留档

**读失败不留档**（与 `Deployer.ASSET_MD5_MEMO` 同口径，见 §2.1）：一次瞬时失败要能重试，留档就等于此后连重试的机会都没有。故 `read()` 读失败时不写 memo。

**读的 memo（快照 + 指纹）**：`read()` 按文件**指纹**（`mtime:size`）复用上一份快照——一次冷启动会连着读两次（落页判定 + 表单铺底），中间没有任何写入，第二次是白读一遍整文件。

- 指纹**必须带 `size`**：`st_mtime` 只有秒级精度，同一秒内改过而指纹不变会漏判。
- 指纹口径对外给出（`configFingerprint()`），供 `ui.ChartConfig` 之类的派生缓存共用 —— 不让各处自己 `stat` 文件。
- 写盘成功（`setAll` / `writeFactoryIfAbsent`）后就地更新 memo（`rememberWritten`），不必等下一次读再解一遍；因与「重新读一遍盘」走同一段 `parseText()`，memo 里的值与重读逐字一致，故同秒内连写两次（mtime 撞车、size 又相同）不会读出旧值。
- **登记前复核**：读盘前先记下当时的 memo，读盘 → 解析完成后，仅当「memo 仍是我开头看到的那个」且「指纹未变」才顺手登记——因为 `st_mtime` 秒级精度认不出同秒内的等长改写，事后无从分辨，故以「读盘期间盘上没变过」为准，否则登记等于把新内容顶回旧内容。
- **线程模型**：全部方法是本地磁盘 I/O，会阻塞（毫秒级）；可在主线程调用，但大批量读写在后台线程更稳。本类不含任何 root 调用。

### 3.6 守护进程产物的直读（AppFiles）

`AppFiles` 是界面直读守护进程产物（曲线时序数据 `tempctrl_webui.data`、日志 `tempctrl.log`）的统一入口，供曲线页与日志页共用。两个文件都落在 app 私有目录，同 uid 普通 File IO 即可读，**不需要 root**。

**未经真机验证的假设**：这两个文件由 **root 的守护进程**创建，权限层面 app 大概率读得到（0644 / 目录 0771），但 **SELinux 标签层面未必**（非 app 域创建的文件不一定是 `app_data_file`）。因此本类**不吞异常**：读取失败一律抛出带「路径 + 异常类型 + errno 文案」的 `IOException`，界面必须把 `diagnose()` 的结果原样展示，不许静默留白。本类不做任何 root 读取兜底（先用直读，真机验证后再说）；部署侧的对应防御（app 自己先建这两个文件，使属主与标签正确）见 §2.5。

**用 `Os.stat` 而不是 `File.exists()`**：前者能给出**真实 errno**（后者把「权限不足」与「不存在」都吞成 false，无法诊断）。`diagnose()` 由两条已知风险提示收尾——`errno=2/ENOENT` 表示守护进程还没写过这个文件（或落点在别处）；`errno=13/EACCES` 表示 SELinux 标签层面拒绝，需真机确认策略；并回吐守护进程侧固定落点 `ConfigStore.DAEMON_PRIVATE_DIR` 供比对，两者不一致时界面读到的路径与守护进程实际写入的路径不是同一个。

**尾读**：`readTail()` 读文件尾部至多 `maxBytes` 字节，并从下一个换行处开始（丢弃第一段半截行；若尾部整块都没有换行则整块给出）。`decode()` 按 UTF-8 解码，非法字节替换。

## 4. Root 调用（RootShell）

`RootShell` 是 app 侧唯一的 root 通道封装（零第三方依赖，只用 `Runtime.exec`），被 `Deployer` 用来跑部署/停起/卸载脚本。除 `getSuCommand()`、`getRecommendedSuCommand()`、`isSuCommandManual()`、`isAlive()` 四个纯读缓存的方法外，**其余公开方法都会阻塞 I/O，禁止在主线程调用**。

### 4.1 通道、超时与「脚本自退会被判成通道失败」

**做法**照 Scene（`a/a70.java`）：`su -v` 嗅探 root 类型 → 命令行选型 → 持久化 → 判活看通道连通性（不看进程）→ 退避重连。改进项：**结束标记 + 读超时 + 退出码回传**。

**结束标记协议**：`Channel` 把脚本写进 su 进程的 stdin，**末尾追加** `echo "<marker> $?"`；读取端扫到该行即拿到退出码。marker 每次调用唯一（`__WW_END_<id>__`）。

**由此派生的硬约束——脚本不得含 `exit`**：脚本自己退出会让末尾标记丢失，整次调用被判成**通道失败**。`Deployer.restartScript()` 等拼脚本时都据此不写 `exit`（见 §2.2）。

**超时**：`DEFAULT_TIMEOUT_MS`(30s) 为 `exec` 缺省（各调用点另按步骤传分级值，见 §2.1）；`SNIFF_TIMEOUT_MS`(5s) 用于 `su -v` 嗅探；`PROBE_TIMEOUT_MS`(8s) 用于判活/诊断的单次 `id`。超时后 `process.destroy()`、给 500ms 收尾仍不死则 `destroyForcibly()`（尽早把会话槽位还回去），并把已读到的部分回吐。双流（stdout/stderr）各自一个收割线程，**都 EOF 才算通道断开**（只看一路会在进程仍活着时误判）。

**串行化与自愈（2026-10-02）**：同一时刻只允许一个 su 会话（`ReentrantLock` 串行锁；交互动作 `exec`/`checkAlive` 阻塞抢锁，后台任务用 `tryExec` 非阻塞抢锁且要求"距最近一次交互动作 ≥5s"）。`exec` 按"实测可用 → 当前推荐 → 裸 `su`"依次尝试，**只在该命令"通道失败且非超时"时换下一条**（脚本自己返回非 0 与超时都不换——前者重跑是重复执行、后者换命令不会更快）。`resetChannel()` 复位失败退避与缓存的实测命令，`deploy()`/`startDaemon()` 入口各调一次——语义是"用户主动要，别被上次失败退避挡着"。这三条合起来消除了"缓存的实测命令失效后 `exec` 永远失败、只能重启 app"这条无自愈路径。**注意 `exec` 不再是单命令一次尝试**：一次调用最多跑候选表里 2~3 条命令。

### 4.2 「不退避」语义

`exec` **不退避**：调用方显式要求执行就真执行；执行失败只**更新**退避窗口，不回退这次调用。退避窗口只被 `checkAlive()` 消费——它命中退避窗口时直接返回 false、不真探测（`BACKOFF_MIN_MS`(1s) 起、逐次翻倍、上限 `BACKOFF_MAX_MS`(60s)）。

**例外（2026-10-02）**：`resetChannel()` 会主动清掉退避窗口与缓存的实测命令，由用户主动动作（部署 / 拉起）在入口调用——退避的本意是"别在后台反复撞"，用户明确要动手时不适用。

## 5. 启动时序与首帧

### 5.1 判定与预热并行的结构（ww-preload）

**要解决的问题**：冷启动时"落哪一页"要先建 `ConfigStore` 单例（读并解析 `assets/params.json`）、整份读 `profile.conf`、算资产 MD5、首读 `SharedPreferences`——四件都在 `onCreate` 的主线程链上，只为定一个页序号；曲线的第一帧（口径与数据文件首次读 + 解析）又串在同一根线程上排在它后面，被白白推迟一个判定的时长。

**结构**：`SetupActivity.onCreate` **首行**就把这两件事交给两根**进程级**单线程执行器（`ww-preload` 与 `ww-chart-warmup`），各在自己那根线程上同时起跑、互不阻塞。

- **预热为什么单独一根线程、不与判定共用**：判定是"主线程在等它"，预热只是纯优化，两者优先级完全不同。共用一根＝串行；共用一个池＝将来有人再塞任务进来，就可能把"判定不能等"的保证破坏。
- **"判定仍最先唤醒主线程"是结构性保证，不靠调度让路**：放行主线程的那次 `countDown` **只可能由判定任务发出**，且判定那根线程上除判定外别无他活，故"谁先跑"不影响这个结论。
- **"判定先提交"只是顺序偏好**：先 `execute` 判定任务让它早一步待跑；这不是调度保证（真保证见上一条）。
- **预热线程的优先级**：降为 `THREAD_PRIORITY_BACKGROUND` **之前**，先在默认优先级下碰一次共享的配置单例——`ConfigStore` 内部有一段 `synchronized` 构造（读并解析 45KB `params.json`），而判定那根线程要的第一件东西就是它。若降到后台优先级之后才触发构造，就可能出现"nice=10 的预热线程持锁解析、nice=0 的判定线程在监视器上等它"——后台线程被限流时，等的就是被拉长的整段解析，与"让判定先跑"正好相反。这一步不比原有路径多做任何事（`ChartConfig.load` 下面本来也要碰它）。降优先级之后才做曲线预热。
- **争抢的代价**：两根线程剩下的只有纯粹的 CPU 争抢。设备有空闲核时不成立；单核或核被占满时判定可能被拉长（**真机未测**）。最坏即退回现状，无副作用。

**主线程的有界等待（`LANDING_WAIT_MS` = 50ms）**：冷启动时 `settleInitialPage` 让主线程**有界等**判定一手。

- **取 50ms 的余量**：判定一步只有建 `ConfigStore` 单例、读一次配置、一次资产哈希（都在 `assets` 与私有小文件上），正常设备是十几到几十毫秒量级；而主线程在 `onCreate` 里已经先做掉 `setContentView` / adapter / 监听器那一串，给了预热线程一段真实的前置时间。
- **等到了就与"当场判定"等价**：直接落定最终那一页，没有后续纠正动作，也就不会闪。
- **等不到也不是无界等**：满 50ms 一定返回（超时、被中断、判定抛异常都照样返回）；超时后由占位页先顶上、判定回来再 `applyLanding` 纠正，故不会把主线程卡在首帧上。
- **`landingDone`（`CountDownLatch`）只覆盖判定**：它只由"算完判定"那一步放行，曲线预热不在覆盖范围内——曲线再慢也不会拖住落页。

**落页判定的判据（`landingPageIndex`，只在后台线程调）**：三级优先里去掉"进程重建取回上次那一页"那一级（它不需要 IO，留在 `settleInitialPage` 里判），剩两级：① 部署入口开关为开、且 `Deployer.needsRedeploy` 为真 → 落状态页（首次部署与 root 授权的入口都在那里）；② `UI_START_PAGE` 设定的起始页（读不到或值非法即出厂 `config`）。**不跑 su 真探测、不自动跳页**——第 1 级只看缓存比对。

**「部署入口开关为开」不是直接读 `UI_DEPLOY_ENTRY` 的存值**（`SetupActivity#isDeployEntryEnabled`）：**自动更新开着时本项按"关"处理**（只在读取时压制，**不写回用户的 `profile.conf`**）——自动更新本就由状态页的后台探测静默重部署（三页在启动时全部建出，见 §8.1），不必再导用户去状态页。**唯 root 尚未取得时例外**：那一次仍按存值生效，好让用户落到状态页去拿 root 授权与首次部署。
例外判据是 `Deployer#rootNotYetGranted`，读的是落盘快照 `KEY_ROOT_OK`（该 prefs 文件与 `needsRedeploy` 用的同一个，故不额外走磁盘）：由状态页探测路径在拿到 `Status#suOk` 后经 `Deployer#rememberRootState` 写入——**su 不通即写 false**，于是 root 丢失后"尚未取得 root"可再次成立、例外自动恢复；首次安装取得 root 后转为 true，此后安装更新不再例外。

**两条落页路径**（`settleInitialPage`）：① 进程重建（`savedInstanceState` 非空）→ 回到上次那一页（纯内存，当场落定）；② 冷启动 → 判定由预热线程算，有界等它一手（见上）；等不到则用 `LANDING_INDEX` 手头已有的那个占着（进程级：本进程早先算过就落在上次那页，一次都没算过才是 `DEFAULT_START_TAB`），判定到达后 `applyLanding` 纠正。**不播放入场动画**：冷启动直接落在那一页，不从第 0 页滑过去。

**预制造（`preInflate`）的提交点**：`ConfigPreInflater` 的提交点是"与落页判定、曲线预热并列的第三件后台活"——趁主线程忙首帧时把配置页要 inflate 的键行控件先造出来（主线程取不到就现场造，故失败或没赶上都没有副作用）。**为什么提交点放在 `super.onCreate()` 之后、而不在 `preload` 里**：预制造要用的 inflater 必须带上 AppCompat/Material 装好的视图工厂（否则 `<TextView>` 造出来的是基类而不是 `MaterialTextView`，预制造件就与现场造的不是同一种控件、也不是同一套样式），而那个工厂是 `AppCompatActivity.onCreate` 里装的——`preload` 在 `super.onCreate()` 之前跑，那时还没有工厂。故提交点放在 `super.onCreate()` 之后（约第 25ms），到建表起点仍有三百多毫秒余量。克隆 inflater、归属比对、关门都在 `ConfigPreInflater` 里做；克隆来源是 Activity 自己那份 inflater（与页面 `getLayoutInflater()` 同源，故造出的控件与现场造的逐像素一致），那份 inflater 只许后台那一根线程用（LayoutInflater 不能跨线程共用）。与主线程共用 AppCompat 视图工厂这一层的边界与警告，见 §6.2。

### 5.2 建表两段与露面闸门

**参数区露面前的那段空窗**：真页面的内容（尤其配置页那份几十行表单）要几百毫秒才建出来。建好之前配置页的参数区一直 `GONE`，空窗里不会出现"半成品"，页面区是空的。

**建表分成两段，分界点就是"用户看得见的部分"**（`ConfigFormController#buildIfNeeded`）：

- **段一**：各分组的**卡头**（标题、总开关、徽标、箭头）+ 组头开关值与卡头徽标。配置页默认全部折叠，此时用户能看到的每一样东西都已就位——故这一段末尾就把参数区露出来、置「就绪」。
- **段二**：各行与全部字段 + 值上屏 + 自检 + 诊断。这一段在"真页面第一帧画完"之后才跑（见下）：用户等的是"看得见的界面"，而不是那几十行还折叠着的输入框；总工作量并没有减少，只是把它挪到了用户看不见的时候。

**默认展开的页面不分段**（设置页只有一组且默认展开）：折叠体可见时先露卡头会露出一张空卡，那就成了"半张表"，故它的两段在同一趟里连着跑完再露出。终点状态与分段前一致。

**露面闸门：等这一趟 pre-draw，且用队首投递而非普通 `post`**（`ConfigFormController#scheduleRowsPhase`）：

- **为什么等 pre-draw**：段二是一段一两百毫秒**不中断**的主线程消息，必须在"真页面第一帧画完"之后才开跑，否则它会把那一帧整段推后。这条闸门**不能**改成"段一末尾直接 post"：在"段一落在首趟 traversal 之后"的形状里，直接 post 会让首见时刻最晚推后一个段二（实测 115~245ms）。
- **为什么是队首投递而不是普通 post**：pre-draw 在 measure/layout 之后、绘制之前派发，这一趟画完就轮到队列里的消息；而普通 post 排在队**尾**——实测"本趟 pre-draw"到"段二真起跑"之间白等 **38~48ms**（排在它前面的是曲线子页的异步事务、曲线首次上数据，谁先谁后纯看运气）。段二要等的只有"这一帧画完"，故插到**队首**：本趟一结束就起跑，不早（不吃首帧）、不晚（不吃排队）。
- **兜底延时（`ROWS_PHASE_FALLBACK_MS`=1500ms）**：pre-draw 只在窗口绘制时派发，万一这段窗口压根不绘制（极端情况）就等不到，故另挂一次性延时（不轮询、不重试、跑过即废），到点也把行建出来。这与"不许等用户展开才建"是同一件事的两面：行必须在某个不依赖用户动作的时机建完，用户展开某组时它应当已经在了（展开只切可见性，从不现场建控件）。

**视图重建时补读一次盘**（`pendingReload`）：建表用的那份预热快照可能已旧，要补读；补读**等行建完之后再起**（正常路在段二收尾），否则先读回来的新值会被随后那一趟建表整片盖掉。定义没到位那条路没有段二，在 `buildIfNeeded` 的错误分支里补上。

**2026-09-26：原先那层"骨架占位层"已整套删除。** 它盖这段空窗（把上次的页面截图先贴上去），但**盖不到首帧**——当前形状下只剩十几毫秒的遮盖窗口，成本却要一次解码 + 一层常驻视图 + 一次重截，故按实测整套删除。删除后参数区的"露面"仍由上面的建表两段与闸门控制，不出现半成品。

### 5.3 启动耗时记账

**是什么**：`StartupTiming` 是启动耗时的**旁路记账**——进程级几张静态槽位，量出"启动那一刻各段各花了多少毫秒"，供诊断区展示（真机排障用，**不参与任何判断，也不影响任何逻辑**）。

**口径**：

- **原点** = `begin()` 被调的那一刻（`SetupActivity.onCreate` 首行）。所有数字都是"相对 onCreate 首行"的毫秒数，同一进程内可比、跨启动也可比；但**不能**与 logcat 的 `Displayed` 之类直接相减（那些从进程 fork 起算）。
- **每槽只记第一次**（首写胜出）：报文说的就是"本次进程冷启动那一次"，故进程内第二次进 Activity（暖启动）不会把这些数字刷成别的含义。**例外**是两个计数槽（`count`）：它们"每来一次加一"，报的是"到此刻为止一共几次"。
- **计时贴在"干活的地方"**：并行之后同一份活可能由这根线程干、也可能由那根干（谁先到谁干，后到的命中缓存）。若在"调用的地方"计时，先干的那条会把耗时算走、后到的只报 0——数字随调度翻脸。故各调用方把计时点放在真正读盘 / 解析的那几行上。

**为什么放在主包**：记账点既在 `ConfigStore`（核心）也在 `ui` 各页里；放主包则两边一致地 import（方向 `ui → 主包`，既有约定）；若放 `ui` 包，就会多出一条"核心反向依赖界面包"的边。

**开销**：每个记账点只有一到两次 CAS（记一段是"起点 + 耗时"两次；失败即放弃，**不重试、不自旋、不阻塞**）或一次 volatile 读 + 一次减法；建表细分的累计槽更轻——只在建表主线程上对一块普通 `long[]` 做两次数组访问与一次加法，**无锁、无 CAS**，一整轮建表收尾才写一次展示槽位。全部记账**无 IO、不建线程、不轮询、不分配对象**（只有 `report()` 拼文本时分配一个 StringBuilder）。除两个计数槽外，每槽在进程内只可能被写一次，故竞争窗口只存在于启动那一瞬。所有方法都**无抛点**，故它在链上调用不可能改变原有逻辑。

**槽位分组（顺序即展示顺序）**：段耗槽（落页判定 / 配置定义 / 配置首份快照 / 曲线口径 / 曲线数据首读）、建表两段（`FORM_BUILD_HEAD` 首屏段 / `FORM_BUILD_ROWS` 可见后段）、建表内部八项累计槽（控件制造 / 说明画笔 / 文本实测宽 / 值回填 / 挂载 / 徽标 / 自检 / 诊断提交）、时间点槽（各 `MARK_*`）、预制造埋点（命中 / 未命中 + 六个成因）、未命中构成（按布局 id 各一个）、备料快照两个。

- **建表两段的拆并史**：两段之和≈原先那一个"主线程建表"槽（总工作量没变），拆开是为了看清"用户实际等了多久"（= 首屏段）与"用户不用等的活有多重"（= 可见后段）。
- **建表细分八项的读法**：八项合计与"建表·首屏 + 建表·可见后"相减，差额就是**没埋到点上的胶水代码**；某一项占比高就说明那一类活是瓶颈。一项都没计入过就整段不显示。
- **"自检 / 徽标 / 诊断提交"三项原先合成一项"自检对齐"**：拆开是为了看清诊断自身占多少（诊断区收起时"诊断提交"应≈0）。
- **`MARK_AFTER_BUILD_FRAME`**：参数区露出之后的第一次 pre-draw；与建表两段的接缝相减，即"参数区露出之后到真正绘制之前"那一段（vsync 与布局，还是队列里的别的活）。露出点落在"建表·首屏"末尾。

**累计槽为什么用普通 `long[]` 而非原子数组**：只有建表的主线程会写（`accBegin`/`accEnd`/`accReset`/`accFlush` 全由建表那条链调用），故不需要任何同步；写进展示槽位的那一步（`accFlush`）才用 CAS，读它的诊断区因此永远看到一份定值。

- **`accFlush` 为何写在建表末行而非每次 `accEnd` 之后**：一是省掉 134 次同步开销，二是这一轮建表没跑完时诊断区读到的仍是上一轮的定值（不出现"只填了一半"的中间态）。
- **细分合计必须与六项同源**（都取已 flush 的展示槽位）：取 `ACC_MS` 的话，第二轮建表（视图重建）会把它清零重算，而展示槽位是首写胜出 → 六项是上一轮、合计是这一轮，两个数永远对不上。

**埋点位置**：`armPageViewMarks` 量第一页 / 第三页的视图各自何时建好，用来切分 `[onCreate 结束, 首帧]` 那一段（外壳布局与类加载占多少、三页的构造又占多少）；`recursive=false` 只收本页三个页签，不把配置页的子 Fragment（曲线区）算进来。`markFirstDraw` 量"页面区第一次绘制之前"（挂在 pager 的视图树上——它是页面区的根；pre-draw 在绘制**之前**派发，故本时刻是"即将画出第一帧"）。两者回调体内都只有静态调用，无 IO、无锁、不建线程，不可能影响逻辑。

**预制造埋点的判读口径**：命中 / 未命中看"池子里有没有件"，六个成因（失败 / 未就绪 / 无实例 / 已关门 / 身份不符 / 已启动）看"谁是死因"；未命中构成把"缺的是哪几种件"按布局 id 摊开；备料快照判"结构性缺件 vs 没赶上"（`126 − POOL_AT_ROWS_BEGIN` = 段二开跑前就缺的件数即结构性；`未命中 − 上面这个数` = 段二期间备料还没赶上的件数即竞态）。

### 5.4 主题必须在 `super.onCreate` 之前

`SetupActivity` 与 `SettingsActivity` 都在 `onCreate` 里**手动** `setTheme(R.style.Theme_B6XTempCtrl)`，且**必须在 `super.onCreate()` 之前**：

- **原因**：`AndroidManifest.xml` 无 `android:theme`（本轮冻结），而 `AppCompatActivity` 要求 AppCompat/Material 主题——它会在自己的 `onCreate` 里校验主题，顺序反了直接抛 `You need to use a Theme.AppCompat theme`。
- **代价**：onCreate 之前的一瞬仍是系统默认窗口背景（无碍）。

## 6. 配置表单界面

配置页（`ConfigFormFragment`，页签「配置 · 曲线」）与设置页（`UiSettingsFragment`，顶栏设置按钮进入）**共用同一套表单实现**，只有这一份：数据流在 `ConfigFormController`，一个键一行在 `ConfigKeyRow`，一个分组一张卡在 `ConfigGroupBinder`，控件预制造在 `ConfigPreInflater`，诊断区在 `ConfigDiagnostics`，设置页的重置栏在 `ConfigResetBar`。两页各自只留自己的壳与自己独有的块（配置页：曲线子页 + 诊断折叠体 + 键渲染自检；设置页：空态与重置栏）。**边界（I3）**：界面只经 `ConfigStore` 读写 `profile.conf`，不自己拼 shell、不直接碰文件、不自己解析 `assets/params.json`。建表的时间线（两段与露面闸门）见 §5.2。

**档位表增删/排序已随 Gear 删除**：原先"按风扇/制冷数量作全局重配对（扇>冷=高配高、冷>扇=低配低）"需服务端支持，故界面已无档位表编辑能力。

### 6.1 五型渲染体与行骨架

**一个键 = 一个 `Renderer`。** 定义里只有 switch / int / multi / path / enum 五种 `type`（`int` 是其余情况的兜底），各一份实现；行骨架（参数名 + 键内控件 + 行级文本）与落盘规则五型共用。键的 label / desc / 单位 / 范围 / 依赖 / 取值域全部来自 `KeyMeta`（背后是 `assets/params.json`），本类不手抄任何键定义、也不自己解析 `params.json`。

**行骨架与换行几何（配合 `WrapRowLayout`）**：行根是 `WrapRowLayout`，子视图分三类，换行全部由容器按这三类标记排（本类不自己算行宽、不自己判换行）：

- **参数名**（leading）：左起第一段，宽由内容定。
- **键内控件**（trailing）：输入框（int / path）、各字段（multi）、开关（switch）、分段开关（enum）——整段贴行尾，放不下整段移到下一行，整行还放不下才在段内折行。
- **行级文本**（fullLine）：说明 / 备注 / 状态，以及单值键从字段里挪出来的单位-范围说明，各自独占一行、按整行宽折行。

行内垂直居中由容器给，本类不再自己算盒高与墨迹位移。

**参数名的两种竖直处理**（都是"看起来对齐"的两条不同路子）：

- 多值键参数名**钉垂直中心**（`alignLabelToInputBox`）：字段根比输入框高（下方挂着单位/范围说明行）时，把参数名中心钉在行顶之下"输入框半高"处。只标多值键，且首个字段必须是输入框型（单值键说明已挂行级、行高就是输入框高；开关行居中即对齐开关中心；首字段布尔的多值键同理——布尔字段根只有开关）。
- 非开关行参数名**整体下移**（`shiftLabelInNonSwitchRow`）@dimen/config_label_shift：这是**渲染位移，不是钉垂直中心**——那些行的行高各不相同（enum 行只有档位按钮高 21dp，带长说明的多值键整行更高），钉死偏移量只在行高恰为 @dimen/field_height 时才对；位移量不进测量、不进排布，行高与换行几何一个字都不变。开关行的名字不动（开关墨迹经 0.75 缩放后与行中心同心）。

**数值字段的宽 = max(说明文字宽, 当前值文字宽, 最小宽)**（三者都已含输入框左右内边距），只在建行与值回填/提交时算——边输边撑宽会让整行跳（值长了框自己横向滚）。

- **说明为什么按画笔量**：material 的 `TextInputLayout` 不参与说明测宽（`onMeasure` 即 `LinearLayout.onMeasure`，框宽只由 `EditText` 撑出），说明只是"画"在框里、画不下就打省略号——量一个空框量不到说明（说明常被截成"每周…"）。量用的是**渲染说明的那档字号**（12sp，不是输入框正文的 16sp），且**字距一并施加**（说明外观的 letterSpacing ≈ 值 3% 的宽，漏掉就是把说明量窄）。
- **末尾那 1dp（`config_hint_slack`）不是余量而是安全量**：material 判"说明装不装得下"用「可用宽 < 文字实测宽」（浮点值与整数宽比），贴到 0 余量时一个像素误差（字距取整、量宽取不取 ceil）就会判成装不下、打上省略号；留 1dp 把临界推开。与字号无关，改小字号只会更宽裕。
- **说明宽按字段缓存**（`Field.hintWidth`）：说明文本与字号不随值变，一轮建表量两遍（建行一遍、上屏一遍），缓存后第二遍只剩值宽要实测。
- **最小宽**取最小可点目标 @dimen/row_min_height(48dp)；"无上限"一侧不设钳制（装不下由容器换行，不为塞一行截断说明）。
- **说明画笔复用一份**（`HINT_PAINT`）：每次先 `set` 成输入框正文画笔再改字号字距（`set` 是拷贝，不改控件自己的 Paint），调用方拿到只做一次 `measureText`。**样式链一轮建表只走一次**（`ensureHintStyle`，失效键=密度×字体缩放），原先每字段每次量宽两趟 `obtainStyledAttributes`（64 字段×2 遍=256 次）。取不到 `hintTextAppearance` 时按正文画笔量（框偏宽但不会截断）。

**path 字段**：单行文本吃满行尾、**不按内容定宽**（路径长度不可控，默认日志路径 58 字符在 16sp 下约 570dp，定宽顶出屏幕，而文字在框里居中、被裁的是两端）。回填时把**光标钉到末尾**——`setText` 会把光标置 0，框架随后在自己的 pre-draw 里按"把光标摆进可视区"（`bringPointIntoView(getSelectionEnd())`）摆一次，留在 0 就摆到路径左段；钉末尾后一律显示右半段（看得见文件名）。`applyPathScroll` 再把横向位置摆到最右端，上限取 `Layout.getLineRight(0)` 减视图宽（**不能**取 `getWidth()`：开了 `scrollHorizontally` 的输入框传给 Layout 的宽是 1MB，拿它算会摆到文本右侧的大片空白里、框里一个字都画不出）。聚焦时都不动（编辑中位置归用户与光标跟随）。

**enum 分段开关**：形态与曲线页顶部窗口档位同源（`MaterialButtonToggleGroup` 单选+必选，按钮复用 `item_chart_window_button.xml`，单一实现）。按钮 id 是"取值↔控件"的唯一纽带；磁盘值不在可选项内时（定义换过取值域）**一项都不选中**：界面不假装成某一项，用户点选即写入合法值。选项文案取 `OptionMeta.label`、取值取 `OptionMeta.value`，两者不混用。

**`setTextIfChanged`：文本没变就不写回控件。** `TextView.setText` 对内容相同的文本**没有短路**——照样换内部 `CharSequence`、把光标复位并请求重排；建表两遍里第二遍的值与第一遍完全相同，这层比较就是替它省掉那些白做的动作。

**什么时候落盘（四条规则）**：

| 型 | 时机 |
|---|---|
| switch / enum | 值只有完整两态 / 取值即完整 → 切换 / 点选即排入防抖队列 |
| int / multi | 每次输入都排入队列（写入前先 `ConfigStore.assess` 钳制，磁盘上不会出现越界值）；失焦时把钳制后的值回写控件并提示"原值 → 钳制后" |
| path | **只在失焦/提交时落盘**：半截路径会被 C 端当真路径去 `open()`，写坏值的代价高于"少一次即时保存" |

- **"还没输完"（`read` 返回 null）一律不写盘**；失焦时退回当前有效值并提示"已恢复"。布尔子开关单独切换时，整键里"没输完"的数字字段回退到当前有效值，绝不把"没输完"当成 0 写下去。
- **值未变则不写**（`ui.equals(onDisk)`）：连 mtime 都不碰，避免无谓触发 C 端重载；待写项本身也是"已经过校验的最终值"（见 §3.2），故不存在铺进非法值的问题。
- **程序化回填屏蔽回调**（`suppressChange`/`suppressMaster`），不当成用户改动。

**"未生效"压暗与判据只有一份**：依 `requires` 压暗本行（参数名、键内控件、行级文本，含从字段里挪到行级的说明行），判据 `isUnsatisfied`（`requires` 任一键当前值为 0 或取不到）。**行内压暗与分组卡头那枚「未生效」徽标共用这一份判据**——后者在"行还没建出来"的时序里要自己问 store 算同一个结论，抄第二份迟早两边不一致（收起态显示错的徽标）。

**分组卡（`ConfigGroupBinder`）**：一张卡 = 卡头（标题 + "未生效"徽标 + 组头开关 + 展开箭头）+ 分隔线 + 键行容器。

- **组头开关就是 `role=master` 的那个键**（也是普通键，改它同样走"改即存"），绑定逻辑与行内开关完全共用 `ConfigKeyRow.commitSwitch`；master 为 null 的组（"未分组"兜底组、设置页的 `webui` 组）卡头不放开关键。
- **两个"整组一句话"的标注都只在卡头出现一次**：本组只要**有任一**键依赖未满足就显示「未生效」徽标并在组内逐行压暗（指向关系靠"压暗的行 + 组头一枚徽标"表达）；只要有任一键 `daemonConsumes=false` 就在卡头显示「界面自用，守护进程不读取」。判据是"有任一"而非"全部"——界面组里 `UI_BACK_HIDE` 是要被 C 端读的，按"全部"判就一次都标不出来。
- **键行全建、展开只切可见性**：卡头在构造时建好，**本组全部键行**由 `buildRows()` 一次建满；`setExpanded` 只切 `config_group_body` 的可见性与箭头旋转，**展开从不现场建控件**。行与定义一一对应，故徽标、压暗、静默刷新与"值未变不写"的判定都只看行。
- **`buildRows` 不铺值、也不刷徽标**：行建起来之后一定紧跟一次 `ConfigFormController.applySnapshot`（建行与上屏是同一次调用里相邻的两行，中间不插别的活），值 / 组头开关 / 徽标 / 压暗由它一次铺满。**原先"建行时铺一遍、上屏时又铺一遍"是同一份值的两遍**（其中字段宽与说明画笔那一段尤其贵），故这里不铺。
- **`refreshBadges` 在行没建全时不能走这条路**（判据是"行数≠键数"，不是"行表为空"）：建表两段之间的窗口里行还没有，段二中途抛异常时行只有一半——按不完整的行表算出的"未生效 0 个"会把卡头徽标错误隐藏，而那枚徽标在收起态是**唯一**可见的依赖提示。故没建全就转走同源判据的另一条路 `refreshHeaderBadge`（直接问 store，不经过行；两条路算的是同一个数）。

**值 ⇄ 控件（`ConfigFormController.applySnapshot`）**：写进控件的值取**当前有效值**（`effectiveValue`：待写项优先、否则磁盘值）而**不是快照本身**——快照可能比用户刚做的改动旧，直接铺会把用户眼前的改动悄悄顶回去；参数区露面与行建好之间隔着约三百毫秒，用户完全可能在这段时间里拨过组头开关（那一下改动此时还在待写队列里）。待写项本身也是"已过校验的最终值"，故不存在铺进非法值的问题。

**键渲染自检（`ConfigFormFragment.renderSelfCheck`）**：**每个定义键都要有可编辑入口**——本页键行（role=setting）、设置页的键（`webui` 组）或组头开关（role=master）。三个分项在建表时一次算定（键行数取各分组"整组"的键，见 `ConfigFormController#rowKeyCount`），不会因展开先后而变；`role=master` 的键不出现在任何 `group.keys` 里，`webui` 组的键在本页不渲染，故只数本页键行会恒少于定义数——自检正是用来暴露这个差额。自检文本渲染在诊断区（折叠体内），顺带把未定义键与读取提示摆出来。

### 6.2 预制造（ConfigPreInflater）

**目的**：配置定义一到位，就用一根后台线程把建表要 inflate 的控件先造出来放着，主线程建表时按布局取用（见 `ViewSource`）——把"134 次 inflate、约 580 个 View 构造"里最贵的那一段从主线程挪到后台空档，建表耗时与"参数区露面"的时间随之提前。与 `ww-preload` / `ww-chart-warmup` 同族：启动期一次的后台线程，做完即闲。

**它凭什么可以不在主线程造**（逐条论证）：

- **不 attach**：造出的件没有任何父容器——走的是 `inflate(layout, 空壳父容器, false)`，第三个参数 false 时 inflate 只借父容器生成 `LayoutParams`，**不会**把件加进去。故这些件不在任何视图树上。
- **不 measure / 不 layout / 不绘制**：本类只调 `inflate`。
- **不读主线程的视图**：造的全是全新控件，不访问页面上任何已 attach 的视图或它的测量结果。
- **不依赖机型时序**：主线程取件时件没造完就**现场自己造**（`ViewSource.inflate` 的兜底路），生产与消费之间没有等待、握手、超时。故"后台被限流"只会把收益削成零，不会退回比改前更差，也不会拖慢任何一步。**主线程绝不预制造——它只问一句"造好了没"。**
- 本类自己的共享可变状态只有一处（`pool`，放/取各是一次队列操作；队列自身的同步即完成了"全新构造的控件"向主线程的安全发布——这是把它做成队列而不是普通 Map 的原因）。

**与官方 `AsyncLayoutInflater` 的关系（不要拿"官方也这么干"当依据）**：官方那条路**不覆盖**本类做的事——它的 `BasicInflater` 源码注释写明"不支持设置 Factory/Factory2"，而且是 `new BasicInflater(context)`（没有工厂），故**不会**与主线程并发进入 `AppCompatViewInflater`（AndroidX 直到 `asynclayoutinflater 1.1.0`，2025-04，才补上 `AsyncAppCompatFactory`）；它的 `InflateThread` 是普通 `Thread` + `LinkedBlockingQueue`，**没有 Looper**。

**本类比官方多出来的一层共享（以及它为什么当前不构成竞争）**：inflater 由 `cloneInContext` 克隆而来，而它**按引用复制** `mFactory2`——于是后台线程与主线程**共用同一个 AppCompat 视图工厂**（`AppCompatDelegateImpl` / `AppCompatViewInflater`）。该工厂里有**无同步**的共享可变状态（`AppCompatViewInflater.mConstructorArgs` 与静态 `sConstructorMap`）。**但这条路径对本模块当前不可达**：`createViewFromTag` 只在"标签名不在 AppCompat 那 14 个已知名内"**且**该标签带 `android:theme`/`app:theme`（`themifyContext` 因此换了一个 Context）时才被调用；本模块 `res/layout` 下 17 个 layout **没有任何一处**带主题属性，故那条分支不会被走到；落回框架 `LayoutInflater.onCreateView` 的 `LinearLayout` 用的是每个 inflater 各自的 `mConstructorArgs`，且整个 inflate 包在它自己的 `synchronized` 里。其余共享面已逐个核过（`AppCompatDelegateImpl.createView` 不写任何字段；`ResourceManagerInternal`/`AppCompatDrawableManager` 的可变缓存全部 `synchronized`）。

> **⚠️ 警告（在本类预制造的任何 layout 里加主题属性前先读这句）**：上面那条"安全"**是布局属性决定的，不是 API 保证的**。将来在任何一个 `item_config_*` 里加一行 `android:theme` 或 `app:theme`，就会点亮那处无同步的共享写（两根线程同时改 `mConstructorArgs`）。真到那天，要么别加，要么先把预制造挪到首帧之后（与主线程的 inflate 错开）。

> `Resources.Theme` 的线程安全官方**没有**文档保证，本类依赖的是 native `AssetManager.applyStyle` 取 `ScopedLock` 带来的串行化——属"旁证支持、无文档承诺"，真机上只能靠长跑观察（见 §10）。

本类**不引入** `asynclayoutinflater` 依赖：它要处理的 parent/attach 语义与本类一样，收益不抵依赖；且本类允许"没造完就不造"，而它没有这个档位。

**备料口径：只备"池子的消费者会取的件"（2026-09-26 按实测收紧）**：池子只有配置页一个消费者（设置页传 `null` 预制造器，见 `ConfigFormController` 的构造点），故备料清单按"配置页会取什么"来定：**不备**只在设置页渲染的那一组（它的卡与它各键的件都不备；判据与页面同源——`UiSettingsFragment.isSettingsGroup`，不复制组名），也**不备** `role=master` 那些键（它们只以卡头开关的形态出现，在 `item_config_group` 里，从来没有"行"可建）。收紧后每一种布局的备料量都**正好等于**消费量（合计 126 件），余量归零。理由实测：旧口径（按定义全量）每轮多造 **28 件**（154 对 126），而备料线程本来就追不上消费侧的尾件——白造的件占住它的时间，代价不是"近零"，而是"尾部十几件每轮必缺"。将来若"设置页也吃池子"或"某页把总开关键渲染成行"，这批件就变成少备——那只是收益退化（取不到就现场 inflate，**不会造出错视图**）。**唯一的"必须对得上"是父容器的类型**（卡片进内容容器 `LinearLayout`、键行与字段进流式行容器 `WrapRowLayout`），否则生成的 `LayoutParams` 类型不对。备料清单与 `ConfigKeyRow` 五个 `Renderer.build` 的 inflate **一一对应**（定义里只有那五种 type），加一种 type 时这里要跟着加一条。

**归属比对（`get` 必须比上下文身份）**：`STARTED` 与 `instance` 都是进程级且永不重置，而这些件握着 `ownerContext` 造出来。页面重建（Activity 重建 / 配置变更）后若照旧取用，新视图树就会挂上一批**属于上一个 Activity** 的控件（既拿到过期的 Context 与主题，又把那个已经销毁的 Activity 钉在新视图树上）。故身份对不上即视为"本页没有预制造件"（代价只是这一轮全部现场造，与不做预制造时逐字一致）。返回 `null` 的三个成因（没提交过 / 已关门 / 身份不符）各记一个时间点，只用于诊断区展示、三者互斥且不影响判断结果。

**关门与池子不变量**：`clearLeftovers` 只服务启动那一轮——留下的件不会再有人取，而每个件都握着它的 Context，留着就是把那个 Activity（连同窗口）钉在静态引用上。**关门与真正的清空必须一起做**（本方法与后台 `produce` 之间没有先后约束，只清不关的话，清空之后后台还会往里放）；`put` 里再补一刀（与 `clearLeftovers` 竞争时），让"release 之后池子必空"这条不变量在任何交错下都成立。

**提交点**：`SetupActivity.preInflate`（`super.onCreate()` 之后）——理由（inflater 必须带已装好的 AppCompat 视图工厂）见 §5.1。**先判闸门、再克隆**（第二次起的调用注定被丢弃，不该白克隆 inflater）；**先发布 `instance` 再提交**（页面可能在预制造还没跑完时就来取件，取不到即现场造）。

### 6.3 写队列与合并触发

写队列（`ConfigWriteQueue`：改即存的防抖层）与"一次临时文件 + rename"的原子写口径**已在 §3.2 写全**，本节只讲配置表单侧的独有动作。

**重置一组：先冲刷待写、再按出厂值一次原子写盘**（`ConfigFormController.resetGroup`）。**为什么必须先冲刷**：待写队列里若还压着同一页的改动，稍后它自己的冲刷会把重置值覆盖回旧值——而 C 端 `st_mtime` 只有秒级精度，补写一次也未必触发重载。冲刷与重置都排在控制器**同一个单线程 executor** 上，故"先冲刷后重置"的顺序由它保证，不需要额外同步。**重置值走 `ConfigStore.setAll`**：整组合成一次 rename；逐键 `set()` 会多次触碰 mtime，可能换来一轮"部分生效"的重载。

**重置结果落地（`applyReset`）**：把本页那些属于该组的键重刷成出厂值并给反馈。**不属于本页的键一个都匹配不上——这是对的**：别的组的键不在本页显示，其显示是否陈旧由配置页自己重读时解决（它每次可见都重读）。成功不必逐行标状态（控件里的值本身已经变了，同一句贴在每一行上是噪音）；失败要留在行上（Snackbar 一闪而过）。

### 6.4 两个顺序为什么不一致

参数定义里有一个**组顺序**，配置表单的重置栏**展示顺序**是另一个，两者**不同**，且都是有意为之：

- **定义里的组顺序**决定 `profile.conf` 的段标顺序（由 `params.json` 的 `groups[]` 给定），**不能为了界面观感去动它**。
- **重置栏的展示顺序**（`ConfigResetBar.DISPLAY_ORDER`）是需求本身（用户指定「界面」紧随「性能参数」——重置界面参数比重置 sysfs 路径更常用），故写成**显式表**而不是"照定义顺序排一遍"：这个顺序不是巧合，也不是排序结果。只列 id 不列组名：组标题正在被改（`[2] sysfs 路径与缩放` → `[2] 路径与缩放` 等），按钮文案一律从 `GroupMeta.title` 取并去段标编号。
- **两级降级都不报错、也不留空按钮**：表里列了而定义里已删的 id 静默跳过；定义里有而表里没列的组追加到末尾（顺序退化为定义顺序）——将来定义新增分组时按钮一定会出现，不会因为忘了改这张表而少一个。

**段标编号剥除（`UiSettingsFragment.stripSectionNumber`）**：编号是给 `profile.conf` 段标对齐用的，定义里必须留着（`check_params.py` 断言分组标题带 `[N]`，且 profile.conf 段标由它派生）；显示时它只是噪音，故剥掉。**设置页卡头与重置栏按钮共用这一份实现**，显示口径只有一处。

### 6.5 诊断区与时钟

**配置页的诊断区**（`ConfigDiagnostics`，只读展示）：显示 `ConfigStore.describeState(Snapshot)`（配置文件路径与大小、落点是否与守护进程一致、参数定义加载情况〈键数或失败原因〉、未定义键与读取提示）与配置 mtime。**整块默认折叠**（数据文件信息、键渲染自检、本节正文都在折叠体内，展开才占高度）。

- **复用调用方刚读到的快照**（`refresh(Snapshot)`）：配置页每次刷新都是"读一次盘 → 上屏值 → 上屏诊断"，把那份快照传进来，本区与 `describeState` 都不再各读一次 `profile.conf`；mtime 也取快照自己的字段。
- **收起态下只登记、不上屏**（`pendingRefresh`）：收起时整块都看不见，为它跑一趟后台 + 三次 `setText`（正文那次还会把整块标脏、连带一次整页重排）在启动链上是**纯开销**。故收起时只登记一笔欠账，展开那一刻再补（`setExpanded` / `flushPending`），多次请求合并成一笔。启动链上那一次"建表触发的刷新"因此不再落在关键路径上；数字一个都不少（展开即见），只是"何时算、何时上屏"推迟到用户真的看得见的时候。
- **在途期间到达的请求排队重跑、不丢**（`refreshQueued`）：一次刷新要跑一趟后台，期间的请求若直接丢掉，写盘刚触发的刷新就可能被吞掉、诊断区一直停在改盘之前的状态。故在途时只登记"还欠一次刷新"（记下最新的快照），本轮上屏后立刻再刷一次；两路请求合一时以**自读盘**为准（它读的是磁盘当下状态，而快照可能正是写盘之前的那一份）。
- **读盘抛异常 / 页面销毁**：本轮作废，但在途标记必须清掉——留着会把后面的请求一起吞掉；读盘失败时正文位立刻改写为「读取失败：…」（不留占位，动画口径见 §8.4）。只调 `ConfigStore` 的公开接口，不碰文件、不拼 shell；读取在后台线程，主线程只做渲染。
- **不提供任何写动作**：出厂配置由 `Deployer` 在部署时写出（`writeFactoryIfAbsent` 的 javadoc 明确"界面不要自己调"）；界面另开一个写入口就是绕过 I5 的重复写入路径。

**启动耗时**：`ConfigDiagnostics` 把 `StartupTiming.report()` **追加在诊断正文之后**（空一行接一段"启动各段耗时"），既有诊断正文一个字不动；没量到任何一段就一个字符都不加。它落在折叠体内（默认收起），故不新增开关也不会常驻界面；展开时重算一次，好让比"建表"更晚的时间点（首帧 / 段二收尾）也现出来——**只读几个静态槽位，无 IO、无后台线程**。记账口径见 §5.3。

## 7. 曲线子系统

曲线区在一个配置页子页（`ChartFragment`）里：顶部窗口档位按钮 + 图例（`WrapRowLayout` 换行）+ 自绘画布（`ChartView`）+ 失败诊断（可拖滚动条）。数据由 `ChartLoader` 在后台线程整份读好、经 `ChartConfig` 取口径，主线程只渲染。

**性能硬约束（`ChartView`）**：`onDraw` 只做 drawLine / drawPath / drawCircle / drawText —— 全部几何量（轴与刻度、每系列 `Path`、标注位置与文本宽度、断联空白）都在 `rebuild()` 里算好并缓存；`rebuild` 只在数据 / 窗口 / 系列开关 / 尺寸 / 配色变化时触发，**绝不在 `onDraw` 内重建 `Path`**。控件本身不读文件。

### 7.1 数据源与行格式

**行格式的唯一权威在 C 端**：`tempctrl.c` 的 `WEBUI_ROW_FMT`（8 列），详见 [../daemon/逻辑说明.md](../daemon/逻辑说明.md) 的〈状态页数据源〉与 [../README.md](../README.md)。读端（`ChartDataset`）只按列下标消费：温度列 `v>=0 ? v/10 : 无效`、转速/制冷列 `v>=0 ? v : 无效`（哨兵 -1 变无效）；第 7 列「目标制冷」写端有、读端**有意不消费**，但列数校验仍按 8 列（校验的是写端格式，读端不擅自放宽或收紧）。

**口径参数（`ChartConfig`）两类来源**：① `UI_GAP_SEC` / `UI_RPM_AXIS_MIN` / `UI_CURVE_FILTER` 与右轴所需的 `COLD_RPM_MAP` / `PID_COLD_RANGE` / `PERF_ENABLED`，一律经 `ConfigStore` 读，字段缺项回落 `assets/params.json` 里声明的默认值；② `params.json` 的 `chart` 块（窗口档位 / 默认档位 / 滚动行数）——`ConfigStore` 只暴露 `groups()/keys()/key()`，`chart` 不是键，故本类是**曲线页唯一直接读 assets 的地方**（只读）；读失败回落已确认常量并把事实写进 `notes`，不静默。`ChartConfig` **只能在后台线程构造**（`load` 内有同步 File IO）。

**进程级缓存**：`ChartConfig.load` 结果按 `ConfigStore.configFingerprint()` 缓存（`chart` 块是 APK 内资产、进程内不可能变；口径键随 `profile.conf` 指纹失效）——曲线页每次重新可见都重读一次口径，本条缓存把那轮的 47KB JSON 重解与整份配置重读一并消掉；失效判据只此一处（指纹），降级结果也一并留档。`ChartLoader` 只缓存**解析产物**（`ChartDataset`）、不缓原始文本，失败一律不进缓存（诊断绝不陈旧）。两者返回的对象可能被多处共用：**只读**。

**预热与记账**：曲线首帧由 `ChartLoader.warmUp` 在冷启动预热（结构见 §5.1）。记账点贴在两处 `ChartConfig.load` 的调用方上（`ChartFragment.loadConfigTimed` 与 `warmUp`），谁先真正加载完这份口径，耗时就算谁的真实成本（首写胜出）。**未验证**：`AppFiles` 直读私有目录文件在 SELinux 下可能 `errno=13`，本机未真机验证——故直读失败是正常路径，界面必须给得出可诊断文本。

### 7.2 数据窗口与断点

**时间轴不是按真实时间等比**（`ChartWindow`）：`x = padL + W * ((序号 + 累计gap) / totalUnits)`——正常段 1 行 = 1 格（与 dt 无关），只有断联处按 `min(dt, gapMaxSec)` 的封顶量补偿。时间戳只用于两件事：窗口裁剪（`t < lastT - winSec` 丢弃）与断联判定（`dt > detectSec`）。窗口裁剪顺序：先按条数取尾部 `winSec` 行，再按时间收紧（保留 ≥ 1 个样本）。

**窗口是切片、滤波与窗口无关**：`ChartDataset` 的滤波在解析后对**全量样本**做一次，窗口只做切片，故同一份数据每次得到同一条曲线。`rollingMaxLines`（= C 端 `WEBUI_DATA_MAX_LINES`）用环形覆盖保留最近 N 行，与 C 端压缩口径一致。

**热端与电池曲线滤波**（两条曲线**共用**同一对参数，均由 `UI_CURVE_FILTER` 配置）：对每段连续有效样本做**零相位双向平滑**（前向一遍 EMA + 反向一遍同一 EMA，等价 filtfilt，每遍权重 α 默认 0.15）——阶跃响应为对称 S 形、稳态等于原始值，无滞后、无稳态偏置；反向一遍以段末前向值为初值做边界延拓，故**段内为完整零相位**，段末沿用前向值、不引入跳变。平滑后再做一遍**最小步长格点吸附**（默认步长 0.05，偏差 ≥ **0.9×最小步长** 才吸附到最近整格，一次可跨多格），消灭平滑后残留的亚格点微挪。

**滤波关闭语义**（`UI_CURVE_FILTER` 双值均 ×100）：每遍权重 α = **0 或 100**（100=1.0 恒等变换）都视为**关闭滤波**；最小步长 = **0** 视为**关闭格点吸附**。两个子步骤**各自独立开关**（可只关其中一个）。

**「平滑」的口径**：格点吸附使输出只取最小步长的整数倍，故曲线必为阶梯、导数不连续——平滑只在**包络**意义上成立（台阶密度沿对称 S 形分布：起段稀、中段密、末段又稀），不是逐点连续平滑。

**分段处理**：热端、电池**各自**按自己的连续有效样本**独立分段**（各自无效处断档、各段独立平滑），处理顺序固定、与显示窗口无关，同一份数据每次得到同一曲线。

**解析量上界跟着保留量走**（`ChartLoader.tailForParse`）：窗口行数超过 `2 × 保留量` 时只把尾部交给解析器——界面「解析 / 跳过」报的是解析器实际扫过的行数，是给用户看数据文件的诊断；C 端文件最多 780 行，远不到这个上界，故常规文件的诊断数字与截断前逐字一致，只有别的写入方撑大文件时才截尾。它按行边界切割、只动交给解析器的那段文本，`TAIL_BYTES`（256KB，绝不整文件无界读）的读取上界不变。

**断联空白**：C 端断联时不写曲线数据行，相邻采样时间差 > `UI_GAP_SEC` **第一值**（默认 2s）视为一次断联：曲线在该处断开，并按**真实断开时长**插入等比空白（空白宽度 = 正常绘制该秒数的宽度），封顶 `UI_GAP_SEC` **第二值**（默认 15s）——短断联窄空白、长断联封顶，直观反映断联长短。断联判定与空白封顶的配置键见 §7.1 的 `UI_GAP_SEC`。

### 7.3 坐标与内边距口径

**双纵轴**：左轴 **℃/百rpm**（温度 ℃ 一位小数 + 风扇转速 ÷100 共轴，标题收在刻度数字块上——左标题左沿与左侧数字左沿平齐、右标题右沿与右侧数字右沿平齐，横向可越进曲线区内，不挤压曲线空间；绘图区左右内边距按该侧最宽的那条数字现算，不留固定空白），右轴 **制冷**（制冷强度**下限恒为 1**＝C 端 `COLD_MIN`；**上限浮动**＝当前可见窗口内 `coldReal` 最高值，夹进 `[COLD_RPM_MAP` 第一值（映射起始强度，默认 40），`PID_COLD_RANGE` 第二值（B6X 制冷上限，默认 190）`]`——两值均在总开关 PERF_ENABLED=1 开启时取配置实际值，否则用默认；窗口口径与左轴同一套，无有效数据时上限回落制冷上限）。**整图只保留一套横线，位置由左轴刻度决定**：右轴不再自算刻度、不再单独画线，只在每条左轴横线的高度上标一个制冷强度整数（= 该高度线性映射进 `[1, 当前上限]` 后四舍五入）。左轴全部系列关闭时无横线可依，右侧不标数字。左轴取值排除风扇转速低于 `UI_RPM_AXIS_MIN`（默认 3000）的样本，该段画到图外；过滤后左轴无有效数据时退回不过滤。

**曲线头部数值标签取实际物理值**：温度 ℃ 一位小数；风扇转速显示**实际 rpm**（如 `3500rpm`），纵轴单位文本仍为「百rpm」（纵轴数值仍是 ÷100）。

**左右内边距现算、不写死**（`ChartView.applyAxisPads`）：padL = 最宽的那条左轴刻度数字（实测宽）+ `TICK_GAP_DP`(4dp)，padR 同理取右侧制冷数字，没有右轴时不占宽。原实现两侧各写死 36dp，比数字实际所需宽出一截、白占绘图区。两个轴标题都收进「数字块」里：左标题左沿与最左那条数字左沿平齐、右标题右沿与最右那条数字右沿平齐，横向允许越进曲线区、**不挤压曲线空间**。量的都是绘制字号（10sp），故先把两支画笔字号设对，免得量到上一帧留下的字号。

**上下内边距是推导出来的**：

- 上 `PAD_T_DP = 17`（**硬下限，不能再小**）：两个轴标题的 baseline 画在 `fPadT − 7dp`，而 10dp 文字的 ascent ≈ 9.3dp，要保证标题整体留在画布内须 `fPadT − 7 ≥ 9.3` → `fPadT ≥ 16.3`，取整 17dp；再低标题会被画到画布外裁掉。
- 下 `PAD_B_DP = 4`：与 PAD_T 合计 21（原为 24 + 8 = 32），省下的 11dp 全给绘图区。再小则最低一条网格线几乎贴住画布下沿，且画布下沿的拖柄横条（`fragment_chart.xml`）紧贴下沿、两者会挨到一起。绘图区高度的 8dp 保护下限在 `rebuild` 里。

**接缝（`fSeamY`）**：转速圆点的下越界下限 = `min(绘图区下沿 + 4dp, 画布下沿 − 5dp)` —— 圆点（半径 3.2 + 外圈 0.5）不许被裁；原 `h−1` 上限不够。PAD_B 缩到 4 后第一项已高于第二项，实际恒取 `h − 5dp`。

**轴定标（`ChartAxis`）**：**档位梯** = 1、2、3，加所有 ≥5 的 5 的整数倍（无亚单位档位）。候选档位限定在 `[跨度/5, 跨度)` 内（该区间枚举完备：步长 ≥ 跨度时段数 ≤2、步长 < 跨度/5 时段数 ≥6，都不合格）；在能形成 3~5 段的候选里取离 `跨度/4` 最近者，无候选取离目标最近的档位。上下限按档位 floor/ceil 扩张，**绝不裁点**。`segmentsOf` 与 `ticksOf` 逐项同构（浮点累加舍入、`1e-9`/`1e-6` 容差、`TICK_CAP` 截断都靠这层同构才与画出来的刻度一致）——**改 `ticksOf` 必须同步改 `segmentsOf`**。


### 7.4 标注选边与防重叠

**落点要素**（`ChartView#buildMarkers` → `placeSingleAnchors`）：每条系列取**最后一个有效样本**作锚点——锚点 `x` 决定标签横向起点、`y` 决定纵向落点；锚点 y 先钳进绘图区（风扇转速系列允许下越界到接缝 `fSeamY`，其余含右轴制冷钳在绘图区下沿）。标签与锚点的水平间距 6dp，`tx + 宽 > 绘图区右沿` 时翻到锚点左侧，左界钳到 2dp。**每个锚点的理想落点只算一次**（单成员口径），此后不再随合并重算。

**选边 = 局部空隙**：比较「锚点到上方最近障碍物」与「下方最近障碍物到锚点」两段空隙，空隙更大的一侧放标签。**障碍物 = 同页其它曲线的端点圆点边缘（相邻锚点）+ 绘图区上沿/下沿，不含曲线中段**。上方放得下 = 空隙 ≥ 抬升 4dp + 文字 ascent；下方放得下 = 空隙 ≥ 一行高 + 1dp + 文字 descent；只有一侧放得下就取那一侧，两侧都放不下时同样取空隙更大的一侧。

**合并判据 = 顺序贪心封组**（`ChartView#buildMarkers`；不再有 `mergeOverlapping` 与并查集）：锚点按 y 升序，沿序扫、**只与当前组的第一条比**——满足「该锚点与组首的标注纵向占位盒相交」（按实测 `FontMetrics` 的 `[ly + ascent, ly + descent]`）**或**「两锚点 y 相距 ≤ `NEAR_DUP_DP`（8dp）」就并入本组，**一旦不满足立即封组、绝不回头**。这里**没有传递闭包**（A 压 B、B 压 C 不会把 A、C 并到一起），也**没有迭代**（不重复「落位→合并」）。`NEAR_DUP_DP = 8dp` 是"近同锚点"判据：两条曲线末端相距不到 8dp（略大于圆点直径 6.4dp）就视为视觉上的同一个点，直接并。**落位公式里的行高用常量 11dp（与 WebUI 同名常量对齐），判据用实测行盒 11.74dp**——两者差 0.7dp 是有意的：判据要判的是文字真实占位，绘制要沿 WebUI 口径。

**组盒与落点同源**：合并组的标签画在该组**第一条**的落点上（`ly = 组首的 ly`）——判定用的盒与画出来的盒是同一个。由此：相邻两组的标签盒必不重叠（下一组之所以能成立，正因为其首条与上一组首条的盒不相交），组内锚点跨度有硬上界（一个文字盒高 + 上/下落点相对锚点的极差 ≈ 27.7dp；100 万随机用例实测最大 27.7dp）。

**明确取舍 ①：判据只判纵向，横向不参与。** 两个锚点的 x 相差很远时（某系列断联、其最后一个样本更早）两个标签横向其实压不到，但纵向相近仍会被合并，且合并后标签起点取成员 x 的均值。这是本口径接受的代价。

**明确取舍 ②：合并组落点取「组首」而非旧口径的「组极值」。** 旧口径按组顶端/底端重算落点，会形成「合并 → 落点外移 → 又压上邻居 → 再合并」的滚雪球（实测单个组能跨到绘图区的 49%）。本口径把落点钉在组首的同一位置以掐断该回路；代价是**当下侧放置时，合并组的标签比旧观感高出一段「组锚点跨度」（≤27.7dp）**（上侧放置与旧观感一致）。另有一处更小的同源错位：「**近同锚点**」（相距 ≤ `NEAR_DUP_DP`）被强制并组时，标签与**较远那条**锚点的圆点最多可相距约 **16dp**（实测两成员 12.0dp、多成员 15.74dp，约一行字高）——因为这两条锚点本就只差 ≤8dp，视觉上当作同一个点并掉。

**合并阈值没有配置键**：原先的 `UI_LABEL_MERGE_PX`（界面「标注合并阈值」，默认 9px）已随本判据**删除**（键数 57 → 56）。阈值现在由文字行盒高自动决定，不再可调；该键本就只被界面读取（守护进程忽略），C 端与生成头都未含它，故 C 侧零改动。删除的连带（定义 → 生成器 4 产物 → `check_params.py` 的 `EXPECTED_KEY_COUNT` → CI）见 [../../参数定义/params.def.json](../../参数定义/params.def.json) 与 [../../参数定义/check_params.py](../../参数定义/check_params.py)。

**与 WebUI 的三处有意偏离**：① 选边改看**局部空隙**——WebUI 只比「簇顶到绘图区上沿」与「绘图区下沿到簇底端」的大小，本 app 把同页其它曲线的端点圆点也算作障碍物，故相邻两簇跨绘图区中线时不会再各自朝中间靠、把两条标注叠在一起；② Java 额外多一条「画布高 − descent」的下沿钳制（本 app 画布下沿即视觉下沿、其下紧贴拖柄触控带，只钳一条会让最低那行文字被裁）；③ Java 的 `fSeamY` 落在绘图区下沿**之上**，故 WebUI 那条「簇最低点越界（落到接缝之下）→ 改放上方」的情形在 Java 不出现——这种贴底簇现由选边判据的「绘图区下沿」障碍覆盖（簇底越出绘图区时下方空隙 ≤ 0 → 判上方），结果一致。**合并判据是本 app 独有的第 4 处偏离**：WebUI 按锚点 y 聚类，本 app 改为「顺序贪心 + 标注盒相交 + 近同锚点必并」（不跑传递闭包、不迭代）。

**未验证项**（本机无真机）：落点与合并的最终观感未实测（含「下侧放置的合并组标签比旧观感上移 ≤27.7dp」这一条）；「数据每秒刷新、锚点微动时某对标签会不会在合并 / 不合并之间跳变」也未实测（旧口径同样有此性质；新判据多了「近同锚点」这条门槛，8dp 阈值附近可能仍有跳变，抖动面未实测）。

### 7.5 配色

**数值标签以背景色描边（halo）**：先用背景色描边再填充，故曲线穿过字形时不会与同色标签糊在一起。描边色 = 卡片底色 `app_surface_container`（halo 与圆点外圈共用它）；**描边字号必须与标签同字号**——曾漏设，`new Paint()` 的 textSize 默认为 0，导致描边根本画不出来。

**色号**：六个系列色 = 原 WebUI 的 Material 500（batt `#F44336` / cool `#4CAF50` / rpm `#9C27B0` / hot `#E91E63` / cold `#2196F3` / cpu `#FF9800`），**明暗两套资源同值**；刻度 / 轴标题 / 合并分隔符 = `#888888`（明暗同值）。网格与卡片底色**不走** `chart_*`，用全主题共用的 `app_outline_variant` / `app_surface_container`（与 WebUI 的白底 + 淡灰网格不同，属有意偏离，避免连带其他页面）。图例色在切明暗时由 `ChartFragment.onResume` 重取（此前只在建视图时取一次、切换不跟随）。

**全部运行时按当前主题取色**（`ChartView.loadColors`，`getColor(id, theme)`），深色由 `values-night/colors.xml` 同名覆盖；**本类不出现任何十六进制色值**。

- **底色 = 卡片底色**（`app_surface_container`，即本类所在的卡片色）：halo 与圆点外圈都靠它把穿过的曲线遮住，两者不同色就会露出异色描边。本类**不铺底色**——底色由卡片给（画布透明），否则卡内会多出一块直角色块。
- **网格线走主题的分隔线色**（`app_outline_variant`）：底色由纯白变为浅灰的卡片色后，原网格色与底色的明度差几乎减半（ΔRGB 34 → 16），改用分隔线色（= 卡片描边色）才保住可见度；深色下同样比原网格色更清楚。
- **图例与曲线同一口径**：勾选框着色 = 该曲线的 `chart_series_*` 色，且**随主题变化一起重取**（`ChartFragment.applyLegendTints`）——原先只在建图例时取一次，主题一变曲线跟着变、图例却不跟。

### 7.6 曲线区外壳与交互

**曲线区在配置页里**：曲线页（`ChartFragment`）是配置页（`ConfigFormFragment`）的**子 Fragment**（合并成「配置 · 曲线」一页，页签 4 → 3），不再由 `SetupActivity` 直接挂载。因此：

- **「数据文件信息」（路径 / 大小 / 修改时间 / 解析量 / 断联）不再画在曲线卡里**，经 `Host#onChartInfo` 交给配置页渲染到「诊断信息」头部，避免两处重复。
- **外壳切页不再 hide/show**（ViewPager2 只把非当前页压到 `STARTED`，不派发 `onPause`），故由父页显式调用 `setPageHidden(boolean)` 转达可见性，停 / 启刷新的口径与独立成页时一致。

**布局**：档位行、图例、画布同处一张卡、全按自然尺寸排布——**不整体缩放、也不覆写容器高度**（原「超宽时整块缩放到 0.5 并覆写裁切框高度」的做法会把图例裁掉、高度塌成一条）。画布高度初值由 `fragment_chart.xml` 给出（本区在配置页的 `ScrollView` 里，`layout_weight` 会被量成 0、不能用），运行时可用画布下沿的拖柄在 `chart_canvas_min_height`～`chart_canvas_max_height` 之间改；改的是运行时 `LayoutParams`、**不落盘**（视图重建即回默认高）。

**图例**：6 条曲线按自然宽依次排（`WrapRowLayout`），勾选框着色与主题同步见 §7.5；「冷端℃ / CPU℃」两条可选温度传感器固定另起第二行（`ChartSeries.startsLegendRow`），排到第二行后图例不再随各项自然宽随机掉行。

**系列开关**（电池/制冷/风扇/热端/冷端/CPU℃）：**默认除 CPU℃ 外全显示**；热端在冷端之前（实时数值列的列顺序由实时行独立维护，不受系列顺序影响）。

**实时数值列 / 实时数值栏**（WebUI 规格：电池 · CPU · 制冷 · 风扇 · 冷端 · 热端，不含目标制冷）：**原生界面不设独立数值栏**，当前值以曲线头部标注呈现；`ChartView` 里为它预留的接缝几何量（`fSeamY`）只用于"转速圆点允许下越界"这一处。**实时数值栏显示原始值**：电池/热端的实时数值栏取 C 端**原始读数**，与曲线（滤波值）**刻意不同步**——该栏语义是「C 端当前读数」而非「曲线上的点」；且零相位滤波在阶跃处会「先动」，属算法固有现象。

**画布高拖柄与让位（`onHandleTouch`）**：只有**纵向**拖动才改画布高，横向一律交给外层 ViewPager2 翻页。按下先只记起点，等手指走出 touch slop 再定方向（判据与页面纵向滚动同一套 `ViewConfiguration`），定为纵向时才把当下的位置与画布高记成拖动起点（画布不会因多走的 slop 先跳一下）。纵向拖动没被页面滚动抢走，靠页面根 `PageScrollView.yieldVerticalDragTo`——从该子视图上开始的纵向拖动页面容器不接管（`PageScrollView` 的判据：按下那一刻落在指定子视图上则本次手势全程不接管；横向仍归外层 ViewPager2）。因此这里**不再、也不能**按下就 `requestDisallowInterceptTouchEvent(true)`：那个开关沿父链设上去，会把 ViewPager2 的横向拦截一并封掉、横向再也翻不了页；而等手指走起来才设又太晚——同一帧里 `ScrollView.onInterceptTouchEvent` 先于子视图的 `onTouchEvent` 判定。登记延到**下一帧**（`resizeHandle.post`）：`onViewCreated` 时本页视图还没挂进父页视图树，走父链找不到页面根，`post` 在未挂载时排队、挂上后再执行。代价是：从该子视图上开始的纵向拖动不再滚动页面。

**失败诊断的滚动条（`ScrollbarDrag`）**：失败文本区可按住滚动条拖动——**框架的滚动条只有绘制能力、没有触摸拖动实现**（`ScrollbarHelper` 全文只有滚动量计算、零触摸代码；`fastScrollEnabled` 专做这件事正说明默认滚动条不响应拖动），故必须自己接 `OnTouchListener`（不包一层容器、不影响现有层次）。三条要点：① 命中区 = 右边缘窄带（滚动条宽 + 8dp 且 ≥ 20dp），按下在滑块上就抓着拖、在轨道空白处滑块先跟到手指；② **抓住滑块前先结束正在进行的惯性滑动**——滚动中的 `ScrollView` 每帧在 `computeScroll` 里把 fling 自己算出的位置写回，本类同帧的 `scrollBy` 随即被覆盖（表现为"按着滚动条不动、得等它自己滑完才跟手"），故 `ScrollView` 用零速度 `fling(0)`（位移为 0、动画当帧即结束）、`RecyclerView` 用 `stopScroll`；③ **拖动期间禁用父容器拦截**——页面根在外层 ViewPager2 的横向 RecyclerView 里，纵向拖动只要带一点横向位移就可能被当成翻页拦走，按下命中窄带时 `requestDisallowInterceptTouchEvent(true)`、抬起恢复。`Metrics` 里按类型分流是因为 `computeVerticalScrollOffset/Extent/Range` 在 `View` 里是 **protected**、`RecyclerView` 才重写成了 public。**未验证（真机需确认）**：右边缘窄带内普通拖拽会被吃掉；系统手势导航若占用最外侧边缘，实际可按区会从窄带内侧开始。

### 7.7 通用换行容器（`WrapRowLayout`）

全项目**唯一**的换行实现（配置表单行骨架与曲线图例共用）：子视图按添加顺序排、一行放不下就换行、同一行内按各自高度垂直居中。子视图分三类——**leading**（从行左界起依次排）、**trailing**（连续的一串构成「尾段」，每行贴本行右界对齐）、**fullLine**（独占一行且铺满可用宽）；另有 `breakBefore`（在其之前强制换行）与行距 `wrapRowGap`（缺省 = 列距）。

**标记存在子视图自己的 `LayoutParams` 上**，容器**不持有任何子视图引用**（不另建 `List<View>`/`Map`）——因此 `removeAllViews()` 之后不残留任何标记，重新添加即从零开始。标记也可直接写在子标签的 `app:` 属性上（`inflate(xml, parent, false)` 走 `parent.generateLayoutParams(attrs)`，由本容器读出）。

**为什么不引第三方**：`FlexboxLayout` 为浏览器级的 flex 语义（收缩/增长/基线/顺序）付成本，本容器只需要上面几条规则，百来行的排布即可覆盖；调用方量级（每页几十个）也不需要虚拟化。

**量摆同源**：量（`onMeasure`）与摆（`onLayout`）走**同一个** `Pass`，换行判定只有一份，不会出现"量一套、摆另一套"。标记变化后由调用方 `requestLayout()` 即可，本类不在任何布局回调里回写状态。仅按 LTR 排布（界面无镜像语言需求）。

**尾段的换行偏好顺序**（`placeTailRun`）：按「换行偏好顺序」逐档尝试，取第一个可行的——**能用整行解决就不混排，混排只在连整行都放不下时才用**：① 全部字段与参数名同行 → ② 全部字段占一整行（参数名独占一行）→ ③ 同行放得下的先放、其余占一整行 → ④ 占两整行 → ⑤ 同行 + 两整行，依此类推（k 整行 → 同行 + k 整行）。每一行（含与参数名同行的那一段）都贴行右界；段内再声明 `breakBefore` 者另起一串。

**几处关键不变量与踩过的坑**：

- **判"放几项"一律用可见项数**（`visibleCount`）：尾段区间由 `collectTail` 收集，而它会**把 GONE 的子视图也收进区间**（GONE 分支在标记判定之前），故下标差 `to − from` 并不等于"区间里有几项要摆"。凡要与 `tailPrefixFit`（逐项前缀累加、只数可见项）比大小的地方都走 `visibleCount`；否则第①档"全部同行"会永不命中。
- **"要几行"的判定与真摆放共用同一份切分**（`tailLineEnds`）：判可行与实际切行不能分家。
- **行宽只有一个口径**（`sideBySideWidth` = 两段宽 + 一个列距）：判"能否同行"、量"本行多宽"都走这一个数。**曾出现**判据用"两段 + 列距"而测量期用"两段取较大"，`wrap_content` 容器于是自报宽偏小（比并排所需小），落位后判据必然为真：尾段折到第二行，而高度只按一行算 → 第二行被裁。
- **垂直定位标记（`setVerticalCenterAt`）**：把子视图垂直中心钉在本行行顶之下 `offsetPx` 处（不按行高居中），只改这一个子视图的纵向落点。行高必须按**占用下沿**（`offsetPx + 高/2`）与其余子视图一起取最大（`occupiedHeight`），否则标记项会盖住下一行。落点可为负（子视图上沿越出行顶）、不钳位；**有意不为越出上方的部分加高、也不平移本行**——向上越出是调用方自己给的偏移，容器不代它兜底（下方越出则必须兜，否则会相碰）。
- **`Pass` 是一趟排布的进行态**，只活在一次 `onMeasure`/`onLayout` 内（局部对象），因此容器本身不持有任何子视图引用；行与尾段都用**子视图下标区间**表示，连临时的 `List` 都不需要。

## 8. 状态页与日志页

### 8.1 状态页（诊断码、部署请求与刷新口径）

`ui/StatusFragment` 是状态页：部署状态 / 一键部署 / 卸载部署 / 拉起daemon / 停止daemon / su 诊断。

**调用边界（I5 的另一半）**：本页只调 `Deployer` 的 `probe()` / `deploy()` / `uninstall()` / `startDaemon()` / `stopDaemon()` / `buildDiagnostics()` / `ensureRoot()` / `updateScript()`，**不拼 shell、不碰文件、不绕过 `Deployer`**。`Deployer` 的方法都阻塞，故一律放后台线程、结果回主线程渲染。

**首次启动的 root 尝试**：`root_tried` 标记落盘（键定义收口在 `Deployer`，见 §2.5），只试一次；被拒或失败都不再自动重试（否则每次冷启动都弹系统授权框）。成功则弹窗问是否立即一键部署。

**脚本自动纠正**：`service.d` 脚本是纯文本、可无损重推，故探测到它与 APK 内资源哈希不一致时自动重推一次。重推**会连带重启守护进程**（脚本与二进制是同一份部署产物，且脚本本身就是常驻的看门狗 shell，只换盘上文件它那一层仍跑旧映像）——理由与实现见 §2.2 的 `updateScript()`。二进制不一致则代价高得多（要重装 + 重启），由 `armDeployPrompt` 判定：自动更新开着就直接重装，否则弹窗请求用户部署。

**刷新分两条路径（消闪烁）**：状态区是**单个 `TextView`**、卡片 `wrap_content`，一旦把约 8 行的结果换成 1 行忙文本，状态卡立刻变矮、其下两张卡整体上跳再回落——这是「每次回状态页闪一下」的根因。故：

- **静默路径**（首次探测在 `onViewCreated`、其后刷新在 `onResume`）：不碰状态区文本、不写操作记录、不做动画，结果先比后写（内容没变就一个字都不动）；30 秒内不重复跑 su 探测。
- **手动路径**（用户点按钮）：写操作记录 + 结果文本淡出→换文本（带高度补间）→淡入。
- **进度条两条路径都显示**（它是刷新唯一的反馈），且它在布局里常占位、可见性只影响绘制，故开关它不引起任何高度变化——高度变化只来自手动路径的文本补间，那是要的效果而非闪烁。

切页时外壳（`SetupActivity`）广播可见性，本页据此收掉在跑的动画（`PageAware`，见 §9.1）。

**首次探测（含那一次 root 尝试）为什么在 `onViewCreated` 而不在 `onResume`**：三页被外壳的 `FragmentStateAdapter` 在启动时一并建出来（`offscreenPageLimit = 2`，见 §9.1），故本页的 `onViewCreated` 在冷启动那一刻就到了——与「进 app」等价，首次滑到本页时结果通常已就绪，不必现场等一趟 su。（原先挂在 `onResume`，那是 Activity 时代的接线：换成 ViewPager2 后非当前页只到 `STARTED`，等于「滑到才探」。）**依赖**：三页须仍在启动时全部建出来，将来改成懒加载就要挪回 `onResume`。

**一次动作的内部纪律**（`runAsync` / `finishAction` / 各种代号）：

- **忙态与占用位**：`actionRunning` 为 true 时拒绝并发触发。它**不是**「那条线程还活着」——结果上屏后紧接着还要接一段（部署→自动拉起），而那一刻线程刚 post 完、往往还没真正结束，按「线程存活」判会把该接的一段挡在门外。它只管「本页同时只有一个动作」：主线程置位于开跑、结果上屏时清除。
- **收尾只有一处**（`finishAction`）：正常上屏、视图已销毁、以及**拿不到 Activity** 三条路都要走它——最后那条尤其不能省（那时进度条还在屏上，早退会把它永久留在「忙」上，此后本页所有动作都被守卫挡下）。
- **代号**（`actionGeneration` / `fadeGeneration`）：每次起跑自增。`onDestroyView` 会无条件放开占用位，若视图随即重建、期间又起了新动作，旧动作的收尾回调就会把**新动作**的忙态清掉（同时守卫短暂失效）；代号一变，旧回调只认自己那一次，不动别人的忙态。淡入淡出同理：连点刷新不会让两段动画交叠。
- **`MAIN` 静态 Handler**：只在「拿不到 Activity」的收尾路径上用（那一刻不能借 Activity 回主线程）。类加载发生在主线程（Fragment 由外壳在主线程建出来），且 `new Handler(Looper)` 本身可在任意线程调用，故静态持有是安全的。
- **手动刷新的换字**（`swapStatusTextAnimated`）：**业务上屏零延迟**——新文本立刻写入（不再挂在上一次的淡出回调里等 100ms），视觉上做「旧文本淡出、新文本淡入」的**交叉淡入**（`status_text_stack` 内新旧两层叠放，旧的在下、新的在上，沿用 100/150ms，进出均强 ease-out）。高度变化按逻辑 2 补间（位移量由换字前预测），详见 §8.4。**打断不丢结果**：打断后当前文本即最新结果（新文本已即时上屏）；**系统动画关闭时**（`Motion.enabled()` 为假）直接换文本，不淡不补间。只碰本页视图树；窗口级设置（`softInputMode`）由日志页接管（见 §8.3）。
- **进度条为什么只切 `VISIBLE`/`INVISIBLE`、绝不用 `GONE`**：它在布局里是**常占位**的，占的高度恒定，可见性只影响绘制；用 `GONE` 会让它参与测量、出现/消失就要改状态卡高度，下面两张卡跟着上下跳。

**探测 → 自动纠正 → 武装请求**（`probeAndAutoFixScript`）：

- 探测部署状态；脚本哈希不一致且 su 可用时自动重推脚本（重推会连带重启守护进程），再复探一次。**su 不可用时不尝试**（否则每次进页面都白撞一次授权框）。
- **副作用两条**：①按最终状态武装部署请求（`armDeployPrompt`）；②顺手刷新「同步清单」（见 §2.5）。两条无论走静默还是手动路径都执行——它们正是「探测才发现的事」，且同一个 APK 版本最多发作一次。
- **脚本自动纠正的三选一文案，判据取自紧随其后的那次 probe**（更晚、更权威，且不额外增加 su 往返）：动作失败 → 失败文案；动作成功但探测显示守护进程没在跑 → 第三条文案（重推本身成功了，说「失败」不实；说「已自动重推脚本」又把「进程没起来」盖掉，同样与事实不符）；其余 → 成功文案。

**部署请求的武装与去重**（`armDeployPrompt`）：

- **三种情形互斥，按此优先级取一条**：① 二进制在、内容与 APK 内不一致（`PROMPT_HASH_MISMATCH`）；② 二进制不在 = 从没部署过（`PROMPT_NOT_DEPLOYED`）；③ 二进制在且一致、但守护进程没在跑（`PROMPT_NOT_RUNNING`）。
- **为什么三种都要 su 可用**：su 不通时 `probe()` 里 `binExists` 必为 false（它来自同一趟 su 往返的输出），不加这一条会让未 root 的设备也弹一次部署请求（去重标记只保证不重复问，第一次仍会弹；且 su 不通时点「一键部署」注定失败）。`binExpectedMd5` 为空＝APK 内资源缺失，同样无从判定。
- **「自动更新」开着时的分工**（开关见 §2.5）：第 1 种属于「设备上的内容旧了」，正是开关的语义 → 不弹，改为在回调里静默重新部署；第 2、3 种**永远只弹**（用户从没同意过部署、或刚主动停过进程，替他决定不合适；设备端脚本那一侧也是同一分工）。
- **去重**：把「情形前缀 + 该情形下的指纹」落盘（键 `KEY_HASH_PROMPTED_MD5` 收口在 `Deployer`，见 §2.5），同一个值最多提示一次；指纹取 APK 侧 expected md5 或设备侧 bin md5，都随 APK 更新而变 → 装了新 APK 会重新武装、重装同一个 APK 不会重复打扰。**先落标记再动作**（同 `KEY_ROOT_TRIED`）：弹窗还没显示就已落盘，中途进程被杀也不会下次再弹。**唯一例外**：部署失败时调用方把标记清掉。
- **刚点过「停止daemon」**（`daemonStoppedByUser`）：抑制第 3 种提示——刚停完马上又被问「要不要拉起来」很烦，而且看门狗会在下一轮 tick 自己把它拉回来；部署 / 拉起会把这一位清掉。
- **清标记的边界**（`clearPromptMark`）：只在部署失败时调——标记是「这一版已经尝试过」的记录，失败却留着它，等于把「下次进页面自动补上」这条路也封死。清一次只换来「下次进页面的一次动作」；收敛条件是「盘面就位且进程在跑」，那时探测不武装任何请求，自然不再动作。不是自转的循环（每次都要用户再进页面）。

**部署 → 自动拉起**（`deploy`）：**接不接拉起看 `Result.placementsOk`（盘面是否已就位），不看 `ok`**——理由见 §2.2。`deploy()` 自身不重启进程；接拉起的是本页：`deploy()` 的 after 回调里若 `placementsOk` 就接着调一次 `startDaemon()`（与手动点「拉起daemon」走同一条路径，是独立的一份——自己的忙态文案、操作记录、进度条）。部署失败时清掉一次性去重标记（见上）。部署结果**直接上屏** `deploy()` 带回的状态，**不再补一次 `probe`**——而且 `deploy()` 内部那次自检也已并入写盘同一趟 su（`deployScript()` 末尾接 `probeTail()`），故整条"一键部署"链路上不再有"写完盘再单独探一次"这一趟；`startDaemon()` 同理（`restartScript()` 末尾接 `probeTail()`），整条链路的主链 su 往返由最多六趟降到两趟；也不把部署动作日志灌进状态区——成没成看状态文本就够，步骤细节在「诊断信息」里。

**「需要重新部署」的缓存写入**（`rememberDeployedBinMd5`）：探测确认设备上二进制与 APK 内一致时，把设备侧 md5 落盘——这是 `Deployer.needsRedeploy` 的缓存来源（见 §2.1）。判据与提示判据互补、互不重叠：一致才记，不一致留给部署请求；没部署过（二进制不存在）时探测到的 md5 为空，`Deployer.rememberDeployedBinMd5` 会拒写。

**首启授权与部署请求的优先级**（`runAsync` 的回调）：本次刚拿到 root 授权 → 状态区已显示「root 可用」，这里只问要不要顺势部署。**这一支优先于「自动更新」的静默部署**——用户刚授权，给他一次明确的确认；**同一次探测武装的另一条请求就地作废**，否则紧随其后的部署回调会把它当成这次探测刚发现的再弹一遍（实测路径：首启授权→部署成功→又弹「尚未部署」）。

- **操作记录归档**：记录产生的当下即写通落盘到 `<files>/oplog/s<毫秒>.log`（本次启动的文件，首条记录时才建；不依赖 `onDestroy`，进程被杀不丢）。下次进入本页时（`onViewCreated`，每进程一次）把全部归档按落盘时间从最旧端整份删除至合计 ≤ 64 KB，**最新一份永不被删**——单次启动的记录不截断，故单份自身超限时保留（合计会短暂超过上限）；文件名撞名（同毫秒二次启动 / 时钟回拨）加 `-2/-3…`。写盘失败只置降级标志、绝不抛异常打断界面。界面在操作记录**展开体内首行**显示一行提示（路径 / 份数 / 占用，并如实标注「超 64 KB 从最旧删、单份超限时只留最新」这一软口径），只展示、不提供翻看；每落盘一条即刷新一次（`OpLog.snapshot()` 为 O(1)：进页面时缓存既有归档的份数与字节，本会话文件按当前长度累加，不重扫目录）。提示行是展开体内的一个**静态控件**（`fragment_status.xml` 的 `action_log_archive_hint`），随展开体一起显隐——折叠时不可见。实现见 `ui/OpLog.java`。

### 8.2 日志分级与分区着色

**C 端行格式**（`lsp模块/daemon/tempctrl.c`）：`[DD HH:MM:SS] <正文>`，由 `write_log()` 拼出（`snprintf` 生成时间戳、`fprintf` 用 `"[%s] "` 加方括号并跟一个空格、末尾补一个换行）。因此**每一行都以 `[DD HH:MM:SS] ` 开头**，正文只可能是这几种：

- `[DEBUG] ...` —— `debug_log` 宏加的固定前缀；宏自身要求 `debug_mode=1` 且对应分区开关=1（`debug_mode` 为文件级总开关，另有 7 个分区开关，如 `debug_pid`）。
- `[PID] ...` —— `pid_log` 宏加的固定前缀，要求 `debug_mode=1 && debug_pid=1`。
- 其余为常规输出，例如 `main()` 启动段的「脚本启动成功」、`reconnect_align()` 恢复对齐分支的「重连 PID 状态已重置，进入待对齐」。

**四类判定规则（按此优先级短路）**（`LogClassifier#classify`）：

1. **ERROR**：正文含 `失败|错误|无法|异常|error|fail`（不区分大小写）。C 端实例：`send_am_broadcast()` 的 fork 失败分支、`create_status_files()` 的状态文件创建失败分支、`load_config()` 的配置打开失败分支。
2. **WARN**：正文含 `未生效|超时|未就绪|断联|断开|丢失|停滞|强制`——均为 C 端「降级/异常但继续运行」的措辞。C 端实例：`send_am_broadcast()` 的 am broadcast 超时、`try_align_actual()` 的回传超时用保守值起步分支、`reconnect_align()` 的两条断联分支、`watchdog_check()` 与 `force_kill_and_relaunch()` 的锁死自动重启分支。
3. **DEBUG**：正文含 `[DEBUG]` 或 `[PID]`（两条宏的固定前缀）。两类同归一档：它们同受 `debug_mode` 总开关约束、属分区调试追踪；且颜色标尺只提供了一档调试色（`@color/log_level_debug`）。
4. **INFO**：以 `[DD HH:MM:SS] ` 开头的正常行。
5. **PLAIN**：都不满足（如尾部半行、空行）→ 界面用普通前景色渲染。

**为什么严重级别先于 `[DEBUG]`/`[PID]` 前缀判定**：两者确有交集，例如 `rescan_cpu_zones()` 的 `debug_log(debug_sensor, "thermal_zone 扫描 无可读 zone…")` 与 `rate_limited_execute()` 的 `debug_log(debug_exec, "实际值未就绪（冷%d rpm%d），跳过下发")`。这类行本身就是异常信号，按严重级别着色比按前缀涂成调试灰更有用。

**分级三角的分工**：级别**定义**在 `LogLine.Level`（五档 + 兜底 PLAIN）、**判定**在 `LogClassifier#classify`、**着色**在 `LogListAdapter`（颜色在构造时一次性解析、bind 时只 `setTextColor`，不在滚动路径上解析资源；`levelColors` 下标同 `Level#ordinal()`，PLAIN 用普通前景色 `app_on_surface`）。

### 8.3 日志尾随与自动跟随

日志链三个文件：`LogFragment`（渲染与刷新节奏）、`LogTailReader`（尾读 + 截断 + 过滤，**全部在后台线程调用**）、`LogClassifier`（分级判定，见 §8.2）。

**`LogFragment`：线程纪律与刷新节奏**

- **线程**：所有 File IO 在后台线程（`LogTailReader#read`）；主线程只做渲染。Context 一律在主线程取出后捕获进闭包，后台线程不再调 `requireContext()`。
- **刷新**：页面可见时每 `REFRESH_INTERVAL_MS`(2000ms) 重读一次。外壳用 ViewPager2 切页（见 §9.1），页面生命周期不再随切页暂停/恢复，故除了 `onPause`/`onResume`，`onPageVisible(boolean)` 也必须停/启刷新——三个入口都走幂等的 `startRefresh()` / `stopRefresh()`。
- **无变化跳过**：内容指纹（`size:mtime`）与关键词都没变时，`LogTailReader` 直接返回 `unchanged`，不触碰 UI——否则每 2 秒重建一次 2000 行列表会白白抖动。
- **软键盘**：键盘弹出时不顶起页面（只覆盖）。该策略与"聚焦滚进可视区"由 `ui/EdgeToEdge` 全 app 统一负责，本页不再自行接管窗口设置，见 §9.2。

**`LogTailReader`：三条硬约束**

1. **只读文件末尾 `TAIL_BYTES`(400KB) 字节**，语义等价 `tail -c 400KB`，绝不整文件读入。
2. **读取一律走 `AppFiles`**（`readTailText`），不自己开 `FileInputStream`，失败信息才不会丢。
3. **渲染行数上限 `MAX_LINES`(2000)**：400KB 全量上屏会卡死，只保留尾部这么多行，界面必须显式写出这个截断；**只切/只解析尾部这一段**，不把整个窗口切成数组（会白造几千个永远不上屏的 String）。

**过滤顺序**：先按 `MAX_LINES` 截出「最近 N 行」，再在其中做关键词匹配。因此界面上的「最近 N 行」就是匹配分母，含义与显示一致（命中范围仅限该窗口）。

**不支持「按分区过滤」**：日志行本身不带分区标记（分区只体现在 `[DEBUG]`/`[PID]` 前缀与 C 端的分区开关上），要做按分区过滤须由 C 端给每行加标签（暂不做），故界面日志页仅支持关键词过滤。

**失败可诊断**：任何异常都不许让页面静默留白——`Snapshot#failureText` 携带必须原样上屏的诊断原文（`AppFiles.diagnose()` 的多行诊断）。

### 8.4 界面动效口径（逻辑 2 时长参数与曲线）

统一口径只有 `ui/Motion` 一处。

**时长模型（逻辑 2：两个值可调）**：`时长 = (位移(dp) ÷ 速率 + 起步ms) ÷ 2`，两个值来自同一个界面参数 `UI_ANIM_TUNING`——`速率 = 第 1 值 / 10`（dp/ms）、`起步 = 第 2 值`（ms）。**公式来历**：把「纯按位移递增」与「固定起步」取平均——`(位移(dp) ÷ 3.2 + 240) / 2`；取平均是为兼顾短窗口（纯递增下 30dp 只有约 9ms，一闪而过）与长窗口。**默认值**（以 `params.def.json` 为唯一出处，本处不写死）：`UI_ANIM_TUNING = 32 240`（= 3.2 dp/ms / 240ms），即默认时长 `(位移 ÷ 3.2 + 240) ÷ 2`——598.9dp → 214ms、0dp → 120ms。两道护栏：① **上限** `HARD_MAX_MS = 600` ms——默认参数下位移 **>3072dp** 才咬到（`(3072÷3.2+240)÷2 = 600`），现实里只有「操作记录」拉满那种超长体够得着；② **帧数下限** `MIN_FRAMES = 2` 帧（帧长按设备实际刷新率折算 `round(2×1000/刷新率)`，120Hz≈17ms、60Hz≈33ms；取不到刷新率或值异常退回 60Hz，绝不抛异常）——**默认参数下最小 120ms，该下限从不生效，保留作安全网**（把「起步」调到很低时才可能咬到）。展开箭头**不套用本公式**：其时长直接取自同一次面板动画的返回值（见下「箭头旋转」）。

> **为什么"平均"有意义（更正更早一轮的口径）**：曾把「0.40ms/dp」与「598.9dp/240ms」当成同一个数（2.5 dp/ms vs 2.495 dp/ms）而判定平均无变化——**那只对长窗口成立**；短窗口差得很远（30dp：纯递增 9ms vs 240ms）。取平均才有意义：把短窗口从"一闪而过"拉起来，又不改动长窗口。公式现已收进**一个可调界面参数 `UI_ANIM_TUNING`（速率 / 起步 / 两端减速强度三个值）**。

- **曲线（两条，按用途分家）**：**面板高度类与展开箭头**（展开/收起、状态卡换字引起的高度变化、三处卡头的箭头旋转）用 `Motion.SlowEndsCurve`——`y = t − (强度/2π)·sin(2πt)`，**强度取自界面参数 `UI_ANIM_TUNING` 第 3 值 ÷ 100**（默认 60% = 0.60）：0 = 匀速直线，强度越大两端越慢、中段越快（三点斜率 `1−强度 → 1+强度 → 1−强度`，左右天然对称；强度 ≤1 时斜率恒 ≥0，永不回退）。默认强度 0.60 等效两个「时间/进度」锚点 `t=0.10→y≈0.044`、`t=0.25→y≈0.155`。**为什么不用三次贝塞尔**：把锚点直接当旋钮这条路走不通——对称三次贝塞尔只有 2 个自由度，两个任意锚点绝大多数无解（实扫 11700 组组合，**98.7% 无解**，表现就是"改了没反应"）；正弦族一个数就能连续调，且两端同强度、单调不回退。**为什么高度类不沿用强 ease-out**：大位移（整块面板）用它前倾过猛（约 25% 时间就走完 78% 位移），观感像"弹一下"而非"推开门"；**为什么箭头也换到这条**：只做到"同一次算出的同时长"还不够——强 ease-out 下箭头会在四分之一处就转完约 78%（90° 里约 70°），剩下四分之三的时间原地等面板（表现为"三角转完一段时间窗口才展开/收起"）；同曲线才能让角度进度与高度进度**逐点相等**，旋转与展开真正锁死。**状态卡交叉淡入**（透明度）另用强 ease-out `cubic-bezier(0.23, 1, 0.32, 1)`——瞬时状态切换要前倾、快到位。两条曲线都只此一处、由 `Motion` 独占（`EASE_OUT` / `panelCurve`，后者同时服务于高度与箭头）。
- **动画参数（单键三值）**：`UI_ANIM_TUNING`（三值：速率 ×10 = dp/ms · 起步毫秒 · 两端减速强度%），与平台上**自动**施加的系统动画缩放相互独立（本层是额外那一层）；算出时长后再压上限 `HARD_MAX_MS = 600` ms 与帧数下限 `MIN_FRAMES`（折算见上）兜底。`SetupActivity` 在启动预热的 `ww-chart-warmup` 后台线程（进程一次、与落页判定同时起跑）读这个键的三个值后喂给 `Motion.setAnimTuning`——**默认值以参数定义（`params.def.json`）为唯一出处，本处不写死**（避免默认值一变、文档与注释就漂）。解析口径：配置文件里缺该键、或配置文件不存在/读失败 → `ConfigStore` 补出厂默认值；值的个数不足、`params.json` 未定义该键、或读取抛异常 → 由 `Motion` 按其内置默认（3.2 / 240 / 0.60）裁决（与「非法值分别退回各自默认」同构）。**老配置里该键只有两个值**（它原为双值）：强度按内置默认算，**不按 0**（0 = 匀速，等于把动效关掉）；表单显示走同一条口径——`ConfigKeyRow` 在值里缺某个字段时按该键默认回填，故"界面显示"与"运行时用"一致，也不会在随手保存时被悄悄写成 0。**改该设置需重启才生效**（进程内只读一次）。
- **展开/收起的容器（三处）**：状态页操作记录体、配置页分组体、配置页诊断体，一律 `Motion.animateHeight(view, expand)` 按逻辑 2 逐帧改 `LayoutParams.height`，结束置回 `WRAP_CONTENT`（收起再 `GONE`）。**两向同一把尺子**：终点都取实高——收起读已布局实高，展开在**最终宽度**上用 `height=UNSPECIFIED` 量自然高（`GONE` 折叠体无已布局高度；量宽与最终宽一致时量到的即实高，故同一面板两向时长相等）。**不再用"是否已排版"作门**：`GONE` 子视图永不参与父容器排版，该判据会让首次展开恒为"直接落位"（零动画）；改判"宽度可知"——宽度只能来自"已布局实宽/父内容宽（扣自身左右外边距）"，退回屏幕宽兜底时不算已知、直接落位（那量出的不是实高，按它动画末尾会跳）。**打断即换向**：同视图在跑的补间先取消、从当前高度接着动，连点不排队、不卡住。系统关动画、或展开时宽度不可知时直接落位。宽度不可知有两源：父容器尚未排版，或容器被显式置 `GONE`（`GONE` 不参与排版、孩子量不到宽）；设置页"默认展开"那次走后一条——`ConfigGroupBinder.setExpanded` 发生在 `revealBuiltForm()` 之前，那一刻容器仍 `GONE`，故直接落位、不播入场动画。
- **诊断体两段动画**（正文要读盘才回来）：正文未就绪时展开先只放一行「读取中…」占位并动画到占位高（**不露旧正文、不闪帧**）；若此刻同体上方的「数据文件信息」行仍停在「读取中…」（曲线区首份数据还没回来），则不再重放一遍、由那一行充当这一屏**唯一**的占位。正文上屏时再由 `ConfigDiagnostics.apply` 从当前高度续动画到最终实高；正文已就绪时**先上屏再量高**、一次动画到位（量高发生在正文之上，末尾不跳）。读盘失败立刻改写为「读取失败：…」文案（不留占位；展开态下按当前高续做，高度需收缩时直接落位），失败后下次展开重走占位 + 取数。状态页展开时把归档提示行重算提前到量高之前（同因）。
- **箭头旋转（三处卡头）**：状态页操作记录、配置页分组、配置页诊断，一律走 `Motion.rotate(view, 角度, 时长)`——**时长直接来自同一次 `Motion.animateHeight` 的返回值，不另设箭头常量**：面板走动画则箭头同一时长，面板直接落位（系统关动效 / `from==to`，此时返回 `-1`）则箭头也直接落位，两者同生共灭。含配置页分组卡头原先**绕过** `Motion` 的 `setRotation` 直落。**曲线也与面板同用对称缓入缓出**——只同时长不换曲线，箭头会先转完再等面板（见上条）。
- **状态卡换字**（`StatusFragment.swapStatusTextAnimated`）：**业务上屏零延迟**——新文本立刻写入，不等淡出结束；视觉上做「旧文本淡出、新文本淡入」的**交叉淡入**（`status_text_stack` 内新旧两层叠放，旧的在下、新的在上，沿用 100/150ms）。高度变化按逻辑 2 补间，位移量由换字前 `Motion.measureTextHeight` **预测**（内容驱动的变化无法在改动前直接得知，故为预判值）。
- **无障碍**：系统动画时长缩放为 0 时 `Motion.enabled()` 为假，上述一切降级为直接落位（信息照常呈现）。

## 9. 界面外壳

### 9.1 三页结构与 PageAware

**三页**：状态 / 配置·曲线 / 日志，由 `ViewPager2` 承载（页面容器即 `androidx.viewpager2.widget.ViewPager2`）。手指跟随滑动、松手 fling 吸附到最近页，都由它给，**不再手写转场**。三页由 `FragmentStateAdapter` 持有，`offscreenPageLimit = MENU_IDS.length - 1`（= 2）让三页都留在 `FragmentManager` 里（页面状态与滚动位置保住）。

**页签数量与顺序**：`MENU_IDS` 的顺序即页序，**必须与 `res/menu/menu_bottom.xml` 一一对应**（同为 3 个、同序）。

**代价：页面生命周期不再随切页变化。** ViewPager2 把非当前页压到 `STARTED`，而 `RESUMED → STARTED` 不派发 `onPause`，也不再走 `hide()/show()`（`onHiddenChanged` 同样不会来）。于是"离开本页要停定时器"这件事必须由外壳显式告知——这就是 `PageAware`：

- 只有当前页收 `true`，其余页收 `false`。
- 页序号由外壳经 `ARG_PAGE` 写进 Fragment 的 arguments 后反查，**页面自身不需要知道自己是第几页**（进程恢复后重建的实例也照样能算出自己是第几页）。
- **广播的遍历方式**：遍历 `FragmentManager` 里的实例，而**不按页序号反查**——`FragmentStateAdapter` 用内部 tag（`"f" + itemId`）持有页面，依赖那条约定太脆；页序号由外壳写进 arguments，故凡 `PageAware` 的页面都能自己算出第几页。

### 9.2 边到边与让位算法

`ui/EdgeToEdge` 做下侧沉浸式：让窗口铺满整屏（含系统手势条 / 导航栏那一条带子），系统栏的让位由它算。

**为什么需要它**：目标观感是"底栏背景一直铺到屏幕底、条目仍留在手势条之上"。把 `navigationBarColor` 设成透明**还不够**：窗口不铺满时那条带子不归 app 画，系统还会按 `enforceNavigationBarContrast` 给透明底压一层对比遮罩，看上去就是"底栏下面还有一条灰带"。所以先 `WindowCompat.setDecorFitsSystemWindows(false)` 关掉"窗口自动让位"，再自己把几处内边距补上。

**谁吃哪段内边距**：

- 顶 / 左 / 右 → 页面根（与原来的 `android:fitsSystemWindows="true"` 等价，标题栏仍留在状态栏之下）。
- 底 → 有底栏时给底栏（高度 = 基准内容高 + 系统条高，底部内边距同样取后者），于是底栏背景铺到屏幕底、条目仍在系统条之上；**没有底栏的页面（设置页）直接给页面根**。
- 让位算法**不含 IME 分支**：键盘弹起时底栏仍在原位（被键盘盖住即可），底栏高度与内边距不随键盘变化。

**为什么要顶掉底栏自带的 inset 监听**：`BottomNavigationView` 在自己的构造函数里就注册了一个 inset 监听，它把 `getSystemWindowInsetBottom()`（键盘弹起时就是键盘高度）**无条件**写进底栏自身的 `paddingBottom`；而 material 是通过 `ViewCompat.setOnApplyWindowInsetsListener` 注册的，属**覆盖式**注册。故 `apply()` 给底栏换上一个"原样返回 insets"的监听把它顶掉，让底栏几何只由 `BottomBarLayout` 那套绝对赋值独占负责——否则底栏会被反复压低。

**与键盘的关系**：全局统一"只覆盖、不顶起"。`apply()` 把窗口 `softInputMode` 锁成 `SOFT_INPUT_ADJUST_NOTHING | SOFT_INPUT_STATE_UNCHANGED`，让位算法只按 `systemBars` 算、**不含 IME 分支**，于是键盘弹起时整页不重排、底栏不上移，键盘直接盖在界面上。`ADJUST_NOTHING` 只管旧的"框架替谁让位/缩窗"那条路；`setDecorFitsSystemWindows(false)` 已把 `systemBars` 从 `fitInsetsTypes` 里清掉，故 adjust 值对 IME inset 的派发不起作用（真机 A/B 复核见 §10）。注：本机无 AOSP 原文逐行核对，该结论以真机判据为准。

**聚焦滚进可视区（兜底）**：`EdgeToEdge` 内建 `ImeReveal`——键盘弹起时，若当前焦点所在的输入框被键盘挡住，就把它所在的那个滚动容器往上滚一点露出来。它**复用 root 上那唯一一个 inset 监听**（另装监听会顶掉让位监听）并挂 `ViewTreeObserver.OnGlobalFocusChangeListener`（焦点在输入框间跳动时重滚）；只改滚动偏移、**零 padding**，读不到键盘高度（`ime.bottom <= bars.bottom`）或找不焦点/滚动容器就 no-op，因此无状态、无残留、无"必须成对"约束。日志页搜索框在页面顶部、祖先链上没有滚动容器，天然 no-op。

**`BottomBarLayout`：底栏几何的持有者**——`height = 基准内容高 + inset`、`paddingBottom = inset`，两者都是**绝对赋值，不是叠加**。

- **幂等的关键**：基准内容高**只在首次调用时量一次**（XML 定高 − 当时的底部内边距；底栏自身没有别的底部内边距——`itemPaddingTop/Bottom` 是作用在菜单视图上的，故这里即 XML 定高），之后恒用该值。
- **旧写法为什么错**：每次都用「当前 `height` − 当前 `paddingBottom`」重新反推，等于把上一次写进去的 inset 也当成了内容高的一部分；而 material 的 inset 监听又会在两次调用之间把键盘高度塞进 `paddingBottom`，反推值随之逐次下漂甚至变负——这正是"每拉起一次输入法，底栏就被压低一次，直到几乎看不见"的成因。
- **只量一次之后**：连续调用 N 次算出的 `height`/`paddingBottom` 完全一致（值未变时还会直接返回，不触发多余布局）；inset 恒取 `systemBars`，键盘弹起与收起都不改变底栏几何（键盘弹起时 inset 仍是 `bars.bottom`），与初始状态逐值相同。

### 9.3 设置页（webui 组键）

`SettingsActivity` 是**设置页外壳**：顶栏设置按钮点进来的独立页面，内容只有 `UiSettingsFragment`（`params.json` 里 `webui` 组——界面标题 `[4] 界面`——那几个界面自用参数）。

- **本类不含业务**：读、改、落盘全在 Fragment 里；返回键只结束本页（设置页是独立页面，不退到主界面，主界面由它自己的页签状态恢复）。
- **返回走派发链而非 `finish()`**：系统手势返回、预测性返回与按钮返回走同一条路径。
- **重建时不重复 add**：`savedInstanceState == null` 才 add，否则 `FragmentManager` 自己恢复 + 重复 add 会叠出两份表单。
- **`setTheme` 必须在 `super.onCreate()` 之前**：与 `SetupActivity` 同因，见 §5.4。
- **底部内边距归页面根**：本页没有铺到屏幕底的栏，故 `EdgeToEdge.apply(this, root, null)`（同一套让位算法，见 §9.2）。

**设置页的键**（`UiSettingsFragment`）：

- **本页不重复实现表单**：键行、开关、落盘规则全在共用的 `ConfigFormController` 与 `ConfigKeyRow`/`ConfigGroupBinder`/`ConfigWriteQueue` 里（见 §6），本页只提供自己的壳、错误位与重置栏。
- **键清单由 `UiSettingsFragment#webuiKeys` 给出**（`webui` 组里定义的键，按定义顺序，不含 `role=master`）：**自检与渲染同源**，不各写一份数字。空列表表示定义里没有这个分组（定义被改坏或换版本），此时页面给出空态而不是静默留白。
- **这几个键是"界面自用"参数**（`daemonConsumes=false`）：曲线怎么画、界面怎么显示，与配置页那些会被守护进程读取的运维参数不是一类东西；搬到设置页后配置页只剩要调的参数。
- **页面形态**：只有这一组，故**默认展开**（否则进页面先看到一张折叠的卡）；**未分组兜底卡不出现**（不重复给入口，由配置页承载）；**无诊断折叠体**（只在配置页的布局里）。
- **反向隐藏（`hiddenWhen`）**：`UI_DEPLOY_ENTRY`（「需重新部署时进状态页」）定义了 `hiddenWhen: ["UI_AUTO_UPDATE"]`——**自动更新开着时整行隐藏**（`ConfigKeyRow#refreshHiddenState` 把行根切 `GONE`，随每次快照刷新重算，故在设置页当场切「自动更新」即即时显隐）。它与 `requires` 的**压暗**是两件事，方向也相反（`requires` 是"值为 1 才生效、否则压暗"，`hiddenWhen` 是"值为 1 就收起"）；**取不到值一律按不隐藏**，与 `isUnsatisfied` 的"取不到即未满足"刻意相反。隐藏只切可见性，**不参与「未生效」徽标计数**。定义与判据另见 §5.1。

> `webui` 组各键本身的定义在 `参数定义/params.def.json`（唯一手写处）；键的渲染与读写见 §6（配置表单界面）与 §3（配置存储）。本节只讲外壳。

本节是**索引**：各未验证项的完整说明写在对应节的原处，这里只列条目与位置。本机（开发环境）无 Android 真机，以下均**未经真机验证**。

- **失败诊断滚动条**（见 §7.6）：右边缘窄带被系统手势导航占用时的实际可按区。
